## Two co-primary process CPU endpoints

For each fresh process let `N=summary.completed` (must equal the scheduled positive count). Both endpoints use `RUSAGE_SELF` user plus system CPU, in microseconds divided by N:

1. **Measured-window process CPU/tx:** `(summary.stats_after − summary.stats_before).(process_user_cpu_us + process_system_cpu_us) / N`. The harness calls this interval **B→C**. It is not the lifecycle endpoint.
2. **Post-identity lifecycle process CPU/tx:** `(summary.lifecycle.stats_after_shutdown − summary.stats_after_identity).(process_user_cpu_us + process_system_cpu_us) / N`. This is the harness lifecycle **E−A**, including startup, fixture, warmup, persisted validation, CSV output and deferred-cleanup/drainer work through database/network shutdown. It excludes identity hashing, terminal summary JSON output and process exit. It is not a steady-state measurement and does not subtract those fixed costs.

## Prespecified inference and exact decisions

For each cell and endpoint, compute six per-epoch paired logs `d=log(productionCPU/tx)−log(baselineCPU/tx)`. With epoch means `m1,m2`, unbiased variances `s1²,s2²`, and `n1=n2=6`:

- Mean log ratio: `m=(m1+m2)/2` (equal epoch weights).
- `SE=0.5*sqrt(s1²/6+s2²/6)`.
- Welch–Satterthwaite degrees of freedom: `(s1²/6+s2²/6)² / ((s1²/6)²/5+(s2²/6)²/5)`.
- Two-sided **95% CI**: `exp(m ± t(.975,df)*SE)`; point estimate `exp(m)`.
- If both variances are zero, SE is zero and the interval collapses to the point (df not estimated).

**FAIL takes precedence if any point estimate is ≥ 1.02 in either endpoint in any cell. Otherwise PASS only if every upper 95% bound is ≤ 1.02 in both endpoints across all eight cells (16 bounds). Otherwise unresolved.** An improvement claim for a cell/endpoint is allowed only when its upper bound is **strictly < 1.00**. Equality at 1.00 is not improvement. These are per-cell/endpoint intervals, not a simultaneous 95% coverage claim. PASS does not authorize merge or substitute for correctness, throughput, tail-latency or other gates.

AA is descriptive for both CPU endpoints: one pair per role/epoch, epoch ratios and the two-pair geometric mean, **no inferential CI and no hard gate**. AA noise is not a substitute decision rule and low counts cannot establish equivalence. Allocation summaries and execution-order effects remain diagnostic only.

## Bounded forensic tail and emergency quarantine

The owner authorizes **at most five minutes of light administrative preservation after sampling stops**, separate from the **hard 30-minute sampling deadline**. All benchmark and cluster workload must stop by the sampling UTC deadline. The tail retains the lane lock but starts no benchmark, build, profile decoder or cluster write. It records its own UTC sampling-stop/start, deadline and finish in `forensic-status.json`, an external population-specific `*-forensic-terminal.json` receipt, and flushed `FORENSIC_STARTED`/`FORENSIC_FINISHED` markers. The monotonic cap begins when group teardown is proved; hashing is chunk-checked and stops after 295 seconds, reserving five seconds for small failure/status writes. Tail expiry invalidates complete status and prints `FORENSIC_INCOMPLETE`, **never an authoritative seal**. No late hash or replacement population is authorized.

If SIGKILL/subreaping cannot prove the group gone by the sampling cutoff, the supervisor enters **QUARANTINE** instead of sealing or releasing ownership. It writes an **unsealed** `quarantine-unsealed.json` fault receipt with UTC start, supervisor PID, process-group ID, observed PIDs/states and any census error, and flushes the distinct `QUARANTINE_OWNER_RELEASE_REQUIRED` marker immediately. The owner-approved emergency exception allows the guardian to retain the same fast-lock descriptor **beyond the five-minute administrative cap**. After the initial fault receipt it performs no hashes, builds, benchmark/cluster work, or further evidence writes; it passively waits for owner intervention. A disappearing group alone does not release ownership. Monitor the fault receipt/marker immediately; do not let an unattended runtime timeout kill the guardian and silently release its lock.

The default release-file path is the population-specific `*-owner-release.json` in the evidence root, or an explicit `--quarantine-release-file`; it must not preexist the slot. **Only the owner, after an explicit release decision, may create it**. Agents must not manufacture an ACK. The small, owner-owned, nonsymlink JSON must contain `action=release_quarantine`, `scope=rfc263-cpu-quarantine`, and the exact `token`, `supervisor_pid`, `pgid`, `population` and `evidence` identity printed in the quarantine receipt, plus a nonempty `owner_ack` recording that decision. The guardian reaps/probes and requires the group to be gone before accepting that ACK and closing the lock. Invalid, missing, stale, or unreadable ACKs leave it waiting. An acknowledged release prints `QUARANTINE_OWNER_RELEASED` and exits without a seal; it never makes the failed campaign analyzable. The owner may instead terminate the guardian after personally verifying safety and deciding release; that is an owner intervention, not an automatic timeout policy.

The diagnostic classifier reuses the rev4 exact-source-line method: count only sampled `q.mu` and `root.mu` lock sites from each arm's archived `timeout_queue.go`, using **Unlock sites for mutex and Lock sites for block**. A broad timeout-queue ancestor is insufficient: descendant transaction cancel/read-error/allocator waits must not be charged to queue locks. Include shard+root, with caller, drainer and clearly labeled cleanup/non-drainer splits. For mutex profiles those names identify the **unlocking holder's context** to which other goroutines' waiting is attributed; for block profiles they identify the **blocked waiter's context**. In particular, mutex cleanup-remove delay is not evidence that cleanup itself waited. The two profiles do not identify matched waiter goroutines or matched contention events. Historical `caller_delay_ns`/`drainer_delay_ns` fields have the same holder-context meaning. Preserve the baseline comparison. A valid zero requires a nonempty positive profile population and synthetic classifier positive controls; an empty profile is not evidence of zero contention.

Gate 5 threshold is strict: **combined shard+root cumulative queue wait / measured-window client CPU < 1% for each production workload/profile**. Report mutex and block independently; **never add them** (they can count the same contention). This diagnoses cumulative wait, not CPU consumed. All four workloads are covered by these diagnostics at 32 workers; do not relabel them as eight-worker profile evidence or a replacement for the 16 CPU NI bounds. Full classifier/testing details are in `rev6-cpu-queuewait.py` and its fixture test module.

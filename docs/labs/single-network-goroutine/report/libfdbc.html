1. Why L (1 Thread) and L4 (4 Threads, 4 DBs) Behave So Differently from Go

L: Single-Thread Reactor Bottleneck & Implicit Coalescing

  • libfdb_c runs the entire C++ client stack (NativeAPI, ReadYourWrites, loadBalance, FlowTransport) on a single OS network thread using cooperative Flow actors.
  • When 64 or 256 Go worker goroutines submit requests via cgo, every call crosses a cgo thread-safe promise queue onto that single network thread.
  • At 256 workers on get100, the single libfdb_c network thread pins at 100% CPU (~50k–57k ops/s = 5.0M–5.7M read RPCs/s). Because requests queue behind the saturated reactor loop, each connectionWriter drain sweeps up 31.8–64.5 storage frames per TCP packet, minimizing server packet-processing overhead at the cost of a 4.5× throughput ceiling and 4.6 ms p50 latency.

L4: Multi-Thread libfdb_c Splits Batching Across 4 Connection Pools

  • Setting client_threads_per_version=4 (MultiVersionTransaction.actor.cpp:3095-3097) copies libfdb_c.so into 4 client network threads and assigns FDBDatabase handles round-robin (:3302-3305).
  • Because each thread owns an independent FlowTransport and independent DatabaseContext, GRV batching, commit batching, and TCP socket coalescing are split 4 ways (7–8 client TCP connections instead of 2):
    • Storage frames/packet on get100/64 drop from 32.1 (L) to 4.2 (L4).
    • Server CPU per transaction jumps to 1.14–3.58× L (e.g. get100/8: 296.0 vs 82.4 kc/tx; get100/64: 62.9 vs 22.8 kc/tx; rate-capped set100/64: 187.8 vs 137.0 kc/tx).
    • Client CPU per op jumps to 1.15–2.73× L, and client syscalls jump 3.4–4.2× (12.4–17.4 syscalls/op vs 2.9–5.2).
    • Even with 4 threads, L4 still reaches only 107k ops/s on get100/256 — less than half of Go's 229k–261k ops/s, which shares a single connection pool and a single GRV batcher across all 8 Ps!

2. Low-Concurrency (8-Worker) Latency Analysis

On set100/8 and getset100/8, Go (D-NG and D-M) already beats L on both throughput and latency (set100/8 p50: D-NG 2,801 µs vs L 3,127 µs; getset100/8 p50: D-NG 3,675 µs vs L 4,409 µs). The only cell where L has lower p50 than D-NG is get100/8 (L 1,219 µs vs D-NG 1,346 µs on netg-r6; D-M 4Ps reaches 1,145 µs vs L 1,223 µs on Box 2).

Why? In get100/8, only 8 goroutines are active across 8 Ps (`client_cores_busy = 0.84`). Each transaction performs 1 GRV + 100 reads. With D-NG, the gap to L shrank from +283 µs (A: 1,502 µs) to +127 µs (D-NG: 1,346 µs) — i.e., 1.27 µs per read. That residual 1.27 µs/read is the cost of waking a parked Go worker goroutine across Ps when `readLoop` delivers a reply plus arming/stopping the 5 s per-read timer in `GetPipelined` (which `D-M` at `GOMAXPROCS=4` eliminates by keeping goroutines on fewer Ps, beating `L` at 1,145 µs vs 1,223 µs).

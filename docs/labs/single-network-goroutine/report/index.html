Headline Findings (Rounds 1–7, including Page 2: Round-7 D-NG Hill-Climb):
  • Round-7 Hill-Climbing Campaign (see Page 2: D-NG Hill-Climb): Starting from the Round-6 D-NG baseline (Step 0), 7 profile-guided steps on feat/dng-transport eliminated 80.9% of all client mutex contention (13.90s → 2.66s), reduced heap allocations by 55.8% vs master A (50.1 → 47.1 → 22.1 allocs/op, 4,980 → 3,729 B/op), cut client CPU to 25.0–25.4 µs/op (-37% vs A, -63% vs L), pushed get100/256 to 262.0k ops/s (Step 7) and 273.4k ops/s (Step 7 + adap20, 5.41× libfdb_c), and closed the get100/8 serial read gap to beat libfdb_c (7,222 vs 6,915 ops/s = 1.04× L, 0.82× L client CPU, 0.96× L server CPU)!
  • Enqueuing without write acknowledgment (D1: per-connection mutex+slice writer signalled on empty→non-empty) and per-transaction weak-pointer time.AfterFunc (D4) strictly dominate today's transport (A) across every concurrency level, reducing client CPU by 12–22%, futex calls by up to 81% at 256 workers, and latency across all workloads.
  • The 10–20 µs C++ coalesce delay (D) is a pure latency-vs-server-CPU knob, not wire correctness: at 0 µs linger (D-NG), Go achieves 257.7k ops/s on get100/256 (5.1× libfdb_c's 50.3k ops/s) and 52k–80k ops/s on get100/64. Adding fixed linger (5–250 µs) traces a smooth Pareto curve trading +10–700 µs of client p50 for 10–25% lower server CPU/tx.
  • Sender-writes without a writer goroutine (D-M / M) is fastest on the happy path when sockets never fill, and matches D-NG on netg-r6, but fails T1 and T2 under socket backpressure: a sender that wins TryLock blocks inside write(2) when the kernel send buffer fills, ignoring ctx cancellation and acting as a queue-wide write acknowledgment (10 deterministic -race failures).
  • Writer queue structure is not the bottleneck: mutex+slice (D-NG), channel (D-NG-chan), and a fixed lock-free MPSC ring with writev (D-NG-ring v2) finish within 5% of each other at 243k–258k ops/s. Profiling shows the send-queue mutex is 0.16% of CPU and 1.2% of lock wait; 75.8% of all lock contention is the connection reply map pendingMu (PrepareReplyTo 50.1% + readLoop 25.8%).

1. Ground Truths (T1–T6) & Architecture Comparison

What libfdb_c 7.3.77 Does (C1–C5)

  • C1. Send is enqueue + future: Peer::send appends to unsent and fires dataToSend only on the first unsent packet (FlowTransport.actor.cpp:1038-1043). Reads use tryGetReply (LoadBalance.actor.h:305,312); callers never wait for socket write completion.
  • C2. Single writer per connection with jittered coalesce delay: connectionWriter (FlowTransport.actor.cpp:704-738) waits delayJittered(max(MIN_COALESCE_DELAY, MAX_COALESCE_DELAY - (now - lastWrite))) (10/20 µs, flow/Knobs.cpp:211-212), writes up to 128 KiB, and sleeps until dataToSend. Note that commit a674cb4ef4 kept delay(0), delay(500e-6), and yield(TaskWriteSocket) commented beside it, and BUGGIFY sets both knobs to 0.
  • C3. Adaptive GRV batching: window is min(EWMA(0.5 × reply_latency), 5 ms) up to MAX_BATCH_SIZE = 1000 (NativeAPI.actor.cpp:7351-7365).
  • C4. Opt-in transaction timeout: one timebomb actor runs only when TIMEOUT is set (ReadYourWrites.actor.cpp:1567-1579). Per-read RPCs arm no reply timeout (only secondDelay when a second storage alternative exists).
  • C5. Local cancellation: cancelling a future drops the caller's wait without mutating already-queued wire frames.

What the Go Client Must Satisfy (T1–T6)

  • T1 (No write ack): Callers enqueue the encoded frame and wait only on the reply channel. Write errors call failConnection and fail all pending replies.
  • T2 (Local ctx): Cancelling ctx ends the caller's wait immediately and never un-queues or truncates a frame, nor blocks inside a kernel write(2) syscall.
  • T3 (Zero-cost unset timeout): No timer is armed when transaction TIMEOUT is unset; one weak-pointer time.AfterFunc per transaction when set (D4).
  • T4 (Parity at equal throughput): At a rate both clients sustain on one box, p50 and p99 are no higher than L's and server cycles/tx are within noise/tolerance of L.
  • T5 (Wire correctness): Identical payload bytes, per-connection frame ordering, whole frames, and identical request sets (verified by 1-worker tcpdump and wiregolden).
  • T6 (Goroutine-per-op hot path): Enqueue + single-waiter wakeup on reply delivery with pooled reply handles/channels (0 allocs on transport reply path).

4. T4 Verdict at Equal Throughput & Concrete RFC Recommendations

T4 Verdict: Equal Throughput vs Closed Loop

  • Rate-capped (equal throughput, the T4 definition across 25%, 60%, and 90% of L):
    • At 25% and 60% of L's ceiling (where L's single network thread is not yet congested), D-NG (0 µs linger) has lower or equal server CPU/tx than L: on get100/64 @ 8,000 ops/s, D-NG is 175.8 vs 221.5 kc/tx (0.79× L, p99 1,948 vs 4,825 µs = 0.40× L); on set100/64 @ 4,800 ops/s, D-NG is 426.0 vs 432.7 kc/tx (0.98× L); on set100/64 @ 11,500 ops/s, D-NG is 209.1 vs 209.8 kc/tx (1.00× L).
    • On the 5-process split cluster (netg-r6b) at set100/64 @ 11,000 ops/s (equal throughput for all 11 arms), every Go arm beats L on total server CPU/tx: D-NG is 378.1 vs 394.5 kc/tx (0.96× L), D is 367.2 kc/tx (0.93× L), and D50 is 355.8 kc/tx (0.90× L).
    • At 90% of L's ceiling on the 3-process cluster (set100/64 @ 17,000 ops/s, get100/64 @ 28,000 ops/s), L's single network thread is ~89% saturated and queues 15–30 frames per write behind its reactor loop. Even there, every Go arm beats L on p50 (0.56–0.92× L) and p99 (0.24–0.74× L), while fixed linger (D50/D100) brings server CPU within 3–15% of L.
  • Why L packs more frames at 28k ops/s on get100/64: 28,000 ops/s × 100 reads/op = 2.8 million read RPCs/s. At 28k ops/s, L's single network thread is 89% saturated, so responses and outgoing reads back up behind one event loop and naturally batch 15–30 frames/write. Go spreads callers across 8 Ps, so each connection's queue drains rapidly unless a linger window holds it.

Concrete RFC Recommendations

  1. Ship D1 (per-connection mutex + byte-slice writer signalled on empty→non-empty) and D4 (single per-transaction weak-pointer time.AfterFunc): Replaces writeLoop's direct-write/writer-turn/write-ack state machine and the global timeoutQueue heap + runtime.AddCleanup. Simpler, satisfies T1–T3, passes the entire test suite under -race, and cuts client CPU by 12–22%.
  2. Do NOT adopt D-M (blocking sender writes) or D-NG-ring (lock-free MPSC ring): D-M violates T1/T2 under TCP socket backpressure, and D-NG achieves the same throughput safely. D-NG-ring v2 adds 200 lines of unsafe-like bit-packing for 0% gain because the send-queue mutex is only 0.16% of CPU.
  3. Coalescing policy (D2): Make flush-on-empty (D-NG, 0 µs linger) or a small adaptive/fixed linger (D5 / DNGa20) the default, while retaining WithCoalesceDelay(min, max) for clusters that prioritize storage/proxy packet reduction over single-op latency.
  4. Next high-leverage follow-ups identified by Round-6 profiling:
    • Shard Conn.pendingMu (e.g. 16 or 64 token-hash shards): PrepareReplyTo (50.1%) + readLoop (25.8%) account for 75.8% of all client mutex contention at 256 workers.
    • Remove or make opt-in the 5 s per-read RPC timer in GetPipelined / waitReply: C++ tryGetReply arms no per-read timeout; removing it will eliminate the remaining per-read timer traffic and shrink the 8-worker serial read gap against L.

# fdb.dev website

The source for [fdb.dev](https://fdb.dev) — landing page, docs, changelog, and
Go vanity-import stubs. Built with [Hugo](https://gohugo.io) + the
[hextra](https://github.com/imfing/hextra) theme (vendored under `themes/hextra`), deployed
to GitHub Pages.

## Develop

```sh
cd website
hugo server          # http://localhost:1313
hugo --gc --minify   # production build into ./public
python3 check.py public  # local links, anchors, canonical/SEO/OG/vanity metadata
python3 -B -m unittest discover -p 'check_test.py'  # checker failure-path fixtures
```

No npm step is required — hextra ships precompiled CSS (`themes/hextra/assets/css/compiled/main.css`).

## Structure

```
content/
  _index.md          landing page (layout: launch-home)
  docs/              getting started, CLI, benchmarks, and maturity
    cli/             canonical CLI overview, reference, connections/metadata, and tutorials
  changelog.md       rendered from the repo CHANGELOG.md (see below)
layouts/launch-home.html  homepage shell (the theme owns docs/navigation)
assets/css/custom.css     homepage styles, including light/dark/mobile
static/og.svg             editable social card; render to static/og.png
static/install.sh         the fdb CLI installer
data/                site data (nested Go module list for vanity imports)
themes/hextra/       vendored theme (no go.mod; not part of the Go/Bazel build — see .bazelignore)
```

## CLI documentation

`content/docs/cli/` is the canonical CLI user documentation: overview, command
reference, connections and metadata, a downloadable protobuf tutorial, and SQL
catalog addressing. The repository's `cmd/fdb/README.md` and old operator-guide
path link here rather than keeping another full copy. Public tutorial assets
live under `static/examples/` and are served from `/examples/`.

## CLI installer

`static/install.sh` installs the `fdb` binary from root `vX.Y.Z` release tags and
`fdb_<version>_<os>_<arch>.tar.gz` archives. It verifies `checksums.txt` before
installing and never downloads legacy archives or nested-module releases.

- `FDB_CLI_VERSION` / `--version` selects the CLI release (default: latest).
- `FDB_INSTALL_DIR` / `--dir` selects the install directory (default: `~/.local/bin`).
- `FDB_BASE_URL` and `FDB_API_URL` override the release-download and API bases.

`FDB_VERSION` belongs to FoundationDB server tooling; the installer ignores it.
The config remains at `~/.fdb/config.yaml` after `--uninstall`.
Fixture-backed installer regressions live in `infra/install_test.go` and run with
`just test` from the repository root; they do not need network access.

## Social card

After editing the source, regenerate the PNG used by Open Graph and Twitter cards:

```sh
rsvg-convert static/og.svg -o static/og.png
```

Keep the card and the page/site descriptions free of unverified performance or
compatibility claims. Check the homepage at narrow and desktop widths in both
themes after changing its layout.

## Changelog (single source of truth)

The repo's top-level `CHANGELOG.md` is the source. The deploy workflow copies it into
`content/changelog.md` (prepending front matter) at build time, so it is never edited here
by hand.

## Vanity imports

The Go module path is `fdb.dev`. GitHub Pages is static, so we can't run a `?go-get=1`
handler — instead the `<meta name="go-import">` / `<meta name="go-source">` tags are
served statically.

`go get fdb.dev/a/b/c` requests `?go-get=1` for each prefix of the path, longest first,
and stops at the first HTTP 200 whose go-import prefix matches. Every page here carries
those tags (`layouts/_partials/head.html`), so **the tag served at `/` resolves every
package in the root module** — present and future. Packages need no stub page and must
not get one; a per-package list would rot on every new package for no benefit.

Nested modules are the one case the
prefix walk can't reach: it finds the `fdb.dev` tag first and resolves the package against
the root module, which doesn't contain it — a nested `go.mod` carves that subtree out of
the parent. Each nested module root therefore needs an HTTP 200 at its exact path, which
`content/_content.gotmpl` mints from `data/gomodules.yaml` using the minimal `gometa`
layout. The CLI is a package of the root module (`fdb.dev/cmd/fdb`), so it needs no
stub or nested-module tags.

`data/gomodules.yaml` is generated by `scripts/gen-vanity-modules.sh` (`just
vanity-modules`). The site build re-runs it, so production can't drift; CI additionally
fails if the committed copy is stale.

## Deploy

GitHub Actions builds `website/` and publishes to Pages on push to `master`; `CNAME`
points the site at `fdb.dev`. See `.github/workflows/` and the DNS notes in the deploy PR.

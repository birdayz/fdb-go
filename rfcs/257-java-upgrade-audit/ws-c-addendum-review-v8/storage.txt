## Findings, most severe first

**1. Medium: RANK hash function.**
- Java knows four hash functions, `JDK`, `CRC`, `RANDOM` and `MURMUR3`, and refuses an unknown name (`RankedSetHashFunctions.java:37-58`).
- Go maps every name except `"CRC"` to JDK, in the maintainer (`rank_index_maintainer.go:61-68`) and in `rankHashFunctionName` (`metadata_evolution_validator.go:969-975`).
- So Go admits a change from unset to `MURMUR3` or `RANDOM`, which Java refuses with "rank hash function changed" (`RankIndexMaintainerFactory.java:86-91`). That is the unsafe direction: a Java store then maintains a JDK-built ranked set with another hash.
- The maintainer also writes a `MURMUR3` index's ranked set with the JDK hash, which is a wire divergence.
- Revision 8 treated the vector metric's lenient parse (m79) but not this one. Neither DIVERGENCES.md nor TODO.md tracks it (grep: 0 hits, with a positive control).
- **Fix:** port the four hashes and the refusal of an unknown name, compare the parsed function, and pin both engines.

**2. Medium: R-tree `rtreeStoreHilbertValues`.**
- Java reads this option only when `rtreeStorage` is set, and then with `parseBoolean`, so an absent option means false (`MultiDimensionalIndexHelper.java:58-65`).
- Go reads it on its own, and only the exact string `"false"` turns it off (`multidimensional_index_maintainer.go:78-82`).
- The verdict flips in both directions (`:1132`):
  - `{}` → `{storeHV:false}`: Java admits, Go refuses.
  - `{storage:BY_NODE}` → `{storage:BY_NODE, storeHV:true}`: Java refuses, Go admits.
- The written bytes differ too. For `{storage:BY_NODE}`, Go writes the Hilbert value into leaf slots where Java writes null (`rtree_storage.go:196-205` against `ItemSlot.java:112-113`). Both engines can read either form (`ItemSlot.java:153-157`).
- Smaller differences: an unparsable minM, maxM or splitS is silently defaulted in Go, where Java throws; and `useNodeSlotIndex` is compared case-sensitively.
- Nothing tracks this either.

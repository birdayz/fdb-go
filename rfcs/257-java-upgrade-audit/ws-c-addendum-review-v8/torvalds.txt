## Findings, most severe first

**1. Medium (from source): comparing "effective values" through Go's parsers now admits changes that Java and v7 refused.**
- **Rank hash function.** `rankHashFunctionName` (`metadata_evolution_validator.go:969`) maps every name except "CRC" to "JDK".
  - Java has four hash functions: JDK, CRC, RANDOM and MURMUR3. It refuses an unknown name (`RankedSetHashFunctions.java:46-58`, `RankedSetIndexHelper.java:64-79`).
  - So changing the option from unset to "MURMUR3" or "RANDOM" gets "rank hash function changed" from Java. v7 refused it too, by raw string. Revision 8 admits it.
  - This is the lenient-parser trap that `hnswMetricName` was written to avoid, left unguarded here.
- **R-tree Hilbert values.** Java reads `rtreeStoreHilbertValues` only when `rtreeStorage` is set, and then reads an absent value as false (`MultiDimensionalIndexHelper.java:62-65`, which tests `rtreeStorage != null`).
  - With `rtreeStorage` set on both sides, unset to "true" is false→true, so Java refuses it. v7 refused it. `:1132` admits it.
  - With storage unset, unset to "false" is admitted by Java and refused by Go.
  - The "admits an option set to its default" spec covers only the case where storage is unset and the value is "true".
- **Booleans and integers.**
  - Java's `parseBoolean` ignores case. Go's `== "true"` does not: `:1133`, `parseRankedSetConfig`, and the HNSW booleans. So unset to "TRUE" is refused by Java and admitted by Go.
  - For integers outside Go's accepted range, Go substitutes the default (`multidimensional_index_maintainer.go:63-77`, the HNSW range checks). Java compares the value it parsed.
- **Fix:**
  - Compare the values Java parses:
    - a name function for the rank hash that keeps an unrecognized name as its text;
    - Java's R-tree `getConfig`, including the storage-gated read, declared at the site;
    - `EqualFold` for booleans;
    - the raw text for any integer Go would clamp.
  - Add JVM shapes for MURMUR3, for the Hilbert option with storage set, and for "TRUE".
- **Adjacent (pre-existing, from source):** the index maintainers behind these parsers differ from Java on the wire for the same values:
  - RANK hashes MURMUR3 and RANDOM as JDK;
  - the R-tree maintainer ignores BY_SLOT storage and the Hilbert gating.
  
  This needs a durable home in DIVERGENCES.md or TODO.md.

**2. Low: a refused nil key has lost Java's program order, and one path loses it entirely.**

  1. `idx.SetSubspaceKey(nil)`
  2. `AddIndex(idx)`
  3. `AddIndex(dup)`
  
  returns "Index … already defined". Java throws at step 1, and v7 returned the refusal.
- This contradicts the comment at `:781`: "nothing a later call recorded can mask or reorder it".
- Two refused indexes are reported in name order, not in the order of the calls.
- `RemoveIndex` deletes the refused index (`:687`), so `AddIndex; SetSubspaceKey(nil); RemoveIndex; Build` succeeds.
- That breaks 7.8's claims "refused on every path" and "Java's throw ends the program's sequence of calls".
- **Fix:** record the refusal in call order (restore the append, and have a set made after `AddIndex` reach its builder). Have `RemoveIndex` carry the error. Pin both sequences.

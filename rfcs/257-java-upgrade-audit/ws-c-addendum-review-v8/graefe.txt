## Findings, most severe first

**1. Medium: the RANK and R-tree "effective values" are Go's parsers, not Java's configs. One of them, new in revision 8, admits a change Java refuses.**
- **Rank hash function.** `rankHashFunctionName` (`metadata_evolution_validator.go:969`) treats every name except "CRC" as "JDK".
  - Java knows four hash functions: JDK, CRC, RANDOM and MURMUR3. An unknown name throws "hash function not found" (`RankedSetHashFunctions.java:47-59`).
  - So JDK↔MURMUR3, JDK↔RANDOM and unset↔MURMUR3 are now **admitted**. Java refuses each one ("rank hash function changed").
  - Revision 7 compared raw strings and refused them.
  - The root cause is in the maintainer: `parseRankedSetConfig` (`rank_index_maintainer.go:61-67`) also folds MURMUR3 and RANDOM into JDK. A Java MURMUR3 rank index maintained by Go therefore hashes differently, which is a wire divergence. It is not tracked anywhere: "murmur" has 0 hits in TODO.md and DIVERGENCES.md, while the control `crcHash` hits 4 files.
- **R-tree Hilbert values.** Java reads `rtreeStoreHilbertValues` only when `rtreeStorage` is set (`MultiDimensionalIndexHelper.java:62-65`, which tests `rtreeStorage != null`). With the storage option set and the Hilbert option unset, Java's effective value is `false`. `parseRTreeConfig` (`multidimensional_index_maintainer.go:78-82`) always defaults to `true`. The consequences:
  - `{storage}` → `{storage, hilbert:"true"}`: Java refuses, Go admits.
  - `{}` → `{hilbert:"false"}`: Java admits, Go refuses.
  - `rtree_storage.go:198` writes a leaf slot's Hilbert value according to this flag, so Go writes such a Java index differently. That is wire-level, and "hilbert" has 0 hits in TODO.md and DIVERGENCES.md.
- **Booleans.** Go matches strings exactly: `== "true"` for count-duplicates and node-slot-index (`:1133`), `== "false"` for Hilbert. Java's `Boolean.parseBoolean` ignores case.
- **Fix:**
  - Port `getHashFunction` (Java's four names; refuse an unknown one) and `MultiDimensionalIndexHelper.getConfig`, quirk included, with Java's boolean parsing.
  - Add JVM shapes for the option families. None exists today; m78 and the default-value spec cover only Go's own view.
  - Book the two maintainer divergences in TODO.md, or fix them.

**2. Low: "every `MetaDataEvolutionError` now starts with Java's message" covers only the validator file.**

- These are mostly unreachable with valid meta-data. The fix is to port them or narrow the sentence.

**3. Low: "a nil key is refused on every path" still misses two paths.**
- **Already-built meta-data.** `SetSubspaceKey(nil)` on an index of an already-built `RecordMetaData` records an error that nothing reads. The only reader is `Build` (`metadata.go:791`), and the key stays unchanged. The v7 reviews (Graefe 2) raised this path. 7.8 neither closes it nor declares it.
- **RemoveIndex.** A refused set followed by `RemoveIndex` before `Build` is lost, because `Build` walks only `b.indexes`.
- **Enum typed nil.** A typed-nil generated-enum pointer panics at `subspace_key_identity.go:160` (`Number()` through a nil pointer).
- **Fix:** declare the first at the setter and in the CHANGELOG, carry the refusal through `RemoveIndex`, guard nil enum pointers, and pin each.

## Findings, most severe first

**1. Medium (wire, from source, not measured): the order Go visits map entries can change stored bytes, contrary to 7.12 (`ws-c-design.md:2221-2223`) and `key_expression.go:973-974`.**
- **The order differs.** `evaluateMap` sorts the keys (`key_expression.go:988`). Java visits them in the message's order, which is wire or insertion order; the design says so itself.
- **Both engines let the last write win:**
  - **Covering index.** VALUE: Java calls `tr.set` for each entry in list order (`StandardIndexMaintainer.java:427-451`); Go calls `SetBytes` (`index_maintainer.go:347-371`). Take `KeyWithValue(NestFanOut("attrs", Concat(Field("value"), Field("key"))), 1)` over `{"trim":"red","color":"red"}`: both entries write the key `("red", pk)`. The stored value is whichever entry came last.
  - **TEXT.** Java runs one entry after another, and each token's `bunchedMap.put` replaces the previous one (`TextIndexMaintainer.java:351, :383-387`); Go does the same (`text_index_maintainer.go:287, :372`). Two entries in one group that share a token store the last entry's positions. Java builds this shape: `TextIndexMaintainerFactory.java:118-127` has no fan-out check.
- **Where it bites.** Go writes records with `Deterministic: true` (`store.go:2191`), so for Go-written records the key order equals the wire order. The difference appears when Go indexes a Java-written record: an online build or rebuild on a mixed fleet.
- **Why the tests can't see it.** The maintenance spec writes its records with `Deterministic: true` (`key_validation_conformance_test.go:231`). Its root `Concat(key, value)` (`:205`) also gives every entry its own FDB key.
- **Undeclared.** Before this revision Go refused the shape and said so; now it writes different bytes without a word.
- **Fix:** visit the entries in the record's wire order, which Go has from the stored bytes. Pin it with a JVM spec: a record written in non-sorted order, plus the covering root above.

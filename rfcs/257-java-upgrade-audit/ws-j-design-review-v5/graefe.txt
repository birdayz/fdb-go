## HIGH

**1. Shape (d)'s refusal rejects SQL templates the target creates and serves.**
- `refuseAmbiguousLegacyUnion` (`metadata_proto.go:415`) refuses any file with a top-level message `UnionDescriptor` that is not the union it finds.
- A template with a quoted table or struct named `"UnionDescriptor"` is exactly that shape: a record message beside the usage=UNION `RecordTypeUnion`.
- Neither engine reserves the name:
  - Java relational: the only hit is `FileDescriptorSerializer.java:77` (`RecordTypeUnion`).
  - Go: 0 hits in non-test `pkg/relational`; control: `RecordTypeUnion` on 4 lines of `builder.go`.
- `deserializeTemplate` loads every template through this loader (`fdb_template_catalog.go:280`). Go would therefore fail with XX000 on a template Java created, and on its own template at the next CREATE SCHEMA or save.
- The pre-upgrade loader could not have written records framed by that message. It took the table message as the union, and scalar fields map to no record type (`e48f5b496:metadata.go:338-360`).
- This makes three statements false: design :1228 ("SQL DDL produces none of them"), the CHANGELOG and DIVERGENCES.
- **Fix:**
  - Do not refuse when the legacy candidate is the message type of one of the found union's fields.
  - Add a JVM-spec shape built by SQL DDL.
  - Correct the three scope sentences.
- Status: SOURCE, not measured.

## MEDIUM

**2. The load order matches Java only up to the records step.**
- Java resolves each index's record types before `new Index(proto)`, one index at a time (`RecordMetaDataBuilder.java:185-217`). Go parses every index first (`metadata_proto.go:273`). A duplicate-option fault can therefore hide "Unknown record type" on the same index or an earlier one.
- Java refuses a `RecordType` entry that names an unknown type (`:219-220`, `:986-995`). Go skips it with `continue` (`:317`).
- The Go-only (d) refusal runs before Java's index checks. A file the target itself refuses therefore gets Go's message instead of the target's; the refusal belongs after `Build`.
- The cite is wrong: the message comes from `throwUnknownRecordType` (`RecordMetaDataBuilder.java:994-995`), not `RecordMetaData.java:826` (design :1173).

**3. Section 3.5's coverage wording (:505) would return wrong rows, and its Java claim is inferred, not measured.**
- The design says the coverage surface "exposes the key's operand fields".
- The `dplus` entry holds `d + 1` and the PK, not `d` (`COVERING(DPLUS … -> [ID: KEY:[2]])`). Exposing `d` would plan `SELECT d … WHERE d + 1 = 5` as a covering scan of a value the entry does not contain.
- Today Go blocks every function-key column (`match_candidate_index.go:660-670`).
- **Fix:** state that a function-key column exposes nothing.
- "The target never reads the value from its entry" rests on two indirect observations: a 0AF00 (the ordering never matches) and a MAP over a DOUBLE key.
  - Run the direct probe: `EXPLAIN SELECT d + 1 FROM T2 WHERE d + 1 = 5`, and `i + 1 = 6` at the INT edge.
  - Add a plan-harness pin that `SELECT i … WHERE i + 1 = 6` does not produce a covering plan.

**4. The merge unit leaves two v5 decisions unscheduled.**
- **(a) The template-save no-lane refusal (:560).**
  - It is in neither section 8 nor gate 8.
  - It depends on section 6's lane table, which is step 6, outside the unit.
  - Step 3 turns on `allowIndexRebuilds`, under which a reverse or no-lane key is admitted as CHANGED (validator :535-537).
  - **Fix:** put a save-time check in the unit (the bitmap functions' lane table is two rows, `ArithmeticValue.java:515-522`), or declare the gap.
- **(b) The `DeleteTemplateVersion` refusal and `RestoreTemplateVersion` (:354).**

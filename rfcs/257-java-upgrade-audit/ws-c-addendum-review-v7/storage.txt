## Findings

**1. Low: a nil subspace key still gets in, and revision 7 made one path worse.**
- **The ways in.** `SetSubspaceKey(nil)` is now refused. But:
  - An `Index` or `FormerIndex` built as a struct literal still has a nil key, because `subspaceKey` is unexported and defaults to nil.
  - A typed nil passes the setter: `tupleEquivalentValue` returns `(*big.Int)(nil)` and `(*FDBRecordVersion)(nil)` unchanged (`subspace_key_identity.go:120-123`, `:135-138`), so `normalized == nil` is false (`index.go:502`). Packing a nil `*big.Int` then panics in `encodeBigInt`.
- **What happens next.**
  - `Build` has no nil check (`metadata.go:1196-1235`). The index is maintained under the null item, and `indexToProto` omits the key (`metadata_proto.go:662-665`), so a reload puts it under its name.
  - `RemoveIndex` turns it into a former index with a nil key (`metadata.go:677-683`). The new `formerIndexToProto` writes that as a null item (`metadata_proto.go:941`), which the new loader refuses (`:974-976`). So Go saves meta-data it cannot reload. Before revision 7, Go wrote the key as absent and read it back as nil.
- **Also:** a `SetSubspaceKey(nil)` made after `AddIndex` is never collected (`:617-619`). Java throws at the call.
- **Java:** this state cannot exist; every constructor normalizes the key or refuses it (`Index.java:89-97`, `:132`; `FormerIndex.java:51-58`).
- **Fix:**
  - default a nil key to the name in `addIndexCommon`, as Java's constructors do;
  - refuse typed nils in the setter;
  - refuse a nil former-index key in `Build` with Java's message;
  - pin each.

**2. Low: the evolution validator and message-parity claims go past the code.**
- **7.7:1210** says "Every check now runs in Java's order with Java's message first", and that `validateIndex` is Java's method. The later arms of `validateIndex` keep Go's messages, none of which starts with Java's:
  - `metadata_evolution_validator.go:479`, `:704`, `:735`, `:739`, `:749`, `:754`, `:762`, `:813`, `:827`;
  - for example, Go's `index "x" type changed` against Java's "index type changed", and Go's "no longer covers record type" against Java's "new index removes record type" (`MetaDataEvolutionValidator.java:663-747`).
- **A different verdict, pre-existing.** The root is compared by proto equality (`:729-740`), not `KeyExpression.equals`:
  - `FieldKeyExpression.equals` ignores the null standin (`FieldKeyExpression.java:406-410`), but Go's proto carries `NullInterpretation` (`key_expression_proto.go:39-47`);
  - so Go refuses a root change that only alters null interpretation, and Java accepts it.
- **Fix:** scope the sentence. Then either compare roots with `keyExpressionEquals` (keeping the literal-carrier extension) or declare the divergence.
- **Build's collision messages.** `CHANGELOG.md:~200` says "Java's message", which holds only in part:
  - Go names the colliding pair in name order (`metadata.go:1196`); Java names it in HashMap order (`RecordMetaDataBuilder.java:148`, `RecordMetaData.java:318-320`). The two differ for names like `c` and `ba`.
  - Go renders the key with `%v`, so a `[]byte` key prints as `[112 98]`.
  - The conformance shapes pass only because `i0` and `i1` happen to hash in name order.

## P2-1 — The peel's time budget turns a slow transaction into a terminal error (design 1097-1110)
- **The claim at 1101-1104 is false.** It says time only chooses between a selected partition and a re-armed reconcile. Above hardMax, though, a budget cut reaches `ClusterUnsplittableError` (1054-1068).
  - That error poisons the context, and build ranges, queue replay and the hand-off all treat it as terminal (830, 1064-1067).
  - So a cluster the peel could split fails a build or a user insert because one transaction was slow; a fresh transaction would have split it.
  - This hits exactly where n is largest and refits are slowest.
- **At or below hardMax, a cut clears SPLIT_MERGE on a cluster that could be split.**
  - In deferred mode with no later insert, the cluster stays over max indefinitely.
  - In inline mode at large d, every insert pays up to 3 s, the cluster never splits, and the count climbs until the terminal error.
  - The budget is measured on the transaction's elapsed time, so the user's own earlier work also decides the topology.
- **The clock is undefined.**
  - Go's `FDBRecordContext` has no `transactionCreateTime`; only `ScanLimiterState` anchors one (`scan_limiter_state.go:123-142`).
  - `pkg/docscheck/dst_seam_gate_test.go` fails any raw `time.Now`/`time.Since` in production code. This call decides persisted topology, so it is not an exemptible metric.
- **The d = 4096 acceptance fixture depends on machine speed.** At the JVM's measured rates the tight 50-outlier shape needs about 2 s of refits at d = 4096, so whether the 3 s budget cuts it depends on the machine. That contradicts "no pinned outcome depends on machine speed" (1104-1106). The "< 2 s" assertion is also a wall-clock test run under `--local_test_jobs=4`.
- **Needed:**
  - A budget cut must never be terminal and never look like structural unsplittability: keep SPLIT_MERGE and leave the task retryable. Specify this on both sides of hardMax.
  - Anchor the clock on `dst.Env` via a `transactionCreateTime` port.
  - Take the peel's RNG split unconditionally at peel entry, so later draws don't depend on time.
  - Drive the fixtures with an injected clock.

## P2-2 — `consumerOutcome` is specified out of Java's statement order, and the skip and `runTask` share it (design 230-238, 312-321, 374)
- **What Java does:**
  - Quantizer before phase 1: SplitMergeTask.java:227 before :232, merge :430 before :435 (and before the no-mergeable-neighbour exit :483-493), ReassignTask.java:241 before :248.
  - With precomputed neighbours, `fetchClusterMetadataForReferences(splitMergeConcurrency)` at :239-240/:442-443 runs before `classifyClusters` (:472-475) and the :483 exit.
- **What the design says:** no-op exits, then phase 1, then mergeable-neighbour, then "the knob or quantizer check at the consumer that follows".
- **Consequences:**
  - Item 15's live task is an insert-armed split with no precomputed neighbours. Under the written order the prediction is "runs", so Go's delete runs it and fails. That contradicts the fixture "a bits9Live head task is skipped".
  - Because `runTask` uses the same function, a merge whose neighbours have vanished would be consumed and committed in two cases where Java throws: under a trained bits-9 index, and under splitMergeConcurrency 0 with precomputed neighbours. That is an undeclared persisted-state divergence.
- **Needed:**
  - Write the per-kind order as Java's: exits, split/merge decision, quantizer, phase 1 and livelock, the neighbour fetch, the merge's mergeable-neighbour check, `fetchCoreClusters`, KMeans.
  - Add fixtures for those vanished-neighbour arms.

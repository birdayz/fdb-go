## P2-1 — The peel's time budget has no defined clock (design 1098-1106)
- **The clock it names does not exist in Go.** Go's `FDBRecordContext` has no transaction create-time or age (`database.go:626-689`). Java has `getTransactionCreateTime` (cited in `scan_limiter_state.go:124-126`).
- **The budget decides what gets stored.** It chooses between splitting and reconciling, so it changes what topology gets written. The repo's DST gate (`pkg/docscheck/dst_seam_gate_test.go:17-27`) fails the build on a raw `time.Now` in `pkg/recordlayer`. Anything that affects persisted bytes must read time through `*dst.Env`. The design doesn't say whether it does (a design grep for dst/env/seam/GRV finds nothing; the same grep does find "wall-clock" at line 819).
- **The anchor is undecided.** RFC-198 established that FDB's 5 s window opens at the read version (GRV), and that the context's creation time is a refuted proxy for it (`scan_limiter_state.go:144-150`). Anchored at creation time inside an explicit SQL transaction, the budget fires early, and clusters that could be split get reconciled instead.
- **The 1 ns fall-through fixture would pass without testing anything.** Under a simulated clock that does not advance, elapsed time and fit duration are both 0, so the budget never trips.
- **Decide:** the clock source (the env clock) for both the anchor and the fit timing, the anchor itself, how the budget interacts with explicit SQL transactions, and that the setting is not persisted. Add a DST fixture.

## P2-2 — `consumerOutcome` does not follow Java's statement order, and its role inside `runTask` contradicts itself (design 243, 311-379)
- **Wrong order (314-321).** The design lists the phase-1 re-enqueue ("runs") and the mergeable-neighbour check before "the knob or quantizer check at the consumer that follows". Java constructs the quantizer first:
  - `SplitMergeTask.java:227/430`, before phase 1 at `:232/:435`;
  - for a merge, before the `splitMergeConcurrency` fetch (`:442`) and the no-mergeable-neighbour exit (`:483-493`).
- **This contradicts a measured case.** The measured bits9Live task is `SPLIT_MERGE/NORMAL/1` (`evidence-run.txt:204`). Inserts enqueue splits with an empty neighbour list (`Primitives.java:1414` → `SplitMergeTask.of`, `:1013-1016`), so that task is in phase 1. By the prose it "runs", while fixture 374 says it is skipped.
- **Contradictory role in `runTask`.** `runTask` calls `consumerOutcome` (323), and the design says the skip decision is "the same code that makes the refusal" (311) with "no second copy of any predicate" (243). Yet 356-361 says the knob prediction, made without reading the posting, is one `runTask` "would not raise" when every candidate is n<k.
  - If `runTask` raises on it, the refusal comes earlier than `KMeans.java:136-141`, and "the next drain reconciles it" (377) becomes false.
  - If it ignores it, the single-predicate claim is false.
  - **Needed:** an explicit outcome value, e.g. "refused unless every candidate is n<k". The skip treats it as skip; `runTask` proceeds to the real consumer.
- **The serializable side has no fixture.** Lines 326-329 claim the false-alarm clear conflicts with a concurrent insert, which is the v8 race. Every listed fixture pins only the snapshot side, where no conflict is added. A mutation that makes the `runTask` prologue read at snapshot would stay green, although v8 asked for a conflict fixture.
- **The bounce hand-off loses the RNG state.** It passes the list and the pick. `BounceTask.java` uses the same `splittableRandom` after `nextInt` (`:161`) at `:190` and `:200`, and undrawn at `:149`. Hand over the RNG state as well.

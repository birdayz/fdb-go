## P2 — The time budget can produce the "unsplittable" terminal error for a cluster that can be split (design 1054-1068, 1094-1111)

1. **The design's claim is false.** It says a budget cut leads to either a selected partition or a reconciled clear, so time "never produces a new state" (1103-1104). But the reconcile fails whenever the reconciled count is above the hard cap (1054-1058), and the design itself says that happens in inline mode and in deferred mode.
   - So cut + count above the hard cap raises `ClusterUnsplittableError`. That error poisons, is terminal for the build-range and queue-replay owners (1064-1068), and ends merge sessions.
   - The cluster is only unsplit *within the budget*, not unsplittable. At large d the cut happens on every run, even in a fresh merge transaction.
   - The design's own d=4096 fixture reaches this: one insert past hardMax, and the partition is permanently stuck on a Go error whose name is false.
   - The list at 1019-1025 ("the population that reaches it is exactly") leaves out budget exhaustion.
   - **Needed:** a budget-cut outcome and retry classification separate from structural exhaustion, stated for inline and deferred mode, plus proof that it cannot livelock or starve the queue.
2. **"The transaction's elapsed time" has no source in Go.** `FDBRecordContext` has no start-time field (`database.go:626-689`). Java has `getTransactionAge()`, taken at context creation (`FDBRecordContext.java:146, 189, 674-676`). The design also needs to address:
   - an explicit `SetReadVersion` (`database.go:1171`), which makes a context-age clock *underestimate* the time left before FDB's 5 s limit;
   - the per-context FDB timeout (`runner.go:299`). Error 1031 is not retried, and a fixed 3 s budget ignores the timeout;
   - the DST environment. The budget decides persisted bytes, so both of its clocks must go through `rc.Env()` (`database.go:631-635`).
3. **The budget covers refits only.** Two costs run after it unbudgeted:
   - the reconcile read, which the design says no cap bounds;
   - materialisation of a selected partition.

   The reconcile also reads per-PK metadata for replicas, which Java's cleanup never does (`Primitives.java:1544, 1552-1560`). So "the reconcile's read is the target's own" (1106) is inexact, and the extra reads add read conflicts on replica PKs.
4. **The acceptance fixture depends on machine speed.** "Completes in under 2 s" (1108) is a wall-clock assertion on real FDB. That contradicts "no pinned outcome depends on machine speed" (1105-1106) and will flake under load. Use an injected clock.

## P3

1. **The heartbeat-admin rewrite introduced an undeclared divergence** (`indexing_heartbeat_admin.go:103-117`).
   - The new code never parses the heartbeat KEY.
   - Java's `getIndexingHeartbeats` throws on a non-UUID key: `getUUID(0)` sits outside the try (`IndexingHeartbeat.java:148`).
   - v8's Go matched Java through `heartbeatIndexerID` (`indexing_heartbeat_admin.go:44-47`).
   - Go admission fails closed on such keys (`indexing_heartbeat.go:128-131`). So "ongoing means exactly a new session would be refused" is false for legacy string-keyed heartbeats, which the code comments say exist.
   - "Exactly three populations" (in DIVERGENCES.md and the function comment) is really four. Parse the key, or declare this case and pin it.
2. **`consumerOutcome` order contradicts Java.** Java builds the quantizer *before* the phase-1 re-enqueue:
   - split: `SplitMergeTask.java:227` before `:232`;
   - merge: `:430` before `:435`.

   The design places the quantizer check after phase-1 (314-321). Taken literally, a phase-1 split under trained bits-9 is predicted "runs", which contradicts the "bits9Live head task is skipped" fixture. State the order explicitly.
3. **Delete-skip isolation.**
   - Java's inline fetch is a *serializable* range read of the queue head (`Primitives.java:984`, then `:1053`).
   - So "conflicts there only because it removes the task" (331-332) is inaccurate: that range read also conflicts with concurrent higher-priority enqueues.
   - For a delete that does *not* skip, require a serializable re-read of the head (or an equivalent conflict range). The prologue re-read alone does not restore Java's conflict footprint.
4. **Evidence provenance.**
   - `evidence-run.txt:4-7` still records v8's source hashes. The tree's files are `9a8fa3c4…` (`.java`) and `f3917cd6…` (`_test.go`), so they no longer match.

   - The item-18 runs and the floor mutation exist only under `/var/tmp`. `evidence-mutations.txt` was not updated, and `wsd-hd-peel-7.log` goes unmentioned.

## MEDIUM

**M1. The catalog lane check does not use Java's names for the key functions.** Read from source; not run.
- Java builds a key function's Value under a separate `valueFunctionName` (`LongArithmethicFunctionKeyExpression.java:121-123`). `subtract`, `multiply` and `divide` map to `sub`, `mul` and `div` (`:247-252`). Go's registry has all three names.
- `index_lanes.go:120` asks `IsArithmeticFunction(fn.GetName())`. That is false for `multiply`, so the key is typed UNKNOWN and gets no lane check. This goes wrong both ways:
  - **Go refuses what Java plans:** `add(multiply(a,b), 1)` gets 42F59, while Java finds MUL_LL and then ADD_LI.
  - **Go stores what Java can never plan:** `multiply(s, 1)` with `s` a STRING.
- The same over-refusal happens for `add(recordType(), 1)`. Java's `RecordTypeValue` is LONG (`RecordTypeValue.java:126`); Go types it UNKNOWN.
- DIVERGENCES.md's entry at :3015 declares a refusal only for "a Go-only function key", so this refusal is undeclared.
- **Fix:** map key-function names to Java's value names, give RecordTypeKeyExpression the type LONG, and pin each alias.

**M2. The resumed-page fix has no test.**
- The fix at `continuation.go:491,512` landed, but nothing tests it:
  - `git grep UnmarshalRecordAsJava` finds no caller in any test;
  - no executor or relational test mentions a closed enum.
- Reverting either line stays green.
- INSERT…SELECT is now also covered by the save's `asJava` (`store.go:587`). The continuation site is not.
- All three v18 gates asked for a resumed-read pin. Add one Java-versus-Go test: a sort or recursive continuation over a STRUCT whose closed enum holds an undeclared number.

**M3. The lane table and the planner are two copies of Java's operator table (the mandatory Graefe review).**
- I checked all 107 rows against `ArithmeticValue.java:406-522`, and they match. `ArithmeticValue.Type()` (`values.go:3661`) agrees with the table on every ADD, SUB, MUL, DIV and MOD row.
- But nothing ties the two together:
  - `ArithmeticLanes()` has no caller;
  - no unit test walks the table;
  - WSJLANE drives only the 11 bitand and `bitmap_bucket_offset` shapes, so none of the five arithmetic operators is tested.
- The planner's own typing and evaluation give a result for every pair of operand types, where Java refuses pairs with no row.
- **Is the split sound?** It is sound as an interim state only:
  - `values` is the right home for the table, since the catalog and the DDL generator can import it and the planner cannot import the catalog.
  - It needs a pin that drives every row through both `LookupArithmeticLane` and `ArithmeticValue.Type()`.
  - Section 6 needs to name `values.LookupArithmeticLane` as the one table the planner resolves lanes from, for the five arithmetic operators as well as the bit operators.

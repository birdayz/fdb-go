**H1. Section 12's transition table reasons about the leaf, but the outermost composite cursor decides the outcome (:1405-1419).**
- **In-union to in-join (:1417) is not refused.** The in-join decodes a `FlatMapContinuation` (`cursor_combinators.go:636-658`). A two-leg `UnionContinuation` has `bytes` fields 1 and 2 (`record_cursor.proto:49-59`), and a `FlatMapContinuation` has the same (`:28-32`), so it parses cleanly. `FromListWithContinuation` then reads any first 4 bytes as a position and clamps it (`cursor.go:358-373`). No check value means the check is skipped. So this transition is at best undetected, and it may silently truncate. F-5's "refused when the new leaf is salted" (:1414) fails the same way under any composite.
- **The F-2/F-3 6a prefix (:1412) cannot work.** Continuations minted before the step carry no prefix, so it cannot guard the step's own transition. If decoding requires the prefix, every in-flight DISTINCT continuation of an unchanged plan is refused at upgrade. If decoding accepts the legacy form, the prefix rejects nothing.
- **Required:**
  - Classify each row by the new plan's outermost decoder, and mark these rows undetected. Java's flatMap and union use the same protos, so this is parity.
  - Pin the actual outcome in both directions, and correct the CHANGELOG text that tells callers what they will see.
  - Delete the prefix plan.

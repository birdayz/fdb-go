## High

**1. W8 (4.2.3): one query per class can't show the class verdict, and Java's rung abstains on the covering class.**
- Java's rule for PREFER_INDEX only fires when the index side is a single index scan *with a fetch* (`PlanningCostModel.java:465-468, 563-567`). A covering scan with no fetch (`w8_covering_all/neq/id_neq`) falls through.
- Reading the source, the lower rungs then tie (`:195-284`; `UnmatchedFieldsCountProperty.java:96-119` gives 1 vs 1 here), so the choice is made by `planHash` (`:335-339`). Go can't reproduce that, because it uses FNV.
- There may also be a cycle: COVERING beats ISCAN on fetch count (`:225-231`), ISCAN beats SCAN on the rung (`:497-501`), and COVERING vs SCAN is decided by hash. v1 already raised that Java's rung isn't a total preorder; v2 still doesn't answer it.
- As designed, the per-class Go pins would lock in a hash outcome as if it were a class verdict.
- **Fix:** have `planRuleTrace` call `PlanningCostModel.compare` on each pair of root members (it already does this for in-union yields). Vary table and index names to move the hash. Then record the covering class as a declared divergence rather than as agreement.

**2. W6 (2.3/2.6): the physical prune interacts with the missing `outerJoinCount`, and the design leaves this open.**
- Under today's virtual prune, the memo still holds the rewritten outer join. Under a physical prune, PLANNING sees only the un-rewritten outer-join select.
- Go's FlatMap for a LEFT OUTER join needs the two legs to be correlated (`rule_implement_nested_loop_join.go:291-307, 387-400`). So the target's `FlatMap + DefaultOnEmpty` index-probe shape may become impossible to derive. "The physical prune does not change that argument" is a hypothesis, not a measurement.
- The census categories also break here:
  - LEFT JOIN is SQL the target accepts, so listing "the materialized outer join" under the Go-extension arm is wrong.
  - A different survivor counts as "comparator-caused, fixed in the comparator", which 2.3 forbids.
- **Fix:** decide before step 7. Either port `outerJoinCount` and derive the materialized NLJ (RFC-152) from the rewritten form, or add a documented Go-only PLANNING rewrite of the outer join. Pin it with a probe of a LEFT JOIN on an indexed ON column.

**3. IN-list (4.3): the stated cause contradicts Go's code, so the one-step landing isn't safe.**
- Go already adjusts the bindings (CHOOSE/SORTED), keeps the provider's ordering set and enumerates satisfying keys (`rule_implement_in_union.go:268-284, 411-495`).
- Reading Java's source, I1 legs look admissible for ORDER BY id too: fixed values are dropped from the ordering sequence (`Ordering.java:636-648`), the record type is bound implicitly (`ValueIndexLikeMatchCandidate.java:154-163`), and the Union enumerator is at `:1337-1394`.
- The trace shows *that* no I1 in-union exists, not *why*. Porting the ordering computation could therefore change nothing, and the size check would then fail on `w8_in25_order_by_id_rows`.
- **Fix:** extend the trace to dump the inner reference's partitions and their orderings on both engines, then fix at whatever layer that points to.
- Separately, the fetch placement still differs, is undiagnosed, and §13 requires these rows to be SAME:
  - ORDER BY col1: target `FETCH(INUNION(COVERING))`, Go `InUnion(IndexScan)`.
  - No ORDER BY: target `INJOIN(ISCAN)`, Go `Fetch(InJoin(COVERING))`.

## Medium

4. **D7:** Java marks *every* restricted reference as explored, PLANNING callers included (`Reference.java:587-594`, reached from `CascadesRuleCall.java:486-490` and `:518-523`). Leaving Go's PLANNING callers unmarked and "measuring at the gate" is a Go-only departure from Java; porting Java's behaviour should be the default. The design's count of 9 callers also misses the three `MemoizeMemberPlansFromOther` callers (`dml_inner_candidates.go`, `rule_implement_filter.go`, `rule_implement_projection.go`), which go through the same helper (`expression_rule_call.go:309-324`).
5. **W13 (0.1, 9.2):** the measured claim is wrong. The Go pin `w13_display_insert_explain` is `OK EXPLAIN "Insert(foo.table$nested)"`, so EXPLAIN INSERT works. Only executing the INSERT fails, which puts the defect on the execution path.
6. **§12:** only leaf swaps are covered. F-2 and F-3 6a remove a DISTINCT above an unchanged leaf, and F-5 moves operators above unchanged leaves. Say whether those continuations resume and that resuming them is correct, and pin one.
7. **F-7** bundles three causes: the configuration flip, the ordering port and the arm deletion. That contradicts "each flip has one cause". Land size 24, the ordering port, the deletion and the check first; flip PREFER_INDEX afterwards.

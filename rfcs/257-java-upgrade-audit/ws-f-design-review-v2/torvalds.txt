## High

1. **Section 4.3's Go-side cause is wrong, so its decision changes nothing.**
   - Go already computes the union ordering the way the design wants to port it: `adjustBindingsForInUnion` promotes to `ChooseBinding()`, then `EnumerateSatisfyingComparisonKeyValues` runs (`rule_implement_in_union.go:279-285, 412-492`). Its comment already says it keeps "the provider's existing ordering set" as Java does.
   - The design also misreads Java: for ORDER BY id, col1 is not in the request, so it becomes `Binding.choose()`, not SORTED (`ImplementInUnionRule.java:272-274`).
   - The unported difference that is actually visible in the source: Java memoizes the whole partition (`memoizeMemberPlansFromOther(innerReference, planPartition.getPlans())`, `:205`). Go instead pre-selects one member with the rule-level cost model and pins it (`memberSatisfiesOrdering` / `pinOrderedSpine` / `FinalOf(pinned)`, `:350-383`).
   - The trace cannot tell these apart:
     - `describe()` goes through `Reference.get()`, which throws unless the reference has exactly one member (`Reference.java:252-258`). So it prints the survivor after pruning.
     - It counts only yields the memo admitted (`CascadesRuleCall.java:224-225`).
   - So "never builds an index in-union ordered by the primary key" is an inference, not a measurement. The trace needs to record the inner reference's members at yield time, then the real divergence needs locating.

2. **Two claims labelled MEASURED contradict the pins.**
   - **In-union, ORDER BY col1** (0.1 "rule trace" row; 4.3): the design says the rule's in-union over COVERING(I1) wins. The pin at `ws_f_probe_conformance_test.go:496` shows:
     - its only final is `INUNION{ISCAN(I1 [EQUALS q])}`;
     - it scores `compare = +1` (it loses) against `FETCH(INUNION{COVERING(I1 [EQUALS])})` and against `INJOIN … SORTED`.
     - The winner comes from pushing the fetch through an in-union whose memoized partition held `FETCH(COVERING)`. Go's `PushInUnionThroughFetchRule` (`rule_push_set_operation_through_fetch.go:179-238`) only fires when the pinned member is a fetch.
     - Nothing in 4.3 reaches the target plan for `w8_in_order_by_col1`.
   - **Quoted dotted table** (0.1 table; 9.2): the design says Go's EXPLAIN INSERT fails. The pin at `:532` is `OK EXPLAIN "Insert(foo.table$nested)"`.
     - EXPLAIN and execution therefore resolve the name differently; INSERT fails at `cascades_generator.go:7104`.
     - That explain-versus-execution split is unexplained, and 9.2's site list and its test plan rest on the wrong claim.

3. **4.2 item 2 still doesn't answer v1's metadata question.**
   - `costModelDiagnosticsOnlyContext` strips metadata as well as configuration (`planning_cost_model.go:1882-1895`).
   - A non-nil context switches on metadata-based criteria: `:1971`, `:2594`, `:2850` (unique index via match candidates), `:3004`.
   - "Keeps the full configuration and drops only … the diagnostics sink" is backwards: the sink is the part it keeps. It also says nothing about metadata.
   - The third caller, `planner.go:253`, isn't named.
   - If metadata switches on at rule level too, F-7's plan flips have two causes, which defeats "one cause per flip".

4. **The rung argument in 4.2 item 3 compares the wrong things.**
   - Java rules only when the other plan is `isSingularIndexScanWithFetch` (`PlanningCostModel.java:465-468, 563-567`).
   - Three of the five measured classes (`w8_covering_all`, `_neq`, `_id_neq`) are covering scans without a fetch. For those, Java's rung abstains and lower rungs decide.
   - Pinning `primaryVsIndexRankOf` to a measured *final plan* therefore cannot detect a disagreement. No reason is given for keeping Go's rank instead of porting Java's abstaining arm. Either port Java's rung, or show that the lower rungs agree for every pair class, including a covering scan carrying more residuals than the primary scan.

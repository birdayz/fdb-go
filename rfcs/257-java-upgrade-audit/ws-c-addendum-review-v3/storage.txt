## Findings, most severe first

**1. Medium: one shared heartbeat identity plus the bounded, detached cleanup lets a late clear erase a live heartbeat.**
- Revision 3 correctly adopts Java's single `indexerId` (`online_indexer.go:474-481`; IndexingBase.java:457).
- But the cleanup is a blind own-key clear whose pure-Go commit can land after the 30s bound returns (`online_indexer_queue.go:290-293`, `:343-366`: "The backend may still finish its detached own-key clear after we return").
- The accepted cleanup design defended that with `rfcs/257-java-upgrade-audit/ws-c-cleanup/README.md:20`: "late clears are harmless because each build uses a new UUID". That premise is now false, and the file wasn't updated. A grep for "new UUID" finds it.
- Consequence: if attempt N's clear commits after attempt N+1 (or a later `BuildIndex` or `MergeIndexes` on the same indexer) wrote the same key `[9, idx, 7, id]`, the live key is gone until the next renewal.
  - During that gap an exclusive REBUILD, or a fresh mark, is admitted and clears state under a running session. That breaks the invariant §7.2 chose to be stricter than Java about.
  - Revision 2's failure mode was a lockout (fail-closed). This one fails open.
- Java awaits `clearHeartbeats()` in the future chain (IndexingBase.java:174) and has no detached return.
- Fix: read the key in the cleanup transaction before clearing it, so a late commit conflicts with the next write, or is rejected as too old. Pin it with the existing readiness barrier: hold the cleanup future past its deadline, run the next attempt, release, and assert the heartbeat survives. Then correct README:20.

**2. Low: a CHANGELOG over-claim.** It says a MUTUAL mismatch "relaunches up to Java's attempt limit (six sessions)".
- CONTINUE over a saved MUTUAL_BY_RECORDS stamp throws at once in Java (OnlineIndexer.java:212-213) and in Go (the catcher's `return indexingCatchFail` after the method switch).
- The same holds for a *blocked* MUTUAL stamp. Only blocked BY_RECORDS, MULTI_TARGET and BY_INDEX stamps cost six sessions.

**3. Low: the declared precedence divergence lists too few cases.**
- The DIVERGENCES.md entry names a blocked stamp, MUTUAL under CONTINUE, and ERROR.
- Go also returns `SynchronizedSessionLockedError` on attempt 1 where Java ends differently in three more cases:
  - `IfMismatchPrevious` MARK_READABLE (Java: `PartlyBuiltException`);
  - a MULTI_TARGET stamp the takeover rules refuse (Java: `PartlyBuiltException` after six sessions);
  - a saved BY_INDEX source that doesn't resolve (Java: the catcher's decode or metadata error).
- Replace the list with the rule: any case where Java's catcher doesn't end on a heartbeat check.

**4. Low: storage v2 finding 4 is only partly closed.**

- The unscannable-source refusal (`:4206`, v2's `:4015`) still checks only the error.
- No spec pins the attempt-limit case that §7.3 and the CHANGELOG describe.

**5. Low (wire): the new check resolves the source by name, then uses the caller's object.**
- `buildIndexingStamp` (`online_indexer.go:1928-1934`) and the scan use `oi.sourceIndex`.
- Java compiles the stamp from `metaData.getIndex(name)` (IndexingByIndex.java:68-71, 95-101).
- So a hand-built `*Index` with a different subspace key or `LastModifiedVersion` writes a stamp Java wouldn't. This predates revision 3, but this check is the place to close it: use the resolved index, or refuse an object that isn't the metadata's.

**6. Low: the `LastBuildOutcome` reset is unpinned.**

## Findings, most severe first

**1. Low: Go refuses RaBitQ with 9–15 extra bits earlier than Java, and the docs call it the same point (source only).**
- `parseHNSWConfig` refuses when the maintainer is built (`hnsw_options.go:218-226`). Every save, delete and scan that touches the index then fails from the first record.
- Java builds its `RaBitQuantizer` lazily:
  - `Primitives.quantizer` returns a no-op quantizer until `canUseRaBitQ()` (Primitives.java:174-183).
  - `firstInsert` builds one at once only for cosine and dot product (Insert.java:274-285).
- So with the default Euclidean metric, Java maintains and searches the index until its centroid exists. Only then does it fail, with an `IllegalArgumentException` that has no message.
- The equivalence is claimed in DIVERGENCES `:2129-2131` ("refused where Go's maintainer makes its quantizer"), the CHANGELOG, the `parseHNSWConfig` comment and 7.16. Nothing measures what Java does at 9 bits beyond the Config check.
- **Fix:** refuse where Go's HNSW first encodes (`nodeVectorBytes` once `opXform` is set, and the cosine/dot first insert at `hnsw.go:573`), or declare the difference.

**2. Low: v15 Torvalds 5 is still open, though 7.16 and DIVERGENCES say it is closed.**
- **Measured from git:** revision 16 changes no line of the wire-order spec (the first hunk after the imports is at `:621`). That spec's raw subspace is only built, never re-saved.
- The new spec's raw arm writes a value for every entry (`intEntry` and `msgEntry` always append field 2).
- So no re-save in either engine starts from an entry stored without a value. DIVERGENCES `:3225` ("raw bytes with an entry missing its value") and 7.16 ("the raw path now meets…") claim otherwise.
- **Fix:** add an entry with no value, and one with no key, to the new spec's `records`.

**3. Low, a regression: a map entry's own unknown fields are dropped.**
- `canonicalEntry` (`record_wire_map_order.go:700`) now writes only the key and the value.
- Revision 15's `Marshal(entry)` kept the entry's unknown fields: a field other than 1 or 2, or field 1 or 2 with the wrong wire type.
- Java's entry is a DynamicMessage that keeps them (DynamicMessage.java:392-397), and `writeTo` writes them back.
- **Already there before revision 16:** a last entry that carries unknown fields makes its key read as changed (`:660`), which collapses a key written twice.
- This only arises from foreign or crafted bytes.
- **Fix:** append `entry.GetUnknown()` after the value, compare only key and value for "unchanged", and add a unit pin.

**4. Low: `elementPriors`' declaration claims more than the code does.**
- **Past `maxLCSCells`** (`:546`, `:602`), matching falls back to content in order. That reopens v15 Torvalds 2: `[A,B]` saved as `[X≡B, B]` makes the unchanged B lose its order. No test covers the bound, and DIVERGENCES `:3236` does not mention it.
- **An inserted equal element:** stored `[B]`, saved `[B′≡B, B]`. The new element takes B's order and the unchanged B is written in key order. That is not "equal elements reordered among themselves", and Torvalds asked for this case to be declared.
- **Fix:** use an unbounded linear-space diff (Myers or Hirschberg), or declare the bound and pin it; and name the insertion case.

**5. Low: two v15 fixes have no regression test.**
- **The dry run over the stored record** (`store_api.go:390-393`): no test file for it changed.
- **The evolution check's RaBitQ bit count** (v15 Torvalds 1): its only row is `"4"` against an absent option (`metadata_evolution_validator_test.go:2878`), which the old `Sscanf` also passes. There is no row with a spelling only Java's parser reads (e.g. `"８"`), and no JVM evolution row, both of which Torvalds asked for.

The additional source findings materially affect the design:

- **Noncacheable cache entries are currently admitted.** The test named “non-cacheable store is not cached” explicitly expects one entry at [store_state_cache_test.go:402](/home/birdy/projects/fdb-go/pkg/recordlayer/store_state_cache_test.go:402). With an existing non-null stamp, a later open can reuse that entry after a noncacheable deletion.
- **Disabling cacheability can leave an old cache entry valid.** `SetStateCacheability(false)` mutates `storeHeader` before `writeStoreHeader` captures `oldCacheable`. Its test manually clears the cache at [store_state_cache_test.go:521](/home/birdy/projects/fdb-go/pkg/recordlayer/store_state_cache_test.go:521), masking cross-transaction coherence.
- **Direct clears miss pending version mutations.** Java’s context clear also removes queued mutations and local versions. Go’s later commit flush can otherwise restore version keys beneath a deleted store or retired index.
- **The initialization override alone is insufficient.** Fresh creation bypasses reconciliation, build-all includes replaced indexes, and plain context commits skip retirement hooks.

The implementable design is:

1. **Keep `DeleteStore(ctx, ss) error` synchronous.** Read precisely `ss.Pack({StoreInfoKey})` through `Transaction().Get(...).Get()`, never snapshot or cached state. Propagate FDB read errors with `%w` before scheduling deletion.

   Decode present bytes as `DataStoreInfo`. Missing header means no bump; successfully parsed header uses `GetCacheable()`; protobuf decoding failure means bump. Do not invoke normal store-open validation: deletion must work with malformed headers, unsupported format numbers, locks, or missing headers with residual data. Empty protobuf bytes are valid and default noncacheable.

   Then conditionally call `SetMetaDataVersionStamp()`, always call `SetDirtyStoreState(true)`, and clear transactionally. Use Java’s subspace bounds, `ss.FDBRangeKeys()`; current Go `PrefixRange` additionally clears the bare prefix and other boundary keys. Pin that boundary difference explicitly in regression expectations.

2. **Complete the cache prerequisites in the same change.** On initial miss, admit only cacheable headers. On stamp mismatch, add cacheable state; otherwise call the existing `invalidateOlderEntry`, including when the header disappeared. Preserve Java’s newer-entry comparison and dirty-context bypass.

   Clone the proposed header before changing cacheability. `writeStoreHeader` must observe the actual old flag, propagate stamp-read errors, and publish the new in-memory header after success. Old cacheable state always invalidates; false→true only initializes an absent stamp. No global serializable stamp read is needed: snapshot stamp comparison handles subsequent transactions; header/index read conflicts protect overlapping transactions.

3. **Separate changed-index enumeration from build eligibility.** Add `RecordMetaData.GetIndexesSince(version)` with the current unfiltered implementation. Make `GetIndexesToBuildSince` exclude indexes whose `GetReplacedByIndexNames()` is nonempty; migrate reconciliation to `GetIndexesSince`. Document this existing API’s semantic correction and update the store convenience method consistently. Add `store.GetIndexesToBuild()` for eligible, non-READABLE indexes.

   In reconciliation, choose DISABLED for every candidate declaring replacements **before invoking `IndexRebuildPolicy`**. The callback must not run for that original index. Ordinary replacements still follow policy.

   Apply the same initialization to `Create` and fresh `CreateOrOpen`, treating every index as new. For ordinary indexes on a new, empty store, preserve Java’s no-record shortcut: non-DISABLED requested states become READABLE. Persist explicit DISABLED entries for replaced originals before returning.

   Do not disable an established original merely because an option-only metadata update adds `replacedBy`: if its `LastModifiedVersion` did not advance, retirement governs its lifetime.

4. **Implement retirement as an atomic state transition.** For each index with replacements, require every named replacement to exist and equal `IndexStateReadable`. `IsScannable()` is wrong because it accepts `READABLE_UNIQUE_PENDING`. Java considers originals in every state, not only READABLE.

   Collect eligible originals, release the state read lock, then disable them through the state mutation path. Never hold `stateMu.RLock()` while calling a method requiring its write lock. Disable only on an actual transition, clearing data and updating persisted/in-memory state, dirty state, and cacheable stamp together.

   Add an internal error-returning state/conflict helper. Retirement must read replacement states from the effective transaction, including its own writes; transition methods must serializably inspect prior state. Scan and maintenance decisions need index-state read conflicts too, including decisions to skip disabled indexes. Preserve public getter compatibility while routing error-capable lifecycle paths through the helper.

5. **Integrate both retirement triggers.** After successful version/header reconciliation, retire immediately, before open returns. After a changed `MarkIndexReadable` or `MarkIndexReadableOrUniquePending`, register one named precommit check per context/subspace. A pending transition schedules a check but cannot satisfy readiness itself. Unchanged marks do not schedule new checks.

   Add context-level named-check deduplication under `commitMu`; a per-store-object boolean is insufficient. Evaluate transaction-visible state when the callback runs rather than freezing readiness at registration. Errors abort commit. Disabling originals must not recursively register retirement.

   Make plain `FDBRecordContext.Commit()` execute the same checks→version-flush→commit→postcommit sequence as `CommitWithHooks`. Existing `Run`, `RunWithWeakReads`, `RunWithVersionstamp`, and `CommitWithVersionstamp` already execute checks; retain exactly one execution per attempt. Retirement is precommit work.

6. **Preserve explicit rebuild semantics and cleanup.** Build-all excludes replaced originals before attempting rebuild. Explicit `RebuildIndex(original)` and explicitly targeted online builds remain allowed; the original survives when any replacement is unready, and otherwise retires at commit.

   Reuse `MarkIndexDisabled`, `clearIndexData`, range-set cleanup, and `eraseAllIndexingDataButTheLockAndRangeSet`, correcting context-aware clearing and preserving Java’s index-build lock subspace. Introduce a small context range-clear helper combining transaction clear with existing queued/local version removal. This requires no asynchronous framework, wire changes, new index-state values, or queue implementation.

The real-FDB regression matrix should use explicit contexts and pinned read versions to expose the first commit result, followed by a separate retry assertion. Run cacheable/noncacheable and cold/warm variants with independent cache instances. A cached-open-only conflict test needs an unrelated sentinel write so it actually exercises commit conflict checking. Stamp equality tests require an isolated cluster or serialized stamp-mutating fixtures.

| Scenario | Required result |
|---|---|
| Missing header, with/without residual store keys | Delete succeeds; store range empty; dirty flag true; stamp unchanged |
| Parsed noncacheable header, including empty protobuf | Same; warm-up must not admit a cache entry |
| Cacheable header | Stamp advances; existing cache instances reload; fresh `Open` reports nonexistent |
| Malformed header: truncated varint, illegal tag, malformed embedded message | Conservative bump and successful clear; no normal-open validation |
| Valid unknown fields or unsupported format | Parsing succeeds; bump follows cacheable flag only |
| Header read fails | Error retains FDB cause; no clear or stamp mutation scheduled |
| **Operation commits first:** cacheability toggle or header-field update | Deleter pinned before operation fails with conflict/1020; retry reads current header |
| **Operation commits first:** record-only write | Deleter succeeds and removes the committed record; header read does not create a whole-store read conflict |
| **Delete commits first:** previously opened writer, cold or cached | Writer conflicts on header; no resurrection; fresh open fails |
| Missing-header delete versus concurrent create | Creator-first: stale deleter conflicts. Deleter-first: creator whose existence read predates deletion conflicts |
| Delete→recreate, same context and separate contexts | New header/state and only new records survive; previous disabled states, header fields, and records disappear; test with populated caches |
| Save versioned record→delete before commit | No delayed record-version or version-index keys survive |
| New/changed replaced original; one/two replacements; all policy choices | Original explicitly DISABLED; policy never called for original; replacement policy respected |
| Existing readable original, partial replacement readiness | Original remains populated and maintained; disable/re-enable replacements in different orders |
| Unique replacement reaches pending | Original remains; replacement range-set retained. Resolve violations and mark READABLE: original retires in that commit |
| Inline and online final replacement build | Original readable before deferred check, DISABLED after commit; reopen with identical metadata version |
| Two replacement builders overlap, both commit orders | State-read conflicts prevent both committing decisions based on the other’s stale unready state; retry retires when all are ready |
| Retirement versus stale original-index writer | Retirement-first: writer conflicts. Writer-first: retirement clears its original-index entries |
| Hook deduplication, multiple stores, failed check, retry, each context commit API | One callback per subspace/attempt; atomic rollback on failure; independent store outcomes |
| Build-all versus explicit original build; remove relationship before readiness | Build-all never attempts original; explicit build remains usable while replacement unready; aborted migration preserves original |

One **source-derived specification edge** needs explicit disposition: Java’s `deleteStoreAsync` does not cancel an already registered retirement callback. A readable-mark→delete sequence can leave the captured callback able to write DISABLED state keys after the clear (`:1886`, `:2951`, `:2981`, `:3705`). Characterize that composition against the pinned oracle before claiming parity. Cancelling or guarding the callback would be an intentional correction beyond the pinned implementation.

**Findings, most severe first**

1. **Blocking: the reason for not porting `ifMismatchPrevious` is false about Java.** `ws-c-design.md:352` and `online_indexer.go:62-64` say "no indexing code reads it … a knob that does nothing". Java does read it. `OnlineIndexer.indexingCatcher` (`OnlineIndexer.java:173-225`) reads it on every `PartlyBuiltException`:
   - CONTINUE, the default, falls back to the previous method (records scan, or retry with the old source index);
   - REBUILD relaunches with `setIfWriteOnly(REBUILD)`;
   - ERROR rethrows.
   
   Go has no catcher at all, so every `PartlyBuiltError` ends the build. That includes cases where Java's default would carry on with the earlier method. The RFC's own research log quotes the read (`ws-c-research/indexer-research.log:17852`). Now that `IfWriteOnly` exists, the REBUILD arm is a relaunch. Per the DFS rule: port the catcher's `ifMismatchPrevious` handling with specs for each arm, fix both copies of the claim, and grep for any others.

2. **Medium (read from source, not run): a Java-legal REBUILD is now refused in mutual mode.** `online_indexer_queue.go:118` rejects a mutual session when any target is `WRITE_ONLY_WITH_QUEUE`, and it does so before the clears.
   - Java makes this check after the clears, in `setIndexingTypeOrThrow` (`IndexingBase.java:465-469`). Its `clearAndMarkIndexWriteOnly` (`FDBRecordStore.java:3188-3191`) has already moved the index to WRITE_ONLY by then.
   - So Java accepts a mutual session with `IfWriteOnly: REBUILD`, or a follower cleared because its own action is REBUILD, and Go refuses it with "cannot continue a pending write queue index build".
   - Before this change no policy could reach that case; porting `IfWriteOnly` made it reachable. Go already has the check at Java's point (`online_indexer.go:1293`).
   - Fix: delete the early check. Add a spec where a mutual REBUILD over a queued index builds, and keep "rejects mutual queued takeover" green.

3. **Low to medium (read from source): an undeclared Go-only ordering.** The heartbeat admission check (`online_indexer_queue.go:86`, and the preflight at `online_indexer.go:1254`) runs before the desired action is resolved. It only admits peers when the primary is WRITE_ONLY. So when any target has a live heartbeat from another indexer, a session Java would skip, refuse with ValidationException, or publish fails with `SynchronizedSessionLockedError` instead. Java touches heartbeats only on the build path (`IndexingBase.java:450-461`). Either run the explicit check only for the clear/build outcomes, or declare this in §7 with a spec.

4. **Low.** The ERROR refusal leaves out Java's `INDEX_VERSION` key (`IndexingBase.java:203-207`). CLAUDE.md requires the same context fields as Java.

5. **Low: text this change made wrong.**
   - `online_indexer.go:935-937` (BuildIndex "marks WRITE_ONLY … then marks READABLE"), `:1238` ("transitions all target indexes to WRITE_ONLY") and `:1245-1248` (implies only Java can skip a READABLE index).
   - `fleet/build.go`: the reason given for skipping READABLE_UNIQUE_PENDING ("a rebuild … would only redo") no longer applies; BuildIndex now publishes such an index rather than rebuilding it.
   - `frl index build` prints "built X (0 records scanned)" for a skipped session (`index_write.go:305`).
   - CHANGELOG: "published without a build" should add that it only happens when publication is enabled, and that under the default policy it fails with the uniqueness violation while violations remain.

6. **Test population.**
   - The "it alone is cleared" follower rule is never exercised by an unmutated spec. At `online_indexer_test.go:3555` the primary is DISABLED under the default REBUILD, so both indexes are cleared; only mut23 reached the real shape. Add a spec: primary DISABLED with `IfDisabled: Continue`, follower READABLE with `IfReadable: Rebuild`. The primary's orphan entry must survive and the follower's must not.
   - The committed reproducer checks the session outcome first (`:4393`). Under mut1 it failed there (`desired-mut1.log:1415`), not at `IndexNotBuiltError`. The exact message (`desired-red.log:1398`) came from the earlier version of the spec. §7 should say so.
   - The MARK_READABLE-on-READABLE spec (`:3487`) looks the same from outside as a skip, so it doesn't prove the MARK_READABLE path ran. The READABLE_UNIQUE_PENDING spec is the one that does.

**Callers that relied on the old clear-on-READABLE behaviour.** None among the non-test callers:

- The fleet builds only DISABLED and WRITE_ONLY indexes.

The four changed specs fit Java's semantics. The census's conversions to start from DISABLED match how Java's indexer tests begin (`disableAll`).

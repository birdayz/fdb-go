## P1: the value of B contradicts the evidence bound to this tree (design 1393-1417)

- **The claim.** The design says B comes from "the worst OBSERVED refit … over every run": 1.02e-7 s per n·d, which gives B = 1.96e7. In the admitted corner it gives a worst single refit of 170.6 ms and refit totals of at most 0.91 s.
- **What the v13 runs show.** `evidence-run.txt` is regenerated from `rfc257-v13-1.log`, and that run measured:
  - 437.6 ms at n=2000, d=1250, which is **1.75e-7** (`rfc257-v13-1.log:2126`);
  - 265.0 ms at n=2000, d=980, which is **1.35e-7** and lies *inside* the admitted corner (`:2134`);
  - a refit total of 918.0 ms (`:2120`);
  - and the isolated `wsd-corner-v13-1.log:44` has a 177.0 ms refit, above the claimed 170.6 ms.
- **The design's own rule refutes its constant.** Applying the rule at 1398-1399 gives B ≈ 1.14e7, or 1.48e7 if only admitted shapes count. Either value refuses **both** acceptance fixtures (W = 1.54e7 and 1.85e7).
- **B does not converge.** It went from 2.5e7 to 1.96e7, and would now go to ≈1.14e7. The run fits are inflated by about 1.4x as well, so the maximum is tracking load on the shared host. B decides persisted topology (peel or reconcile), so it needs a reproducible derivation. Either state the protocol (the corner spec run alone, load average recorded, n≥2, a declared statistic) or anchor B to something that does not depend on timing. Then restate B, the admitted corner, the volumes and the fixtures, and correct 1404-1406 and README items 29/30.

## P2

1. **The "do not commit" chaos arms cannot hold on the DDL or catalog-bootstrap routes** (design 1050-1052 and 1097-1099).
   - `runDDL` and `ensureCatalogInit` commit *inside* `fn` (`ddl.go:862`, `:890` → `FDBRecordContext.Commit` → `tx.Commit().Get()`, `database.go:1334`). SimFDB already documents this double commit (`txn.go:1342-1348`).
   - So `FaultConflict` lands the DDL and its post-commit hooks, then reports 1020. The fixture then pins 40001 for a DDL that committed, a state production cannot reach.
   - **Needed:** either the arm wraps the transaction so an in-`fn` Commit returns the injected code without committing (`runInner(wrap)` already exists in `fault.go`), or the in-closure Commit is dropped (the transactor owns commit on this path, `database.go:298-301`). The fixture must assert the DDL did not land.
2. **"None of them retries" (design 881) is false, and the census misses a GuardiANN retry owner.**
   - Three of the named paths retry:
     - The queue drain runs on `OpenContext` through `throttledRetryingIterator` (`online_indexer_queue.go:143`, `throttled_retrying_iterator.go:73-91`). It retries *any* error up to 100 times, as Java does (`ThrottledRetryingIterator.java:70`, `:268-280`, used from `IndexingPendingWriteQueue.java:83-91`). The design's own line 262 says the same.
     - `AutoContinuingCursor` retries through `isRetryableError` (`cursor_combinators.go:939-984`). D-0 deletes that function (912-913) without giving this caller a replacement.
     - `cleanupHeartbeatWithin` is itself a retry loop.
   - **Consequences:**
     - GuardiANN's queued replay has no policy row in D-0.
     - The 1007 owner list (1586-1607) leaves it out. That owner costs up to 100 × ~5 s per failing head entry, a Go-only cost where Java's throw fails fast.
     - The chaos transactor never sees these attempts.
   - **Needed:** a census class for owners built on `OpenContext`, stating each one's Java bound and predicate, plus a declared statement that chaos cannot see them.
3. **1200 is misdescribed** (design 913-917).
   - `commitpath.go:59-62` raises 1200 before any commit is sent, and libfdb_c waits this condition out inside commit.
   - Under D-0 each 1200 uses up an attempt. A DDL (one attempt) fails on the first one. `Run` fails after 10 attempts, about 1.6 s expected (at most 3.3 s) of delay, during a recovery that Java simply waits through.
   - "As the target's client would have waited" is therefore wrong: this is a new Go-only failure where the target succeeds.
   - **Needed:** a commit that was never sent should not count as an attempt (bounded by ctx), or the client should wait inside commit as the C++ client does.

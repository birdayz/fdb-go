## Findings, most severe first

**1. Low: `equalsJava` differs from `Index.equals` in three fields.**
- **Type.** `index.go:668` compares `CanonicalType()`, which maps `min_ever`/`max_ever` to `*_long`. Java compares the raw strings (`Index.java:703`), and its `hashCode` hashes the raw type (`:716`).
  - `[own(min_ever), copy(min_ever_long)]`: Go drops the copy and builds; Java keeps the copy and refuses it.
- **Root.** `keyExpressionEquals` has no `DimensionsKeyExpression` case. It falls to `default: false` (`key_expression.go:1195`), even for the same pointer. Java's `DimensionsKeyExpression.equals` is structural (`:200-213`).
  - So Go refuses `[own, equal copy]` of any MULTIDIMENSIONAL index, which Java accepts. This is the reverse of the gap v5 closed.
- **Predicate.** `index.go:686-688` compares stored protos structurally, and the comment (`:657-659`) says "Java's IndexPredicate equality is structural".
  - In 4.14.2.0, only `RowNumberWindowPredicate` overrides `equals` (`IndexPredicate.java:790-801`). And, Or, Not, Constant and Value predicates compare by identity.
  - `Index(proto)` builds a fresh predicate (`Index.java:238`). So two separately decoded copies of a filtered index are unequal in Java; Go drops the one listed after the metadata's own and builds, and Java refuses it.
- **Consequence.** No wrong bytes: Go either builds the metadata's own object or refuses. But `CHANGELOG.md:138-141`, §7.6 and the code comment all claim Java's equality.
- **Test coverage.** The spec varies only a Field-rooted VALUE index with no predicate. Its impostor also differs in versions and component positions, so the subspace-key comparison alone is never pinned.
- **Fix:**
  - compare the raw `Type`;
  - add a Dimensions case (whole key, prefix size, dimensions size). It is harmless to `buildPrimaryKeyComponentPositions`, which unwraps Dimensions at `:1094-1095`;
  - compare predicates by identity, except `RowNumberWindowPredicate` structurally, or declare the difference;
  - add a table spec for `equalsJava` that varies one field per row.

**2. Low: the merge's lock-out holds only against exclusive builders.**
- A Java mutual builder never checks peers: `checkAndUpdateHeartbeat` with `allowMutual` only writes its own key (`IndexingHeartbeat.java:88-93`). Go's continued mutual session skips every peer too (`indexing_heartbeat.go` `checkAdmission`, `if allowMutual || … continue`).
- So a mutual builder that starts during the merge is not refused. It proceeds, and the merge then fails at its next commit with `SynchronizedSessionLockedError`.
- These sentences overclaim:
  - DIVERGENCES.md:2781-2784: "so that no build interleaves with it" and "a builder, a Java one included, that starts meanwhile is refused by it";
  - DIVERGENCES.md:2803-2804: "which a Java builder honours as a live session";
  - CHANGELOG.md:164-165;
  - ws-c-design.md:1008.
- **Fix:** say "an exclusive builder", and state what a mutual builder does. Also worth one clause: Java's heartbeat-based ongoing-build check will report the merge as a build in progress.

## What holds

**Source:**
- **Dedup and sort.**
  - `new HashSet<>(list)` keeps the first of equal objects, and `hashCode(name, type)` is consistent with `equals`, so Go's first-kept loop matches.
  - Java's reordering through the HashSet only moves objects that share a name. Such a group always contains a foreign object and is refused with the same name, so Go's stable order cannot be observed.
  - The sort now runs where Java's does (`:879`). With the nil guard in front, the identity check is equivalent to `:880-883`.
- **Builder methods.** `SetIndex`, `AddTargetIndex` and `SetTargetIndexes` match Java in every order: set then set, add then set, set then add, `SetTargetIndexes([])` then set, and `SetIndex(nil)`. Go returns the refusal as a sticky error from `Build`, which is what a builder chain needs.
- **No caller relied on the deleted single mode.**
  - The only non-test builders are frl (`index_write.go:279-283`) and the fleet (`build.go:234-238`). Each calls `SetIndex` once on a fresh builder.
  - Test callers are covered by the green `just test`.
- **Merge specs.**
  - `afterTransactHook` fires after `Transact` returns, i.e. after the commit, once per `Run`. It reads through `sharedDB`, not the hooked database.
  - So `seen[0]` is the merge transaction's committed state, the last entry is the state after cleanup, and a non-empty guard is present.
  - The live-peer spec pins that the peer's key is untouched. The DISABLED spec pins the error class, message and index name, and that no key is left.
- **Storage.**
  - A refused or failed merge transaction aborts entirely, because the pre-commit callback's error fails it. Cleanup clears only the merge's own key.
  - v5 fixes are in place: citations, the reason, the CHANGELOG entry, the IndexerID wording, the `Built` doc, the retitled spec, the hook docs, and `found == nil` removed.

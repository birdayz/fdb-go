## Findings, most severe first

**1. Low: `equalsJava` differs from `Index.equals`, and its comment misstates Java.**
- **Subspace key.** Java normalizes every key when it is constructed or set (`Index.java:89-97`, `:222`, `:415`, through `TupleTypeUtil.toTupleEquivalentValue`, `TupleTypeUtil.java:98-123`):
  - Byte, Short and Integer become Long, so Integer 1 equals Long 1.
  - A `byte[]` becomes a ByteString, so two byte arrays with the same content are equal.
  - A Tuple or List becomes a normalized List.
  - So `index.go:653`, "a Long never equals an Integer, and an array equals only itself", is false.
  - Go's `javaObjectsEqual` (`index.go:699`) treats `int` and `int64` as unequal. It never finds two `[]byte` or `tuple.Tuple` keys equal, and those are the types `metadata_proto.go:844` stores (`t[0]`).
- **Root.** `keyExpressionEquals` (`key_expression.go:1132-1195`) has no arm for `*DimensionsKeyExpression` or `*CardinalityFunctionKeyExpression`, and no identity check. So a root the two objects *share* compares unequal. Java's `DimensionsKeyExpression.equals` (`:200-213`) is structural.
- **Type.** Java compares the raw string (`Index.java:130`, `:703`). Go compares `CanonicalType()`, so `min_ever` equals `min_ever_long` in Go only.
- **Effect:**
  - The first two gaps make Go refuse `[own, equal copy]`, which 7.6 says it accepts "as in Java".
  - The third makes Go accept `[own, copy differing only in that alias]`, which Java refuses.
  - No bytes are written wrongly either way.
- **Fix:**
  - Compare subspace keys as packed tuples. `TupleTypeUtil.java:79-83` documents that this matches normalized equality.
  - Give `keyExpressionEquals` an identity check and the two missing arms, or compare the roots' protos.
  - Compare the raw `Type`.
  - Correct the comment and 7.6.

- So deleting any single comparison at `index.go:670-693`, the subspace key's included, leaves all four cases' outcomes unchanged. This is inferred from source, not run. m39 shows only that duplicates are no longer removed by name.

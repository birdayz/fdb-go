## Findings, most severe first

**1. Medium (source): an SPFresh index stored with 0 extra bits now crashes the process instead of being refused.**
- Revision 17 removed the clamp in `NewQuantizer`, so a count of 0 reaches `NewRaBitQuantizer`, which panics with a string.
- Only two places run `ValidateSPFreshConfig`: the maintainer (`spfresh_index_maintainer.go:57`) and the build (`:1124`).
- Two public paths parse the config without checking it:
  - the rebalancer (`spfresh_rebalancer.go:369`);
  - refine (`spfresh_refine.go:543`).
- Both hand that config to split, merge, GC, refine and NPA. Those build a quantizer (`newSPFreshQuantizer`) and call `Encode` (`spfresh_split.go:275,462`, `spfresh_merge.go:179`, `spfresh_gc.go:287`, `spfresh_refine.go:146`, `spfresh_npa.go:267`).
- `panicToError` (`fdb/transaction.go:523-532`) re-throws any panic that is not an error, so the host process dies.
- Before revision 17, 0 was accepted, built and stored with 4-bit codes. So this is reachable from data the previous code wrote. Ruling 9 lets Go refuse pre-release data; it does not cover crashing on it.
- **Fix:**
  - one function that parses and validates, used by every SPFresh entry point (including verify at `spfresh_verify_api.go:164` and recall at `spfresh_recall.go:77`);
  - no path from a `Quantizer` to that panic;
  - a regression test: a stored 0-bit index with a queued split, where rebalance and refine return an error.
- The CHANGELOG should also tell operators what to do: the option cannot be changed under evolution (`metadata_evolution_validator.go:973`), so the index has to be dropped and added again.

**2. Low: two unknown-field claims go further than the measurement.**
- **Within-field order is from source, not measured.** 7.17 says "measured … within a field, by wire type", but the raw bytes in the P3 spec already put the varint before the fixed32 in both fields 10 and 12. That part is therefore unmeasured. I believe it is true from protobuf-java's `UnknownFieldSet.Field.writeTo`, but I did not read that source here.
- **"Differ in field order only" is too strong for raw bytes.** DIVERGENCES says the bytes "differ in FIELD ORDER only". From protobuf-java source (not read locally): Java re-encodes unknown fields, writing varints, tags and lengths in minimal form, and sorts the contents of an unknown group recursively. Go keeps those bytes exactly as stored, so crafted bytes can differ in other ways.
- **What does hold:** "the orders agree over any bytes Java wrote" is correct. Java's output is already sorted and minimal, and Go keeps what it read.
  - Measured at the record and entry level (RESAVE_P3, `raw=false`, byte-equal).
  - Nested messages use the same mechanism (from source).

  - **Queue replay:** deletes the old entry, then inserts the new one (`index_maintainer_queue.go:51-70`, matching `VectorIndexMaintainer.java:453-467`).
  - **Sliding window:** an update is a delete then an insert (`SlidingWindowIndexMaintainer.java:381-388`), and an already-tracked reinsert calls the delegate's insert (`:556-566`).
  - The 32 "replays tracked inserts" rows are green (measured).
- **Refusal points:** Go refuses at `hnsw.go:391, 596, 888, 1211`, each before its operation writes anything. These match `Insert.java:209,284`, `Delete.java:205-213` and `Search.java:226-236`; `OutwardTraversalIterator` goes through `search`.

  - Measured: EXTRA_BITS gives the same outcome for every operation at Euclidean 9 and 15, cosine 9, and 8 bits.

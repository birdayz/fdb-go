## Findings, most severe first

**1. Medium (source): a plain VECTOR index rewires its graph on an unchanged re-save, and revision 17 turns that into a refusal Java doesn't make.**
- **Java:** `VectorIndexMaintainer` extends `StandardIndexMaintainer` without overriding `update`. `update` drops entries that are the same in old and new (`StandardIndexMaintainer.java:209-227`; `IndexEntry.equals` compares key and value, `:268-270`). Re-saving a record whose vector didn't change never touches the HNSW graph.
- **Go:** `vectorIndexMaintainer.Update` (`vector_index_maintainer.go:203-223`) always deletes and re-inserts. That repairs neighbours, re-selects edges and can move the entry point: stored index bytes Java never writes. It is the same defect class 7.17 fixed for a present-node insert.
- **Revision 17's part:** with 9–15 extra bits after the centroid exists, that delete reaches `raBitQuantizerAdmits` (`hnsw.go:888`). So Go refuses a save that changes only a non-vector field, where Java accepts it.
- **Claims that overreach:** DIVERGENCES VECTOR (≈`:2131-2133`, "refuses every save") and CHANGELOG (≈`:491-493`). The gap is undeclared: 0 hits for `skipUpdateForUnchangedKeys`, `commonKeys` or delete-then-insert wording in DIVERGENCES.md (control: 3 `RaBitQ` lines).
- **Fix:**
  - Apply `removeCommonEntries` (`index_maintainer.go:820`, already Java's `commonKeys`) when both records are present.
  - Add a JVM spec: re-save with a non-vector field changed, compare graph bytes, including the 9-bit case after the centroid.
- The sliding window is not affected: Java splits its delegate calls too (`SlidingWindowIndexMaintainer:381-388`).

**2. Low (source): the planner and the maintainer parse the metric with two different parsers.**
- **The two parsers:** `VectorIndexMetricOption` returns the raw string, and the planner then applies its own `vectorMetricOperator` (`:3914-3927`). Java's planner gets the engine's parsed `Metric` instead.
- **Empty value:** a present-but-empty `hnswMetric` or `vectorMetric` becomes a Euclidean candidate. Go's maintainer refuses it (`javaMetricName`, `hnsw_options.go:173-189`), and Java's planner throws on it. The `ok` result is discarded at `:3858`.
- **SPFresh:** `spfreshMetric="cosine"` or `"inner_product"` plans as cosine or dot product. `parseSPFreshConfig` (`spfresh_config.go:277-293`) silently maintains the index as Euclidean, which gives wrong-metric results. This is reachable only through meta-data built directly, not through the DDL.
- **Fix:** export the maintainer's parsed metric (return an error on a bad value) and map it to the planner's distance operator; have SPFresh refuse names it doesn't know.

**3. Low (source): a panic path opened by removing the clamp.**
- `rabitq.Quantizer.Encode` → `NewRaBitQuantizer` panics outside 1–8 (`rabitq.go:62-66, 340-343`).
- The SPFresh rebalance, refine, recall and verify paths parse the config without `ValidateSPFreshConfig` (`spfresh_rebalancer.go:369`, `spfresh_refine.go:543`, `spfresh_recall.go:77`, `spfresh_verify_api.go:164`). A 0-bit SPFresh index bootstrapped before revision 17 now panics in the rebalancer instead of encoding with 4 bits.
- **Fix:** validate on those paths, or make `Encode` return an error.

**4. Low: superseded text left in place.**
- `vector_index_maintainer.go:294` and `chaos/chaos_test.go:706` still say "VECTOR insert is idempotent (same PK replaces)".
- `spfresh_config.go:266-267` says "matching parseHNSWConfig's tolerance"; the HNSW parser no longer tolerates bad values.
- **Unknown-field order is over-claimed:**
  - 7.17 says Java orders a field's unknown fields "by wire type". Java actually writes varints, fixed32s, fixed64s, length-delimited, groups, which is not numeric wire-type order. DIVERGENCES (≈`:3236-3239`) states that order correctly.
  - DIVERGENCES presents all five kinds as what the spec pins. The spec measures only field-number order and varint before fixed32. The rest comes from protobuf-java source, which is not in this checkout; I'm relying on source knowledge for it.

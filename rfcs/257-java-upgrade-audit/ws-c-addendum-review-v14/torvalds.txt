## Findings (all Low, most severe first)

**1. The validator and the VECTOR maintainer now read the same options differently.**
- The validator uses Java's parsers (`vector_index_validation.go:53,77,90`).
- `parseHNSWConfig` still uses `fmt.Sscanf("%d")`/`("%g")` and silently falls back to a default (`vector_index_maintainer.go:142,179,185,206`). The meta-data evolution check uses it too (`metadata_evolution_validator.go:1044`).
- Revision 14 therefore turns inputs Go used to refuse into inputs it accepts but misreads:
  - `hnswNumDimensions="３"` means 3 in Java; Go's maintainer uses 128.
  - `hnswM="８"` means 8 in Java; Go uses 16.
  - An evolution from `"８"` to `"16"` looks unchanged to Go.
- The JVM rows cannot show this: every value they accept equals Go's default (M `16`/`１６`/`+16`; probability `0.5`/`0.5d`/` 0.5 `/`.5`; conformance `:975-987`).
- 7.14's "parse as Java's `VectorOptionKey` parses them" is true of the validator only.
- **Fix:** have `parseHNSWConfig` use `javaParseInt`/`javaParseDouble`, and add a row with a non-default spelling only Java accepts that checks the resulting config value.

**2. The re-save looks for the old bytes only under the preferred union field.**
- `store.go:2168` calls `unionInner(prior, recordType.unionFieldNumber)`.
- `fnToRT` (`metadata.go:1263-1267`) decodes a record stored under any union field of its type.
- So a record stored under an older union field of its type is re-saved in key order, and the stale covering value from v13 Graefe 2 can come back.
- **Fix:** take the inner bytes of whichever union field the old record decoded from.

**3. The path keys can collide, and a twice-written key merges its nested orders.**
- `record_wire_map_order.go:374,457` format a string key with `%v`, unescaped.
- In `google.protobuf.Struct` (the type 7.14's own FDB spec uses), the top-level key `a}/5/1{b` yields the same path as key `a` → `b` → nested map. The two maps' orders merge, and one is re-saved out of its stored order.
- For a key written twice with a message value, the nested orders are merged, first seen first. Both decoders keep only the last value, so its map can be reordered.
- **Fix:** quote string keys (`%q`), and reset the nested orders when a key repeats.

**4. The tests pin less than the claims say.**
- `TestSerializeUnionOverKeepsTheStoredMapOrder` (`:329` "nested maps too") and 7.14 ("pins each case") cover only the top-level map `m` and the repeated field `h`.
- No re-save test covers a map inside a singular message or inside a map value (`:374/:386`, `:457/:471`). The Struct spec never re-saves, and the JVM re-save uses top-level maps only.

**5. "Java's text" is not true for every refusal.**
- For a second decimal point (`"1.2.3"`), JDK FloatingDecimal throws "multiple points" (from JDK source, not in the repo). `javaParseDouble` (`java_parse.go:170-175`) returns `For input string: "1.2.3"`.
- 7.14, DIVERGENCES and the test comment all claim Java's text.
- `expectWindowedVerdictAsJava` (`:1076`) compares only the top-level class and message, so the cause's text is never measured against Java.

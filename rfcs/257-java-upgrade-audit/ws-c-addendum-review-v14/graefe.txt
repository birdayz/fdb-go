## Findings, most severe first

**1. Low: re-saving a Java record with a key written twice follows Java's generated-message serializer, not the default one that Go's read path models.**
- **What Go does.** `collectMapOrders` keeps the first position (`record_wire_map_order.go:359-368`) and the Go map keeps the last value. The spec pins the result, `{2: [x y]}` (`key_validation_conformance_test.go:486`), and the index loses the `(1, 2)` entry.
- **What Java does** (from source). Java's default serializer is `DynamicMessageRecordSerializer` (`FDBRecordStore.java:5668`). Its load-then-save writes the entry list verbatim, so both `x` entries and their index entries stay.
- Go *reads* as that default serializer does (`record_wire_map_order.go:24-28`) but *writes* as the generated-message path does.
- The index stays consistent with the bytes in both engines. But the stored bytes differ from what Java writes for the same operation, and that is the hard line.
- **Not declared as a divergence.** The CHANGELOG (`:430`) says "a Go map holds it once" without saying that Java's default keeps both. DIVERGENCES has no map-order entry (**measured**: a grep of DIVERGENCES at the commit finds no map entry-order text; its only hit is line 332, on FlatMap).
- The spec comment "(Java's load-then-save keeps it)" (`:431`) is from source. The spec never runs Java's re-save.
- **Fix, either:**
  - in `marshalMapRecord`, when a map equals prior's last-write-wins view, re-emit prior's entry bytes unchanged, duplicates included; or
  - declare it in DIVERGENCES and add Java's re-save to the spec.

**2. Low: the windowed VECTOR metric still accepts names Java refuses (pre-existing).**
- `vector_index_validation.go:101-104` accepts `cosine`, `inner_product` and `euclidean`.
- Java reads the metric with `Metric::valueOf` (`VectorOptionKey.java:236`, `HnswVectorIndexEngine.java:190`), whose only constants are `EUCLIDEAN_METRIC`, `EUCLIDEAN_SQUARE_METRIC`, `COSINE_METRIC` and `DOT_PRODUCT_METRIC`.
- Java rethrows the refusal as "incorrect index options" (`VectorIndexMaintainerFactory.java:106-110`). So Go builds windowed meta-data that Java cannot open. That is the same class as v13 Torvalds 1, and revision 14 fixed only two of `VectorOptionKey`'s three parsers.
- DIVERGENCES `:2120-2123` declares only the cause text for an unknown name, not this difference in whether the meta-data builds.
- Go's DDL writes the enum names (`ddl.go:446-454`), so only record-layer API callers reach this.
- **Fix:** accept only the four enum names in the validator, and add a JVM row (`hnswMetric=cosine`).

**3. Low (from source, JDK-version dependent): one refusal text in `javaParseDouble` is not Java's.**
- JDK 8–21's `FloatingDecimal.readJavaFormatString` throws `NumberFormatException("multiple points")` for inputs like `1.2.3` or `..5`.
- Go returns `For input string: "1.2.3"` (`java_parse.go:153-154`).
- The code comment and 7.14 say every refusal carries Java's text, but neither `TestJavaParseDouble` nor the 13 JVM rows include a second point.
- **Fix:** add a JVM row and port the text.

## Nits
- **Test comment claims more than the test covers.** `TestSerializeUnionOverKeepsTheStoredMapOrder` says "nested maps too" (`record_wire_map_order_test.go:329`), but it covers only the top-level map and a map in a repeated element (`:390`). The `{key}` path arm of `collectMapOrders`/`orderMapEntries` (a map inside a map value's message) and the singular-message arm run in no re-save test.
- **Nested order for a twice-written outer key.** `collectMapOrders` joins the nested map orders of both occurrences. The decoder keeps only the last value, so the nested order can come from the dropped occurrence.
- **Instance paths can collide.** The paths use `%v` of the key, which is not injective for string keys containing `}`, `/` or `{`. These are edge cases.
- **Per-record descriptor walk.** `mapReach{}` is fresh for every decoded record and every save, while `Build`'s memo (`metadata.go`, `reach := mapReach{}`) is thrown away. Keeping it for the meta-data's lifetime would be bounded and cheaper. This is a performance note only.

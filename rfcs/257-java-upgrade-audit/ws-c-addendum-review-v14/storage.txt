## Findings, most severe first

**1. Medium (from source): the HNSW maintainer reads the options differently from the validator, so Go now writes index bytes Java would not.**
- Revision 14 makes the windowed VECTOR validator accept Java's number formats (`vector_index_validation.go:53`, `javaParseInt`).
- The maintainer still reads the same options with `fmt.Sscanf("%d")` and falls back to the default if that fails (`vector_index_maintainer.go:139-252`; dimensions at `:141-145`, M at `:205-209`).
- Java's maintainer reads them with the same parser its validator uses (`HnswVectorIndexEngine.java:191-194`, `VectorOptionKey.java:213`).
- Example: `hnswNumDimensions="３"` (a full-width digit). Java builds with 3 dimensions. Go now builds too, but maintains 128 dimensions. Likewise `hnswM="１２"`: Java uses 12, Go uses 16.
- Before this revision Go refused these at build, which was loud. Now it writes different index bytes without saying so.
- The JVM row `hnswM="１６"` cannot catch this, because 16 is already Go's default M (`hnsw.go:135`).
- **Fix:** have the maintainer read through `javaParseInt`/`javaParseDouble`, and add a JVM row whose value differs from the default.

**2. Low (from source): a record stored under an older union field loses its map order on a Go re-save.**
- `serializeUnionOver` finds the old record's bytes only under the type's current union field (`store.go:2168`, `unionInner`).
- But Go decodes a record under any union field of its type (`metadata.go:1263-1267`), and Java allows a type several union fields (`RecordMetaDataBuilder.java:866-887`).
- So when Go re-saves a Java record stored under an older field, it writes the map in key order. That reopens v13 Graefe 2: a covering index whose key two entries share keeps a value that a rebuild would change.
- The CHANGELOG ("a record Java wrote that Go loads and saves unchanged keeps its entries' order and its index entries") and `record_wire_map_order.go:40-42` claim more than the code does.

**3. Low (from source): a map inside a repeated element is matched to the old record by the element's position.**
- The instance path uses the element's index (`record_wire_map_order.go:379-384`, `:464-469`).
- If a save inserts or removes an element, an unchanged element gets another element's stored order. When the entries are otherwise equal, the order-blind common-entry filter then leaves the covering index stale, the same failure as v13 Graefe 2.
- Java keeps each element's own order.
- 7.14 and the CHANGELOG say "by their instance path" and never say this means position.
- **Fix:** declare it and pin that shape, or match elements on something other than position.

**4. Low (coverage): nothing tests that a saved record is indexed in the order it was written.**
- The JVM re-save check cannot detect it:
  - Record 1's old and new entries are equal, so nothing is written in either order.
  - Records 2 and 3 have distinct index keys.
- The unit test evaluates a fresh decode of the written bytes (`record_wire_map_order_test.go:~370-381`), not the saved record.
- A shape that separates the two:
  - Stored `[z→1]`, then save `{z→5, a→5}` under `KeyWithValue(NestFanOut(m, Concat(value,key)),1)`.
  - Go writes `[z, a]`, and the index must hold `(5,pk)→a`.
  - If the saved record carried no wire, key order would insert `z` last and leave `z`.
- **Fix:** pin that shape through `SaveRecord` and the batch save.

**5. Low (text; a source hypothesis, since the JDK source is not in the tree):** For a second decimal point, JDK `FloatingDecimal` throws `NumberFormatException("multiple points")`. `javaParseDouble` returns `For input string: "1.2.3"` instead (`java_parse.go:128`, `:170-198`). DIVERGENCES and `vector_index_validation.go:32-37` say "with Java's text". The JVM spec compares only the top-level message, so it cannot catch this.

## Findings, most severe first

**1. Low (docs, new in v5): the closing sentence of the DIVERGENCES section is false.**
- `DIVERGENCES.md:2790-2791` says "The one difference another engine can observe is the standalone merge's heartbeat key". Bullets in the same section contradict it:
  - **MARK_READABLE (`:2761`):** Java publishes the index and erases its queue; Go refuses, so the index stays unpublished with its queue.
  - **Clear or fresh WRITE_ONLY mark (`:2731`):** Java resets under a live mutual peer; Go refuses.
  - **Out-of-date metadata (`:2736`):** Java reconciles under a live peer; Go refuses.
  - **Follow-up:** Java commits the drain; Go commits nothing.
- Each of these leaves different stored state, just not a different format.
- The merge bullet (`:2774`) also leaves one thing out. The merge itself fails with `SynchronizedSessionLockedError` under any live heartbeat, a running Java build included (mutual or not), and Java's standalone merge goes ahead. "Admitted exclusively" only implies that.
- Fix: "No stored format differs. The refusals above leave state Java would have changed. The merge heartbeat is the one key Go writes that Java would not." Then state the merge's own refusal.

**2. Low (revision 5's refusal has a gap).**
- `online_indexer.go:789-795` removes duplicate targets by NAME before the identity check at `:807`.
- So `SetTargetIndexes([own, impostor])` silently drops the impostor and the build goes ahead.
- Java removes duplicates with a `HashSet`, i.e. by `Index.equals` (`OnlineIndexer.java:871-874`), and `Index.java:695-711` compares `subspaceKey`. Both objects stay in the list, and `:881` refuses the impostor.
- There is no wire effect, because the object kept is the metadata's own. But the CHANGELOG (`:133-136`) and 7.5 claim `Build` refuses every target that is not the metadata's object.
- Java also sorts before the check (`:879`), so it names the alphabetically first bad target.
- Fix: remove duplicates by Java's equality, and pin that `[own, impostor]` is refused.

**3. Low (pre-existing, undeclared): `SetIndex` and `AddTargetIndex` interact the opposite way from Java.**
- In Java:
  - `setIndex` throws a `ValidationException` ("setIndex may not be used when other target indexes are already set") only when targets are already set (`:668-671`);
  - `addTargetIndex` never checks (`:719-722`).
- In Go:
  - `SetIndex(a).AddTargetIndex(b)` fails with a plain `fmt.Errorf` (`:841-842`); Java builds both.
  - `AddTargetIndex(b).SetIndex(a)` silently replaces the list and builds only `a` (`:612-615`); Java throws.
- The spec "rejects SetIndex combined with AddTargetIndex" (`online_indexer_test.go:2131`) pins the non-Java behaviour.
- Fix: port Java's check at set time, returning it from `Build` as an `IndexingValidationError`. Delete `:841-842` and flip the spec.

**4. Low (pre-existing): `SetIndex(nil)` panics.**
- The nil dereference is at `idx.Name` (`:790`).
- Java's `setIndex(@Nullable)` skips a null (`:672-674`), and `validateIndexSetting` then throws `MetaDataException("index must be set")` (`:862-864`). That is the error revision 5 just ported.
- Fix: skip nil in `SetIndex`, and pin it.

## Findings, most severe first

**1. Low-medium: the standalone `MergeIndexes` divergence (DIVERGENCES.md:2774-2785, 2790-2792) is untested and incomplete.**
- **Untested (measured):** `git grep '\.MergeIndexes\('` over all `*.go` finds one call, `indexing_merger_test.go:211`. That spec builds a struct-literal indexer over a freshly created store and asserts only the merge count and a nil session heartbeat.
  - None of the three declared arms is exercised: the live heartbeat over a WRITE_ONLY target, the Java builder it locks out, and the `RecordCoreStorageError` over a DISABLED target.
  - Yet the section header says "each pinned where named", and this bullet names no spec. It is the one difference the section says another engine can observe.
- **One behaviour is missing.** Over WRITE_ONLY, the merge's non-admitted heartbeat goes through `renewSessionHeartbeat` → `CheckAndUpdate` (`online_indexer_queue.go:419-424`, `:478`). So a live peer, Java or Go, makes the Go merge itself fail with `SynchronizedSessionLockedError`, while Java's merge proceeds (`IndexingBase.java:969-972`). "Admitted exclusively" only implies this; state it.
- **Wrong citation (measured).** `:1085-1096` is `IndexingBase.java` (`mergeIndexes`). `OnlineIndexer.java:1085-1096` is the `IndexStatePrecondition` getters. The same citation is in §7.5.
- **The reason given is overstated.** §4 requires every backend write to *consume* the heartbeat callback. It does not require a standalone merge to create a session heartbeat where Java has none: Java's callback over a null heartbeat does nothing (`:969-972`). Present it as Go's own choice.
- **Missing from the CHANGELOG (measured).** `MergeIndexes` does not exist on master (a control grep for `BuildIndex` hits master). It appears nowhere in CHANGELOG, yet it now locks out Java builders.
- **Fix:** add one spec per arm through `MergeIndexes`, correct the text and citation, and add a CHANGELOG line.

**2. Low: the new target-object refusal misses one case: a same-named object added after the metadata's own.**
- The dedup (`online_indexer.go:786`, "by name (matches Java's HashSet dedup)") runs before the identity check at `:808`.
- Java's `HashSet` removes duplicates by `Index.equals`, which compares name, type, root expression, **subspace key**, versions, options and predicate (`Index.java:695-711`).
- `AddTargetIndex(own).AddTargetIndex(foreign)`, with a foreign subspace key:
  - Java keeps both and throws `MetaDataException` on the foreign one (`OnlineIndexer.java:880-883`).
  - Go drops the foreign object by name and accepts the build.
- No wrong bytes are written, because the metadata's own object is the one built. But this is a refusal Java makes and Go doesn't, it is untested, and the CHANGELOG ("refuses a target that is not the metadata's own index object"), §7.5 and the comment all claim more than the code does.
- **Fix:** remove duplicates by Java's equality, keeping the first, then run the identity check. Test `[own, foreign]`. Removing duplicates by pointer would instead refuse `[own, equal copy]`, which Java accepts.

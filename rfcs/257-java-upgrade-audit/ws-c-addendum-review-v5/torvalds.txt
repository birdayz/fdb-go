## Findings, most severe first

**1. Low-medium: a target that only shares a name is still accepted when it comes after the real one.**
- `Build` removes duplicates by name (`online_indexer.go:786-793`) before the new identity check at `:808`. So if `SetTargetIndexes` or `AddTargetIndex` receives the metadata's own object first and then an object that only shares its name, the second one is silently dropped and the build is accepted.
- Java refuses that list. Its `HashSet` removes duplicates with `Index.equals`, which compares name, type, root expression, subspace key, both versions, options and predicate (`Index.java:695-717`). So the second object survives, and `OnlineIndexer.java:880-883` throws `MetaDataException`.
- Go's result also depends on order: with the two objects the other way round, Go refuses.
- The comment at `:786`, "matches Java's HashSet dedup", is false.
- Nothing is written under the wrong key, because the dropped object is never used. But the refusal this revision ports is incomplete.
- Fix: remove duplicates by identity (or by Java's equality) before the check. Pin both orders.

**2. Low: the standalone `MergeIndexes` divergence is incomplete and has no test.**
- The code path is `indexing_merger.go:169` → `:40` → `refreshFollowupHeartbeats` (`online_indexer_queue.go:443-481`). On a WRITE_ONLY target it calls `CheckAndUpdate`, so a live builder, whether Java or Go, **refuses the merge** with `SynchronizedSessionLockedError`. Java's standalone merge checks no heartbeat and goes ahead. The bullet in DIVERGENCES.md (`:2774-2785`) declares only the reverse direction.
- It says "disabled under it", but the code refuses a target that was DISABLED from the start as well.
- The section says each difference is "pinned where named", but this bullet names no spec. The only standalone `MergeIndexes` test (`indexing_merger_test.go:211`) uses a READABLE vector index, which never reaches either branch.
- The cross-engine claim that a Java builder honours the merge's heartbeat is a hypothesis from source; nothing has run it.
- Fix: declare the refusal, add specs for WRITE_ONLY (key written, live peer refused) and for DISABLED, and mutate them.

**3. Low: `SetIndex(nil)` panics (`online_indexer.go:612-613`, `:790`).**
- Java's `setIndex` accepts null and leaves the list empty (`OnlineIndexer.java:668-675`), so it reaches the "index must be set" error this revision ports.
- Go stores `[]*Index{nil}`, passes the length check, and dereferences nil at `idx.Name`. That is a panic in library code.
- Fix: ignore nil the way Java does, and pin it.

**4. Nits.**
- The doc for `IndexBuildOutcomeBuilt` (`:489-495`) is now narrower than the code. `outcomeOfCall` returns `Built` whatever the last attempt found, including a retry that publishes under MARK_READABLE. v4's wording, "whatever the attempt that ended the call then found", was accurate.

- CHANGELOG says `SynchronizedSessionLockedError` carries "the refusing indexer's" ID. It is the refused indexer's, as `errors.go` says.
- CHANGELOG never mentions `MergeIndexes`: zero hits for `MergeIndexes|explicit index merge|standalone merge`, against five in DIVERGENCES.md. The function does not exist on `master` (control: `BuildIndex` hits once there). Yet its heartbeat is the one difference another engine can observe.

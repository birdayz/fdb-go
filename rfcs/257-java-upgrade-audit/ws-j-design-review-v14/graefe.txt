## HIGH
**H1. The store-open probe can refuse stores Java opens** (`:2520-2533`).
- A record type U whose primary key does not begin with `recordType()` stores its records under `(p, …)` whenever its first key element equals p. The limit-1 read at p then finds U's record.
- The design skips the probe only when another type's EXPLICIT key equals p. So Go locks itself out of a Java store, the outcome v14 withdrew `LegacyFramingError` to avoid.
- "Java never writes a record of T under that number" holds only under `FDBMetaDataStore`'s validator. A Java store opened with in-code metadata gets no evolution check.
- A store holding rows under both p and the smallest number gets a remedy (explicit key p) that strands the rows under the smallest number.
- **Fix:**
  - require the found record to parse as T through one of T's union fields, or require every type's key to be type-prefixed;
  - also read the target's number, and refuse a store holding both with no route offered;
  - scope the "never" claim.

**H2. Section 3.6 says deserialization becomes "Java's, whole", but `NullStandin` is missing.**
- Go keeps only a UNIQUE bit (`key_expression.go:91-98`), and its comment says UNIQUE is "not yet" evaluated.
- A Java `NOT_NULL` field is read as NULL, where Java reads the type's default (`FieldKeyExpression.java:205`, `:234`). It is re-saved as `NOT_UNIQUE`.
- So primary-key and index bytes for unset fields differ from Java's. That is a wire difference.
- It is not tracked anywhere: `NullStandin` and "null interpretation" match 0 lines in DIVERGENCES.md, TODO.md and the design. The positive control, PENDING, matches 19, 77 and 4 in the same files.
- **Fix:** port `NullStandin` in step 3, or narrow 3.6's claim and book the gap.

## MEDIUM
**M1. Several of 3.6's refusals are ones Java cannot reach as stated.**
- `field_name` and `fan_type` are proto2 `required` (`record_key_expression.proto:36-37`), and FanType is a closed enum.
  - Stored bytes fail at parse in both engines: Java's `parseFrom`, and Go's `proto.Unmarshal` (`metadata_store.go:146`, `fdb_template_catalog.go:286`).
  - The arms only apply to protos built in memory, so the design must say how the JVM oracle builds them (for example `buildPartial`).
- "Invalid fan type" (`KeyExpression.java:197`) is dead code in Java: a wire value 7 becomes an unknown field, and Java reports "missing fan type". The `:1637` pin expecting "Invalid fan type 7" is wrong.
- Java also wraps a failed record-count-key read (`RecordMetaDataBuilder.java:260-266`; Go's `:366`), which `:1625-1627` leaves out.
- Function refusals:
  - Java's arity check counts `arguments.getColumnSize()`, and `fromProto` wraps any `RecordCoreException` from `create` (`FunctionKeyExpression.java:236-240`).
  - Go's registry has no arity bounds.
  - Go's registry holds `get_versionstamp_incarnation`, which Java has only as a SQL Value, so Go would load a key Java refuses.
  - Lucene and geo functions move from an evaluation-time failure to a whole-store load refusal in Go.
- The citation `:1619` is stale; the error is at `key_expression.go:1569-1570`.

**M2. The framing policy contradicts itself.**
- Shape (d) stays refused "because a loader cannot tell who wrote the records" (`:2352-2353`), including SQL templates Java creates (r).
- 9 (y) (`:3141-3145`) withdraws the (f)/(g) refusal because a refusal locks Go out of Java stores.
- **Fix:** state the criterion that separates them (which engine's convention produced the shape), apply it to both, and put both to the owner as one decision.

**M3. The writer argument is per metadata, but the writer is a property of each record store** (`:2458-2474`).
- One `FDBMetaDataStore` can serve a Go-written store and a Java-written store. No single writer is then correct. Declare this.
- For shape (g) with a type-prefixed key, the route should check the stated writer with the probe's reads.

**M4. `checkReservedNumbers(storedProto, newProto)` (`:2635`) cannot pair messages "as the validator pairs them" for the two legacy writers.**
- The pairing needs `union` and the writer's framing. With the raw proto alone, a `_X` of type Y pairs stored Y with the new X.
- "Every reservation of every message" conflicts with pairing. Unpaired messages include the candidate the migration's (d) arms remove. If removing it counts as dropping its reservations, the migration refuses whenever that candidate has a `reserved` statement.

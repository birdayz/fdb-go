## HIGH

**H1. Once the translator folds are deleted, nothing in Go simplifies a single-source WHERE (§5.4a/c, lines 1412, 1476). (SOURCE)**
- **Why nothing reaches it:**
  - Go's QueryPredicateSimplificationRule matches only a `SelectExpression` (rule_query_predicate_simplification.go:31). §5.4c keeps Java's select matcher.
  - Go's translator emits a single-source WHERE as `LogicalFilterExpression([pred])` (cascades_translator.go:3005-3010), under a `LogicalProjectionExpression` (:347).
  - No rule turns that filter into a select. The comment at rule_match_intermediate.go:219 says the filter survives into planning.
  - Today those predicates fold in one place only: the 19 translator calls that 5.4a deletes.
- **The oracle's own rows are this shape.** The target plans them as selects (trace_conj_true: `SelectExpression selects=1`). These rows all run over T alone and would keep today's Go outcomes:
  - conj_true_where and conj_false_where, whose GO lines are 22012;
  - null_strict_div0_cast_null_is_null_where;
  - the COALESCE-head rows;
  - is_not_null_coalesce_div0_where and is_null_cast_string_to_bigint_where.
- **The tie pins fail too.** The tie rows are also over T alone, so no Go row reaches the hash rung. §5.4g's requirement that inverting the hash comparison reddens a pin cannot be met.
- **The obvious fix is a trap.** Reading a filter as a select and yielding a `SelectExpression`, as 4.1(b) does, loses rung 1 ("fewer SelectExpressions", designated_final.go:145) to the filter every time. The unfolded member would win deterministically.
- **Why the fold-free run missed it:** only the tests that pin the translator fold failed.
- **Fix:**
  - Choose one shape: the translator emits the target's select, or the rule matches a filter and yields a filter.
  - State what happens to the Go-only REWRITING filter rules that already rewrite these predicates (default_rules.go:42-44, 63: DropTrue, Dedup, Merge, NoOp).
  - On a prototype, measure a single-table conj_true row and one tie row in Go.

## MEDIUM

- **M1. The explode rule's phase and its IN-join route (4.1b, lines 525-567). (SOURCE)**
  - **Phase.**
    - Java runs InComparisonToExplodeRule in PLANNING only.
    - Go registers it in DefaultExpressionRules (default_rules.go:118), which Go's REWRITING phase runs (:419).
    - Today it matches filters, so its select yield loses rung 1 and does no harm.
    - Once it also matches selects, an exploded multi-source select ties the original through the conjunct and level rungs, and the hash can prune the IN-predicate form before PLANNING.
    - Specify PLANNING-only registration.
  - **Route.**
    - The IN-join now depends on Go's partition rules moving `value = QOV(explode)` into a correlated inner.
    - The rule_partition*.go files never mention explodes, and nothing is measured.
    - This path decides every IN-list index plan. Prototype it and dump the corpus, as was done for the tautology filter.
- **M2. The UUID site census is wrong (line 1036, "exactly the five non-test calls").**
  - The design's own `git grep` returns six calls. The one it misses is promote_prepared.go:388.
  - That is PromoteValue's STRING_TO_UUID arm: the Go port of the Java lane this section specifies (PromoteValue.java:163-170). It fails with an untyped `fmt.Errorf`.
  - Fix the count, and make the guard test's allowlist empty.

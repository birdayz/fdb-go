## Findings, most severe first

**1. Low: v3 Torvalds #1's exact scenario is unpinned, and the spec that claims to pin it tests a different path.**
- The reported bug was: attempt 1 indexes records, fails into a retry, a peer publishes, and attempt 2 is left alone, so the call reported `LeftAlone` although records were built.
- The spec "reports a call whose earlier attempt built…" (`online_indexer_test.go:4072`) never retries.
  - It is a single-target mutual build. Its one attempt fails with `UnexpectedReadableError{AllReadable}` and ends through the catcher's done path (`online_indexer.go:1097`).
  - There is no "earlier attempt" in it.
- So m24 goes red only through the done path. Replacing `outcomeOfCall(outcome)` with `outcome` on the success return (`:1088`) would stay green. That return is exactly the path frl and the fleet read after a retry.
- The docs are also incomplete:
  - `IndexBuildOutcomeBuilt` (`:489-492`) does not cover an ending attempt that indexed records and then finished through the done path, which is what the spec pins.
  - `CompletedByPeers` (`:501-502`) should say "and this call indexed nothing".
- Fix:
  - Pin retry-then-skip. Two chained `nthTransactHook`s would do it: a peer changes the stamp between build transactions (partly-built error, records fallback), then publishes before attempt 2's state transaction.
  - Mutate the success return and show the new spec goes red.
  - Correct the two docs and 7.4 line 857.

**2. Low (wire, already on master; the target side of storage v3 #5): target `*Index` objects are accepted by name only.**
- Java refuses a target object that is not the metadata's own object (`OnlineIndexer.java:881-882`, an identity check, `MetaDataException` "Index X not contained within specified metadata").
- Go checks only the name (`online_indexer.go:797-802`), then keys everything off the caller's object:
  - the range set (`indexing_range_set.go:18`, via `primaryIndex()` at `:2039`);
  - the heartbeat subspace (`indexing_heartbeat.go` `heartbeatSubspace`);
  - the stamp and the clears.
- A foreign subspace key therefore builds and records progress where Java never looks. Java peers cannot see Go's heartbeat, so a Java exclusive REBUILD would be admitted under a running Go build.
- The comment at `:797` says "matches Java's OnlineIndexer.Builder", which is false. The error is a `fmt.Errorf`, not a `MetaDataError`.
- Fix: resolve targets by name, as revision 4 now does for the source, or refuse a non-identical object with Java's class and message. Pin it with a target object that has a foreign subspace key.

## What holds (source)

**Late-clear fix.**
- `cleanupHeartbeatAttempt` reads each key before clearing it (`online_indexer_queue.go:365-370`), with a plain read, not a snapshot read. `update` writes with a plain `Set`, which keeps its write-conflict range.
- Every read version comes before the cleanup returns, and so before the next attempt's write. A late commit, including an unknown-outcome retry that lands late, therefore either conflicts (1020) or is too old (1007).
- Both production callers of the cleanup share this path: the attempt defer (`online_indexer.go:1248`) and `MergeIndexes` (`indexing_merger.go:170`). No other code clears an own heartbeat key.
- The `holdDispatch` mode holds the real transaction, skips its timeout, ignores cancellation, and commits it later.
- The spec asserts that the clear was dispatched, that code 1020 comes back, and that the key survives. Two things rule out a vacuous pass:
  - a cancelled transaction would give 1025, not 1020;
  - under m23 the late clear commits.
- The README is corrected.

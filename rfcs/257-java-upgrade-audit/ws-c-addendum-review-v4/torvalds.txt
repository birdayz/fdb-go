## What holds

**From source:**
- **The late clear.**
  - `cleanupHeartbeatAttempt` reads every target's key before clearing it, in the same transaction. The clear site is the only `Cleanup` in non-test code, and `MergeIndexes` goes through the same function.
  - The cleanup is synchronous, so its read version always precedes the next attempt's write. A late commit therefore conflicts, or is rejected as too old.
  - The new read is bounded by the transaction timeout, which the pure-Go client enforces on reads (see `settimeout_test.go`).
  - Java awaits the clear (`IndexingBase.java:174`).
- **`holdDispatch`** models what it claims. The commit is withheld, the timeout and cancellation are skipped, and the real transaction is committed afterwards by `landLate`.
- **The late-clear spec cannot pass vacuously.** It asserts:
  - that the clear was dispatched;
  - `DeadlineExceeded`;
  - code 1020 exactly (a cancelled or too-old transaction would fail it);
  - that the key survives.

  It runs on the pure-Go client (`recordlayer_suite_test.go` imports `fdbgo/fdb`).
- **Catcher and CHANGELOG.** The retry-cost text matches `OnlineIndexer.java:188-225` arm by arm, and the precedence rule is true for each path.
- **Source index.** Resolving it by name matches `IndexingByIndex.java:68-71, :95-101`; a continuation resolves by subspace key, then by name to the same index.
- **Heartbeat info.** It matches `IndexingBase.java:457`.
- **Builder order.** It matches `:866-878`.
- **The follow-up divergence** is declared and true: after disable, `clearIndexData` leads to `IndexNotBuiltException` at `FDBRecordStore.java:3983`.
- **Callers.** frl and the fleet are the only non-test callers of `LastBuildOutcome`, and they are consistent. `buildPending` adds `total` after the error check.
- **v3 findings.** Every one is addressed, except the partial gaps in findings 1 and 2.

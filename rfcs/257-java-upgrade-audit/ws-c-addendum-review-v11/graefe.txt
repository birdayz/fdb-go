## Findings, most severe first

**1. Low: the TEXT validator's tokenizer texts are not Java's, yet 7.11 and `CHANGELOG.md:344-349` say they are.**
- Java's messages have no log info (`LoggableException` does not override `getMessage`): "unrecognized text tokenizer" (`TextTokenizerRegistryImpl.java:100`), "tokenizer version could not be parsed as int" (`TextIndexMaintainer.java:185`), "unknown tokenizer version" (`TextTokenizer.java:210`).
- Go's `validateTextIndex` (`index_validator.go:208-235`) returns texts with Go suffixes: `text_tokenizer.go:325` ("…: X"), `text_index_maintainer.go:87` ("(index=…, …)") and `text_tokenizer.go:72` ("tokenizer=… version=… min=… max=…").
- So one Java text has two Go forms. `index_validator.go:223` special-cases an empty name to the bare text; any other unknown name gets the suffix.
- Revision 11 knew this: its edit at `text_index_metadata_validation_test.go:173-193` says "Go appends it" and switches the check to `HavePrefix`. Nothing declares it.
- The sliding-window decorator runs in the same per-index sequence and appends "(index %s)" (`sliding_window_index_validation.go:49`, `:62`).
- 7.11 says the 30-shape spec has "a shape per check above". It does not: there is no JVM shape for the TEXT version, value, tokenizer-version or text-field checks, VERSION's version count or uniqueness, MULTIDIMENSIONAL's cover and width checks, or MAX_EVER_VERSION's grouped-key version checks.
- **Fix:** use Java's bare texts and add JVM shapes for them, or declare the difference and narrow the sentence.

**2. Low: the Then arity fault is read from the builder's final state, not in program order.**
- `firstFault` walks only the current primary keys and the current count key (`metadata.go:2252-2262`). `SetPrimaryKey` and `SetRecordCountKey` just assign (`:1339-1341`, `:463-468`).
- Example: `SetPrimaryKey(Concat(Field("a")))` followed by `SetPrimaryKey(Field("id"))` builds in Go. Java throws at the first `concat` (`ThenKeyExpression.java:63-65`).
- A key set on the placeholder that `GetRecordType("Nope")` returns is never walked either. If the Then was built before that call, Go reports "Unknown record type" where Java reports the Then.
- 7.11's "each primary key, the record count key" is wider than the code.
- **Fix:** record the fault when the key is handed over, as `addedIndexes` already does for indexes, and pin the replaced-key case.

**3. Low: v10 storage finding 2 is only half resolved.**
- `CHANGELOG.md:298-301` still says a bad `rankNLevels` index "refuses every write until its option is corrected".
- Both engines' evolution validators refuse that correction, which is what v10 found. The owner's ruling also rules out remedies for such data.
- 7.11 says both lists' findings are answered. The grep for the superseded wording missed this copy.

**4. Low: "`GetSnapshotRecordCountForRecordType` … refuses a nested count key, as Java's does."**
- Java's per-type count never reads the record count key. It uses a COUNT index on the type, or a universal COUNT index grouped by record type; otherwise it throws "Require a COUNT index on X" (`FDBRecordStore.java:2431-2453`).
- Go's version reads only the record count key and never looks at a COUNT index (`record_count.go:338-352`).
- That is an undeclared Go-only path, whatever happens in the nested case.

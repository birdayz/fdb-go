## Findings, most severe first

**1. Low (wire): Go's key validation is not Java's for two key-expression types, so `Build` accepts meta-data Java's build refuses.** 7.11 and `index_validator.go:34-40` describe the per-index key step as Java's `Index.validate`. It is not, for two types:
- **`DimensionsKeyExpression`.** Java checks it at `DimensionsKeyExpression.java:89-101`: prefix plus dimensions must fit the columns, and every dimension column must be `INT64`. Go's `key_expression_validate.go:41` only recurses into the whole key.
- **`CardinalityFunctionKeyExpression`.** It embeds `FunctionKeyExpression`, so the type switch misses it and it falls to "skip validation" (`:50`). Java refuses duplicate-producing arguments and validates the arguments (`CardinalityFunctionKeyExpression.java:156-161`).
- **Consequences:**
  - A MULTIDIMENSIONAL index over an `int32` or `sint64` dimension builds in Go and is refused by Java. Go then maintains it: `asInt64` accepts `int32` (`multidimensional_index_maintainer.go:196-199`, `time_window_leaderboard_maintainer.go:1185`). A Go-created store's meta-data is then one Java cannot open.
  - When prefix plus dimensions is too wide, Go reports the factory's text. Java reports "dimensions declared a prefix size…".
  - A CARDINALITY over a missing field builds in Go.
- **Undeclared:** grepping `pkg/`, `DIVERGENCES.md` and `conformance/` for the three Java texts finds 0 hits. In the same run, the positive control "is repeated with FanType.None" was found.
- **Coverage:** none of the 30 index shapes probes either type.
- **Fix:** port both `validate` overrides and add JVM shapes for them.

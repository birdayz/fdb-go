## P2 — The inline bound fires on states the target itself produces; "a state only the Go terminal reconcile produces" is false (design:498, 883-915)

**Why the flag key is not unique to Go's reconcile.** Four Java facts combine:
- **REASSIGN is added while COLLAPSE is set.** `updateClusterMetadataAndEnqueueReassignTaskMaybe` arms REASSIGN without checking COLLAPSE (`Primitives.java:1222-1226`), and `withAdditionalVectorsAndStates` adds states rather than replacing them (`ClusterMetadata.java:185-190`). Two ordinary triggers while a collapse is pending:
  - a neighbour's split passes its new cluster ids as the cause set (`SplitMergeTask.java:911`);
  - an insert over the underreplication threshold (`Insert.java:366`).
- **The collapse keeps REASSIGN.** CollapseTask removes only COLLAPSE (`CollapseTask.java:415-416`).
- **The bounce does not re-arm.** It skips the re-arm whenever REASSIGN is present (`BounceTask.java:295-300`), so SPLIT_MERGE is never set again.
- **The reassign clears everything.** ReassignTask rewrites its target with no states, whatever its size (`ReassignTask.java:730-735`).

**What each engine does then:**
- The result is a Java-made cluster above max, with no flags and no pending task.
- Java's next insert re-arms the split (`Primitives.java:1161-1163`).
- Go's bound refuses exactly that insert once count+1 > hardMax, so Go refuses permanently (until deletes) where Java is healthy.

**The enumerated window also fails its own claim (:903 "succeeds on retry once the bounce has run"):**
- The collapse and bounce ids are both random high-priority ids (`AbstractDeferredTask.java:275-281`), so the collapse can sort first.
- An inline insert routed to that cluster then runs the collapse as its own head task, is refused, and rolls the collapse back.
- Every insert routed there repeats this, so the bounce never runs through them.

**Reachability:**
- hardMax = max+1 is the configuration the design itself calls healthy (oracle items 8 and 14).
- hardMax is mutable (engine `:84-97`).

**Evidence gap.** "It fires in no measured healthy inline scenario" is a prediction: the goldens record only final cluster states, not the state at each insert.

**Needed:**
- Either key the bound so neither Java shape can fire it, or declare both under (h).
- Add JVM and Go fixtures for:
  - a collapse that gains REASSIGN while pending, followed by its reassign;
  - a collapse that sorts ahead of its bounce, with the cluster at or above hardMax.
- Correct :498, :896 ("one exception") and :903.

## P3

1. **(d) reads only the head task's kind (:271-274).** A bounce at the head of the queue runs its dependency in the same transaction (`BounceTask.java:161-169`). Two cases where Go's inline delete then fails:
   - collapseConcurrency 0 with a live collapse dependency;
   - splitMergeConcurrency evolved to 0 with a dependent split. Here the target's delete succeeds, so the difference is undeclared.

   "Removal always remains possible" is therefore false for inline deletes. Extend the config-only reading to the bounce's outstanding dependencies (point reads of their task keys, visible within the transaction), or declare the gap.
2. **The Go-only inline capacity error does not poison.**
   - "Rolls back that reconcile" (:911) holds only when the caller does not commit.

## P2-1: The inline bound's collapse-window case is analysed wrongly (design 883-918, 367-370)

- **The window is real, and the design's list of flag writers is correct.** `CollapseTask.java:415-424` clears COLLAPSE without re-arming. The paired bounce is a separate high-priority task with a random id (`AbstractDeferredTask.java:275-288`), and it re-arms only an idle cluster (`BounceTask.java:294-307`).
- **"Succeeds on retry once the bounce has run" (902-903) is false when the refused insert's own inline task is the collapse.**
  - The refusal aborts the transaction, which rolls the collapse back.
  - The next insert runs the same collapse and is refused again.
  - Where every insert routes to that cluster, inserts are refused until a delete or MergeIndexes commits the collapse. That covers lone-cluster partitions, which is every measured shape.
  - The target accepts all of these inserts, because it has no inline cap (`Insert.java:334-338`).
  - More generally, any refusal after the inline task rolls that task back, so inserts can never advance the queue in such a partition.
- **It is reachable by an operator.** `primaryClusterHardMax` is mutable (`GuardiannVectorIndexEngine.java:97`) and can go as low as max+1 (`Config.java:200`) on a live index that has a backlog.
- **The error is not poisoned.** The bound raises the capacity error, which never poisons (194-196, 522-525). In this case the error is Go-only, so catch-and-commit leaves the record unindexed where the target would have indexed it. That conflicts with the design's own rule that Go-only refusals poison (191-194).
- **No fixture covers this case.** Lines 919-923 cover only the reconcile-residue case.
- **Needed:**
  - Either make the bound unable to fire while the paired bounce is pending, or prove this case unreachable.
  - Correct the recovery claim.
  - Decide whether this refusal poisons.
  - Add fixtures for both cases, plus a non-firing guard that includes a collapse.

## P2-2: The inline-delete skip (d) fires where the target's inline delete succeeds (268-276, 363-365)

- **The predicate is too broad.** It keys on task kind plus knob value alone, so it also skips:
  - obsolete and false-alarm tasks that the target consumes (item 13; `shrink=ok drain=1` at `evidence-run.txt:78`);
  - because SPLIT_MERGE covers both directions, every live split under `mergeNumNearestClusters<1`. The target's inline deletes succeed there (`deletes=[ok*27,]`, `evidence-run.txt:140`).
- **So two statements are false:** the declared population "where the target's inline delete fails" (364-365), and "everything else … matches Java" (373-374).
- **This is a second copy of the predicate** in all but name, which 212-213 disclaims.
- **"Removal always remains possible" (274) is also false** in two cases:
  - `deleteConcurrency<1` fails the delete itself (231, parity);
  - a trained bits-9 index with a live head task throws at the quantizer, and the skip does not cover it.
- **Needed:**
  - Put each task's no-op exits and its split/merge/neighbour determination in ONE read-only function, called by both `runTask` and the skip. The skip then fires only where the consumer would refuse. Alternatively, declare the real population and pin it with a fixture.
  - Limit 274's guarantee to deleteWhere, clear, disable and drop.

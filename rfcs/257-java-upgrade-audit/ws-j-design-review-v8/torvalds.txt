## MEDIUM

**1. The EQUIVALENT carrier has no route into storage.**
- The design says the save path "stores that same `gen.MetaData`" (:1238).
- Both `CreateTemplate` implementations take an `api.SchemaTemplate`:
  - The FDB one re-serializes `rl.Underlying().ToProto()` (`fdb_template_catalog.go:153`, `:252-262`). `indexToProto` drops `index_type`, `value_expression`, extensions and unknown fields, so the spliced index cannot survive.
  - The in-memory one stores the object itself.
- Also, the (d) check in `serializeTemplate` runs on the in-memory metadata, not on the bytes that would be stored.
- The write-path table (:767) has no row for saving carried bytes.
- **Fix:** name the route. For example, a template loaded from the spliced proto whose serialization emits that proto verbatim, as `recordsSourceProto` already does for the records file. Give it a table row covering both catalogs, and pin that an index stored with `value_expression` survives a new version created through the SQL driver.

**2. A restore can still put two histories under one name.**
- The at-or-above guard (:391-406) closes create-then-restore. But `RestoreTemplateVersion` (:441) never refuses when no schema binds (t, v).
- **Sequence:**
  1. Drop template t and every schema bound to it.
  2. CREATE SCHEMA TEMPLATE t again: a fresh v1, a new history.
  3. `Restore(t, 3)` with the old history's bytes. Nothing binds (t, 3), so it is admitted.
- The latest version is now foreign to v1, which falsifies section 4's premise (:1360-1371). A `RepairSchema` onto it that differs only in a predicate, with matching index versions, passes the validator, which compares no predicates. Reads through that index then return wrong rows.
- **Fix:** refuse a restore when nothing binds (t, v); that is the restore's only purpose. Add this sequence to the FDB tests.

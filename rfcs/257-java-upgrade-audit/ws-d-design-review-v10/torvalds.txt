## P2 — Sampling bounds the peel's cost, but it is unmeasured at high d, and the d = 4096 fixture probably cannot commit (design 1189-1235)

**Sampling changes the result once d > S.** The pinned rows already show it on `hdTight50N2000D768`:

| Refit mode | Selected partition |
|---|---|
| unsampled | [1001 999] / [1074 926] |
| S = 256 | [445 1555] / [579 1421] |
| S = 64 | [201 1799] |

- The S = 64 row sits two vectors from INVALID: fewer than 200 of 2000 is INVALID (`PartitionEvaluator.java:124`).
- The design reports only "same exit" and round counts (1204-1209), not child sizes.
- Child sizes decide whether the larger child is still over primaryClusterMax (1000, `Config.java:144`) and re-arms another peel.

**The case that motivated v10 is not measured.**
- d = 4096 at S = 256 is d/S = 16. That is a worse ratio than the S = 64, d = 768 row that nearly went INVALID, and the probe stops at d = 768.
- Once the rule samples, "ClusterUnsplittableError always means no usable partition under the rule" (1113-1115) is true by definition and proves nothing.
- Whether a splittable cluster stays splittable at d = 4096 is still a hypothesis.

**The d = 4096 acceptance fixture (1233-1234) is probably infeasible as written.**
- A split dissolves the core and rewrites every reference with its quantizer-encoded bytes (`SplitMergeTask.java:819-864`, `StorageAdapter.java:405-419`).
- 2000 unencoded vectors at d = 4096 are at least 16 MB (half precision) or 32 MB (float). That exceeds FDB's 10 MB transaction limit, so both engines fail with 2101.
- The fixture must specify a trained RaBitQ configuration. That also changes the estimator, so the probe's measurements no longer describe it.

**Needed:**
- Add d = 1536 and d = 4096 shapes at S = 256 to the pure-algorithm probe, and pin the final child sizes.
- Choose S from that data, for example by scaling it with d if balance collapses.
- Specify the fixture's encoding.
- Name 2101 among the failure modes past the bound.

## P3

1. **The merger's handling of 1007 is misstated (1224-1225).**
   - `IndexingMerger.shouldAbort` aborts only on 1051, 1213 and 1515 among FDB errors (`:189-203`; Go `indexing_merger.go:96-100`).
   - 1007 and 2101 are retried about 12 times with a halving time quota (`:246-258`). Each attempt runs inside `db.Run`, which retries 1007 up to 10 times.
   - So a stuck task re-runs its evaluation and peel up to roughly 120 times. That matches Java, but the design should say it instead of "aborts".
2. **The cost ratio uses the wrong number (1226).** "The bounded factor above" is the KMeans-only ratio of 1.28. Yet the design itself says the passes over P dominate (1213-1214). Measured on the tight shape, sampled refits take 89-107 ms against a target fit of 36-46 ms, about 2.4×.
3. **The heartbeat spec has no "bad key after a live UUID" case.**
   - Both bad keys sort before the UUID heartbeat: byte string is type code 0x01 and string is 0x02, both below UUID 0x30 (`tuple.go:167-177`). The test comment "0xff… is last" is wrong.
   - The claimed "before and after" coverage therefore does not exist, and "wherever it sits in the range" (DIVERGENCES.md and the code comment) is not pinned.
   - A regression that parses keys lazily and returns early on the first live heartbeat would stay green.
   - Fix: add a versionstamp-typed key (0x33) after a live UUID, in both the Go spec and the JVM spec.
4. **Step 2's "exactly" population is inconsistent (1110-1111).** "Whatever the 2->3 candidate is" contradicts 1027 and 1036-1040, where a usable 2->3 candidate is selected. It should read "absent, n<k or INVALID".
5. **The peel's RNG split is described two ways:** "after candidate enumeration" (1100-1101) and "ONCE, at peel entry" (1228). State that no split is drawn on any path where Java completes. An unconditional split on the ordinary path would shift the materialisation and task-id bytes relative to Java.

## P2-1: The peel's one remaining cost exit retries forever in Go (design 1219-1226)
v10 removes the time budget and says a task past FDB's 5 s limit gets `transaction_too_old` (1007), which "every retry owner treats as it treats the target's own". Both halves of that claim are wrong in this tree:
- **`db.Run` has no 10-attempt limit.** `runner.go:199` belongs to `FDBDatabaseRunner`, which `db.Run` does not use.
  - `db.Run` goes through `runTransactCtx` → `TransactCtx` (`database.go:272-275, 353-356`), which defaults to unlimited retries. `pkg/fdbgo/fdb/unbounded_default_pin_test.go:7-11` and `chaos/scenario.go:92-93` both document this.
  - `pkg/recordlayer` sets no retry limit or timeout on it.
- **The merger does not abort on 1007.**
  - `indexing_merger.go:96-100` aborts only on 1051, 1213 and 1515, as `IndexingMerger.java:189-199` does. On 1007 both engines halve the merge count or time quota and retry.
  - In Go the merger never even sees 1007, because its own `db.Run` (`indexing_merger.go:27`) retries it first.
  - Java's merger retries through `runner.runAsync`, which is bounded by `maxAttempts` (`IndexingMerger.java:85-86`), then by `failureCountLimit` (`:125-128`) and the quota halving.

**Consequence:** the design itself says "a retry repeats exactly the same work with the same outcome" (1199-1200). So a task that exceeds 5 s retries forever in the merger and in any inline write run under `db.Run`, bounded only by the caller's context. Where the peel runs, the target instead fails at once with a non-retryable error (`:397` or `KMeans.java:136`). v9 asked for proof that this cannot livelock; v10 moves the unbounded behaviour from the budget into retry handling. The same gap applies to the target's own heavy splits at large d once GuardiANN work flows through the merger. The "remains single" statement at 772-773 does not cover it.

**Needed:**
- Run GuardiANN drain transactions through a bounded owner with Java's `maxAttempts` semantics (the runner Java's merger uses).
- Or declare the livelock and pin it with a fixture using an injected retry limit.
- Correct 1222-1226 either way.

## P2-2: Acceptance fixtures are not checked against FDB's 10 MB transaction limit (1227, 1231-1235)
- **Every rewritten reference carries full vector bytes** (`StorageAdapter.java:405-419`, `Primitives.java:760-770`).
- **By default nothing shrinks them.** `useRaBitQ` is false by default (`Config.java:167`), so vectors are stored as the input type with an identity transform (`Primitives.java:312-315`).
- **The d=4096 fixture cannot fit.** Materialising a split of 2000 primaries writes 2000 × 4096 × 2 B = 16 MB (half precision) or 32 MB (single) of references. That fails with `transaction_too_large` (2101) whatever the peel does.
- **The d=768 fixture depends on the element type.** Single precision is about 6-7 MB with up to 300 replica writes; double precision is about 13 MB and fails.
- **The analysis only covers time.** "Materialising … is not part of the bound" (1227) is true of the time bound, but the fixtures include materialisation.

**Needed:**
- State each fixture's vector type, RaBitQ setting and computed write volume. Enabling RaBitQ changes the estimator, and oracle item 20 measured only raw Euclidean vectors.
- Classify 2101 for every retry owner: `db.Run` returns it; the merger halves its quota about 12 times, then gives up.
- Declare that at the peel sites 2101 is Go-only, because the target never materialises there.

## P2 — D-0 doesn't say what commits an attempt (design 847-875)

**How Go commits today.** `Run` commits through `d.transactor`'s own loop (`database.go:272-316`). `NewFDBDatabaseWithTransactor` exists so that fault injection and tracing wrappers see `Run` traffic (`database.go:187-190`), and every chaos scenario runs `chaosDB.Run` through a `ChaosTransactor` (`chaos/scenario.go:68-72, 190-293`).

**What D-0 adopts.** D-0 says it shares one mechanism with `RunWithRetry`. That function's `runOnce` builds the transaction with `CreateWritableTransaction` and commits it directly, never touching `d.transactor` (`runner.go`). The TODO recipe the design points to says the same: "INSTEAD OF delegating straight to `d.transactor.Transact`" (`TODO.md:6995`).

**Consequence.** Built as written, the chaos suite injects nothing and stays green. This is exactly the "green from an empty set" failure CLAUDE.md warns about.

**The design's own 1007 fixture cannot be built (873-875).** It needs "a chaos-transactor fault" that raises 1007 to the retry owner. `ChaosTransactor` never returns an FDB error that way (`fault.go:151-207`):
- `FaultTransactionTooOld` commits and then re-executes the closure;
- `FaultReadError` fails reads with a non-retryable error.

**Needed:**
1. **Commit route.** State that each attempt is one `d.transactor.TransactCtx` call, with the raw loop capped at one attempt. For example, set a retry limit of 0 on the transaction: pure-Go `OnError` then returns the input error (`transaction.go:~2504`), and libfdb_c's `retry_limit` behaves the same. Move `RunWithRetry` onto the same route.
2. **What that route drops.**
   - The raw client's handling of "may have committed" errors (1021, 1039): its retry copies the previous attempt's write conflicts into read conflicts (`transaction.go:2555-2579`). A fresh attempt loses this.
   - A transaction timeout would apply per attempt rather than across all retries.
   - The commit-unknown barrier is unaffected: it stays inside `Commit` (`transaction.go:1979-1980`).
   - Fresh attempts match Java's runner, but say so.
3. **Retry predicate.** `isRetryableError` is not `fdb_error_predicate(RETRYABLE)`: it adds 1235 and 1242 (`runner.go:410-440`). `fdb.IsRetryable` is the pinned 12-code predicate (`retry_predicate_pin_test.go:15-37`). Use that.
4. **Backoff.** Java's delay is full jitter: a random fraction of a current delay that doubles from 10 ms, with a 2 ms floor (`ExponentialDelay.java:62-72`). `RunWithRetry` uses 0.5–1.5× jitter instead. Sharing one mechanism means changing the runner too; say so.
5. **Weak reads.** Java clears weak-read semantics on every retry (`TransactionalRunner.java:181-192`, called with `currAttempt != 0`). `RunWithWeakReads` re-applies CausalReadRisky on every attempt (`database.go:391-395`).
6. **`RunRead`.** It belongs to the stated `Run*` population but never commits. State how its loop is bounded.
7. **Fixtures to add.**
   - 1021 on attempt 1: post-commit hooks run exactly once, `RunWithVersionstamp` returns the final attempt's versionstamp, and `FaultCommitUnknown` is still observed through `Run`.
   - A new chaos fault that returns a retryable code to the retry owner.

## P3

1. **The admission cost W leaves out the KMeans settings.**
   - Each refit costs in proportion to `kMeansMaxIterations × (restarts + 1)`. Defaults are 8 and 3 (`Config.java:182-183`); both are per-index options fixed at creation (`GuardiannVectorIndexEngine.java:345-346, 435-438`).
   - The "about 1.7 s" at the bound (1143-1145, 1320) holds only at default settings and on JVM timings.
   - Fold the settings into W, which stays a pure function of the input, and require a Go-side measurement of cost per unit of W before fixing B.
2. **The balance claim is too broad (1215-1217).** "0.33 to 0.49 on every measured shape at d = 768 to 4096" is false. On the spread shape at d = 4096, seed 1 selects [1726 274], a fraction of 0.137 (`wsd-gen-1.log:329`). README item 23 correctly limits the range to the tight shapes.
3. **Two numbers are wrong.**
   - At n = 1001 the limit is d ≤ 4440, not 4444: 9 × 1001 × 4441 exceeds 4 × 10^7.
   - At d = 768 the refits took 0.355–0.398 s, not "0.39 to 0.40" (`wsd-gen-1.log:316`, `wsd-gen-2.log:30`).
4. **Accepting (UUID, x) keys creates a heartbeat case "exactly three populations" does not cover.**
   - Java's ongoing check reads a `Map<UUID,…>` built by `getIndexingHeartbeats`, where a later key for the same UUID overwrites an earlier one (`OnlineIndexer.java:459-462`, `IndexingHeartbeat.java:151`).
   - Go's `CheckAnyOngoingOnlineIndexBuilds` checks every key-value pair on its own.
   - A live (U) key next to a (U, x) key dated at least one lease ahead: Java says not ongoing, Go says ongoing.
   - Declare and pin this case, or evaluate over the collapsed map.
5. **D-0's blast radius is only partly covered.**
   - SQL autocommit statements run through `DB.Run` (`pkg/relational/core/embedded/connection.go:416`). Their failure surface changes after 10 attempts; name it and pin it.
   - Decision (3) finds affected tests with one suite run. That cannot catch tests that only occasionally exhaust 10 attempts under contention. Run the chaos-concurrent, mutual-indexing and sqldriver concurrency targets with `--runs_per_test`, before and after the change.
6. **"Retry/commit ownership remains single" (797-798) is no longer true.** After D-0 there are two nested bounded loops: build `maxRetries` over `Run`'s attempt limit, as Java's `IndexingThrottle` runs over the runner. Restate it.
7. **Admission for fewer than two primaries.** floor(log2(n − 1)) is undefined there. State that admission is evaluated only after Step 1's other preconditions pass, so the error's cause field is deterministic.
8. **README item 25 overstates the reruns.** "The other 92 served from run 1" is not accurate: run 1 itself executed only 8 of 94 (`just-test-v11.log:8530`). Those cached results are valid because Bazel keys them by content, but say so.

## Findings, most severe first

**1. Medium: VECTOR options keep Go's value ranges, not Java's.**
- **Java.** `parseConfig` finishes with `builder.build`, i.e. `Config`'s compact constructor (`Config.java:93-120`): m in [4,200], mMax in [4,200], mMax0 in [4,300], m ≤ mMax ≤ mMax0, efConstruction in [100,400], efRepair in [m,400], RaBitQ bits in (0,16). The validator reaches it through `VectorIndexEngine.java:198-203`, and `VectorIndexMaintainerFactory.java:106-110` rethrows any failure as "incorrect index options".
- **Go's validator** only parses the values and checks the metric (`vector_index_validation.go:63-111`).
- **Go's maintainer** applies its own ranges (`vector_index_maintainer.go:209,214-225`): M in [2,128], RaBitQ bits in [1,8].
- **Silent, different graph.** `{hnswNumDimensions:3, hnswM:150, hnswMMax:150, hnswMMax0:300, hnswEfRepair:150}` gives m=150 in Java. Go's validator accepts it and Go maintains with m=16. Bits 9–15 behave the same way.
- **Meta-data Java cannot open.** `hnswEfConstruction=50`, `hnswM=3`, or `hnswM=20` alone (above the default mMax of 16) are refused by Java and built by Go. This is v14 Graefe 2's class, which revision 15 fixed for metric names only.
- **Which claims are false:**
  - The `vector_index_maintainer.go:145-146` comment: "a value both accept means the same number to both".
  - DIVERGENCES `:2120-2122`, same claim.
  - DIVERGENCES `:2129-2132`, which lists only two remaining differences.
  - 7.15's heading "The maintainer reads the options as the validator does".
- **Why the JVM rows miss it:** every accepted value lies inside both ranges (**measured**: m 8, mMax 12, mMax0 24, efConstruction 150).
- **Fix:**
  - Port `Config`'s checks into the windowed validator, as `IllegalArgumentError` with Java's texts.
  - Make `parseHNSWConfig`'s ranges Java's.
  - Add a `VECTOR_CONFIG` row with m=150, and refusal rows for efConstruction=50 and m>mMax.

**2. Low: "Byte for byte" is not true of the field order.**
- `rewriteMaps` keeps raw's order (`record_wire_map_order.go:429-488`), and raw is protobuf-go's deterministic marshal (`:659`). That marshal writes real oneof members after all other fields (v1.36.11 `internal/impl/codec_message.go:177-184`, `proto/encode.go:247-253`) and extensions first (`impl/encode.go:159-161`).
- Java writes known fields in field-number order (`FieldSet.java:613-619`, `Descriptors.java:1790-1796`), then unknown fields sorted by number.
- The unit-test schema shows the difference: `Rec` has oneof `ha=5`/`hb=6` before `mh=7`/`tree=8` (`record_wire_map_order_test.go:64-71`). Go re-saves `{ha, mh}` as 7 then 5; Java writes 5 then 7.
- Indexes are unaffected. But the CHANGELOG ("stored byte for byte as Java's own load-then-save"), DIVERGENCES `:3213-3215` and `record_wire_map_order.go:43-45` all claim equal bytes. `store.go:2218-2224` already disclaims this for the non-map path.
- **Fix:** write known fields in number order in `rewriteMaps`, or narrow the claim and declare the difference. Add a JVM re-save row with the oneof shape.

**3. Low: A proto3 map entry with a zero key or zero value loses it on an unchanged re-save.**
- `canonicalEntry` (`:642-648`) marshals the entry as a dynamicpb message.
- For proto3, the key and scalar value have implicit presence (`filedesc/desc.go:369-374`), so dynamicpb skips a zero, `""`, or `false` (`dynamicpb/dynamic.go:494-519`).
- Java's `DynamicMessage.buildPartial` fills and writes both fields (`DynamicMessage.java:379-390`). That is the source of the proto2 `k=0` measurement. I read this in the protobuf-java copy in the Bazel cache and did not check it is the conformance JVM's version.
- So `map<string,int64>{"a":0}` is re-saved as `0a0161` where Java writes `0a01611000`. Changed and new keys go through the map coder and keep both fields.
- **Scope of the measurement:** the "byte for byte" check covers 3 records of one shape — proto2, a top-level `map<string,int64>`, no oneof, no nested map (**measured**). The nested expectations are Go's model of Java.
- **Fix:** always encode both key and value in `canonicalEntry`. Add proto3 and nested-shape rows to `resaveRecordsJava`.

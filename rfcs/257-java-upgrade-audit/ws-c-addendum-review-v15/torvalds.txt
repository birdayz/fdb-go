## Findings (most severe first)

**1. Medium, a regression: the evolution check and the maintainer now read `hnswRaBitQNumExBits` differently.**
- `hnswRaBitQNumExBits()` (`metadata_evolution_validator.go:1069-1079`, used at `:1017`, file unchanged since `51c3f90eb`) still uses `fmt.Sscanf`. Its comment says it gives "the count parseHNSWConfig gives".
- `parseHNSWConfig` now uses `javaParseInt` (`vector_index_maintainer.go:209`). Before this revision both used `Sscanf`, so they agreed.
- Example: a windowed index with `"８"` passes the validator (`vector_index_validation.go:73`). The maintainer reads 8 and the evolution helper reads 4. Evolving to `"4"` passes as unchanged while the quantizer over existing data goes from 8 bits to 4.
- A plain VECTOR index going from `"8x"` to `"8"` has the same problem in reverse.
- This reopens v14 Torvalds 1's evolution bullet for this option.
- **Fix:** read the count through `parseHNSWConfig`, and add a unit pin and a JVM evolution row.

**2. Low: `elementPriors` lets an earlier element take a later unchanged element's stored match.**
- The same-position check runs inside the per-element loop (`record_wire_map_order.go:527`), so an earlier element's content search can claim a later element's own stored element.
- Example: stored `h=[A,B]`, saved `[X,B]` where X's content equals B's. X takes B's stored order, and the unchanged B is written in key order. Java keeps B's own order.
- DIVERGENCES ("an unchanged element keeps its own order wherever the list moved it") and 7.15 therefore claim too much.
- **Fix:** run the same-position pass over all elements first, add a subtest, and declare the case no pass can fix (an inserted element equal to a later unchanged one).

**3. Low: "byte for byte" is claimed without scope.**
- The claims are at `DIVERGENCES.md:3214`, `CHANGELOG.md:433` and `record_wire_map_order.go:44`. They were measured only on a proto2 `MapRec` with no oneof and no unknown fields.
- **(a) Oneof order.** protobuf-go writes oneof members last (`internal/impl/codec_message.go:177-184`; `proto/encode.go:247-253` for dynamicpb). Java writes fields by number (source hypothesis).
- **(b) A defect, proto3 only.** `canonicalEntry` (`:642-643`) marshals a standalone dynamicpb entry, which drops a zero key or value (`dynamicpb/dynamic.go:502-518`). protobuf-go's own map codec always writes both (`codec_map.go:242-259`, `encode.go:313-325`).
  - So Go's unchanged re-save of its own `{"a":0}` rewrites the bytes.
  - Within one map, the unchanged, changed and new-key arms encode entries differently.
- **(c) Unknown fields** stay in Go's order (Java's order is a hypothesis).
- **Fix:** write the key and value unconditionally with `protowire`, and state what is not covered.

**4. Low: the boolean HNSW options still use `== "true"`.**
- Where: `vector_index_maintainer.go:187,190,196,207`. Java uses `Boolean::parseBoolean` (`VectorOptionKey.java:227`, `HnswVectorIndexEngine.java:193-205`).
- With `hnswUseInlining="TRUE"`, Java writes the inlined layout and Go does not. That is storage 1's class.
- Design `:1528-1530` assigns booleans to WS-D, but DIVERGENCES' VECTOR entry does not declare it. The spec "options are read as Java reads them" compares no boolean.

**5. Low (evidence, deduced from measured output): no re-save met an entry stored without a value.**
- Both re-saves start from Java's first save. That save is `DynamicMessage.parseFrom` plus `saveRecord` (`metadata_store_conformance.java:1107-1112`), the same parse-then-write as the re-save.
- Java's re-save holds `…6b1000…` (log :23), so the first save already wrote `k=0`.
- So 7.15's "the entry stored without a value" was measured of Java's first save. Go's path for such an entry is pinned only by `record_wire_map_order_test.go:429-444`.
- **Fix:** have both engines re-save the `raw` subspace (`:408-428`) and compare.

**6. Low: an incomplete conversion in the dry run.**
- `DryRunSaveRecord` (`store_api.go:391`) still calls `serializeUnion` with no stored record.
- Its `ValueSize`/`Split` preview can differ from the save it previews (a twice-written key kept, defaults filled). Java's dry run serializes exactly what its save writes.

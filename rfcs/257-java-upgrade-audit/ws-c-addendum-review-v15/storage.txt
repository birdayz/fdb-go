## Findings, most severe first

**1. Low (from source; a regression against revision 14): a proto3 map entry whose key or value is zero is written without that field.**
- `canonicalEntry` (`record_wire_map_order.go:642`), used for every unchanged entry (`:616`), marshals the entry as a dynamicpb message.
- For a proto3 map entry, key and value have no presence, so `dynamicpb.isSet` skips `0`, `""` and `false` (`dynamicpb/dynamic.go:502-518`, v1.36.11). `holdKeyAndValue`'s `Set` of the default does not change that.
- So Go loads `{"a": 0}` stored as `0a0161 1000` and writes it back without `1000`.
- Both of the following write both fields:
  - Go's own map marshal: every new record, and revision 14's re-save.
  - Java: `DynamicMessage.Builder.buildPartial` puts every map entry's key and value into its FieldSet (`DynamicMessage.java:379-390`, protobuf-java source in Bazel's repo cache).
- The JVM spec cannot see this, because `MapRec` is proto2 (`key_validation_conformance_test.go:46`), and so is `wireMapFile`.
- **Fix:** write an entry's key and value unconditionally, as a map marshal does. Add a proto3 map with a zero value and an empty key to the JVM re-save comparison.

**2. Low (claim): "byte for byte" claims more than the code does.**
- Where the claims are: `CHANGELOG.md:433` says a record Go loads and saves unchanged "is stored byte for byte as Java's own load-then-save stores it"; `DIVERGENCES.md:3214` says "Go's load-then-save writes the same bytes".
- protobuf-go marshals oneof members after every other field:
  - generated types: `impl/codec_message.go:177-183`;
  - dynamicpb, when deterministic: `LegacyFieldOrder`.
- Java writes fields in number order. `store.go:2218-2224` already disclaims Java-equal bytes.
- The unit test's own `Rec` shows it: `ha=5` sits in a oneof beside `mh=7` and `tree=8`. With `ha` and `mh` both set, Go writes 7 before 5.
- Only the proto2, oneof-free `MapRec` is measured.
- **Fix:** scope both sentences, or declare the oneof order in DIVERGENCES.

**3. Low (from source): elements with equal content can swap their map orders after an insertion or removal.**
- `elementPriors` first prefers the stored element at the same position (`:527`).
- Example: stored `[H1{z,y}, H2{y,z}]`, which have equal content, and one new element inserted in front.
  - Current element 1 claims `H2`'s order, and element 2 then takes `H1`'s.
  - Go writes `[N, {y,z}, {z,y}]`; Java keeps `[N, {z,y}, {y,z}]`.
  - A covering index whose key `z` and `y` share then holds `y` in Go and `z` in Java.
- `DIVERGENCES.md:3222` says an unchanged element "keeps its own order wherever the list moved it". The subtests use only elements of distinct content.
- **Fix:** match the k-th current occurrence of a content to the k-th stored one, which keeps relative order. Declare the one case that remains ambiguous: equal elements reordered among themselves. Pin the example above.

**4. Low (from source; text): the VECTOR maintainer is not "Java's `parseConfig`".**
- The claims:
  - `HNSWConfigOf`'s doc (`vector_index_maintainer.go:138-140`): "Java's HnswVectorIndexEngine.parseConfig".
  - `DIVERGENCES.md:2120-2123`: "a value both engines accept is the same number … as to Java's HnswVectorIndexEngine".
- Java reads each option under its `hnsw*` name and then its `vector*` alias (`VectorIndexOptionKeys.java:53-73`, `VectorOptionKey.read:145-152`). `IndexOptions.java:244-248` tells users to create new indexes with the `vector*` names.
- Go's maintainer and validator read only the `hnsw*` names. For a windowed index with `hnswNumDimensions` set:
  - `vectorMetric=COSINE_METRIC`: Java uses cosine; Go builds and maintains Euclidean, without saying so.
  - `vectorMetric=cosine`: Java refuses; Go builds.
  - `vectorNumDimensions` alone: Go refuses what Java builds.
- The booleans differ too: `== "true"` (`:187,190,196,207`) against `Boolean::parseBoolean`, which ignores case.
- WS-D owns the option catalogue (`ws-d-design.md:265-267`). **Fix:** scope both sentences to the `hnsw*` names and integer/double options, and point at WS-D; or read the aliases now and add JVM rows for them.

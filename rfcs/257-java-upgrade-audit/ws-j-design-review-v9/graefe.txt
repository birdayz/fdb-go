## MEDIUM

**1. A concurrent drop and fresh create can defeat the restore's "nothing binds" refusal (design :491, :528-536).**
- The listing checks that some schema binds (t, v). The final transaction only re-checks that (t, v) is not stored and adds a conflict range. The design calls a DROP SCHEMA in the window harmless ("only shrinks the set", :534). Under the v9 rule it is not harmless.
- **Sequence:**
  1. The restore lists S, the only schema bound to (t, 3), and reads its header.
  2. DROP SCHEMA S commits.
  3. CREATE SCHEMA TEMPLATE t commits a fresh v1: the guard sees no bindings.
  4. The restore commits: no conflict, because both writes came before its read version.
- That is the v8 Torvalds #2 two-history state again.
- **Fix:**
  - In the final transaction, re-read with limit 1 that some (t, v) binding remains. This is O(1) and keeps the conflict range.
  - Correct :534.
  - Add this interleaving as an FDB test.

**2. The edited-file route bypasses evolution validation (:1865-1885, (p)).**
- The route admits an edited file when:
  - it frames every stored record type at the same field number;
  - it loads;
  - its version is stored + 1.
- It checks nothing else. `SaveRecordMetaData` runs the evolution validator (`metadata_store.go:111-117`); this route cannot, because the stored file does not load.
- So the route admits these edits unchecked:
  - an index root changed with its last-modified version kept, whose old entries are then served as-is;
  - a changed primary key or record-type key;
  - a non-holding field retyped;
  - a holding field retyped to a message with a different wire meaning.
- "Which is the whole requirement" (:1877) overclaims.
- **Fix:**
  - Require everything outside the two union candidates and the named holding fields to be proto-equal to the stored file, apart from the version and pure additions.
  - Restrict a holding field to removal or a wire-compatible retype.
  - Add refusal tests for an index-root edit and a primary-key edit.

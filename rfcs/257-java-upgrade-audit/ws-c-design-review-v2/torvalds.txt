**Required correction: serialize checked readability with in-flight enqueues sharing the context.** The [design’s registry check](/home/birdy/projects/fdb-go/rfcs/257-java-upgrade-audit/ws-c-design.md:242) handles completed enqueues, but does not specify atomicity between validation and state publication.

The current [readable setter validates before changing state](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:144); only [the eventual state write acquires `stateMu`](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:523). Meanwhile, [maintenance holds its read lock](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1011). A permitted interleaving is:

1. Writer observes state 4, then pauses before registering queue mutations.
2. Readable validation finds both registry and persisted queue empty.
3. Writer registers its mutations and releases the read lock.
4. Setter publishes READABLE; commit flushes the unapplied queue entries.

FDB conflict ranges cannot resolve operations within the same transaction. Separate store handles make a handle-local lock insufficient; [same-context concurrency is supported](/home/birdy/projects/fdb-go/pkg/recordlayer/database.go:618).

Specify context-shared ordering spanning writer state-read→enqueue registration and readable validation→state publication, reusing existing context lock infrastructure. Define acquisition order and deterministic same-handle/cross-handle regression schedules. **Do not hold `versionMu` while waiting for `stateMu`**: maintenance takes the opposite order. This is a source-derived counterexample, not an executed test.

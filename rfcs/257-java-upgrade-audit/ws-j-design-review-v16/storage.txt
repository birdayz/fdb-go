## Storage and concurrency (sound as landed)
- **Guard and delete refusal.** The delete-vs-bind pair conflicts in either commit order: the delete reads the binding range, and the bind reads the template row with a serializable `LoadRecord`. A refused write commits nothing. A fresh template reads the whole `(t)` prefix.
- **Restore:**
  - it writes the exact bytes back;
  - it re-reads the version, a limit-1 binding and every row of t inside its own transaction;
  - after commit_unknown_result, a retry that finds its bytes counts as done;
  - a restore below latest does not conflict with a concurrent CreateTemplate, and that is still serializable.
- **In-memory lock order.** It is store then template on every path, with no re-entry.
- **Literal fix.** It matches Java's Integer packing. The explicit record-type key is normalized to Long in both engines (`RecordTypeIndexesBuilder.java:91`).
- **Maintenance filter.** Java's relational layer sets none (0 hits), so NORMAL is the default in both engines.

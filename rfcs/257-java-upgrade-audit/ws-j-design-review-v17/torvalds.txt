## HIGH
**H1. A fan type outside the enum: the claim is false for Go, and its pin never tests Go.** Found by reading source, not by running anything.
- The 3.6 marker (`ws-j-design.md:1675-1677`) and `key_expression_proto.go:264-267` both say both engines parse fan type 7 into the unknown fields.
- protobuf-go does not. `coderEnumPtr = coderInt32Ptr` (`internal/impl/codec_unsafe.go:12`), and nothing in `internal/impl` calls `IsClosed`. So `proto.Unmarshal` stores `FanType=7`.
- `fieldFromProto` then passes its `FanType == nil` check, and `fanTypeFromProto`'s default case (`key_expression_proto.go:30`) reads 7 as SCALAR.
- Java refuses the same bytes ("missing fan type"). Go instead loads them, carries them as EQUIVALENT (roots are compared after Go re-serialises them), and restores them, all under a different key layout. That is fail-open on metadata the target refuses.
- The spec hides it. "a field whose fan type is 7" (`conformance/key_expression_absent_child_conformance_test.go:96-100, :110`) hands Go a proto built with `SetUnknown`, so Go's decoder never sees the bytes Java parsed.
- Fix: refuse any value outside {SCALAR, FAN_OUT, CONCATENATE} with Java's text. Pin it by unmarshalling the same bytes in Go. Sweep the other proto2 enums the loader reads.

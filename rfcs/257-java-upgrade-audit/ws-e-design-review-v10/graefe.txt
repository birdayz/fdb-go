## HIGH

**H1. A NaN known only at runtime, at a non-terminal component, has no mechanism (1030-1045).**
- The design says: "every later comparison is a residual filter over the scan".
- A plan-level residual only works for a literal NaN, which Go knows at planning. For `nan_in_then_in`, a bound `f = ?`, or a comparand source, the plan has already put `[EQUALS q0, EQUALS q1]` into the scan. The binder (`scan_range_binding.go:388-392`) only builds ranges; it cannot filter entries.
- The two ways out are both unstated, and each is a Graefe-gated choice:
  - **(a) Binder-level entry filter:** its continuation semantics and scan-limit accounting need to be specified.
  - **(b) Never make a component after a possibly-NaN float equality sargable:** every dynamic float composite equality loses its second key component, and the target's nested shape over DOUBLE columns is lost.
- The third option, refusing as today, leaves `nan_in_then_in_where` failing.
- This is the v9 Torvalds M3 / storage M1 finding, still half-resolved. State the mechanism, and for (b) measure the plan corpus.

## MEDIUM

**M1. The NaN extension's SOURCE premise is false (1026-1028, 1047, 1051, 3265).**
- The claim that every NaN a statement produces is "`CAST('NaN' AS DOUBLE)`'s one pattern" does not hold in Go:
  - Go's `CAST('NaN' AS DOUBLE)` is `strconv.ParseFloat` = `0x7ff8000000000001` (`values.go:4639`; `embedded/utilities.go:19-27`).
  - `CAST(CAST('NaN' AS FLOAT) AS DOUBLE)` is `0x7ff8000000000000`.
  - Java's `Double.parseDouble` gives `0x7ff8000000000000`.
- On a shared cluster:
  - The target's index probe misses rows that Go SQL wrote.
  - A UNIQUE index accepts one NaN row per engine.
  - So "the rows are the same" and "two canonical NaNs" are wrong.
- This write-side divergence (different stored bytes for the same SQL) has no entry: zero hits in DIVERGENCES.md and TODO.md.
- **Fix:** make Go's SQL NaN produce Java's bits, which is the wire rule, or restate the declaration and test NaNs written by both engines, including the UNIQUE case.

**M2. The RFC-182 union leg is handed to WS-F, which does not carry it (2407-2410).**
- The design says "WS-F's census covers the RFC-182 leg".
- `ws-f-design.md` has 0 lines matching `182|PreservingMembers|No finals`, against 10 for "census" as the control.
- Its D7 ("any child with none → no yield") keeps groups without finals, so the crossing that preserves members (`unified_tasks.go:98-108`) survives, unpruned.
- `union_leg_type_annulling_fold_where` then rests on SOURCE. Make it an explicit WS-F dependency.

**M3. The negative control needs a configuration WS-F retires (2701).**
- The test runs "with WS-F's physical prune off (its test-only option)".
- After that option becomes the default, D9–D12 "never run without it", the designated final is deleted, and `Verify(==1)` returns an error (`ws-f-design.md:355-378`).
- WS-E lands after that point, so the control cannot run. Build it by ranking the two members directly, or have WS-F keep a no-prune test path.

**M4. #7 is load-bearing, not an open refinement (803-826).**
- With the arm, #7 moves from a streaming `FlatMap(outer=InUnion(IndexScan(IDX_VAL,[=])))` to `InMemorySort(InJoin(FlatMap…))` (`wse11-explode-F.diff:5-8`).
- That happens because the arm replaces the upper placement that produced the old plan.
- So step 5 cannot land without #7's derivation. Say so; add a guard that no ordered two-IN query gains an InMemorySort; and probe the hypothesis now. A task observer on the compensation member of the prototype would test it, instead of naming D5.

### High

1. **Constants versus ConstantObjectValues, and where folding happens (§5.4, §1.5, §4.1).**
   - Java's default value rule set never folds a ConstantObjectValue (`DefaultValueSimplificationRuleSet.java:50-54`). Only predicate simplification runs `DereferenceConstantObjectValueRuleSet` (`ValuePredicateSimplificationRule.java:62-71`).
   - That rule set turns a NULL COV into `NullValue` and a BOOLEAN COV into a non-null `LiteralValue` (`DereferenceConstantObjectValueRule.java:70-83`). Then it runs `EvaluateConstantPromotionRule` and `EvaluateConstantCoalesceRule` (`DereferenceConstantObjectValueRuleSet.java:50-56`).
   - Consequence: `WHERE COALESCE(TRUE, 1/0 = 1)` folds in Java. Under "simplifyCoalesce stops folding them", Go raises.
   - In projections Java never runs the coalesce rule, but Go's `SimplifyValue` does (`simplifier_value.go:43`).
   - The same predicate-only placement decides IN/array NULL timing. "At planning for constants" (§4.1) is still unmeasured, which leaves v1's timing finding half-open.
   - §1.5's "never folds a PatternForLikeValue *whose evaluation fails*" implies a valid pattern does fold. That contradicts the target's EXPLAIN (`LIKE @c7 ESCAPE 'ab'`).
   - Fix: state the mapping between Go's ConstantValue/BooleanValue/NullValue and Java's COV/LiteralValue/NullValue. Port both folding regimes, and keep PatternForLikeValue unfoldable.
   - Probes needed: a boolean-first COALESCE with an erroring tail, in WHERE and in SELECT; `IN (CAST(NULL AS BIGINT))` and `[CAST(NULL AS BIGINT)]` over an empty table.

2. **"Nullable iff any argument is" for every scalar function is unsound and not Java's rule (§5.3).**
   - Java's MOD, BITAND/BITOR/BITXOR and BITMAP_* are `ArithmeticValue`s, which are always nullable (`ArithmeticValue.java:126-127`, `Type.java:404-405`). Go implements them as scalar functions (`scalar_function_catalog.go:359,397-410`), so `MOD(5,2)` would become NOT NULL in Go.
   - Several Go functions return NULL on non-NULL input: LN and LOG out of domain (`values.go:3160-3190`), SQRT on Inf/NaN, NULLIF, and type-mismatch declines. The new rule would type all of them NOT NULL.
   - Go consumes that nullability in uniqueness enforcement (`physical_equality_shape.go:166`) and in promotion (`promote_prepared.go:341` raises `NonNullableFieldError`). So a wrong NOT NULL can change results, not just metadata.
   - The oracle cannot catch this: every nullability probe has a nullable argument, `id` included. "Any" is never told apart from "always", even for GREATEST.
   - Fix: derive nullability per catalog entry from the Java class it ports, list the NULL-introducing entries, and test every entry. Add all-NOT-NULL probes: `GREATEST(1,5)`, `COALESCE(1,2)`, `MOD(5,2)`, `BITAND(5,3)`.

3. **A Go `int` binds as LONG, and the strict lattice rejects it for INTEGER columns (§4.3).**
   - The idiomatic `db.Exec("INSERT INTO I VALUES (?, ?)", 1, 7)` passes an `int`, which is int64, and §4.3 types int64 as LONG.
   - `PromoteValue` has no LONG→INT and no DOUBLE→FLOAT (`PromoteValue.java:76-83`). So a typical INSERT or UPDATE of an `int` into an INTEGER column changes from success to 22000, and a `float64` into a FLOAT column does the same.
   - This is the section's largest user-visible break, and it is neither declared nor tested (v1 storage #7).
   - Decide explicitly: either type an `int` as literals are typed (INT when it fits), or declare the break. Measure DOUBLE→FLOAT and UPDATE.

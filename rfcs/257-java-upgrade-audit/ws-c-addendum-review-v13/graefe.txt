## Findings, most severe first

**1. Medium (from source, not measured): a global cache that never shrinks, on every save and every read.**
- `mapReach` (`record_wire_map_order.go:217-227`) is a `sync.Map` keyed by descriptor identity. It stores true and false results alike.
- It is consulted for every record type on every save (`store.go:2162`) and every decode (`store.go:2275`, via `newRecordWire` at `:57`).
- Meta-data built from proto creates fresh descriptors on each load: `metadata.go:1251` builds dynamicpb records from `desc`, and `FDBMetaDataStore` and the relational catalog call `RecordMetaDataFromProto` each time they load. Each load therefore keeps its descriptor graph alive forever.
- The repo already names this exact problem and bounds its cache for it: `positionalTypeCache` (`query/executor/query_result.go:115-145`).
- **Fix:** compute the answer once per `RecordType` when the meta-data is built (at the `metadata.go:1251` site) and pass it to `serializeUnion` and `deserializeAndDiscover`. Nested lookups can go uncached, or be cached per `recordWire`.

**2. Low (from source): when Go re-saves a record Java wrote, its map is re-sorted, and a covering value two entries share can then stay stale. Nothing declares this.**
- Scenario: Java writes a map as `[b→5, a→5]` under `KeyWithValue(NestFanOut(m, Concat(value, key)), 1)`. The stored value for `(5, pk)` is "a", the last entry.
- Go loads the record and saves it unchanged. The old entries (in wire order) and the new entries (in key order) contain the same pairs, so the common-entry filter (`index_maintainer.go:328-334`, `:820-866`) writes nothing. Java's filter is also order-blind (`StandardIndexMaintainer.java:219-227`).
- The index keeps "a", but the new bytes are `[a, b]`, which a rebuild in either engine turns into "b".
- Java's load-then-save keeps the entry order: a DynamicMessage keeps its list order, and a generated map keeps insertion order. So Java would not reach this state from the same operation.
- The CHANGELOG entry on map fields does not say that a Go save reorders a map Java wrote.
- **Fix:** declare it in CHANGELOG and DIVERGENCES and pin it with a JVM spec (Java writes, Go loads and saves, both engines rebuild and compare), or make the diff aware of order for shared keys.

**3. Low (from source): the new marshal checks proto2 required fields.**
- The new branch in `serializeUnion` (`store.go:2163`) calls `proto.Marshal` without `AllowPartial`.
- A generated type that has a map and leaves a proto2 required field unset is now refused with protobuf-go's error text. Before, vtproto saved it, and types without a map still save it.
- Java also refuses such a record (`UninitializedMessageException`), so the direction matches Java. But the change is not declared, it depends on whether the type has a map, and the error is not Java's class.
- The same check on read (`record_wire_map_order.go:141`) makes the whole record fall back to key order without saying so.

**4. Low (docs): some changed sentences are not marked, and one claim is too broad.**
- 7.13 (`:2291-2292`) says every changed 7.11/7.12 sentence is marked. Two are not:
  - `:2092`, "the mutation reddens this test alone", which 7.13 withdraws at `:2394`.
  - `:2209`, "The tests compare the whole text". This is still false: `sliding_window_index_test.go:1861` checks "requires a RowNumberWindowPredicate" with `ContainSubstring`, and the synthetic-types text has no test.
- `:2299`, "in Java a record's entries are always visited in its bytes' order", holds for the default DynamicMessage serializer. It does not hold for a `TypedRecordSerializer`: a generated parse collapses a key written twice. Narrow the sentence to the default serializer.

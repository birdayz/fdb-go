### Findings, most severe first

1. **Medium: the new `frl index build` pre-read bypasses the open-time quiescence check.**
   - `index_write.go:304-314` opens the store with plain `Open()` in its own transaction, which commits. That path runs `checkPossiblyRebuild` (`store_builder.go:1441-1445`) with no preflight.
   - So after `frl meta apply`, reconciliation (inline rebuilds, disables) runs before `checkOpenHeartbeats`. The indexer's own open then finds the metadata current, and the "reconciliation demands quiescence" rule declared in 7.2 never fires.
   - The state it reads can also be stale by the time `BuildIndex` runs.
   - The READABLE_UNIQUE_PENDING message (`:327`) is not tested. 7.2 says it is pinned in `TestIntegration_IndexSetState_ReadableRequiresBuilt`, but the MARK_READABLE census shows frl ran 374 tests with 0 failures, so no frl test publishes without a build.
   - Fix: have the indexer report which session outcome it took (a Go-only API addition), not a separate open.

2. **Medium: a new indexer ID per attempt, where Java keeps one.**
   - `online_indexer.go:1139` creates a heartbeat each attempt, and `NewIndexingHeartbeat` draws a fresh UUID (`indexing_heartbeat.go:50`).
   - Java creates `IndexingCommon.indexerId` once (`IndexingCommon.java:53`) and shares it across every catcher relaunch.
   - Heartbeat cleanup is best-effort ("Expiry is the fallback", `online_indexer_queue.go:289-292`). If it fails, the next exclusive attempt finds its own previous heartbeat, still live, and refuses with `SynchronizedSessionLockedError` for a whole lease. Java recognises that heartbeat as its own.
   - 7.2's reason, "as each Java attempt builds a new indexer", is wrong about identity: the indexer object is new, the ID is not.
   - Fix: mint the ID once per `OnlineIndexer`.

3. **Medium-low: Go-only `IndexingValidationError`s now trigger the catcher's BY_INDEX fallback.**
   - Two sites Java has no equivalent for:
     - `online_indexer_queue.go:427`, "index state changed during follow-up", reached from the merger's pre-commit (`indexing_merger.go:40`);
     - `:498`, "index state changed during build", when a target switches between WRITE_ONLY and WRITE_ONLY_WITH_QUEUE.
   - Java never raises a ValidationException in either place. Its follow-up heartbeat update skips a target that is not write-only (`IndexingBase.java:969-972`), and its state check throws `RecordCoreStorageException`.
   - Consequence in a BY_INDEX build: an operator disables the target during a merge → records-scan fallback → the next attempt finds it DISABLED → the default REBUILD clears and rebuilds it. Java fails the build.
   - 7.2 says the "index state changed during build" error was replaced; it was replaced only for the published case.
   - Fix: return `RecordCoreStorageError` from both sites, and add a spec for each.

4. **Medium-low: a source index missing from the metadata now falls back silently.**
   - Revision 1's builder refused it, because it found 0 record types.
   - Now `validateSourceAndTargetIndexes` (`:791`) sees no source types and reports "source index has multiple types". The catcher treats that as a validation failure and falls back to a records scan, after the state transaction has already committed a BY_INDEX stamp naming the missing index.
   - Java resolves the source inside the state transaction (`IndexingByIndex.java:68-73`, `:94-106`) and throws `MetaDataException`, which the catcher does not handle (`OnlineIndexer.java:228`).
   - Fix: check the source exists before stamping and return a `MetaDataError`; add a spec.

5. **Low: an undeclared change in which error wins.**

   - 7.2 declares only that a follower mismatch now wins over a live peer. Declare this too, or run the stamp check first for continued sessions.

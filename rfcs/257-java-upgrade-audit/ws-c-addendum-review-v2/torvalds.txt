## Findings, most severe first

1. **Medium: revision 2 adds a store open to `frl index build` that skips the heartbeat check.**
   - `cmd/frl/internal/cmd/index_write.go:300-314` opens the store with an ordinary `NewStoreBuilder()...Open()` before `BuildIndex`, only to read the state for the message.
   - That is the same reconciling open that `openStoreWithPreflight` (`online_indexer.go:2132`) guards with `checkOpenHeartbeats`, but without the guard.
   - With stale stored metadata, the CLI now runs reconciliation (which can rebuild or disable indexes) under live peers. That is exactly the hole 7.2 closes for the indexer. The message also reads a state that can change before the build starts.
   - This also leaves Torvalds v1 finding 7 (a skip looks the same as an empty build) worked around rather than fixed.
   - Fix: have the indexer report how the session started, or read the state without reconciling.

2. **Medium: each attempt gets a new heartbeat ID, which Java does not do.**
   - `buildIndexAttempt` (`:1139`) creates a new UUID on every attempt. The comment and §7.2 justify this as "as each Java attempt builds a new indexer".
   - But Java's heartbeat key is `IndexingCommon.indexerId` (`IndexingCommon.java:53`), shared by every attempt.
   - So Go's retries depend on the previous attempt's cleanup succeeding, and that cleanup is best-effort and discards its error (`online_indexer_queue.go:283-287`).
   - If it fails, the next attempt's exclusive admission (REBUILD, restore, or fallback, `:167`) sees its own leaked key as a live peer and fails with `SynchronizedSessionLockedError`. Java cannot lock itself out this way.
   - Fix: one indexer ID per `OnlineIndexer`, and correct the Java claim.

3. **Low: the unique-pending CLI message is claimed as pinned but is not tested.** §7.2 says it is pinned in `TestIntegration_IndexSetState_ReadableRequiresBuilt`. That test (`write_integration_test.go:133-141`) pins only the READABLE message. `git grep "without a build"` finds the string only at `index_write.go:55` and `:327`. Measured: in `census-markreadable`, with MARK_READABLE made an error, `frl` stays green.

4. **Low: an undeclared ordering change.**
   - Go checks heartbeats for all targets (`queue.go:167`) before the queue refusal and stamp checks (`:188`, `online_indexer.go:1499`).
   - Java runs those checks per index before `updateHeartbeat` (`IndexingBase.java:459-516`).
   - Now that the catcher consumes `PartlyBuiltError`, this matters. Example: an exclusive build against a live peer holding a MUTUAL_BY_RECORDS stamp returns a lock error in Go and `PartlyBuiltException` in Java.
   - §7.2 declares only the follower ordering.

5. **Low: the validation arm (`:1077`) also catches Go-only errors.**
   - Under a BY_INDEX policy it also catches "index state changed during build/follow-up" (`queue.go:498`, `:427`), which have no Java equivalent.
   - They are treated as an unusable source: the build falls back, then after records were scanned hits `PartlyBuiltError`, and repeats until the attempt limit.
   - The error finally returned hides the real cause.

6. **Low: a source index missing from the metadata now falls back silently.**
   - `RecordTypesForIndex` (`metadata.go:1998`) returns no types, so the failure reads "source index has multiple types" and the build falls back to a records scan.
   - Go also commits a BY_INDEX stamp naming that nonexistent index before validating.
   - Java's `getSourceIndex` (`IndexingByIndex.java:95-100`) throws `MetaDataException` inside the state transaction, which does not trigger a fallback.
   - Separately, the "synthetic" message cannot be reached (`IsSynthetic` always returns false, `metadata.go:1902`), so "Java's six messages" is five in practice.

1. **P1 — Former-index cleanup can leave the authoritative shared view stale, causing a newly added index to commit as READABLE without being built.**

   [index_state.go:472](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:472) updates shared state only when that particular handle already has `indexStateView`. However, [loadStoreState](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1901) installs only the handle’s header and local state map. Attachment happens later during lazy initialization.

   Metadata reconciliation calls [removeFormerIndexData](/home/birdy/projects/fdb-go/pkg/recordlayer/store_builder.go:386), which [clears the former index’s state through setIndexState](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:724), before ensuring that attachment.

   Concrete sequential sequence, all within one context:

   - Open populated metadata v1 with index `I` DISABLED; read its state to establish the shared view.
   - Open v2 dropping `I`. Former-index cleanup clears its persisted state key, but the existing shared view still says DISABLED.
   - Open v3 reintroducing name `I` with a **different subspace key** and a DISABLED rebuild policy. Name reuse with a fresh subspace is permitted. The new handle attaches to the stale shared view, and [MarkIndexDisabled](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:254) returns without writing anything.

   The state key remains absent, meaning READABLE on disk. The new index subspace is empty despite existing records, and the committed v3 header prevents automatic reconciliation on the next open. A cold reopen can therefore query an incomplete index.

   **Required:** attach reconciliation handles to the authoritative context state before any state mutation, and ensure every mutation updates that authority. Add a real-FDB same-context drop/re-add regression with a distinct subspace, DISABLED policy, committed state inspection, and cold reopen.

2. **P2 — Concurrent handles can publish shared state in the opposite order from their transaction mutations.**

   [setIndexState](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:450) holds a **per-handle** `stateMu`. It writes the transaction at lines 455–460, then acquires the shared view’s mutex at line 473. Those two orders can diverge:

   - Starting READABLE, handle A writes DISABLED and pauses before updating the shared view.
   - Handle B still observes READABLE, writes WRITE_ONLY, publishes WRITE_ONLY, and returns.
   - A publishes DISABLED and finishes.

   The transaction now contains WRITE_ONLY, while every attached handle observes DISABLED. Subsequent maintenance can skip an index that requires WRITE_ONLY maintenance; another `MarkIndexDisabled` can incorrectly return “unchanged.” Explicit read conflicts cannot reconcile inconsistent state inside the same transaction.

   The context expressly supports concurrent goroutines. This is a logical ordering defect protected from detection by ordinary memory-race instrumentation.

   **Required:** serialize the transaction mutation and shared-state publication across handles using common synchronization and consistent lock ordering. Add a deterministic interleaving test comparing the raw transaction state with both handles’ operational decisions after both transitions finish.

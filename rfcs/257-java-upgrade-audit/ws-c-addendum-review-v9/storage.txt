Every revision-8 finding is resolved in the code, and the new parsers and bytes match Java. The NAK is for an incomplete upgrade instruction that leads to silent corruption when both engines share a store, plus two claims wider than the code.

## Findings, most severe first

**1. Medium (docs; wire consequence): the upgrade note misses node-slot-index R-trees.** The note is at design `:1589-1592` and CHANGELOG `:289-290`.
- Before this revision, Go wrote no node slot index at all: v8's `rtree_storage.go` has no node-slot-index code.
- `flushNodeSlotIndex` only updates entries for the nodes an operation touches. So a `{rtreeUseNodeSlotIndex: true}` index that Go maintained before stays partial forever.
- Go never reads that index, but Java finds leaves through it for every insert and delete (`NodeSlotIndexAdapter.java:106-176`, `RTree.java:1497`). Java then picks the wrong leaves and corrupts the tree silently. This index is not in the rebuild list.
- "Created by Go" is also too narrow. A Java-created BY_SLOT or node-slot-index index that an earlier Go maintained is corrupt too, as the CHANGELOG itself says at `:280-282`.
- Lesser cases with the same cause: `rankCountDuplicates`, `unique` or `textOmitPositions` spelled "True"/"TRUE" were read as false by earlier Go, so the existing entries were written under the other meaning.
- **Fix:** say "every multidimensional index with `rtreeStorage`, a true `rtreeUseNodeSlotIndex`, or `rtreeStoreHilbertValues` without storage, that an earlier Go release maintained", and list the boolean cases.

**2. Low: "`Build`'s index and record-type checks … are in a fixed order" is not true of the whole of Build.** The claim is at design `:1559-1563` and CHANGELOG `:248`. Three error-returning loops still range over the `b.recordTypes` map in `metadata.go`:
- `:834`, the primary-key checks;
- `:1034`, the record-type-key collision. Its message names `prevName, name` (`:1045-1046`), so even with only two colliding types the names swap from run to run;
- `:1319`, the since-version check.

Sort them and pin them, or narrow the claim.

**3. Low: "every index ever handed to its `AddIndex`" (design `:1573-1575`) misses one path.**
- `AddIndex` with an unknown record type returns before `addIndexCommon` (`metadata.go:581-586`), so the index never reaches `addedIndexes` (`:621`).
- So `SetSubspaceKey(nil)` followed by `AddIndex("Nope", idx)` builds to "Unknown record type". Java throws at the setter.
- **Fix:** record the index before the type lookup, and pin it.

**4. Nits**
- **Stale "Go kept the default" for RANK levels** (CHANGELOG `:272-273`). v8 used "1" as one level and clamped values above 8 to 8 (`97d0b918:ranked_set.go:88-93`); only a non-int or ≤0 took the default. Such an index now fails every write, and the CHANGELOG should say so.
- **Wrong comment on deletes** (`ranked_set.go:113-114`). "A delete re-tosses them, as in Java" is false: neither engine hashes on remove (`RankedSet.java:382` is the only `getKeyHash` call). Also, `:120-122` silently turns a randomness read error into hash 0.
- **Mutation label for m84/c2.** The mutant keeps the storage gate and only flips "absent means false". The other half (not read without storage) is pinned by a unit case and the JVM set "Hilbert false without storage keeps them", but no mutation covers it. Rename the row.
- **Vector wording.** CHANGELOG `:240-241` still says the vector checks compare effective values "as Java's do", without 7.9's scope to the `hnsw*` names only.

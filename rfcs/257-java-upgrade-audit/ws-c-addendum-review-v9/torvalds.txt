## Findings, most severe first

**1. Low: the upgrade guidance leaves out indexes whose bytes revision 9 changes.**
- The rebuild lists (`CHANGELOG.md:275`, `:290`; design `:1589-1592`) leave out Go-created indexes with `rtreeUseNodeSlotIndex`. Go never wrote their node slot index. After the upgrade it keeps only the entries of nodes it touches.
- On the delete path, Java's `scanIndexForNodeId` returns null when an entry is missing (`NodeSlotIndexAdapter.java`, `!isInsertUpdate` branch), so the delete does nothing. Stale R-tree entries then stay on a shared store.
- Also missing: `rankCountDuplicates`, `unique` and `textOmitPositions` spelled in another case (e.g. "TRUE"). Go wrote them as false before this revision and Java as true.
- **Fix:** add these to both rebuild lists.

**2. Low: "`Build`'s … record-type checks are in a fixed order" (design `:1557-1563`, `CHANGELOG.md:248`) is not true of the code.**
- `metadata.go:834` (primary key), `:1034` (record-type key collision) and `:1319` (since version) still range over the `b.recordTypes` map and return at the first violation.
- With two violating types, which one the message names changes from run to run.
- No 32-run test covers these three loops.

**3. Low: the `Integer.parseInt` conversion is incomplete.**
- `permutedSize` is still read with `strconv.Atoi` (`permuted_min_max_index_maintainer.go:45-48`), and an error silently becomes 0.
- Java's `getPermutedSize` throws on an absent or unparsable value (`PermutedMinMaxIndexMaintainer.java:107-112`). Its build-time validator also refuses a negative size or one larger than the grouping count (`PermutedMinMaxIndexMaintainerFactory.java:70-78`). Go's `Build` has neither check.
- So a value Java accepts, such as "٢", is maintained by Go at size 0, which writes other entry bytes.
- It is not tracked anywhere: "permutedSize" or "permuted size" has 0 hits in TODO, DIVERGENCES and CHANGELOG, against a control of 4 lines for "node slot index".
- The CHANGELOG heading "parsed as Java parses them everywhere" (`:293`) is also wider than the code: the vector booleans still compare `v == "true"` (`vector_index_maintainer.go:163,166,175,195`). Scope it to WS-D, as 7.9 does.

**4. Low: "the entries stored are the ones Java stores" (DIVERGENCES) is inferred from source beyond the child ids.**
- The unit oracle derives the expected keys through the production `nodeSlotIndexEntries` (`rtree_layout_test.go:77` calls `rtree_storage.go:333`). A mutation of the key layout there moves both sides, so the test cannot catch it.
- The JVM raw check reads only the last tuple element (`multidimensional_options_conformance_test.go:209`).
- m86 and c4 mutate the call site, not the layout.
- A Java-written index has never been compared with Go's derivation for level, Hilbert value and key.
- **Fix:** decode the entries independently against their parents' slots, and run the same check on the Java-written trees in the JVM spec.

**Nits.**

- **Maintainability.** `orig`, `origHeight` and `fetched` are copied by hand into the new root structs (`rtree.go:790`, `:937`). And `deleteNode` (`rtree_storage.go:296`) on an intermediate node silently skips the index. Recording `orig` in the per-operation map at first fetch would remove both hazards.

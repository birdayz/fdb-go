## HIGH

**H1. Provenance is lost when the memo deduplicates a yield (5.4(c)).**
- `Reference.Insert` returns false for a yield equal to an existing member (`reference.go:643-690`, fast path at `:655-657`). So a provenance field on the yield vanishes whenever two sources simplify to the same member.
- Go keeps `FilterDropTruePredicatesRule` and `FilterDedupPredicatesRule` in REWRITING (`default_rules.go:43-44`). From S1 `[id=5, X, X]` (or `[id=5, TRUE, X]`), with X = `COALESCE(1/0,5) IS NULL`, they derive S2 `[id=5, X]`.
- simp(S1) and simp(S2) are the same `[FALSE]` filter over the same quantifier. The second yield deduplicates, so S2 forms no class and crosses into PLANNING unpruned.
- PLANNING's cardinality rung then picks S2's primary-key probe and raises 22012, where the target answers no rows. This is the rescue the prune exists to remove. (SOURCE)
- **Fix:** record provenance as a group-level relation at yield time, dedup hits included, and make a class the connected component. Pin both rows above.

**H2. The nested-IN mechanism is a hypothesis that the only measurement contradicts (4.1(b)).**
- The prototype removed the same partition guard (`PROBE_PARTITION`, `fdb-explode-probe/.../rule_partition_binary_select.go:104`) with the NLJ sibling guard intact. It planned `FlatMap(outer=Fetch(InJoin(IDX_A)), inner=PredicatesFilter(Explode))` (`wse8-explode-suites.log:15018-15020`).
- The guard fires only on an explode leg that is not correlated to the other leg (`rule_implement_nested_loop_join.go:122-135`). A PredicatesFilter over the explode is correlated, so "the sibling guard is what keeps the FlatMap from winning" is false.
- Java's `PartitionBinarySelectRule` matches exactly two quantifiers (`PartitionBinarySelectRule.java:96-97`).
- Java's `ImplementInJoinRule` and `ImplementInUnionRule` each consume ONE predicate-free select holding every explode, and nest or union them in a single firing (`ImplementInJoinRule.java:114-164`, `ImplementInUnionRule.java:99-163`).
- v9 gives the two shapes two different derivations and does not label either SOURCE.
- **Fix:** trace the prototype to find whether the target-shaped member was built or lost on cost, then state the Java derivation.

## MEDIUM

**M1. "Lands after D3" understates the dependency.**
- The chain needs WS-F D1 (progress) and D4 (the conditional task), and WS-F D12's cleanups. WS-F lands D12 only at its step 7, behind a test-only option (`ws-f-design.md:316-321, 349-360`).
- D12 removes the standalone `DecorrelateValuesRule` (`default_rules.go:159`). While it stays, the chain's decorrelate yield deduplicates, which is not progress (WS-F 2.1), so the simplification fires beside the decorrelated member anyway.
- `OptionalRewritingRuleNames` (`:425-431`) would return the wrapper's name, not the two inner names, so `DISABLE_PLANNER_REWRITING` would not disable the chain.
- WS-F v2 is itself NAK'd.

**M2. Duplicate mechanism with WS-F's physical prune.**
- WS-F ports Java's physical prune, deletes the designated final and makes `Verify(finals==1)` an invariant (`ws-f-design.md:183-196`).
- WS-E never mentions this and gives its boundary prune no retirement condition. Once one final per group holds, every class is a singleton and the prune-disabled unit test can no longer observe anything.

**M3. The NaN mapping is incomplete.**
- For a runtime float probe, the planner claims 1 seek at a terminal coordinate and 2 point seeks otherwise (`physical_equality_shape.go:416-429`). The two NaN blocks are not adjacent, and a non-terminal NaN coordinate cannot be followed by later comparisons.
  - Example: `IDX(f, g)` with `f IN (NaN) AND g IN (1)`, the `nested_ins` shape over DOUBLE columns.
- Not addressed:
  - `UnsupportedKnownNaN` (`:389-392`).
  - `EqualityPinsSinglePhysicalKeyOnColumn`'s `n != 0`, which is true for a NaN constant (`ordering.go:534-537`).
  - Reuse of the existing NaN-block builder (`scan_range_binding.go:832-852`).
- "(values.CompareFloat64's total order)" is wrong. That order collapses every NaN above +Inf (`coercion.go:33-40`); the tuple order differs (`scan_range_binding.go:820-824`).
- The target's index probes one packed NaN, so returning payload NaNs through the index goes beyond the target. Declare it as an extension. (SOURCE)

**M4. The converters cannot see the column type.**
- Both write converters dispatch on the proto kind (`proto_value.go:317-323`, `executor.go:4459-4463`).
- DATE and TIMESTAMP are plain `TYPE_STRING` fields (`builder.go:1019-1022`), and "the SQL type is not recoverable from the proto descriptor" (`proto_types.go:73-77`).
- **Fix:** name how the SQL type reaches both converters, for array elements, struct fields and after a schema load.

**M5. The GREATEST/LEAST property contradicts itself.**
- A stored TIMESTAMP may hold non-canonical text, and same-type promotion passes it through unchanged (`promote_prepared.go:372-374`).
- So "agree with the instant order" over generated RFC 3339 or garbage text fails by construction.

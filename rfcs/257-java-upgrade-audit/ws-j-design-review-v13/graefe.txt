## HIGH
**H1. Shape (g) compares the wrong key, and only the ordinary load checks it** (`:2335-2341`).
- **What each build uses as the key:**
  - Java's implicit record-type key is the SMALLEST union field of the type (`RecordType.java:172-179`), and current Go matches it (`metadata.go:416-418`).
  - The "preferred field" the design cites (`metadata.go:420-422`, Java `:878-887`) is the field records are WRITTEN under, not the key.
  - Pre-upgrade Go let the last declared field win both (`e48f5b496:metadata.go` loop and `:1833-1837`).
- **As written, (g) misses Java's deprecation shape** `{T old = 1; T _T = 5}`. Pre-upgrade gives 5 and the preferred field is 5, so nothing is refused, yet the real key is 1. Rows pre-upgrade Go keyed under 5 would be read under 1.
- **Corrected to last-versus-smallest, it reaches Java stores.** It would refuse every Java-authored library file of that shape, which current Go reads exactly as Java does. The stated remedy, an explicit key equal to the pre-upgrade number, would re-key a Java-written store. SQL templates are immune, because Java sets explicit keys (`RecordMetadataSerializer.java:70`).
- **The same shift is unchecked where the design rewrites files.** The route's step (iii) and the migration's output check compare only the record-type name and message per field number (`:2386-2390`, `:2508-2527`). The as-framed load keys by today's rule. So a migrated or edited (a), (c) or (d) file that has two union fields of one type and a `recordType()` key is re-keyed silently.
- **Fix:**
  - compare the last declared field with the smallest;
  - carry the pre-upgrade key into the as-framed load, and compare keys at (iii) and in the migration's check;
  - scope the load refusal to files where a key expression reads the record-type key;
  - make the remedy "the number your rows were keyed with";
  - put the Java-store trade-off to the owner, since it crosses the wire line.

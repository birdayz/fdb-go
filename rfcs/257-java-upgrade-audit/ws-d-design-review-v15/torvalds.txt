## P2

**1. The new chain recorder has no test that can fail, and its rule is underspecified (design 1033-1039, 1053-1058, 1133-1135).**
- **Nothing tests the recorder.** Both client prerequisites land before D-0. After that, the pure-Go client, SimFDB and libfdb_c all keep the body's error chain. So the `Run`/`RunRead` chain pins stay green if the recorder is deleted. The client-suite pin tests the wrapper, and nothing tests the recorder.
- **Its stated reason is also unpinned.** The design justifies the recorder as holding "for any transactor, including chaos, tracing and custom". No fixture uses a transactor that strips the chain.
- **Line 1133 will be false when it ships.** It says the loop sees the signal "only because of the recorded body error". Once the wrapper prerequisite has landed, that is no longer true.
- **The rule needs a per-execution scope.** The recorded error must be the last closure execution's: reset when the closure starts, and nil when the body returns nil.
  - Otherwise a transactor that loops internally can pair a stale typed error with a later commit failure that has the same code.
  - If that stale error is `SPFreshSplitWindowError`, a real 1020 becomes an uncounted, unbounded retry.
  - The wrapper prerequisite has the same hole once the retry limit is above 0. The Apple binding avoids it only because it compares on every iteration (bindings/go/src/fdb/database.go:163-191).
- **Needed:**
  - `Run` and `RunRead` pins through a test transactor that returns a bare `fdb.Error{code}`, which go red when the recorder is removed;
  - a stale-error pin: a typed error on execution 1, a commit 1020 on the last execution, and the result must be a bare, counted 1020;
  - the per-execution rule stated for both mechanisms.

**2. The liveness claim for uncounted retries is false, and a stall under DST now hangs (1136-1147, 1165-1172; RFC-094 §2).**
- **The spacing claim is wrong.** `ExponentialDelay` draws uniformly from [0, current) (ExponentialDelay.java:62-72). Two re-runs can therefore be about 0 ms apart; the mean gap is about current/2. "At most once per maximum delay … never in a hot loop" is false. The same sentence is in RFC-094 §2.
- **Under simulation it is an actual hot loop.** The delay is drawn but never waited (1167), and SimFDB's 100-retry cap no longer applies (1141). The hunts pass `context.Background()` (hunt.go:158).
- **The only protection is a rule for authors.** "No DST hunt stalls a seal without scheduling the takeover" (1145) is not a mechanism.
- **So an accidental stall hangs instead of failing.** For example, a non-retryable error between SEAL and publish on the single goroutine used to fail loudly at the 100-retry cap. Under v15 it spins forever.
- **Needed:**
  - Correct both texts, and grep for the phrase: 0 hits outside review directories and the paragraph that records the withdrawal.
  - Add a simulated-environment bound: a typed stalled-seal failure after K uncounted retries against an unchanged SEALED posting, with K stated, or a required deadline on SimFDB drivers.
  - Add a fixture that stalls a seal with no takeover scheduled and asserts a loud failure, not a hang.

## P3

1. **The predicate pin cannot be built as written (1097-1101).**
   - `fdb.Error` is just `{Code int}` with no `Unwrap` (fdb/error.go:10-12). A single-cause chain can therefore hold at most one `fdb.Error`, and on such a chain the two predicates always agree.
   - Restate the pin over trees:
     - `errors.Join(fdb.Error{non-retryable}, fdb.Error{1020})`: first-cause false, any-cause true;
     - multi-`%w`;
     - a `RecordCoreRetriableTransactionError` on a later branch.
   - State that capability errors, `ClusterUnsplittableError` and `RecordContextNotActiveError` never unwrap to a retryable code. Otherwise `Run`'s any-cause walk retries errors that (e) and section 6 call terminal ("db.Run returns it without a retry").
2. **`AttemptTransactor` covers writes only (1185).** It has one method, for writable bodies. `RunRead`'s read arm (1409; the 1007 fixture) needs the call's identity too. Add a read method, or say how reads get it.
3. **The setup-DDL evidence depends on something the default client cannot produce (1311-1316).**
   - The design relies on "the conflicting-keys report the client returns".
   - The pure-Go client rejects `report_conflicting_keys` (fdb/options.go:261-269; API_PARITY.md:57), and SimFDB ignores it (options.go:74).
   - `GetConflictingKeys` returns only the context's own read ranges (database.go:1188-1197).
   - Either name libfdb_c as the backend for that evidence, or build the read-back into the pure-Go client.
4. **The reconcile's classes do not cover every outcome (1278-1283).** Define UNKNOWN by the MAYBE_COMMITTED set (1021 and 1039; runner.go:417-421), not the literal 1021. Otherwise a real cluster whose last attempt ends in 1039, 1042 or 1213 falls into neither class.
5. **`AttemptCall.Attempt` and the observer's index are undefined for uncounted retries (1190).** The stalled-seal fixture and "faults the call's first attempt" both depend on that definition.
6. **The performance criterion has no load condition (1814-1822, 2055-2061).**
   - The acceptance fixtures run in the Bazel suite beside other FDB containers (`--local_test_jobs=4`). A maximum measured on a quiet machine does not show the one-attempt assertion is "stable rather than lucky". Measure under the suite's concurrency, or state the load bound.
   - "Go at its best" is not a stopping condition for lowering B.
   - The 2.5 s / 5 s split assumes one peel per transaction. Inline multi-row transactions run one task per insert. Price that shape, or declare it parity.
7. **The `ensureActive` port needs one more sentence (959).** Say whether a *failed* commit also deactivates the context. Java's `closeTransaction(false)` runs on both outcomes (FDBRecordContext.java:515-531).
8. **Where the resolver's loop lives is unspecified.** `keyspace` imports only fdbgo, and `attemptLoop` is unexported in `recordlayer`. Say where the loop lives for the resolver, and that D-0 threads the context the resolver ignores today (fdb_resolver.go:48-50).
9. **Evidence binding and stale references:**
   - The pin record says only "restored": it has no comparison output and no hash tying `simfdb.go.good` to blob `a129771b`, although line 1064 says "compared".
   - Line 977 cites ddl.go:857 and :884, which are the `Run` lines. The `Commit` grep finds :862 and :890.
   - Line 1341 cites `:2646`; the actual line is `:2645`. That `RunRead` route also sits under a heading that says those routes are "not a ReadTransactCtx".

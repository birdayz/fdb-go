# WS-J design v18 review: **NAK**

I reviewed commit `d2e47b8bd`. `ws-j-design.md` at that commit hashes to SHA256 `5f6990f66f23f4a12f56766a016217d0adf8edfd77a826bfc3eaf8e05ea9643f` over 2950 lines; I recomputed both. The review was read-only: commit objects, Java 4.14.2.0, protobuf-go v1.36.11, protobuf-java source from the Bazel cache (I have not confirmed it is the JVM's exact version), and the evidence logs.

The sweep, the operand and the reader pins are sound. The NAK is for the first finding below: a closed enum's move to the unknown fields happens after protobuf-go has already checked required fields.

## HIGH

**H1. A required closed enum with an undeclared number: Java's full parse refuses it, Go's does not.**
- **Where Go goes wrong.** `UnmarshalAsJava` and `unmarshalVTAsJava` (`proto_closed_enums.go:97-125`) and both record decoders (`store.go:2281-2284`, `:2385-2388`) decode first, then move the number.
  - The decode passes the required-field check because the undeclared number counts as set.
  - The move then leaves the required field unset, and nothing checks again.
- **What Java does.** protobuf-java moves the number while parsing (`MessageReflection.java:1223-1232`), then `buildParsed` checks required fields (`DynamicMessage.java:93-96, 364-373`; generated `parseFrom` checks the same way).
- **Fields affected.** `Field.fan_type` (`record_key_expression.proto:37`), `RowNumberWindowPredicate.direction` (`record_metadata.proto:334`), and any required enum in a user's record type.
- **Consequences** (from reading source; none of this was run):
  - **Stored template with fan type 7.** Java's `MetaData.parseFrom` (`RecordLayerStoreSchemaTemplateCatalog.java:221`) fails, so Java reports XXXXX. That is the same post-parse state as the measured "a root field without its fan type" row. Go parses it, then refuses with `MetaDataProtoDeserializationError`, so `deserializeTemplate` (`fdb_template_catalog.go:375-381`) reports **42000**.
  - **`FDBMetaDataStore`.** Both engines refuse, but with a different error class.
  - **Records.** Java refuses the record ("Error reading from byte array", `DynamicMessageRecordSerializer.java:150-153`). Go reads it, indexes the field as null, and then fails its own re-save in `Marshal`'s required check.
- **Why the pins miss it.** This is the same simpler-cousin pattern as v17 H1:
  - The fan-type-7 JVM rows parse partially on both sides (`keyExpressionFromPartialProtoJava` and `buildPartialMetaDataAnyVerdict` for Java, `AllowPartial` for Go).
  - The stored-template spec has no fan-type-7 row.
  - The record spec's enums are only optional and repeated.
- **The repo already has the correct shape.** `unmarshalPendingQueuePayload` (`pending_writes_queue.go:~228-271`) strips undeclared `operation` numbers *before* decoding. So the required check sees Java's reading, and "the last KNOWN occurrence wins", which is Java's rule for a repeated singular field. The general helper does neither; the Go-reads-last divergence and the oneof-member divergence come from the same root.
- **Fix.** Strip before decoding, or run `CheckInitialized` after the move on every full-parse route.
- **Pin, Java versus Go:**
  - fan type 7 through the catalog and through `FDBMetaDataStore`;
  - a record whose required closed enum holds an undeclared number.

## MEDIUM

**M1. The recursion limit is off by one on top-level decodes, and the claims about it are wider than the code.**
- **Go.** protobuf-go counts the top-level message against the limit (`internal/impl/decode.go:105`, `proto/decode.go:124`). `RecursionLimit: 100` therefore admits 99 nested levels.
- **Java.** protobuf-java checks the limit only on nested messages (`CodedInputStream.java:186-190`, `:994-997`), so it admits 100.
- **Why the spec can't see it.** Its 49 and 50 shapes reach a maximum depth of 99 and 101, which straddle the boundary.
- **A shape that splits the engines.** A `record_count_key` (a KeyExpression at depth 1) that nests 50 KeyExpressions puts its leaf `Field` at exactly depth 100. Java parses it; Go refuses it.
- **Records happen to be right.** Go decodes a record's inner bytes one level below Java's union parse, so the limit of 100 matches there.
- **False scope sentences:**
  - `DIVERGENCES.md:3276`: "this never differs from Java";
  - `CHANGELOG.md:505` and `DIVERGENCES.md:3301`: headers, stamps and continuations are "parsed with protobuf-java's recursion limit". They go through `UnmarshalVT`, which has no limit at all. That is harmless for those non-recursive schemas, but the sentences are false.
- **Fix.** Use 101 in `UnmarshalAsJava`, keep 100 for records, pin a depth-100 meta-data proto, and narrow the sentences.

**M2. Go's own marshal→unmarshal round trips undo the move.**
- **Continuations.** The continuation value codec decodes buffered STRUCT values with plain `proto.Unmarshal` (`query/executor/continuation.go:488`, `:509`). protobuf-go puts the unknown varint back into the field.
  - So a STRUCT enum that read NULL before a sort or recursive continuation reads the raw number after resume.
- **INSERT…SELECT.** `rematerializeProtoScalar` (`executor.go:4162`), which copies a composite value on INSERT…SELECT, does the same.
  - The saved row then holds the number in the field, so Go writes an index entry of 7 where Java writes null.
- v18 introduced this inconsistency; before it, Go read the number consistently everywhere.
- **Fix.** Apply `closedEnumsAsJava` at both sites and pin a resume across that shape.

## HIGH

**H1. A save and a later load now read a closed enum differently. v18 introduced this.**
- Only the decoders apply Java's reading. `git grep closedEnumsAsJava|javaClosedEnums` hits only the record decoders (`store.go:2284`, `:2388`), map entries, meta-data and the stored-proto helpers.
- `saveRecordInternal` works on the caller's in-memory message. It evaluates the primary key there (`store.go:589-591`), the record count (`:738`) and every index (`:746`, `:779`).
- Go code can put an undeclared number in a closed-enum field (dynamicpb or a generated setter); Java cannot build such a message.
- Such a record is indexed and counted under the number. The next Go update or delete loads it as null and removes the null entry. The number's entry is orphaned and the count drifts, in Go alone. Before v18 both sides read the number.
- Two query-executor paths put the number back into the field with a plain `proto.Unmarshal`:
  - buffered rows re-parsed from a continuation (`query/executor/continuation.go:488`, `:509`), so a resumed page reads a value that page one read as null;
  - `rematerializeProtoScalar` (`executor.go:4162`), so an INSERT…SELECT saves it.
- So CHANGELOG's "indexed as null, as Java indexes it" is false for these records.
- **Fix:** give the record Java's reading at save, on a clone, or refuse it; declare which. Pin save→update→delete on the JVM spec's `EnumRec` (entries and count) and pin a resumed-page read.

## MEDIUM

**M1. The enum is moved after protobuf-go's required-field check.**
- `UnmarshalAsJava` parses without AllowPartial (`proto_closed_enums.go:98`) and moves only afterwards (`:101`); the record decoders do the same.
- Java checks required fields on its own reading. There, fan type 7 leaves the required `fan_type` unset, so the full parse fails.
- The design says so itself (4f item 7): "a stored required field left unset fails Java's full parse (XXXXX) before … 'missing fan type', which only a partial parse … reaches".
- Yet every fan-type-7 JVM row is a partial parse, and the spec "a stored template Java cannot load" has no fan-type-7 row.
- **Outcome for v17 H1's exact bytes through the catalog:** Java gives XXXXX; Go gives 42000, because `fdb_template_catalog.go:372-379` maps `MetaDataProtoDeserializationError` to `MetaDataError`.
- `FDBMetaDataStore` loads diverge the same way. A record with a required closed enum loads in Go and fails Java's parse.
- **Fix:** parse with AllowPartial, move, then run `CheckInitialized`. Add the fan-type-7 row.

**M2. The recursion limit is off by one at root decodes.**
- protobuf-go counts the root message (`proto/decode.go:107,124`; `internal/impl/decode.go:105`), so a limit of 100 admits 100 levels.
- protobuf-java checks before each nested `readMessage` and never counts the root, so it admits 101. This is from its source, which is not in the tree; I did not measure it.
- The spec's shape is 2d+2 levels deep, always even, so its 49/50 result is the same under 100 or 101 and cannot tell them apart.
- An odd-depth shape diverges: Java loads it and Go refuses it. Examples: a joined record type's join key nested 49 deep, or an index predicate of 47 nested ANDs (its leaf Value is at level 101).
- Records are correct at 100, because Java's root there is the union message.
- So `DIVERGENCES.md:3277` ("past 49 levels in both engines") and 4f `:2529` ("gives the same boundary") are false.
- **Fix:** use 101 for root decodes and keep 100 for the record inside the union. Pin an odd-depth shape.

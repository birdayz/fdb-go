## HIGH

**H1. The Java reading is applied only when Go decodes. The save path and Go's own re-parses put the number back into the field, which corrupts indexes.** This comes from reading source; I did not run it.
- The move is called only in the decoders (`store.go:2284`, `:2388`), `RecordMetaDataFromProto` and the map-entry parse.
- `saveRecordInternal` (`store.go:563-675`) maintains indexes from the caller's `record` as given. The old record it replaces is read through `deserializeAndDiscover`, with the move (`:643`).
- So a message holding `E(7)` in its field is indexed as `(7, pk)`. A later update or delete computes the old entries as null, and `(7, pk)` is orphaned. Java's, or Go's own, online build over the same bytes writes null.
- Before v18 both paths read 7 and agreed. v18 introduced the split.
- Two in-process round trips reintroduce the number the same way:
  - `continuation.go:488,509` re-parses buffered row messages with plain `proto.Unmarshal`, so a nested enum reads null before a continuation and 7 after it.
  - `executor.go:4157-4162`: the INSERT…SELECT composite copy marshals the value and re-parses it with plain `proto.Unmarshal`.
- Nothing probes this. The JVM spec only saves records that Go itself loaded.
- Fix: make the reader treat an undeclared closed-enum number as absent (key evaluation, FieldValue, rowstruct). Alternatively, normalise in `saveRecordInternal` and at both round-trip sites. Pin it with a Go save of a message holding `E(7)`, followed by a delete, and assert no index entry is left.

**H2. The required-field check runs before the move, so the stored fan type 7 — the route v17 named — is still not refused as Java refuses it (v17 Torvalds H1 and storage M2 are only partly resolved).**
- `UnmarshalAsJava` (`proto_closed_enums.go:97-103`) parses with `AllowPartial: false`. At that point the field holds 7, so the required check passes. The move then clears the field.
- Java runs `MetaData.parseFrom(...)` (`RecordLayerStoreSchemaTemplateCatalog.java:221`) and fails that parse. The measured analogue is in `wsj18-red/console.txt:186`: "Message missing required fields…", XXXXX.
- Go instead reaches `fieldFromProto`, raises `MetaDataProtoDeserializationError` and reports **42000** (`fdb_template_catalog.go:365-379`).
- The same gap affects `RowNumberWindowPredicate.direction`, and any record type with a required closed enum: Go loads a record that Java's `DynamicMessage.parseFrom` refuses.
- The pins are the simpler cousin again. Both engines use a partial parse (`key_expression_absent_child_conformance_test.go:128-146`, `:199-213`; `keyExpressionFromPartialProtoJava` and `buildPartialMetaDataAnyVerdict`).
- Fix: after the move, run `proto.CheckInitialized` (and the equivalent after VT decodes). Add a "stored template: fan type 7" row, XXXXX on both engines.

## MEDIUM

**M1. The recursion limit is off by one, and the claim is wider than the code.**
- protobuf-go counts the top-level message (`proto/decode.go:124`, `internal/impl/decode.go:105`), so `RecursionLimit: 100` admits 99 nested messages.
- protobuf-java admits 100, checking `recursionDepth >= limit` before incrementing. This is from protobuf-java source; it is not in this tree and I did not measure it.
- The 49/50 spec agrees only by parity: its deepest message sits at nested depth 99 or 101.
- Even-depth shapes diverge. Examples: `MetaData.record_count_key` nested 49 deep, and an index predicate's operand at depth 2k+6.
- Records happen to match, because Go skips the union level.
- `unmarshalVTAsJava` has no limit at all. That covers store headers at `store_builder.go:1014`, `index_state.go:443` and `store_state_cache.go:293`, while `store_api.go:174` limits. So the same header bytes get two verdicts inside Go. It also covers stamps, heartbeats and continuations.
- These sites therefore over-claim:
  - 4f.2 (`:2526-2532`), "the same boundary";
  - `CHANGELOG.md:505`, "store headers, index-build stamps … continuations";
  - `DIVERGENCES.md:3276-3279` and `:3301-3302`, "every stored proto of the store".
- Fix: set the limit to 101 for top-level stored protos, and put a limit on the VT decodes. Add a JVM row whose deepest message is at an even depth.

## P2

1. **The loop ports the wrong Java predicate (951-957 against 848-851).**
   - `FDBDatabase.run` retries through `RunRetriable.handle`. That handle checks every FDBException in the chain and retries if any is retryable, and it accepts `RecordCoreRetriableTransactionException` at any depth (FDBDatabaseRunnerImpl.java:195-205).
   - v14 ports `FDBExceptions.isRetriable` instead. That predicate stops at the first FDBException (FDBExceptions.java:236-247), and in Java only AutoContinuingCursor uses it (AutoContinuingCursor.java:140).
   - Line 913 then merges the two predicates. The design's own Target paragraph (849, "some cause in the chain") contradicts line 956.
   - **Needed:** two named predicates, plus a pin on a chain where they disagree: a non-retryable FDB error that wraps a retryable one.

2. **`BodyCommittedError` fires after the commit is already durable (890-897).**
   - `CommitWithVersionstamp` reaches `rc.tx.Commit().Get()` before any flag can be checked (database.go:1334).
   - So a self-committing body lands its write and then reports failure. That is the false "not committed" report v13 was NAK'd for.
   - A raw `rc.Transaction().Commit()` never sets the flag at all.
   - **Needed:** on a route-owned context, `Commit` refuses before `tx.Commit` is called. The fixture should assert that nothing committed. The raw-transaction path also needs to be named.

3. **The EXHAUSTED reconcile is a blind resync (1049-1060).**
   - Copying the operation's keys from the store into the model hides a double apply or a partial apply. For `deleteAll` (hunt.go:284-297) it resyncs the entire model.
   - **Needed:** assert that, for the operation's keys, the store equals either the model before the operation or the model after it, and that nothing else changed; only then adopt it. On SimFDB, cross-check with `LastCommitUnknownApplied`. Add a fixture where the store matches neither and the hunt goes red.

4. **Page outcomes contradict each other and the source.**
   - Line 1131 says a page is read-only, "so 1020 and 1021 are not page outcomes".
   - Lines 1081-1084 and 1117 say the opposite, and so does cascades_generator.go:2162-2171: page 1 can write the store header "and can come back not_committed".
   - Pages run through `DB.Run` → `TransactCtx` (connection.go:418), not `ReadTransactCtx`, so line 1130's "SQL read routes are fault-driven" through `ReadTransactCtx` is wrong for them.
   - The fixture at 1167-1168 injects only `FaultTransactionTooOld`.
   - **Needed:** a page-1 `FaultConflict` fixture that asserts no rows are lost, and line 1131 corrected.

5. **Owning 1007 has no limit on what it costs (1471-1492, 1671-1683).**
   - Line 1492 says Go's timing "does not move B", and v13's downward rule for the fixtures was dropped with nothing in its place.
   - At W = B the JVM estimate is already 3.43 s for refits alone. The sentence "the timer covers KMeans only" was removed, so the sort and assignment passes are now untimed without saying so.
   - If Go's peel is slower, every admitted edge peel fails with 1007 on every attempt. In inline mode the head task re-runs on every insert, so each insert stalls about 10 × 5 s under Run and then fails, where the target fails in about 0.3 s.
   - The acceptance fixtures (W = 1.54e7 and 1.85e7) then 1007 or flake.
   - **Needed:** at implementation, time Go's whole peel on the two edge shapes: n ≥ 2 runs, load recorded, a declared statistic, and a stated margin under 5 s. If it misses the margin, lower B once (never raise it) and move the fixtures in the same change. Restore the refits-only scope sentence.

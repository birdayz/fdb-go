## P1: On the default backend the body's error chain is dropped, so the SPFresh split-window fix does not work in production

- **What the code does.** `fdb.Database.TransactCtx` replaces the body's error with `unconvertError(e)` (`pkg/fdbgo/fdb/database.go:384-399`). That function returns a bare `&wire.FDBError{Code}` whenever the chain contains an `fdb.Error` (`transaction.go:552-561`). `ReadTransactCtx` (`:415-434`) and `Tenant.TransactCtx` (`tenant.go:28-41`) do the same. The client's OnError then hands that bare error back at the limit, and `convertError` turns it into a bare `fdb.Error{Code}`.
- **This is the backend production uses.** `fdbclient.Open` in the default build is `fdb.OpenDatabase` (`pkg/internal/fdbclient/open_purego.go:29`).
- **So design 926-927 is false** at the layer the record layer actually calls. The line says "the pure-Go client's OnError returns the caller's error". That is true of `client.Transaction.OnError`, but the adapter has already stripped the chain before OnError sees it.
- **Consequences:**
  - (a) `SPFreshSplitWindowError` (979-984) is invisible to `attemptLoop` on the pure-Go client. The signal arrives as a plain 1020, is counted, and the write fails after ten attempts. That is exactly v13's SPFresh liveness failure, now only on the production backend. The fixture would pass on SimFDB (fixed) and on libfdb_c, whose `runLoop` keeps `ee` when OnError re-raises the same code (`libfdbc/backend.go`, the comment block before the final return).
  - (b) The justification for the landed SimFDB change (the `declinedRetryError` comment) cites a parity that does not exist. SimFDB now preserves the chain where pure-Go strips it.
  - (c) Any typed error or marker wrapped around a retryable code reaches the caller stripped after exhaustion, on pure-Go only.
- **Needed:** make chain preservation independent of the backend. The attempt closure should record the error it returned, and `attemptLoop` should prefer that recorded error whenever the transactor returns an error with the same FDB code. This also covers the chaos and tracing wrappers. Pin it on pure-Go, tenant, SimFDB and libfdb_c.

## P2

1. **The loop's retry predicate is ported from the wrong Java function.**
   - Lines 952-957 port `FDBExceptions.isRetriable`, where the first `FDBException` in the chain decides (`FDBExceptions.java:236-247`). That is AutoContinuingCursor's predicate (`AutoContinuingCursor.java:140`).
   - The runner that `Run` and the merger port, `RunRetriable.handle`, ORs `isRetryable` over every `FDBException` in the chain, plus any `RecordCoreRetriableTransactionException` (`FDBDatabaseRunnerImpl.java:195-205`). The design's own line 849 says this.
   - Use the any-cause predicate for `attemptLoop` and the first-cause predicate for AutoContinuingCursor. In Go, the any-cause walk must also cover `errors.Join` trees.
2. **The acceptance fixtures now depend on wall-clock time, with no rule for when Go is slower.**
   - v14 dropped v13's rule that moved a fixture when Go was slower ("does not move B", 1491-1492).
   - The d = 2048 fixture has W = 1.845e7, which is 0.94 B. At the JVM's measured maximum rate that is about 3.2 s of refits. Add the fit (up to 0.31 s) and roughly 4-5 MB of reads and writes, all inside FDB's 5 s window. Go's rate has not been measured.
   - These fixtures (1706-1717) must commit a split. A 1007 there is an acceptance failure or a flake, not the "owned" production consequence.
   - **Needed:** make Go's measured peel plus fit at both admitted fixture shapes an implementation-gate criterion, with a stated ceiling, at least two runs, and load recorded. If Go is over the ceiling, treat slow Go KMeans as a performance defect to fix, not a reason to move the fixture.

**The lease algorithm is a two-transaction coordination protocol.**

A faithful Go merge invocation should:

1. Return immediately for HNSW.
2. Set maintenance step to MERGE.
3. Require the session UUID supplied by the driver; never invent a UUID per invocation.
4. Set the direct-task budget to the positive limit capped at `MaxInt32`, or one when unspecified.
5. Examine at most 16 yielded positive-count prefixes. Snapshot-read each lease. Prefer an already-owned live prefix; otherwise collect free/stale candidates.
6. If an owned prefix is found, refresh and drain it.
7. Otherwise, choose a free candidate uniformly, write its lease, report `(0,1)`, and commit **without draining**.
8. If none is actionable, report `(0,0)` and stop this invocation sequence.

The next transaction must re-read ownership before draining. A lease is stale when its timestamp is **at or beyond either boundary**: `timestamp <= now−60000` or `timestamp >= now+60000`. [VectorIndexMaintainer.java:529](/home/birdy/projects/fdb-go/fdb-record-layer/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/indexes/VectorIndexMaintainer.java:529), [VectorIndexMergeLock.java:94](/home/birdy/projects/fdb-go/fdb-record-layer/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/indexes/VectorIndexMergeLock.java:94).

Claims are intentionally blind writes. Two competing claims may both commit; subsequent observation determines which owner proceeds. Do not replace this with compare-and-set or claim that the lease is an absolute distributed mutex. Task and graph conflicts remain essential to correctness.

Every acquire/refresh adds a read conflict on the index-wide delete guard. `DeleteWhere(prefix)` must clear matching counts, leases, and primary partitions, then add a write conflict on that guard. This covers both commit orderings: an earlier claim is cleared; a later conflicting claim aborts. Release performs a serializable lease read and clears only a matching owner. **Task execution and budgets have two different notions of work.**

An owned-prefix drain requests `min(discoveredCount, taskBudget)` tasks. A nonpositive time quota becomes 4,000 ms and is written back to the control for adaptive feedback. The deadline is an absolute epoch-millisecond value.

The backend fetches a bounded batch in task-key order. Before running each task, it point-reads the task key using the writable transaction. Missing tasks are skipped. Present tasks are removed before execution; execution notification occurs only after success. Failure rolls the deletion, algorithm changes, and accounting back together.

The first fetched position is considered regardless of deadline; subsequent positions require `now < deadline`. The returned count includes only directly executed batch tasks. A bounce may execute a dependency internally, generating another execution event without increasing that outer count. Therefore:

- `mergesTried` is not total execution-listener calls.
- The count budget is not a hard bound on all nested work.
- The deadline cannot interrupt a task already running.

After draining, snapshot-read the prefix count with read-your-writes, including follow-up tasks. Release only when it is zero; negative throws. Report `(executed, executed+1)` even when that prefix just emptied, forcing another discovery transaction. **A depth-first implementation order avoids wiring an incomplete backend into record writes.**

1. **Freeze codec/config fixtures:** engine identity, aliases, effective defaults, immutable/mutable distinctions, exact tuple encodings.
2. **Finish shared primitives:** raw/provenance-preserving vector carrier, operation RNG/UUID helpers, cosine closure, sample UUID keys; consume accepted WS-A.
3. **Complete centroid-HNSW prerequisites:** covering preservation, fetch/cardinality, quick-start/ring/outward traversal; keep direct upsert isolated.
4. **Implement GuardiANN value/storage types:** roots, identities, roles, statistics, peak, membership, listeners and transaction-local caches.
5. **Implement independent clustering dependencies:** Java K-means, evaluator and ordered/distinct bounded helpers; leave SPFresh algorithms untouched.
6. **Implement backend write/read lifecycle:** bootstrap/access info, insert/replication/backpressure, delete, search and stale filtering.
7. **Implement task codecs and executor:** enqueue notifications, point recheck, remove-before-run, rollback and direct-count/deadline semantics.
8. **Complete task algorithms:** collapse and membership rules; reassignment; split/merge; bounce dependency/follow-up handling, resolving their shared primitive dependencies first.
9. **Add secondary accounting and lease helpers:** exact sparse counts, negative errors, guard conflicts, two-transaction ownership.
10. **Integrate the record maintainer:** neutral dispatch, shared apply/replay, task-event composition, scans, `DeleteWhere`, negative-disable hook and vector `MergeIndex`.

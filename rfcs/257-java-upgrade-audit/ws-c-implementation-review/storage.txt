1. **P1 — Fresh preparation deletes heartbeats before admission validation.** [online_indexer_queue.go:67](/home/birdy/projects/fdb-go/pkg/recordlayer/online_indexer_queue.go:67)  
   When the primary is readable or disabled, preparation clears every target before calling `CheckAndUpdate` at line 91. Both clear-and-mark paths call `clearIndexData`, whose bookkeeping cleanup includes heartbeat subkey 7 ([index_state.go:956](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:956)). The subsequent read therefore sees the transaction’s cleared keyspace. A legacy or malformed heartbeat—including one on a write-only follower—is silently removed and the build admitted. This violates the accepted requirement to refuse **any** incompatible heartbeat until explicit administrative cleanup after quiescence. Perform serializable admission checks across all targets before preparation can erase heartbeat evidence; cover fresh ordinary, queued, and multi-target builds.

2. **P2 — Terminal heartbeat cleanup is not bounded to 30 seconds.** [online_indexer_queue.go:168](/home/birdy/projects/fdb-go/pkg/recordlayer/online_indexer_queue.go:168)  
   `context.WithTimeout` bounds the retry context, but `db.Run` deliberately detaches dispatched commits from cancellation ([database.go:349](/home/birdy/projects/fdb-go/pkg/recordlayer/database.go:349)). The supported C backend waits in `tr.Commit().Get()` outside its cancellation watcher, with no default transaction timeout ([backend.go:219](/home/birdy/projects/fdb-go/pkg/fdbgo/libfdbc/backend.go:219)). If the cluster becomes unavailable during cleanup commit, the deferred cleanup can indefinitely block a canceled or failed `BuildIndex`, exceeding the design’s maximum and preventing return of the original result. Use a cleanup transaction whose commit and retries are bounded and canceled/closed on exit; cover a stalled commit.

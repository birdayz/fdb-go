## Findings, most severe first

**1. Low: "A Then is flat, as Java's is" is wider than the code.**
- `key_expression.go:748-753` says "every Then Go writes has the flat shape Java writes". `CHANGELOG.md:331-335` says the same. Neither holds for Go's own `RecordTypeKeyExpression.Nest` (`key_expression.go:520-523`):
  - Its `ToKeyExpression` writes `Then{RecordTypeKey, nested}` directly (`key_expression_proto.go:100-115`).
  - `RecordTypeKey().Nest(Concat(a,b))` therefore writes `Then[RTK, Then[a,b]]`.
  - `Concat(RecordTypeKey().Nest(x), y)` writes `Then[Then[RTK,x], y]`, because `Concat` flattens only `*CompositeKeyExpression`. That exact call is in `key_expression_fastpath_test.go:531`.
  - Java never writes either shape. Go's own loader now flattens both, so a Go round trip changes the bytes and the Go type. This is not declared in DIVERGENCES.
- The same comment says one-child composites are ones "which Build refuses as primary keys". Build refuses only `ColumnSize()==0` (`metadata.go:877`).
  - So `Concat(Field("id"))` builds, and is written as a one-child Then.
  - Java's reader refuses that (`ThenKeyExpression.java:83-85`), and so does Go's (`key_expression_proto.go:293-294`).
  - The production DDL paths guard against a single child (`relational/core/metadata/builder.go:1151,1330`), so this is reachable only through the library API.
- **Fix:** flatten `Nest` through `Concat` (or declare it), and refuse one-child composites at Build.
- **Adjacent defect, pre-existing, from source:** `keyExpressionEquals` treats every `RecordTypeKeyExpression` as equal and ignores `nested` (`key_expression.go:1174-1176`).
  - When both metadatas are built in memory, the primary-key comparison in `comparePrimaryKeys` (`metadata_evolution_validator.go:429`) cannot see `Nest(Field("a"))` change to `Nest(Field("b"))`.
  - Against metadata loaded from the store (a Composite), it always reports "primary key changed".

**2. Low: the upgrade list misses meta-data that will no longer load.**
- `RecordMetaDataFromProto` ends in `Build()` (`metadata_proto.go:374`), and Build now runs `validatePermutedIndex` (`metadata.go:1370-1376`).
- So meta-data an earlier Go stored with a PERMUTED_MIN/MAX index whose `permutedSize` is absent, negative, larger than the grouping count, or unparsable now fails to load. The store is unusable until the option is corrected.
- `CHANGELOG.md:346` lists only "not a plain decimal", and as a rebuild. "-1" and a too-large "3" are plain decimals that `Atoi` accepted.
- v9's `rankNLevels` finding got the "refused until corrected" wording. This case needs it too.

**3. Low: key validation "its texts and its classes" does not hold for proto map fields.**
- `key_expression_validate.go:78` uses `fd.IsList()`, which is false for a map field. Java's `isRepeated()` is true for one (`FieldKeyExpression.java:152,158`).
- For a map field with `None`:
  - Java throws the KeyExpression class: "m is repeated with FanType.None".
  - Go throws the Query class: "m is a nested message, but accessed as a scalar".
- `Nest("m", FanOut, …)` validates in Java and is refused by Go.
- This predates revision 10 and matches Go's evaluator, which also uses `IsList` (`key_expression.go:174` and others). It is undeclared, and 7.10 says `TestKeyValidationTextsAreJavas` "pins every validation text and class".

1. **P1 — Reload can deadlock with unique-index maintenance.**

   [ReloadRecordStoreState](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1896) now acquires `indexStateMu` before `stateMu`. An existing maintenance path acquires them in the opposite order:

   - `DeleteRecord` holds `stateMu.RLock()` through [updateSecondaryIndexes](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1012).
   - For a unique WRITE_ONLY or READABLE_UNIQUE_PENDING index, deleting one of two duplicates reaches [removeUniquenessViolations](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1352).
   - Pause after its real range read returns the remaining violation. Concurrent reload on the same handle acquires `indexStateMu` and waits for `stateMu.Lock()`.
   - Cleanup then calls `context.ClearRange` at line 1361 and waits for `indexStateMu`.

   Neither goroutine can release its held lock. Cancellation cannot break this mutex cycle, and reload holds the registry for the entire context.

   **Required correction:** establish a consistent lock order across reload and maintenance-triggered context clears while preserving atomic reload publication. Add a deterministic real-FDB duplicate-deletion/reload interleaving asserting both operations complete and persisted/shared state remains coherent.

2. **P2 — Clear invalidation overrides the approved noncacheable deletion policy.**

   [clearRangeWithIndexStateViews](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:340) unconditionally bumps the global metadata stamp whenever a registered state region overlaps the clear, even when its state map is empty.

   Reproduction: commit a valid noncacheable store; in a fresh context, open it with unchanged metadata, then call `DeleteStore`. Open now registers its view. DeleteStore correctly decides the header requires no stamp bump, but its [context clear](/home/birdy/projects/fdb-go/pkg/recordlayer/store_api.go:185) subsequently bumps it anyway.

   This contradicts [approved design §2](/home/birdy/projects/fdb-go/rfcs/257-java-upgrade-audit/ws-b-design.md:50) and tagged Java’s [deleteStoreAsync](/home/birdy/projects/fdb-go/fdb-record-layer/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/FDBRecordStore.java:1886). It unnecessarily invalidates caches across the cluster. Existing header-policy tests delete without first opening, so they miss this composition. [Clear-history preparation](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:311) also unconditionally bumps the stamp during a subsequent load.

   **Required correction:** preserve the validated header-based invalidation decision through deletion and retained-clear processing, while retaining shared-view updates and necessary cache invalidation. Add opened-noncacheable deletion and delete/recreate stamp controls alongside the warmed-cache regressions.

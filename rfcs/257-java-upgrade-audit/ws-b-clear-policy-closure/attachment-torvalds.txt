1. **P1 — Reload introduces a reachable lock-order deadlock.**

   [ReloadRecordStoreState, store.go:1896](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1896) acquires the registry mutex before `stateMu`. Existing record maintenance takes the opposite order: [updateSecondaryIndexes, store.go:1012](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1012) holds `stateMu.RLock`, and uniqueness-violation cleanup can call [context.ClearRange, store.go:1361](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1361), which acquires the registry mutex.

   Concrete interleaving: delete one of two duplicates from a unique WRITE_ONLY or READABLE_UNIQUE_PENDING index. Pause its violation-range read while maintenance holds `stateMu.RLock`. Concurrent reload acquires the registry mutex and waits for `stateMu`. Resume deletion: its one-survivor cleanup waits for the registry mutex. Neither operation can finish.

   **Required:** establish one compatible lock order across reload and maintenance while preserving atomic read/publication. Add a deterministic regression using this uniqueness-cleanup path; reload-versus-clear alone misses the cycle.

2. **P1 — Clearing state and committing without opening the store leaves warmed caches valid.**

   [index_state.go:338](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:338) records clear history, but immediate invalidation considers only registered views. Otherwise, invalidation depends on a subsequent [prepareIndexStateLoadLocked call, index_state.go:311](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:311). Commit never processes that history.

   Reproduction: warm a cache for an **empty cacheable store with DISABLED index I**. In a fresh context, call `ClearRange(ss.Sub(IndexStateSpaceKey))` and commit without opening that store. The registry is empty, so the metadata stamp remains unchanged. The next context’s cached Open still reports DISABLED. Saving a record skips maintenance and can commit successfully; uncached reopening observes READABLE with a missing index entry. The clear preceded this writer’s read version, so adding state-key conflicts cannot repair it.

   Both new warm-cache tests open the store inside the clearing context and therefore miss this case.

   **Required:** make supported state-clear invalidation effective without requiring a later Open. Retain the ordinary-record-clear negative control and add this separate-context sequence.

3. **P2 — Exported state snapshots still read stale handle-local maps.**

   [GetRecordStoreState, store.go:1836](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1836) and [GetAllIndexStatesMap, store_api.go:224](/home/birdy/projects/fdb-go/pkg/recordlayer/store_api.go:224) copy `store.indexStates`, whereas operational getters use the shared view.

   Open two handles, change a state through the transaction, and reload the first. The second handle’s `GetIndexState` reflects the reload, but its exported snapshots retain the old state. Context clearing likewise updates the shared view without updating these maps—even on the clearing handle.

   **Required:** obtain exported index-state snapshots from the common authority under its mutex. Extend the reload and clear regressions to assert agreement across these public APIs.

4. **P2 — Unconditional clear invalidation defeats header-aware deletion.**

   [index_state.go:340](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:340) bumps the global metadata stamp whenever a clear overlaps a registered state subspace, regardless of cacheability.

   Open an unchanged **noncacheable** store, then call [DeleteStore, store_api.go:165](/home/birdy/projects/fdb-go/pkg/recordlayer/store_api.go:165). Its header check correctly declines to bump the stamp, but its subsequent context clear bumps it anyway. This happens even when the registered state map is empty.

   That contradicts approved design §2 and tagged Java’s header-aware `deleteStoreAsync`, restoring unnecessary database-wide cache invalidation.

   **Required:** preserve deletion’s header-derived invalidation decision while maintaining view coherence. Add an opened-noncacheable-store negative control; the current header-policy fixtures have no registered view.

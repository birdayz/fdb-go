1. **[P1] Clearing state and committing without opening the store leaves the shared cache stale.**

   [index_state.go:338](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:338) retains clear history only inside the current context. Stamp invalidation occurs for registered views or during a subsequent load through [prepareIndexStateLoadLocked:311](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:311). Commit does not process unresolved clear history.

   Reproduction: warm a shared cache for an **empty, cacheable store with DISABLED index I**. In a fresh context, call `ClearRange(ss.Sub(IndexStateSpaceKey))` and commit **without opening the store**. No view exists, so the metadata stamp remains unchanged. A later cached Open accepts the old DISABLED map although the absent persisted key means READABLE. Saving a record skips index maintenance; a cold uncached reopen sees READABLE with missing index entries. State-key conflicts cannot catch a clear committed before this transaction began.

   **Required:** make state-clear invalidation durable before the clearing transaction commits, using a store-aware mechanism if necessary. Add the clear-only transaction to the warmed-cache regression, asserting stamp invalidation, maintenance and committed scan results. Both current variants [open within the clearing transaction](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state_test.go:2857), masking this gap. Preserve ordinary record-clear negative controls.

2. **[P1] Reload introduces a registry/state mutex deadlock with uniqueness cleanup.**

   [ReloadRecordStoreState:1896](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1896) acquires `indexStateMu`, then waits for `stateMu`. Record maintenance already holds [stateMu.RLock:1012](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1012). When deleting or changing one of two duplicate records in a WRITE_ONLY or READABLE_UNIQUE_PENDING unique index, the [maintainer:329](/home/birdy/projects/fdb-go/pkg/recordlayer/index_maintainer.go:329) invokes survivor cleanup, which calls [context.ClearRange:1361](/home/birdy/projects/fdb-go/pkg/recordlayer/store.go:1361) and waits for `indexStateMu`.

   Thus maintenance can hold `stateMu` waiting for the registry while reload holds the registry waiting for `stateMu`. Transaction cancellation does not release these Go mutexes.

   **Required:** remove this reverse acquisition while preserving atomic reload publication and pending-version cleanup. Add a deterministic real-FDB interleaving between survivor cleanup and reload on the same handle. The retained reload/clear test does not exercise maintenance holding `stateMu`.

3. **[P2] The new invalidation bypasses header-aware deletion policy.**

   [index_state.go:340](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state.go:340) unconditionally bumps the global metadata stamp for an overlapping registered state region.

   Open an existing noncacheable store, then call `DeleteStore` in that context. [DeleteStore:170](/home/birdy/projects/fdb-go/pkg/recordlayer/store_api.go:170) correctly decides that no bump is required, but its range clear reaches this unconditional bump because Open now registers a view. Deleting an opened noncacheable store therefore invalidates caches across the database.

   This contradicts the explicit [approved design:50](/home/birdy/projects/fdb-go/rfcs/257-java-upgrade-audit/ws-b-design.md:50) and tagged Java’s [deleteStoreAsync:1886](/home/birdy/projects/fdb-go/fdb-record-layer/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/FDBRecordStore.java:1886).

   **Required:** preserve the header-aware stamp decision through clearing and subsequent clear-history processing. Add opened-noncacheable delete and delete/recreate cases asserting unchanged global stamp, alongside cacheable/malformed positive controls.

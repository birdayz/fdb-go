1. **P1: Bulk deletion still skips disabled indexes without a state conflict, allowing orphan entries after a rebuild.**

   [store_delete_where.go:53](/home/birdy/projects/fdb-go/pkg/recordlayer/store_delete_where.go:53) uses `getIndexStateLocked`, bypassing the new transaction-visible state reader. Store opening does not supply the missing protection: index states are loaded with snapshot isolation at [store_state_cache.go:275](/home/birdy/projects/fdb-go/pkg/recordlayer/store_state_cache.go:275).

   Concrete sequence: transaction D opens with original index O disabled. Transaction B explicitly rebuilds O while its replacements remain unready, then commits. D executes `DeleteRecordsWhere` using its cached disabled state, skips O, and clears the selected records. D has neither read O’s state serializably nor included O in its index-clear actions. B’s earlier record reads cannot prevent D’s later commit. The result is a readable O containing entries for deleted records.

   Java’s bulk-delete filter calls `getIndexState` at [FDBRecordStore.java:2035](/home/birdy/projects/fdb-go/fdb-record-layer/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/FDBRecordStore.java:2035), which registers the state conflict at line 4242.

   **Required:** use the error-returning transactional state gate before every bulk-delete skip. Add real-FDB coverage for both commit orders, cold/cached opens, and two store objects sharing one context. Assert both commit outcomes and surviving record/index bytes.

2. **P1: Direct query and vector scan paths bypass the new lifecycle gate and can scan an index already made unreadable in the same context.**

   The query executor checks cached state at [executor.go:824](/home/birdy/projects/fdb-go/pkg/recordlayer/query/executor/executor.go:824), then invokes `maintainer.Scan` directly at [executor.go:470](/home/birdy/projects/fdb-go/pkg/recordlayer/query/executor/executor.go:470). Vector entry points retain cached checks at [vector_index_maintainer.go:1338](/home/birdy/projects/fdb-go/pkg/recordlayer/vector_index_maintainer.go:1338) and line 1381.

   Open handles A and B for the same context/subspace while an index is readable. Through B, call `ClearAndMarkIndexWriteOnly`. A retains cached READABLE. A’s direct query scan therefore accepts the index and scans its now-cleared data, potentially returning an empty result while matching records remain. The corrected `ScanIndex` rejects this same operation. This is exactly the multiple-store-object contract tested for only three scan routes at [index_state_test.go:1121](/home/birdy/projects/fdb-go/pkg/recordlayer/index_state_test.go:1121).

   **Required:** centralize the error-returning, transaction-visible state gate across these dispatch paths, preserving queries’ stricter READABLE requirement. Extend the existing stale-handle, state-read-error, and refused-scan conflict tests to these routes. Audit the same cached selection pattern in [record_function.go:71](/home/birdy/projects/fdb-go/pkg/recordlayer/record_function.go:71) and [aggregate_function.go:219](/home/birdy/projects/fdb-go/pkg/recordlayer/aggregate_function.go:219).

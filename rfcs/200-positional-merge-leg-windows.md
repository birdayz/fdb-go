# RFC-200 — A merged leg is a NESTED row, and the layout authority must say so

Status: **proposed**, revision 1 — awaiting the query-engine joint-review ACK
(Graefe + Torvalds) before implementation starts.
Closes: the `legIsOrdinalSafe` half of CQ-53 phase 3; advances the
`DIVERGENCES.md` retirement condition for the runtime binding-namespace widening
(`executor.bindMergedOuterLegs`).

Every number in this document is one run of the whole real-FDB sqldriver corpus
at `f50cee43e`, recorded in TODO.md's CQ-53 PHASE 3 block (measured on branch
`feat/cq53-parent-chained-binder`, HEAD `4dccc50f0`). Line citations are verified
at that HEAD for `rule_implement_nested_loop_join.go` (the one file that moved
between `f50cee43e` and `4dccc50f0`) and at `f50cee43e` for everything else.

## The defect, measured

Go's EXISTS-over-join lowering is two-level — a step-1 nested-loop join whose
merged row the step-2 FlatMap ranges over. **All 174 leg-correlated reads on that
path pass through un-re-anchored.** `MergedReAnchor` in the leg-local bakeability
census is `0 of 174`; every one takes the leg-alias pass-through
(`rule_implement_nested_loop_join.go:2899-2903`), which is the arm that consumes
the Go-only runtime namespace widening this whole line of work exists to retire.

The decline census, per firing of `implementJoinWithExistential`:

```
DECLINE correlatedStep1                                    108
DECLINE reconstruct nil (left=FlatMap right=Scan)           77
DECLINE reconstruct nil (left=Scan  right=FlatMap)          77
DECLINE rv does not reference exist alias                  200
ACCEPT                                                      78
```

**The 108 `correlatedStep1` declines are PERMANENT and OUT OF SCOPE.** They are
settled by a prior architecture ruling (TODO.md:6229-6249): a WHERE-EXISTS
correlating into a leg buried in an inner join is the canonical semijoin, its
good plan is a SARG'd correlated index scan under the FlatMap, and that
*requires* name binding to flow the sibling comparand into the index. Java binds
every correlation by name and has no positional-correlation concept, so the
ordinal seed is a Go-only optimization for the independent-legs materialized-NLJ
case and this shape stays name-model, permanently. This RFC does not touch it,
does not shrink it, and treats any movement in it as a regression (see §7).

The 200 `rv does not reference exist alias` declines are not a residue either.
They are `foldStep1Seed`'s condition (2)
(`rule_implement_nested_loop_join.go:2270`): a WHERE-EXISTS whose projection sits
*above* the existential level has no folded projection to seed. There is nothing
to fold, and folding is what the seed is for.

**What is left is the 154, and the finding is what those legs flow.**
`reconstructFoldStep1Seed` returns nil (`:2077-2079`) because `legIsOrdinalSafe`
(`:1956-1986`) has no case for `*plans.RecordQueryFlatMapPlan` and falls through
to `default: return false` at `:1981`. Split by what the declined FlatMap leg's
result value is:

```
rv=*values.QuantifiedObjectValue        x94   (identity pass-through)
rv=RC(2) [QOV-record:2]                 x60   (a nested UNNAMED merge)
```

**The 60 are Java's own merged row, built by Go, and declined by Go's own layout
authority.** `RC(_i: QOV(leg_i))` is `PartitionSelectRule.java:284-291`'s
`RecordConstructorValue.ofColumns(… Column::unnamedOf)` verbatim — one unnamed
column per collapsed lower quantifier, each holding that quantifier's *whole*
row — and Go builds it 1:1 in `positional_merge.go`'s `positionalMergeCase`
(`:122-125`, names minted as `values.OrdinalFieldName(i)`, the `_i` spelling
Java's `Type.java:2922 isAutoGenerated` describes). `values.OrdinalSeedLegWindows`
names "positional-merge" as a declined class in its own doc
(`ordinal_seed_layout.go:58`) and the decline fires at `:129-132`: a bare QOV
field is not a `*FieldValue`, so the walk bails.

With `reconstructFoldStep1Seed` nil, `foldStep1Seed` returns
`(sel.GetResultValue(), false)`, `ordinalSeedLegWindowsOf(step1RV)` is nil at
`:3759`, and all three rebase sites take the lazy path with `legLayout=nil`
(`:3796`, `:3847`, `:3909`). The step-1 result values that survive to it are
folded projections carrying an `ExistsValue`
(`RC(1)[ExistsValue] x26`, `RC(2)[ExistsValue,FV-multi] x48`,
`RC(2)[ExistsValue,FV-unpinned] x80` — 154, exactly the declines), so there is
nothing for the layout authority to read *there* either. The gap is upstream, at
the leg.

## Why this is not a missing capability

Java needs no window machinery at all, and the reason is the whole design.

Java's row is a protobuf `Message` tree. `RecordConstructorValue.eval`
(`RecordConstructorValue.java:113-138`) sets **one proto field per child**, whole
(`:124`, `:133`) — leg *i*'s entire record Message goes into slot *i*. A
reference to a collapsed sibling is rewritten by `PartitionSelectRule` to
`FieldValue.ofOrdinalNumber(QuantifiedObjectValue.of(newUpperQuantifier), index)`
(`PartitionSelectRule.java:301-302`), replayed over the predicates
(`:310`) and the result value (`:315`). Evaluating that is a binding lookup
(`QuantifiedObjectValue.java:82-95` — `context.getBinding(CORRELATION, alias)`,
returning `binding.getMessage()` for a record) followed by an ordinal walk
(`FieldValue.java:163-175` → `MessageHelpers.getFieldValueForFieldOrdinals`,
`MessageHelpers.java:93-107`), which descends intermediate steps as sub-Messages
and returns the final field — a whole Message when the field is of message type.
**Nesting is free; a one-step path over the merge returns the leg's whole
record.**

And composition is a path FUSION, never a flattening. When
`translateCorrelations` rebuilds an enclosing `FieldValue(QOV(lower), [f])`, the
leaf swap produces `FieldValue(FieldValue(QOV(upper),[i]), [f])`, and
`ValueWithChild.withChildren` → `FieldValue.withNewChild`
(`FieldValue.java:159-161`) → `ofFieldsAndFuseIfPossible` (`:326-332`) merges the
two accessor lists via `FieldPath.withSuffix` (`:525-534`) into the single
two-step path `FieldValue(QOV(upper), [i, f])`. Nothing is materialized, nothing
is re-offset.

**The negative was checked, not assumed.** The only row-flattener anywhere in
Java's cascades tree is `GroupByExpression.flattenedResults`
(`GroupByExpression.java:764-790`), the deliberate counterpart to `nestedResults`
(`:752-761`), and it flattens the `(groupingKey, aggregate)` pair for aggregate
index matching. It is never applied to a `PartitionSelectRule` merge. Java's
merged row stays nested, always.

**Go's executor already speaks this shape at runtime.** This is the load-bearing
measurement behind the decision, and it is entirely present in `f50cee43e`:

- `newOrdinalJoinBuild` (`executor/ordinal_join.go:1176-1272`) *enables* on
  `values.IsPositionalMergeRC` (`:1184`) — a second trigger beside
  `ContainsBakedOrdinal`, added precisely because "the lowest merge level carries
  no baked refs at all, but its rows must build positional: the level above reads
  them by ordinal";
- it types each bare-QOV field from the leg's own QOV (`:1243-1261`) and derives
  the built row type through `rcOutputType` (`:986-1030`), which emits **one slot
  per RC field** and — because its leg-table loop requires a `*FieldValue`
  (`:1003-1007`) — emits a **leg table of length 0** for this shape;
- `WindowsOK` is **false** for it: `ordinalJoinSpans` declines the positional
  merge on both arms, and `unnestMixedSeedSpans` says so in its own doc
  (`:89-92`, "the positional-merge RC (whose bare QOVs are over RECORD leg
  types)");
- at evaluation, each `_i` field is a bare QOV whose binding is the leg's adapted
  `OrdinalRow` (`evaluateBound` `:1581-1586`), so **slot `i` of the built
  `PositionalRow` holds the leg's whole row object**;
- and reading into it already works: `FieldValue.descendResolvedPath`
  (`values/values.go:825-872`) has an explicit `case OrdinalRow` arm (`:844-849`)
  that descends a nested step **by ordinal**.
- The executor's *span* side already resolves the fused two-step address:
  `resolveSpanLeaf` (`executor/ordinal_join.go:301-349`) descends `legRVs` — "the
  positional-merge RC mapping `_i` → `QOV(leg)`" — for a multi-accessor pinned
  path, and composes accessor lists at `:343-345`, which is
  `ofFieldsAndFuseIfPossible` by another name.

Go also has the planner-side primitives: `FieldPath.WithSuffix`
(`values/values.go:502-522`, documented as Java's `FieldPath.withSuffix`) and
`NewFieldValueOfOrdinal` (`:1347`, documented as `FieldValue.ofOrdinalNumber`),
which over a merge QOV whose field *i* is a leg `*RecordType` yields a node typed
with that leg's record type — exactly the child a suffix fuses onto.

So: nested addressing is the shape Go's runtime already produces and already
reads. **The single thing that cannot express it is the planner's layout
authority**, whose `OrdinalSeedLegWindow.Offset` means "offset into a flat
concatenated row" and nothing else.

## Decision

### 1. The layout authority learns a NESTED window kind. It does not learn to flatten.

`values.OrdinalSeedLegWindows` gains a branch for the positional-merge row, and
`finalizeSeedWindows` gains the ability to emit a sub-window that addresses a
whole slot rather than a sub-range. Two entry points, and they compose:

**(a) The merge row read directly.** Handed an RC that satisfies
`values.IsPositionalMergeRC` (`values/values.go:643-663` — every field
auto-generated-named `_i` in position order, every value a bare QOV of a
*distinct* quantifier), the authority returns one window per slot:

```
OrdinalSeedLegWindow{Kind: nested, Offset: i, Typ: leg_i's *RecordType, Alias: leg_i}
```

`Offset` is the FIELD INDEX of the slot holding the whole leg row, not the first
column of a run. This is what `planBuriedLegConcat`'s new FlatMap arm consults.

**(b) The step-1 seed built over such a leg.** `reconstructFoldStep1Seed` emits
`ofOrdinal(QOV(leg, rt), j)` for each `j` in the leg's row. When `rt` is the
merge's nested type, slot `j` of that run holds sub-leg *j*'s whole record — so
the *top-level* run walk (`ordinal_seed_layout.go:129-166`) already accepts it
unchanged (every field a frontier-pinned single-accessor `FieldValue` over a leg
QOV, consecutive, full coverage). What must change is `finalizeSeedWindows`
(`:196-364`): today it derives buried sub-windows from `w.Typ.Legs` as flat
sub-ranges `[Start, Start+Width)` (`:288-315`). A nested sub-leg occupies exactly
one slot and a read into it must DESCEND, so it emits

```
OrdinalSeedLegWindow{Kind: nested, Offset: w.Offset + leg.Start, Typ: sub-leg's type, Alias: leg.Alias}
```

**Mixed merge rows are real and must be handled.** `positional_merge.go:190-202`
measures 18246 merge slots over the corpus: 17492 typed by the quantifier, 4
scavenged, **750 stating nothing at all**, and every distinct witness of the 750
is an unnest ELEMENT alias (an array element type Go does not infer). So a merge
row can legitimately carry both record legs and scalar elements. The nested
branch therefore requires a slot's QOV to flow a `*RecordType` to produce a
NESTED window; a non-record slot keeps the existing element treatment (a
synthesized 1-field window, `Kind: flat-run`, width 1, `Offset + 0` — numerically
identical to what it produces today). A branch that admitted an untyped slot as a
nested leg would inherit the width hazard
`leg_layout_derivation_test.go:112-138` documents; a branch that treated a typed
record leg as an element would give a multi-column leg a ONE-column window, which
is that same hazard from the other side.

**Rejected: flatten at materialization.** It keeps the flat window contract
uniform, and that is its only virtue. It contradicts Java's semantics twice over
— accesses FUSE (`FieldValue.java:326-332`), Java's own row-flattener is
group-by-specific and never reaches a merge — and it contradicts Go's own runtime
representation, which puts an `OrdinalRow` in the slot today. Adopting it would
mean a new materialization pass in the executor, re-derived offsets on both sides
of the planner/executor contract, and a divergence from `newOrdinalJoinBuild`'s
existing `IsPositionalMergeRC` trigger that would have to be justified rather
than inherited. The cheapest-looking option is the one that changes the most.

### 2. The kind is an EXPLICIT discriminator. It is never inferred.

`OrdinalSeedLegWindow{Offset, Typ, Alias}` (`ordinal_seed_layout.go:15-53`)
currently means one thing. Overloading `Offset` to mean "field index" in some
windows and "run start" in others, with the reader distinguishing them by
`len(Typ.Fields) == 1` or by whether the field type is a record, is the
wrong-offset wrong-rows failure this authority was consolidated to prevent. A
1-column flat leg whose one column is a struct is shape-identical to a nested
leg. **The kind is a stored field, set by the producer, read by every consumer.**

The discriminator lives in two places, because the layout crosses two carriers:

- `OrdinalSeedLegWindow.Kind` — the planner's rebase authority;
- `values.RecordTypeLeg` (`values/type.go:372-…`), which is `{Alias, Name, Start,
  Width}` and today can express only a flat `[Start, Start+Width)` boundary. It
  is what carries sub-leg boundaries on a leg's own row type into
  `finalizeSeedWindows`, and onto the merged row type consumed by the executor's
  runtime binders. It gains the same explicit kind, sourced at construction like
  `Alias` is, and excluded from identity exactly as `RecordType.Legs` already is
  (`type.go:366` — "carries NO identity semantics").

**What the discriminator means at every keyed reader.** All five are enumerated
in `values/seed_window_reader_census.go:68-101`; each is listed with what it does

### 3. ONE accept predicate, extended bit-for-bit, shared with the executor twin.

The planner walk (`values.OrdinalSeedLegWindows`) and the executor span twin
(`executor.ordinalJoinSpans` / `unnestMixedSeedSpans`) walk independently, and a
disagreement about which field is a leg and which is an element shifts the offset
of every field after it. That is why the element test is ONE function
(`values.IsMixedSeedElementType`, `ordinal_seed_layout.go:406-412`) and why
`pkg/docscheck`'s `TestSourceCommentHygiene` sibling
`mixed_seed_element_authority_test.go` structurally bans a discarded
`*RecordType` assertion inside the two layout files — because folding two copies
into one already missed a third copy in `resolveSpanLeaf`, and prose asserting
agreement does not notice when one copy is edited.

**The nested kind extends that SHARED predicate, in the same file, under the same
ban.** The recognizer is `values.IsPositionalMergeRC` (already exported, already
the executor's build trigger at `ordinal_join.go:1184`) plus the per-slot record
test that routes a slot to nested-leg or element. Neither side gets a private
copy.

The executor side owes three changes, all twins of the planner's:

- `unnestMixedSeedSpans`' decline note (`ordinal_join.go:89-92`) — "the
  positional-merge RC (whose bare QOVs are over RECORD leg types)" — **retires
  with this work**. That sentence is the executor stating, correctly, that it
  declines the exact shape this RFC admits.
- `mergedLegsOfSpans` (`:271-287`) emits sub-legs at `s.Offset + sub.Start`; it
  must carry the kind through, like the `Alias` it already carries verbatim
  ("A REBASE, not a re-mint").
- `resolveSpanLeaf` (`:301-349`) already descends `legRVs` for the fused path.
  What it gains is nothing: it is the runtime proof that this address is
  resolvable, and its existing coverage is the strongest evidence in this RFC
  that the design is not new machinery.

`span_window_cross_agreement_test.go` grows a NESTED matrix — the pristine
(`:145`), mixed (`:341`) and box-leg (`:445`) fixtures joined by a nested-merge
fixture and a mixed nested/element fixture, each asserting the two walks produce
identical `(Alias, Kind, Offset, Typ)` for every window, and identical DECLINES
for every rejected shape.

### 4. `legIsOrdinalSafe` and `planBuriedLegConcat` move in LOCKSTEP.

`legIsOrdinalSafe` (`:1956-1986`) gains a `*plans.RecordQueryFlatMapPlan` arm,
and its acceptance is CONDITIONAL: the FlatMap's `GetResultValue()` must be a
window-derivable merged row — the positional merge, recognized structurally.
`planBuriedLegConcat` (`:1997-2060`) has the same node census by construction
(they are the predicate and the layout for one question) and gains the matching
arm: the leg's concat is its N merge slots, each field typed with that sub-leg's
`*RecordType`, and its `.Legs` records each sub-leg at its slot as a NESTED leg.
A FlatMap whose result value is anything else keeps declining.

The plan walk is the route and not a preference: `RecordQueryFlatMapPlan.
GetResultType()` returns `values.UnknownType`
(`plans/flat_map.go:86`), exactly as `RecordQueryNestedLoopJoinPlan`'s does
(`plans/nested_loop_join.go:140`) — which is why `reconstructFoldStep1Seed`'s own
comment says `GetResultType()` cannot be used for a join leg (`:2088-2089`).

**Three existing pins constrain this arm, and all three must stay green:**

- `exists_join_fold_seed_test.go:107-111` — "a name-model join leg must NOT be
  ordinal-safe". Its fixture is a `RecordQueryNestedLoopJoinPlan` with a **nil**
  result value; `legIsOrdinalSafe`'s NLJ arm requires a `*RecordConstructorValue`
  (`:1977-1979`). Adding a FlatMap arm gated on the positional merge cannot weaken
  it, and `:114-116` (the reconstruction declining over that leg) follows.
- `leg_layout_derivation_test.go:103-109` pins that a **2-slot RC of bare TYPED
  leg QOVs is DECLINED** by `OrdinalSeedLegWindows`. That is the shape *family*
  this RFC admits, and the pin stays green only because its fixture names the
  fields `"A"`/`"B"` while `IsPositionalMergeRC` requires `_i` in position order.
  **This is a hard constraint on the discriminator**: the nested branch is keyed
  on the FULL structural recognizer, never on the looser "every field is a bare
  typed QOV". The pin's failure message must be updated in the same change to say
  what it now guards — a NAMED typed-leg RC is still not a merge row — rather
  than left describing a decline that has become conditional.
- `plan_leg_concat_layout_test.go` and
  `executor/leg_layout_cross_agreement_test.go` pin
  `cascades.PlanLegConcatLayout` (the exported wrapper over
  `planBuriedLegConcat`, `:2522-2535`) against the runtime's
  `concatLegPositionals`. That agreement is why `PlanLegConcatLayout` is exported
  at all. A FlatMap arm that states a nested concat the runtime's merge does not
  produce is precisely the drift those pins exist to catch, so the nested case
  joins that fixture.

### 5. Success is measured at the ORDINAL path, not at `mergedReAnchor`.

This is the subtlety that would otherwise make a working change look like a
failed one.

`MergedReAnchor` counts ARM 1 of `rebaseOuterLegValue`
(`rule_implement_nested_loop_join.go:2883-2892`, recorder at `:2885`). When
`ordinalSeedLegWindowsOf(step1RV)` turns non-nil, the rule does not call
`rebaseOuterLegValue` at all — it takes `rebaseOuterLegRefsOrdinal` (`:3781`) for
the predicates and `rebaseOuterLegValueOrdinal` (`:3904`) for the projection,
which are a DIFFERENT function in a different file. And when
`gatedSeedStep1` is true, the projection is not rebased at *any* site
(`:3889-3898`): the step-2 cursor evaluates it over the merged row through
`legWindowRowContext`. **So `MergedReAnchor` may remain `0 of 174` on complete
success**, and reading it as the activation signal would report this work as
having done nothing.

The honest instruments, named exactly:

- **`foldStep1Seed`'s ACCEPT count.** This is the primary signal and it does not
  currently exist as a standing instrument: the `108/77/77/200/78` breakdown
  above came from "a call-site probe added for this question and removed after"
  (TODO.md's own words). Re-adding it is part of this work, not a follow-on —
  a standing outcome census at `foldStep1Seed` with the classes the removed probe
  produced (`ACCEPT`, `DECLINE correlatedStep1`, `DECLINE rv-no-exist-ref`,
  `DECLINE reconstruct-nil`), the reconstruct-nil class sub-classified by leg
  shape (bare QOV / positional merge / other), gated by
  `values.LegIdentityCensusEnabled` and asserted from the sqldriver `TestMain`
  beside its siblings (`embedded_fdb_test.go:101-169`). It lands FIRST (§Sequencing

### 6. Producer-first: the dotted readers, analyzed one at a time.

  innerKey`). Its counterparty is the inner scalar key

- **`ordinal_seed.go:794`** (`legRef`'s `strings.Contains(fv.Field, ".")`). It is

## Rejected alternatives

**Flatten the merged row at materialization.** Covered in Decision §1. It is the
option that keeps one contract shape and pays for it by contradicting Java's
evaluation model, Go's runtime representation, and the executor's existing
`IsPositionalMergeRC` build trigger — and by requiring a new materialization pass
plus re-derived offsets on both sides of a planner/executor contract whose entire
history is drift.

**Reuse `Offset` and infer the kind at the reader.** `len(Typ.Fields) == 1`,
`Typ` being a record, `Width == 1` — every candidate is satisfied by a legitimate
flat leg. A 1-column leg whose column is a struct is shape-identical to a nested
one. The inference is silent when wrong, and what it is silently wrong about is
which column a read addresses. This is the same class as the `Alias`-less
`RecordTypeLeg` hazard `finalizeSeedWindows:222-224` fails loud on today.

**Key the nested branch on "every field is a bare typed QOV".** Simpler, and it
turns `leg_layout_derivation_test.go:103-109` red — a pin that exists because
admitting such a constructor once gave multi-column legs one-column windows. The
full `IsPositionalMergeRC` recognizer (auto-generated `_i` names in position
order, bare QOVs, distinct correlations) is Java's own shape
(`PartitionSelectRule.java:284-291`, `Type.java:2922`) and is documented as
unconstructible from SQL (`values/values.go:639-640`). Recognize the shape Java
mints, not a superset of it.

**Re-anchor the leg through a qualified `QOV(merged)."LEG.COL"` name.** Already
dead, deliberately: the mint was deleted in phase 3, ARM 1 now names its node
`values.OrdinalFieldName(ord)`, and Java's re-anchored accessor has no name at
all — `FieldValue.ofOrdinalNumber` (`FieldValue.java:335-338`) builds `new
Accessor(null, ordinalNumber)`, resolved against a `Field.unnamedOf`
(`Type.java:2918-2919`) whose `ResolvedAccessor.getName()` is null
(`FieldValue.java:657-659`). Reviving it here would re-open the exact RFC-197
channel this line of work closed.

**Teach only the executor and leave the planner declining.** The executor already
handles the shape; the temptation is to conclude nothing is needed. But the
planner is where the DECISION is made — `legIsOrdinalSafe` refusing the leg is
what keeps 154 reads on the pass-through. An executor that can read a layout no
planner states is what the current 60 already are.

**Widen `RecordTypeLeg` by adding a second parallel leg table for nested legs.**
Two tables mean two producers, two readers, and a precedence question at every
consumer. The kind is one bit on the entry that already exists.

- **3a — the instrument, first.** The standing `foldStep1Seed` outcome census

  asserted. Its four classes must sum to the arm's firings. Nothing else changes,
  so its baseline is directly comparable to the phase-3 probe's numbers.
  *Also measured here, because it is an INFERENCE today and must become a
  measurement:* that all 60 declined positional-merge legs satisfy
  `IsPositionalMergeRC` and not merely "two bare QOVs over record types" — the
  removed probe recorded value shapes, not field names, and the identification
  rests on `positionalMergeCase` being the sole producer.
- **3b — the discriminator, with no new acceptance.** `OrdinalSeedLegWindow.Kind`

  every consumer switches on it explicitly, both walks updated together under the

- **3c — the nested branch in the layout authority.** `OrdinalSeedLegWindows`

## Acceptance gates

**(a) An END-TO-END WRONG-ROWS probe, on a shape where leg offsets and merged
offsets DISAGREE.** Cross-agreement of two walks is necessary and not sufficient
— two walks of the same wrong model agree perfectly. The fixture is a multi-leg
EXISTS whose merged row would produce DIFFERENT ROWS under a wrong window:
distinct leg widths so `Offset + legOrdinal` and the nested two-step address
resolve to different slots, at least one duplicate column NAME across legs so a
name fallback cannot rescue a wrong ordinal, and the projected value drawn from a
non-first leg at a non-zero leg-local ordinal. Rows asserted, not just plan shape.
Mutated in BOTH directions separately: (i) the nested window read as flat
(`Offset + legOrdinal`) must go red on rows; (ii) the flat window read as nested
must go red on rows. A fix with two independent failure directions needs two
mutations.

**(b) The 1M stress before and after, with real plan movement EXPECTED.**
`foldStep1Seed`'s ACCEPT population grows by up to 60 firings, so plans change —
that is the point. Every moved `EXPLAIN` golden and every plandiff record is
justified line by line WITH ROW COUNTS, never blanket re-blessed. A cost or shape
change that makes a plan worse is a regression this RFC would otherwise hide.
Results recorded in TODO.md's baseline table.

**(c) Censuses stay green, or retire WITH their channels.** Concretely:
`Declined` stays 0; both seed-window hard zeros stay 0; all five reader floors
hold; the leg-local bake cross-check
(`IdentityInLegDomain == Baked + MergedReAnchor`) holds; the merged-leg binding
activation criterion holds; the leg-column provenance census does not move
(§5 — a movement means the scalar-seed channel was touched);
`MergeSlotTypeDisagreements` stays 0. `rule_select_merge.go:234`'s `len(w) > 2`
gate is RE-MEASURED explicitly, because a nested merge leg changes window count
and that gate is the one consumer reading cardinality rather than nil-ness.

**(d) The DIVERGENCES.md:105 retirement condition advances MEASURABLY, and the
remainder is stated.** The condition is that a leg-correlated read be rewritten
to `ofOrdinalNumber` against the merged quantifier before execution — Java's
`PartitionSelectRule` — so no sibling alias need be resolvable at runtime. Of the
174:

- **60 are covered by this work** (the positional-merge legs), moving from the
  leg-alias pass-through to the ordinal path;
- **94 remain** — the bare-QOV legs, see §Residues;
- **108 remain permanently** — `correlatedStep1`, by the ruling in §The defect.

So the retirement is not completed by this RFC and this RFC does not claim it is.
What it claims is that the largest addressable block closes and the remainder is
named, measured, and attributable.

## Residues, measured and OUT OF SCOPE

**The 94 bare-QOV legs.** A FlatMap leg whose result value is a bare
`*values.QuantifiedObjectValue` — Java's single-live-lower arm
(`PartitionSelectRule.java:274-276`, flowing `quantifier.getFlowedObjectValue()`,
which Java types unconditionally at `Quantifier.java:801-803`). Go mints this
shape UNTYPED in at least one place on this very path:
`rule_implement_nested_loop_join.go:3879` builds
`values.NewQuantifiedObjectValue(mergedOuterCorr)` — the untyped constructor
(`values/values.go:4340`), not `NewQuantifiedObjectValueOfType` (`:4354`). A bare
QOV is not an RC, so `ordinalSeedLegWindowsOf` returns nil at its type assertion
(`left_outer_existential.go:277-280`) before any derivation runs, and an untyped
one states no row for anything to derive FROM. **This is CQ-63's machinery
applied one site further:** typing the identity result value the way Java always
has. It is a separate change with its own blast radius (it changes what 94 legs
state to every consumer of a FlatMap's result value), and it is named here rather
than absorbed. It is not blocked — the leg-derivation census reports
`underivableLegs 0 of 960`, so every leg already states its row where a
quantifier is asked.

**The 200 `rv does not reference exist alias` firings are CORRECT
pass-throughs, not a residue.** A WHERE-EXISTS whose projection sits above the
existential level has no folded projection; `foldStep1Seed`'s condition (2) is
doing its job.

**The `26 + 48 + 80` step-1 result-value shapes are a CONSEQUENCE, not an
independent population.** They are what survives as `step1RV` after the 154
declines (26+48+80 = 154), and they are folded projections carrying an
`ExistsValue` — not merged rows, which is why the layout authority has nothing to
read at that point either. When 60 of the declines become ACCEPTs, this
distribution shrinks with them; it is not separately actionable.

**Untyped merge slots (750 of 18246).** Every distinct witness is an unnest
element alias whose array element type Go does not infer that far
(`positional_merge.go:190-202`, and the same gap
`values.IsMixedSeedElementType:399-405` documents about its own predicate). Under
the nested branch these keep the existing element treatment. Typing the unnest
element quantifier is a planner-wide change and is not a rider here.

## What this does not do

It does not retire the runtime binding-namespace widening — 94 + 108 of the 174
still take the pass-through, and `executor.bindMergedOuterLegs` stays. It does
not touch the correlated-index EXISTS name path, which is permanent and
Java-correct. It does not retire `RecordTypeLeg.Name`, whose two surviving
readers are dotted-text readers blocked at their producers (CQ-52). It does not
touch the correlated-scalar ordinal seed, whose `LEG.COL` field names feed the
executor's last dotted arm — that is a separate producer-first line, and this
RFC's §5 makes "did not touch it" a checkable prediction rather than an
assurance.

What it does is smaller and exact: it stops Go's own layout authority from
declining the merged row Go's own planner builds and Go's own executor already
evaluates — the one Java has built since `PartitionSelectRule` was written.

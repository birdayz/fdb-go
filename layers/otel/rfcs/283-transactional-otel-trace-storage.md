# RFC-283: Serve transactional OTel traces with exact custom-attribute indexes

**Status:** Proposed production design; a bounded immutable kernel and diagnostic measurements exist, not a full implementation or production validation.

**Reference:** FoundationDB 7.3.77; Java Record Layer 4.14.2.0; repository base `a7349ff657e1448a4f6937535129cfdb5afafcda`.

**Semantic reference:** OpenTelemetry GenAI Development snapshot `e19717d65f890955777b044bca2a3cd71ae8b498`, observed 2026-10-27; not a released SDK contract.

**Research:** [OTel/GenAI](../research_notes/Transactional%20OTel%20trace%20storage/otel-genai.md), [competitors](../research_notes/Transactional%20OTel%20trace%20storage/competitors.md), [FDB design](../research_notes/Transactional%20OTel%20trace%20storage/fdb-design.md), [repository feasibility](../research_notes/Transactional%20OTel%20trace%20storage/repository.md).

**Decision synthesis:** [Research report](../reports/Transactional%20OTel%20trace%20storage.md).

## 1. Decision and evidence boundary

Build a **Record Layer–owned transactional serving tier**, initially using stable per-span records and one exact posting per admitted attribute occurrence. Maintain the record, revision, equality/range postings, trace/session/graph witnesses and expiry bookkeeping in the same FDB transaction. All eligible scalar custom attributes get equality coverage; all eligible numeric scalars get typed range coverage. GenAI names receive useful semantic projections, not exclusive access to indexing. Use a purpose-built typed executor for span, trace and session semantics, and improve reusable Record Layer extension points rather than bypassing the layer or forcing this physical format through ordinary VALUE scans.

The competitive hypothesis is narrow: fresh, selective tenant-scoped retrieval, arbitrary identifiers, bounded trace/session navigation and predictable correction/deletion visibility could beat a well-tuned ClickHouse deployment at a useful latency/cost frontier. **There is no measurement establishing that hypothesis.** Broad scans, group-bys, quantiles and inexpensive long retention are credible ClickHouse/object-storage strengths. Keep compressed immutable history and an analytical replica as measured alternatives, not promises of future compression that justify an expensive hot design today.

The repository is explicitly **pre-1.0 and not declared production-ready**. The research sources establish transaction/lifecycle primitives, not production capacity or best-in-class latency. At the original research stage, no prototype or benchmark had been run: ownership of the observed local FDB container and a usable ClickHouse comparator had not been established. A bounded immutable [executable kernel](../cmd/otelbench) has since been exercised; its [scope and exclusions](../README.md#implemented-semantic-class), retained [10k diagnostic receipts](../bench/evidence/2026-10-27/diagnostic-10k/) and [pipelined 100k receipts](../bench/evidence/2026-10-27/pipeline-100k/README.md) describe that narrower evidence. These single-node, closed-loop diagnostics do not implement the full proposal or establish sustainable ingest capacity, query tails under concurrent load or comparative production cost. ([Repository status](../../../STATUS.md), [repository investigation](../research_notes/Transactional%20OTel%20trace%20storage/repository.md))

### Proposed envelope, not supplied requirements

The owner has not supplied traffic, retention, budgets, privacy obligations or approved SLOs. Initial experiments should sweep 10M/100M/1B retained spans where feasible, 1-hour/1-day/30-day windows, and sustained ingestion through saturation; those populations are not product commitments. A candidate selective-serving objective is p99 below 100 ms for point-trace retrieval of bounded traces and newest-100 rare-attribute results, with p99 durable-ack-to-query-visible below 1 second and p99.9 below 5 seconds. A successful span commit is already atomically searchable at a sufficiently new read version; these visibility objectives measure the surrounding service, routing and caches. They do not relax index atomicity or promise a complete trace. Approve actual workload/SLO/cost envelopes before treating any numerical threshold as an acceptance requirement.

## 2. Preserve observability semantics before optimizing them

### 2.1 The record boundary is a span, not a flattened tag bag

Logical span identity is `(authenticated tenant/project namespace, trace_id, span_id)`. OTLP uses a 16-byte trace ID and an 8-byte span ID; span IDs are unique within a trace. Preserve resource, instrumentation scope, span, event and link namespaces; both schema URLs; scope name/version; typed `AnyValue`; flags/tracestate; status/kind; timestamps; parent; links; events in source order; drop counters; field presence, open enums and unknown protobuf fields. Literal key `a.b` is not path `a -> b`. Events can have timestamps outside the span interval. Links are not additional parents. ([OTLP trace definition][O1], [common values][O0], [trace API][O2])

Store a complete admitted OTLP envelope alongside an extracted, versioned operational projection. “Admitted” means after explicit privacy policy: redacted content is not secretly retained in raw bytes. Preserve original types and values for retained fields. Unknown fields can contain sensitive content: retain opaque bytes only with an explicit protected-opaque capture opt-in and independent ACL/retention; otherwise reject an envelope whose unknown fields cannot be safely sanitized by an approved decoder. Do not silently discard unknowns or let opaque preservation bypass capture-off/redaction. Original incoming wire capture likewise requires explicit authorization. Opaque values are not indexed as understood fields. Normal protobuf deterministic serialization is not cross-version canonicalization or proof of identical source bytes. ([Repository serialization evidence](../research_notes/Transactional%20OTel%20trace%20storage/repository.md))

Attribute addresses are `(signal, scope, literal_key, optional explicit path, occurrence)`. Event/link occurrence IDs are stable source ordinals within a span revision, not timestamps. Array-path predicates carry element positions at every repeated level. `same_event(A AND B)` and `any_element(A AND B)` require the same witness; independently finding A and B somewhere in an array is insufficient. Whole-value array equality preserves order, duplicates, empties and types. Map canonical equality sorts unique keys, while the source representation remains available. Reject duplicate attribute/map keys with an explicit admission error instead of choosing an undocumented winner.

Typed equality does not coerce string, bytes, boolean, int64 and double. Preserve integers beyond 2^53. Numeric ordering uses separate integer/double domains; an explicit cross-type numeric operator uses exact comparison and a union of both domains, never int64-to-float rounding. Numerical double equality normalizes signed zero; ordinary equality/ranges exclude NaN and provide `is_nan`; infinities have their ordered IEEE meanings. A distinct raw representation remains inspectable. Missing, empty, redacted, dropped and unsupported are not interchangeable. Negative predicates range over **observed authorized retained telemetry**, not every operation that happened.

### 2.2 GenAI is versioned source data, not a frozen column schema

The conventions moved from `semantic-conventions` to **`semantic-conventions-genai`**. This RFC pins commit `e19717d65f890955777b044bca2a3cd71ae8b498`; its conventions are **Development**. Deployed SDKs can emit older released conventions, vendor names or structured-data fallbacks. Preserve source schema URL, instrumentation name/version, declared adapter/convention version and the raw keys. Never guess a producer's exact convention version from one spelling. Historical v1.37.0 migration guidance is not evidence that every current SDK implements that opt-in. ([Pinned overview][G1], [historical v1.37.0][G2])

| Concern | Pinned Development fields or signal | Storage/query consequence |
|---|---|---|
| Inference | `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model` | Requested alias and actual model stay distinct; provider IDs need namespace qualification. |
| Agent/tool | `gen_ai.agent.id/name/version`, `gen_ai.workflow.name`, `gen_ai.tool.name/type`, `gen_ai.tool.call.id` | Agent definition is not invocation identity; a model-supplied tool-call ID is not a span ID. |
| Conversation/response | `gen_ai.conversation.id`, `gen_ai.response.id`, `gen_ai.request.previous_response.id` | First-class cross-trace correlation. Do not synthesize missing conversation IDs from trace IDs or random UUIDs. |
| Usage attributes | `gen_ai.usage.input_tokens`, `.output_tokens`, `.cache_read.input_tokens`, `.cache_write.input_tokens`, `.reasoning.output_tokens` | Missing count is unknown, not zero; cache/reasoning/modality categories overlap inclusive totals. |
| Streaming attribute | `gen_ai.response.time_to_first_chunk` | Seconds-valued double, distinct from nanosecond span duration and not universally first-token latency. |
| Content | `gen_ai.system_instructions`, `.input.messages`, `.output.messages`, `.tool.definitions`, `.tool.call.arguments/result` | Structured `any`, sometimes JSON-string fallback; separate content authorization and indexing policy. |
| Evaluation | `gen_ai.evaluation.result` event; evaluation name/score/label/explanation | Often logs-signal data, separately correlated and revised; not a mutation of model output. |
| Metrics | `gen_ai.client.inference.duration`; usage `gen_ai.client.inference.usage.*`; per-operation token distributions | Instruments are not span attributes. Counters and histograms must not be reconstructed as if every span carried them. |

The pinned token metrics distinguish usage Counters from per-operation Histograms. Input totals include cached tokens; output totals include reasoning. For example, 100 text tokens including 40 cached plus 200 image tokens means 300 total input, not the sum of every reported breakdown. `fetch_response` polling must not re-count usage. There is no basis here for labeling `gen_ai.usage.cost` a standard OTel field: the pinned registry census found no cost/price/currency keys. Accept vendor/custom cost values with original names; derived billing records require source, currency, pricing version/effective time, reported-versus-inferred status and a contribution identity. Human corrected answers, telemetry corrections, evaluation updates and billing reconciliation are separate records. ([Registry][G3], [inference][G4], [token metrics][G5], [agent/tool conventions][G6])

Versioned adapters can expose normalized conversation, model, user and cost fields without destroying originals. OpenInference and Langfuse mappings remain separate source conventions. Qualify sessions by tenant/project and configured producer/provider namespace, resolve conflicting aliases explicitly, and record mapping version. `app.run.id`, customer request IDs and repository/workflow identifiers are examples of arbitrary custom fields, not standards. Real agent sessions can join many per-turn traces; token usage can be reported only on the last observation of a turn. ([Langfuse sessions][A1], [Cursor integration][A2], [OpenInference][A3])

### 2.3 Include correlated OTLP logs; do not claim span-only completeness

Implement OTLP trace **and log/event** ingestion in the first product scope. The first kernel proof can cover spans alone, but its claims stop there. `EVENT_ONLY` content and evaluations can live on logs, leaving spans content-free. Store `LogEnvelope` with resource/scope/schema provenance, event name, timestamps, severity, body, attributes and optional trace/span correlation. Index its eligible scalar attributes using the same typed machinery with a distinct signal/record-kind discriminator. Maintain trace-correlated log membership and explicit response-ID correlation; missing trace IDs do not become fabricated parent edges. Metrics ingestion/aggregation is a separate service/interface, explicitly out of the initial store. ([Logs model][O3], [GenAI events][G7])

For spans, the protocol below provides logical deduplication. Generic OTLP logs have no universal ordered correction/unique-delivery identifier. If a trusted producer supplies a stable namespaced event ID, use it; otherwise allocate a receiver UUID outside the FDB retry loop. Transport retransmissions can then remain duplicate observed logs. Do not silently collapse identical legitimate events by payload hash, or claim exact billing/event counts without stable producer identities. Describe this limitation in service documentation and query metadata. Standard OTLP has no per-record receipt extension; proprietary correction/receipt APIs are separate.

## 3. Queries determine the physical design

Time filters default to span start time or log event time, `[start,end)`. Interval-overlap, ingestion-time tail and whole-retained-trace context are distinct operators. Every existential has an explicit temporal scope; a parent outside an anchor's time window is available only when the query requests retained-trace context. Results expose witness identities and observed/incomplete topology.

| Query family | Exact semantics | Access path and boundary |
|---|---|---|
| Span/trace lookup | Exact logical span; all retained authorized spans of trace | Stable primary key/range; pagination for huge traces, no root-required assumption. |
| Arbitrary custom ID | Exact scoped typed customer request/run/tool/response ID | Complete equality posting plus collision verification; no field-promotion prerequisite. |
| Same-span conjunction | One span has model M AND error E AND custom feature F | Intersect/probe **span** identities; not merely trace IDs. |
| Trace existential | Some span has model M AND some span has failed tool T, or an explicitly correlated evaluation log failed | Union tagged witnesses over all partitions before joining trace IDs; retain signal/correlation provenance. |
| Event/array association | One event has evaluation N AND score below V | Occurrence-aware intersections or source verification; no cross-element matches. |
| Parent/descendant/link | Failed tool is descendant of agent; incoming link to async work | Separate parent adjacency and link indexes; bounded graph verification, missing ancestors remain unknown. |
| Long session | Ordered turns across traces, logs, buckets and resumed interactions | Per-source span/log session witnesses; log-only sessions remain discoverable, no session counter bottleneck. |
| Numeric/time/top-K | Duration/token/custom numeric range; newest 100 distinct traces | Typed ranges or ordered-time driver, residual checks and sound stopping frontier. |
| Discovery/negative | Keys/types present; missing key within a defined universe | Equality key-prefix enumeration or primary universe scan; budgets and ACLs apply. |
| Aggregation | Usage by model; cost, percentiles, wide group-by | Bounded exact scans initially; analytical tier/materialization when measured; no exact totals from missing counts. |
| Content | Prompt/tool body equality, substring, regex or semantic retrieval | Separate opt-in content capability; equality is not text/vector search. |
| Live incident tail | Changes after ingestion cursor | Versionstamped change index; correction/delete events, not event-time pagination. |

This separation follows real scoped/structural query semantics rather than inventing “trace contains tags” as a sufficient index model. ([TraceQL construction and structure][Q1])

## 4. Versioned records and physical keys

### 4.1 Stable identity, immutable descriptors, bounded ownership

Each authenticated tenant/project owns a Record Layer store prefix; authorization never comes from an OTLP attribute. Below that prefix, use ordinary Record Layer protobuf records and its normal split-record format. The notation below gives logical primary tuples, **not a replacement for Record Layer record serialization/chunk suffixes**. Baseline span PK is `(SpanV1, primary_shard, trace_id, span_id)`, with `primary_shard = stable_hash(trace_id) mod 16`. Sixteen is an experiment default, not a capacity claim. Log PKs are `(LogV1, log_shard, producer_namespace, event_id)`, where `event_id` is the supplied stable ID or receiver UUID and `log_shard` hashes that identity. The primary routing function is immutable within store format v1; changing secondary sharding never changes logical identity. Direct trace lookup computes one prefix without probing time buckets.

The stable envelope is also the authoritative identity lifecycle row: `state=LIVE|DELETED|EXPIRED`, lifecycle generation, monotonic source revision, admitted-source fingerprint, expiry generation and optional payload/projection references. A tombstone retains identity/generation after payload removal. Every create, correction, delete and replay reads this row with ordinary conflicts, including when payload is absent. Encoding/ownership metadata records how old entries were written; it does **not** select current maintainers. The store's transactionally read writable/readable epoch manifest is authoritative for foreground dispatch. Backfill explicitly targets its configured epoch without changing source revision or emitting ingestion events.

Intern only policy-approved **non-subject-sensitive** resource/scope components into immutable, bucket-local descriptors. Put subject-sensitive fields, opaque bytes and unclassified components in source-exclusive protected overlays, preserving their original scope and source representation. Unknown components never enter shared descriptors by default. Descriptor identity includes the approved fields/schema/scope components; digest candidates require exact canonical comparison. Random collision suffixes are generated outside retries; bounded collision scans fall back to noninterned descriptors. No global allocator or shared-use refcount is required.

Queries merge descriptor plus overlay for exact verification; caches include policy epoch and source ownership for overlays. Non-sensitive descriptors can wait for bucket retirement and completed primary cleanup. Overlays, descriptor-like fallback records containing sensitive data and their caches cannot: source/subject deletion enumerates and erases them under the content lifecycle below before physical completion. A timestamp correction acquires descriptors in the new bucket. Payload interning does **not** remove per-source attribute postings; normalized descriptor indexing is a separate optimization (§8).

### 4.2 Index key contract

Rebuildable `TRACE_SEARCH` data lives below its maintainer's owned **primary or secondary index subspaces**. Identity envelopes, operation receipts, content manifests and `ChangeEvent` journal entries are source Record Layer record types with independent lifecycle ownership; no invented untracked store-level prefixes. Let `e` identify layout/canonicalizer/HMAC/routing epoch, `b = floor(start_ns / bucket_width)` (one day initially), and `s = hash(trace_id) mod S_e` (16 initially); uncorrelated logs instead hash their log identity. For logs without event time, route by observed time or receiver time with an explicit fallback marker, preserving the original zero/missing timestamp. `rid` is a tagged logical span/log identity; `o` is the event/link/array occurrence path, empty for ordinary scalar fields. Every value includes source revision, start time and enough ownership metadata to retract exactly. Encoding uses fixed-width binary IDs and versioned, length-delimited tuples; no ambiguous string concatenation.

| Name | Logical suffix below owned subspace | Purpose |
|---|---|---|
| `EQ` | `(v1,e,b,s,signal,scope,key_token,type,value_token,rid,o)` | Exact equality candidates; type/key-prefix scan also supplies complete key/type existence without another mandatory posting. |
| `NUM` | `(v1,e,b,s,signal,scope,key_token,numeric_type,sortable_value,rid,o)` | Integer/double range; key identity still verified. Intrinsic duration has its own reserved scope. |
| `TIME` | `(v1,e,b,s,signal,effective_event_time,rid)` | Complete timestamp driver; bounded index-only projection includes revision, IDs, kind/status and authorization class. |
| `SESSION` | `(v1,e,session_namespace,key_token,value_token,s,effective_time,rid,o)` | Span or log membership across buckets; value carries bucket/revision/source alias and optional trace correlation. No shared session row. |
| `CHILD` | `(v1,e,parent_trace,parent_span,child_span)` | Parent adjacency; parent must be in the same trace. Source start/revision in value. |
| `LINK_OUT/IN` | `(v1,e,source_rid,target_trace,target_span,link_ordinal)` and reversed target/source | Explicit directed links, including cross-trace links; no implicit cross-tenant access. |
| `LOG_TRACE` | `(v1,e,trace_id,span_id_or_empty,effective_event_time,log_rid)` | Correlated logs independent of span existence/arrival. |
| `EXPIRY` | `(v1,expiry_bucket,rid,expiry_generation)` | Bounded sweep of trace-first primaries and scattered memberships. |
| `SOURCE_CHANGE_ORDER` (separate index) | `(v1,ingest_shard,commit_versionstamp,event_id)` | Commit-order access to immutable source `ChangeEvent` records; not owned by `TRACE_SEARCH`. |
| `SUBJECT` | `(v1,subject_namespace,subject_token,s,rid,revision)` | Authorized deletion discovery, only for declared identity mappings. |

`key_token` and `value_token` are 256-bit tenant-keyed HMACs with domain separation over encoding version, signal, scope, literal key, type and canonical value as applicable. Store key-ID/canonicalizer epoch. **Digest equality is candidate equality:** verify both original key and typed value before a row matches; injected small hashes must exercise collisions in tests. Short verification values can be covered inline within a fixed projection cap; otherwise fetch one compact projection/descriptor per candidate, and only then an authorized large object if required. Numeric keys use sign-adjusted big-endian int64 and tested sortable IEEE-bit transforms, not HMAC order. HMAC does not hide equality frequency, ordered numeric values or access patterns, and is not anonymization.

The ingest coordinator writes immutable `ChangeEvent` source records `(ChangeV1,ingest_shard,event_id)` and their separate commit-order index atomically with accepted changes, guarded by lifecycle/receipt decisions. Preserve the original commit version in record-version metadata so index rebuild never assigns a new event time. `TRACE_SEARCH` applies only to live Span/Log sources, never journal/receipt/manifest records; its backfill does not emit events. Dropping/rebuilding `TRACE_SEARCH` cannot delete this journal or its consumer checkpoints. Retain events until every required consumer checkpoint passes them and the independent journal horizon expires (seven days minimum initially); stalled consumers cause backpressure or explicit operator-approved abandonment, never silent loss. Minimal events identify source/lifecycle-generation/revision/action for idempotent reconciliation of latest authoritative state; historical replication needs retained revision images separately. Source deletion does not retract deletion events; tenant destruction must drain or explicitly abandon consumers before whole-store removal.

The baseline includes `EQ` for every admitted scalar and bounded whole structured value, and `NUM` for every admitted numeric scalar, including custom names. Array membership/path accelerators are optional; exact source evaluation is available within budgets. Scalar event/link attributes carry occurrence IDs. No universal second time-ordered copy of every term, mutable posting chunk, global dense span ID or shared `(term,trace)` bit is required. Each posting has one source owner; removing one span never deletes another span's term/session membership. A hot trace can still overload a contiguous primary range: admission/fairness and measured optional span-striped generations are the response, not a claim of limitless one-trace scale.

### 4.3 Coverage is a contract, not an adaptive guess

Proposed v1 limits are 512 indexed attribute occurrences per record after resource/scope expansion, 1,024 UTF-8 bytes per key, 64,000 bytes per ordinary scalar, 64 nesting levels, 256,000 bytes of admitted operational metadata, and the tighter mutation budget in §5. Whole-value arrays/maps count toward canonical bytes; optional element/path fanout counts separately. These are configurable **experimental admission limits**, not OTel limits or validated production defaults. Tenant distinct-key and bytes/second quotas protect against adversarial custom schemas.

Privacy-classified content is excluded from metadata indexing even when represented as a scalar JSON string. Its capture and indexing opt-ins are independent. For ordinary accepted scalar attributes there is no “cold field not indexed” state: either publish complete baseline entries or reject the record. Unknown types and nonindexed nested operators return `UnsupportedCapability`, or run an explicitly chosen bounded exact scan; they never return an empty set as if exhaustive. Queryable coverage reports distinguish admitted/indexed, content-restricted, opaque, redacted and policy-rejected states without exposing unauthorized names/values. Adaptive statistics choose faster plans, never whether a field exists historically.

OTLP input validation classifies malformed identities, duplicate keys, disallowed opaque data and individual quota violations as permanent rejections. If processing finishes with only permanent rejections, return standard partial success with rejected counts; clients must not retry it. If **any transient unfinished work remains**, including after earlier subbatches committed, return a retryable whole-request error/backoff, not partial success that would lose unfinished records. Whole-request replay deduplicates committed spans; unidentified logs can duplicate. Standard OTLP exposes no per-record receipts or atomic unlimited batches. Test failure immediately after the first committed subbatch. No silent truncation, hidden coverage loss or unconditional latest-arrival-wins is allowed. ([OTLP delivery protocol][O4])

## 5. Ingestion, correction and retention are bounded protocols

### 5.1 One logical span revision publishes atomically

OTLP provides no universal monotonic span revision. Default to **immutable-first**: exact admitted-envelope replay is a no-op; divergent same-ID replay is rejected/quarantined with no overwrite. A product correction API requires authenticated authority, stable operation ID and expected current revision; an explicitly configured producer revision protocol can substitute. Human feedback is not that correction API. Timestamps do not order corrections.

Before the transaction, decode, authorize, apply policy, calculate canonical terms, generate stable IDs and stage content. Inside it, ordinarily read identity lifecycle, **old and target bucket fences**, subject fences and the store epoch manifest. A logically expired/retired/deleted source cannot be corrected into a fresh bucket, even if its payload still exists or cleanup has not written the tombstone. A correction requires LIVE, unexpired source, expected revision and authority. Restore is a separately authorized, audited operation with a new lifecycle generation, out of v1 scope. A missing lifecycle row permits initial creation only within admission/replay rules; it never permits an expected-revision correction. For live duplicate detection, verify canonical admitted bytes after a fingerprint match; externally checked immutable data still requires revision/generation revalidation inside the transaction.

| Atomic source operation | Required writes/checks |
|---|---|
| Create | Read absent identity with conflict protection; validate fences; write LIVE generation/revision, synchronous indexes, expiry, source journal and optional proprietary receipt. |
| Correct | Check LIVE generation/revision and fences; clear removed keys; **Set all current revision-bearing values, including unchanged posting keys**; replace envelope/expiry, transfer or retire content ownership, append journal and receipt. Key equality saves clear/reinsert work, not the required revision refresh. |
| Delete/expire | Check generation/revision; write mandatory DELETED/EXPIRED tombstone in the stable row, revoke visibility, retract owned memberships, retire content, append journal; explicit deletes also write an operation receipt. |
| Replay | Read lifecycle and receipt. Never republish tombstoned data. An authorized receipt retry returns the recorded historical result without claiming that revision remains current. |

Proprietary corrections/deletes require `ReceiptV1(rid,operation_id) -> (request_fingerprint,lifecycle_generation,accepted_revision,result,commit_barrier)`, written atomically with the effect. Reusing an ID with different request bytes is rejected; exact fingerprint collisions are verified against an admitted canonical request representation or separately retained verification data under the same privacy policy. An unknown-commit retry after a subsequent correction returns its original receipt, not a second effect or a misleading conflict. Receipt horizon is seven days initially, separately configurable; signed operation tokens carry an admission epoch/deadline, and expired or erased receipts fail closed rather than re-executing old operations. Ordinary OTLP creates have no such token/receipt promise. Receipts retain no content output; any sensitive verification data belongs to the deletion population. These are proposed product APIs, not OTLP extensions.

All writes use the Record Layer transaction; changed timestamps move indexes, not identity. Per-source conflicts avoid trace/session summary contention. Foreground maintenance targets every writable epoch from the store manifest, extracting old terms with their recorded encodings and new terms for each configured target. Backfill writes only target-epoch derived entries. ([FDB retry guidance][F2], [local maintenance dispatch](../../../pkg/recordlayer/store.go#L1411))

Bound batches by measured **affected bytes**, mutations, decoded bytes and elapsed time, including removal of old entries, read keys/conflict ranges and descriptor writes. Initial targets are under 500,000 affected bytes and under one second elapsed per attempt, leaving headroom below FDB's 10,000,000-byte transaction, 100,000-byte value, 10,000-byte key and roughly five-second transaction-age limits. Estimate conservatively and enforce runtime guards. Oversized replacements are rejected atomically, leaving the old revision intact; a future generation-staging protocol is not implicit permission to partially update. ([Pinned FDB limits][F1])

### 5.2 Giant content has an explicit publication boundary

Prompts, tool inputs/results, files and multimodal bodies use protected immutable content objects when too large for the operational envelope. Proposed initial object admission is 16 MB decoded, with configurable lower limits and decompression-ratio limits; larger content is rejected or supplied through an authorized pre-upload reference API. If FDB stores chunks, use values comfortably below 100,000 bytes and many bounded staging transactions. If object storage stores them, upload/verify immutable version, size, checksum and durability **before** publishing the FDB reference. Neither route makes external storage part of an FDB atomic transaction.

Baseline objects are **source-exclusive**, owned by `(rid,lifecycle_generation,slot)` with unique immutable object generation; no cross-source dedup/sharing. Before upload dispatch, one registration transaction creates the generation's `ContentManifest`, source/subject ownership entries and upload-attempt registration while **ordinary-conflict-reading the source lifecycle (including absent identity) and every applicable subject-deletion/policy fence**. Only an eligible live source or permitted initial creation can register; preliminary authorization is insufficient. Charge ownership writes and fence reads to the staging budget.

Deletion commits its source/subject fence **before** enumerating those durable ownership entries and draining their registered generations/attempts. Registration therefore either commits before the fence and belongs to deletion's cleanup population, or conflicts/retries and fails before dispatch. No new generation or attempt may register after the fence; physical completion requires draining that fenced population under the GC protocol below. An FDB `ContentManifest` governs publication and GC:

| State/transition | Ordinary-conflict predicate and effect |
|---|---|
| STAGED → READY | Atomically register generation/ownership/attempt with the lifecycle and deletion-fence checks above and a live staging lease/state check before dispatch. Every additional attempt repeats those checks. Record verified immutable bytes/checksum/version only after fresh fence/lease/state checks. |
| READY → PUBLISHED | Final source transaction reads matching object generation, READY state/live lease, source lifecycle and policy; atomically publishes source reference and manifest ownership. A GC claim conflicts with this read/write. |
| PUBLISHED → PUBLISHED/RETIRED | Correction atomically transfers unchanged references to its new revision or removes them and marks RETIRED; delete/expiry retires all references. Retries cannot retire a currently owned generation. |
| STAGED/READY/RETIRED → GC_CLAIMED | After lease/grace expiry, transaction reads manifest, authoritative source reference and reader-pin range; requires no current reference or live pins, then claims that exact generation. PUBLISHED is never swept as an orphan. |
| GC_CLAIMED → DELETED | Retain cleanup ownership until all registered uploads are durably completed/aborted or backend-confirmed quiescent, then confirm exact-generation deletion. Retain a minimal DELETED manifest through the retry horizon; claimed generations are never reused. |

Lease expiry alone does not stop an in-flight upload. A late completion must observe GC_CLAIMED and trigger idempotent deletion of its exact generation/version, not READY publication. A durable reconciler handles uploader crashes and unknown outcomes, repeating backend reconciliation and deletion, including abandoned multipart data. Enforce bounded upload/deadline protocols, but treat a client timeout as insufficient proof of backend quiescence. No DELETED state or physical-completion receipt is permitted until outstanding attempts cannot recreate bytes and final cleanup is confirmed; unresolved attempts remain GC_CLAIMED. This content subsystem is unimplemented and excluded from the initial kernel prototype.

Before fetching outside a transaction, acquire a bounded reader pin in a transaction that verifies current source reference, PUBLISHED generation and authorization; GC and pin creation conflict on manifest/range. Existing pins can finish during retirement; no new pins attach after retirement/claim. A changed source between page snapshot and pin acquisition requires retry or explicit stale-payload error, not an unprotected historical fetch. Expired pins cannot continue reads; deletion completion waits for grace/pins and cache revocation. Failed publication leaves leased staged data, never a race-prone unnamed orphan. Upload/delete side effects stay outside retries. The proprietary reference contains tenant/object/version/policy/key IDs, not bearer URLs; content loss is an explicit error. OTel's external-reference format is unfinished. ([GenAI content guidance][G8])

### 5.3 Retirement fences prevent late-data resurrection

Track event time, ingestion time, revision, expiry and deletion state independently. A tenant retention manifest defines active bucket epochs, cutoff and late-arrival grace. Ingestion reads the target bucket fence with ordinary conflicts; retirement atomically changes it to RETIRED. New old-timestamp data then receives `OutsideRetention`/quarantine instead of silently reopening the bucket. Corrections cannot move into retired buckets. Readers also consult the fence, hiding retired records before physical cleanup. A changing clock alone is not the synchronization primitive.

The sweeper scans `EXPIRY` in bounded transactions, checks identity/revision/expiry generation, and replaces LIVE payload with a **mandatory EXPIRED tombstone** while retracting scattered memberships and retiring content. Stale expiry cannot delete a corrected live generation. Until sweep completion, the old bucket fence/expiry predicate already makes that identity ineligible for correction or replay publication. Bucket-first indexes can be cleared after fencing, but **trace-first identities do not disappear with that clear**. Non-sensitive descriptors wait for primary cleanup; protected overlays follow source deletion immediately. Range clear is not instantaneous disk reclamation.

Keep lifecycle tombstones for seven days after retirement/deletion initially, at least through outstanding operation-token deadlines and receipt horizons. Every access checks them even when payload is absent. Old timestamps are independently blocked by bucket fences. After all documented horizons expire, fresh-timestamp ID reuse cannot be detected forever: forbid it contractually or retain longer identity history at measured cost. Subject-deletion fences persist for their required nonresurrection horizon. Policy erasure of a receipt's sensitive verification data returns `ReceiptUnavailable` on retry, never re-executes the operation; retain approved minimal lifecycle fencing or explicitly stop accepting that identity namespace.

Atomic publication means a reader sees one coherent admitted span revision and its indexes. It does **not** mean all children, linked work, logs or other collector batches have arrived. Expose observed counts and optional quiescence hints, never “complete trace” merely because the root ended. ([OTel span lifecycle][O2])

## 6. Exact execution requires witnesses, ordering and honest budgets

### 6.1 Span intersections and trace joins are different algorithms

Compile a typed query AST with explicit quantifiers, scopes, time domains and authorization. Estimate from sampled/sharded statistics, choose bounded scans/probes and expose the plan. For same-span equality, scan the narrowest term and point-probe other terms at that candidate's bucket/epoch, or merge compatible span-ordered postings. Verify canonical key/value, current revision and policy before accepting. Numeric predicates use `NUM` ranges or residual evaluation on a selective equality anchor. Read compact projections once per candidate; fetch complete span/content payloads only for accepted output or unavoidable exact verification. Charge every scanned key, fetched byte, probe and decoded object, including rejected candidates.

For trace-existential predicates `A_i`, the correct relation is:

```
W_i = UNION over all relevant (bucket, shard, readable epoch)
      of (tagged_rid, occurrence, revision, optional_trace/span_correlation) witnesses
T_i = DISTINCT authorized_trace_correlation(W_i)
answer = INTERSECT_i T_i
```

**Union each existential before the trace join.** `UNION_partition(INTERSECT_predicate(...))` misses a model span in yesterday's bucket and a failed tool in today's. Changed shard counts, mixed epochs and span-striped alternatives also require global reconciliation. An alternative drives the smallest `T_i` then probes each candidate's complete relevant trace range for the other existential predicates. Both retain witnesses and honor each predicate's temporal scope; neither assumes a trace is contained in one bucket. Budget global distinct/join state, spilling only in a declared multi-transaction mode.

Witnesses retain full span/log identity: several logs attached to one span are not one event. Cross-signal joins explicitly use `LOG_TRACE` or exact qualified provider/response-ID matches; trace-only logs can satisfy trace existentials but not a span-correlation join without span identity. Ambiguous response matches retain candidate provenance, not fabricated uniqueness. `SESSION` accepts eligible log attributes even if no span carries that session ID; uncorrelated logs remain session members without invented trace IDs.

Structural checks then use actual parent IDs/adjacency, not temporal overlap or trace-level membership. Child, descendant, sibling and directed link relations are separate operators. Traverse with visited sets, depth/node budgets and cycle detection for malformed inputs. Missing parents give an unknown path, not a positive ancestry match; a budget limit is not proof of absence. Links to unretained or unauthorized targets remain unresolved. Session existential queries similarly join across all member traces, not just one bucket or one trace.

### 6.2 Newest-first results need a real stopping frontier

`EQ` is trace/span ordered within a term partition; timestamps in values do not make it time ordered. If that is the only selected path, scan **all** eligible candidates and maintain a top-K heap, or fail the budget. Do not stop after the first K matches and label them newest.

For a timestamp-driven plan, reverse-scan every relevant `TIME` partition or a **complete** promoted term-time accelerator. Heap-merge by total key `(effective_event_time,tagged_full_rid[,occurrence])`, using identical type/byte ordering in frontiers and continuations; this distinguishes every log, including multiple logs on one span. Span-only ordering specializes to its full span identity. Verify residual predicates and current revision. Unopened buckets require certified maximum timestamps. Stop only when K distinct accepted results exist and every next-unseen partition upper bound is at or below the Kth result. Deduplicate overlapping epochs by logical identity/revision. A selective predicate can reject arbitrarily many candidates, so this algorithm proves correctness, not a latency bound.

For top-K traces define score explicitly as **latest matching anchor span start**, not root end, observed trace duration or ingestion time. The anchor is part of the query; other existential witnesses can be different spans. Descending anchor enumeration plus full witness verification gives the same frontier proof, with a bounded distinct-trace set. Ordering by trace-level extrema/aggregates requires a different proven driver or complete scan. Duration top-K similarly needs ordered duration drivers; approximate sketches only influence planning, never exact stopping.

### 6.3 A continuation is not a durable FDB snapshot

Choose these v1 contracts explicitly:

* **`snapshot_page` (default):** all scans, verification, ACL/retention reads and output for one page use one FDB read version in a bounded transaction. If an exact page cannot be completed within its budgets, return `QueryBudgetExceeded`; do not combine older batch state and call it one snapshot. A complete first-page top-K needs the frontier proof within that transaction. A too-old transaction restarts the entire page or fails.
* **Continuation to another page:** starts a new read version and resumes stable sort position. It is live pagination, not the original snapshot. Inserts behind the cursor can be omitted; corrections can change order/results. A bounded server-side query lease can suppress repeated trace identities across pages, but cannot recover unseen insertions behind the frontier. Expired state gives `ContinuationExpired`, not silently restarted results.
* **`live_scan` / asynchronous export:** all cross-batch existential/session/ancestry joins produce **candidates only**. Before emitting a batch-view-exact result, revalidate **all** its witnesses, revisions, graph/correlation edges, lifecycle, ACL and retention fences in one bounded final transaction. Disappeared or superseded witnesses require recomputation/rejection. Negative predicates also require their full bounded authorized universe. If verification cannot fit, fail the budget; an explicitly requested `observed_candidates` mode can expose weaker historical evidence without claiming simultaneous truth. Exact rows report final-validation read versions; different rows need not share a snapshot. Scan completion is not global snapshot completeness, top-K or aggregate exactness.

Signed continuations bind tenant/ACL context, query digest, index/encoding/routing epochs, order/frontiers, limits, policy generation and lease expiry. No OFFSET. No promise to reuse an old read version after the MVCC age limit. Durable snapshot export over mutable hot data is **not supported in v1**; it requires application-level retained revisions plus a proven visibility frontier, or a fully immutable pinned corpus. Collecting pages before a wall-clock cutoff is insufficient because late data can arrive behind it. ([FDB limitations and snapshot guidance][F1], [F2])

## 8. Amplification decides whether this architecture is affordable

### 8.1 Two explicit modeled populations

This is arithmetic, **not measured encoding, compression, performance or customer distribution**. Let `A` be equality terms, `R` numeric terms, `D` other entries including source journal record **and** commit-order index, `P` envelope/projection bytes including LIVE identity state, and `H` amortized descriptor bytes. Assume EQ/NUM **180 bytes**, other entries **100 bytes**, one unsplit primary, two non-sensitive descriptors reused by `F=100` sources, no content/path fanout or compression. Initial ordinary-OTLP mutations are `1+A+R+D+d`, with descriptor creation `d=2/F=0.02`; logical bytes are `P+180(A+R)+100D+H`. Proprietary receipts and later lifecycle costs are additional below.

| Modeled span population | Ordinary service mix | Resource-heavy agent mix |
|---|---:|---:|
| Span/resource/scope scalar terms | 12 / 6 / 2 | 20 / 50 / 10 |
| A / R / D | 20 / 4 / 7 | 80 / 12 / 9 |
| P / H bytes | 1,500 / 64 | 3,000 / 128 |
| Initial logical mutations/span, including amortized descriptors | 32.02 | 102.02 |
| Modeled logical bytes/span | 6,584 | 20,588 |
| At 100M retained spans | 658.4 GB | 2.0588 TB |
| Three-copy uncompressed logical-byte estimate under assumptions | 1.9752 TB | 6.1764 TB |

`D=7/9` models time, expiry, parent/session/subject, journal plus commit-order entries and selected links, not a universal graph count. **The three-copy estimate is not a physical lower bound:** compression can reduce it, while logs, engine overhead, backups, build peaks and network replication add costs. Actual splitting/encoding and each structure's retention must replace these assumptions. Two unique/collision-fallback descriptors raise `d` from 0.02 to 2; sensitive overlays lose shared-byte amortization. Additional bidirectional links cost two entries; existence acceleration costs `A` more; universal term-time order duplicates its entire indexed population.

| Additional lifecycle component | Explicit modeling obligation |
|---|---|
| Stable identity | LIVE state is included in the primary; retirement rewrites it to a mandatory tombstone. Illustrative retained bytes add `128 * tombstone_count`, plus later GC mutations. |
| Operation receipts | Add at least one mutation and assumed 160 bytes per retained proprietary create/correct/delete receipt, plus any sensitive collision-verification data. Ordinary OTLP initial inserts in the table have no proprietary receipt. |
| Correction | `1 primary + 1 receipt + 2 journal + removed_key_clears + all_new_revision_value_sets`, plus expiry moves, descriptor creation and content ownership transitions. Unchanged posting keys still incur Set/bytes; only redundant clears disappear. |
| Protected objects | Assuming 192-byte manifests: STAGED, READY and PUBLISHED are three writes before visibility; retirement, claim and DELETED add three later, plus lease/pin writes and external upload/delete or FDB chunks. Count retained object tombstones and cached overlays separately. |

If 10% of spans carry one 32,000-byte object, add **320 GB of content and 1.92 GB of live manifests per 100M spans**, before object redundancy, plus 0.3 staging/publication mutations per ingested span under those assumptions. These extras and measured correction rates belong in the competitive bill, not outside it.

In the agent population, resource/scope fields account for **60/80 = 75% of equality memberships** even when descriptor payloads are interned. With 100 spans per immutable descriptor, a normalized term-to-descriptor index plus two descriptor-to-span memberships could amortize those 60 equality entries toward `60/100+2=2.6` entries/span. That is an illustrative saving, not free performance: queries join matching descriptors to spans; common service descriptors have enormous fanout; numeric/time/top-K drivers and occurrence/epoch semantics must remain correct. Prototype this reusable normalized covering join against the direct baseline if resource expansion dominates cost.

Read amplification also scales with the population. For `q` terms, `B` buckets and `S` shards, naive setup costs up to `q*B*S` ranges. A 30-day, 16-shard, three-term query means up to **1,440 range setups**, before postings. A selective driver with `n` candidates needs roughly `n*(q-1)` probes plus verification reads; trace existential joins and long sessions can need much more state. Complete empty-partition directories can prune fanout; samples cannot certify emptiness. Report actual scanned/returned bytes, rejected candidates, descriptor cache hits and content verification fetches, not only K output rows.

### 8.2 Compare representations before promoting them

Per-span KV postings give simple ownership, atomic corrections and sparse singleton efficiency. Fixed bitmaps need dense IDs and nonshared ownership; a 10,000-bit operand already occupies about 1,250 bytes before overhead. Random trace IDs do not provide exact bitmap positions, and hashing to bits loses exact identity. Mutable compressed/bunched containers can save bytes but introduce rewrite amplification, contention and splits. Existing BITMAP_VALUE/TEXT formats are precedents to measure, not justification for a universal trace bitmap. ([Java bitmap maintainer][R2], [Lucene postings][C7])

Promote only after measured costs identify a problem. Candidate triggers to ratify are more than 50% retained-byte cost in postings, repeated common-term scans dominating query CPU, or a sealed-bucket representation showing at least 2× net byte savings after dictionaries/tombstones/dual-write cost without missing latency/freshness gates. These are experiment thresholds, not established optima. Select hot term-time accelerators, cached packed lists or normalized descriptor joins independently. Keep complete baseline coverage until replacement coverage is proven; popularity never removes cold custom keys.

An immutable history tier assigns **block-local** document IDs, sorted dictionaries, compressed postings and numeric columns. Stage bounded chunks or immutable object-store blocks, validate checksums/completeness, then atomically publish a versioned FDB manifest. Queries union complete block coverage with delta postings and revision-aware tombstones. Late events enter deltas; corrections/deletes supersede old source revisions. Compaction must fence its input generation and never clear deltas written after its input boundary. Pin manifests with bounded leases; swap atomically and GC old blocks only after readers finish. External publication remains a manifest protocol, not cross-system atomicity. This tier is justified only by measured economics and adds considerable correctness surface. ([Quickwit architecture][C8])

## 9. Lifecycle, privacy and operations remain part of correctness

New search generations get fresh subspaces/options/metadata versions. Atomically install them in the authoritative writable-epoch manifest as WRITE_ONLY; every source mutation conflict-reads that manifest, so it cannot miss a concurrently added epoch. Backfill uses its configured target epoch and source lifecycle/revision, not the envelope's historical epoch list. Maintain concurrent writes, backfill persisted ranges, validate, and publish READABLE only after coverage is proven. Queries use the complete old generation until then, or a proven union; deduplicate source identity/revision. Old continuations either retain a generation lease with continued foreground maintenance or fail explicitly at cutover; a frozen old index cannot answer a new live page. Retire old generations after cutover/lease expiry, including primary and secondary structures, build ranges, queues, manifests and external-object GC. Changing HMAC keys or canonicalization never silently reinterprets existing bytes. ([Java online build][R3])

Prefix deletes must refuse layouts not aligned with the record prefix. Per-span delete uses exact old ownership. Full-store deletion must additionally schedule external object/cache/export cleanup even though existing Record Layer `DeleteAllRecords` clears owned primary/secondary index subspaces. Rebuild/repair validates each custom structure rather than applying the generic root-key-expression validator to opaque postings. Interrupted jobs resume idempotently from persisted checkpoints with backpressure; no unbounded transaction is hidden in compaction, drop or retention.

Privacy policy runs **before** base storage and index extraction. Default content capture/indexing is off; tool schemas/descriptions, custom metadata, prompt variables, file contents and URLs need policy too. Separate metadata/content encryption keys and ACLs; authorize object retrieval independently. HMAC terms are sensitive derived data. Apply tenant/row/content authorization to existence checks, discovery, facets, errors, exports and session/link traversal, not merely final payload fetch. FDB cluster access is not a substitute for application ACLs. ([Sensitive-data guidance][S1], [GenAI content controls][G8], [FDB limits][F1])

Subject deletion first fences visibility/nonresurrection, then enumerates primary/overlay records, descriptor fallbacks, receipt verification data, subject/session/graph witnesses, content versions/manifests, evaluation/feedback, downstream copies and caches. Shared descriptors contain only approved non-subject-sensitive components; misclassification triggers descriptor/cache quarantine and repair, never a false completion receipt. Physical completion requires protected orphans and old-revision overlays erased, pins drained and caches revoked; waiting for bucket retirement is insufficient. Retained minimal receipt/lifecycle fences must be explicitly permitted by the deletion policy, and disclosed separately from erased payloads. Recheck authorization at content fetch. Backup/export retention and key-destruction policy require deployment decisions; do not promise universal legal compliance from `Clear`. Avoid shared encrypted blocks that make selective content deletion impossible. A read that began before a fence can finish under its old snapshot; the deletion API must define drain/revocation behavior for active queries and caches before claiming immediate erasure.

Operational controls include per-tenant byte/mutation/QPS budgets, fair query queues, ingest backpressure, bounded candidate/graph/spill memory, retry caps and maintenance quotas. Measure p50/p95/p99 ingest attempts/ack/visibility, conflicts and unknown commits, bytes/mutations per span, hot ranges, GRV/commit latency, scanned-versus-returned work, query budget failures, retention lag, queue/build lag, descriptor reuse, content orphans, delete completion and index audit mismatches. Do not label metrics with arbitrary attribute values. Keep telemetry about this store bounded and redact its diagnostic payloads. Reserve capacity for deletion/retention/recovery before admitting backfills or tenant bursts.

## 10. Alternatives and an honest ClickHouse comparison

Reject an ordinary fixed-column-only schema as the sole interface: it makes arbitrary customer keys second-class. Conventional VALUE indexes remain useful baseline comparators for known fields, not a replacement for typed dynamic postings. Reject bucket-only primary identity because corrections/replays across buckets need a stable locator anyway; its bulk-primary-expiry advantage is a valid later alternative with locator cost included. Reject shared per-trace/session counters or term bitmaps as the first design because source ownership and write hotspots become unnecessary correctness risks.

Modern ClickHouse is not a full-scan strawman. Compare a tuned MergeTree design with appropriate tenant/service/time ordering, ZSTD, sparse primary pruning, PREWHERE, TraceId and Map key/value bloom/minmax skip indexes; typed materialized hot GenAI/custom fields; alternative projections including `_part_offset` where supported; and practical materialized views/alternative tables for arbitrary attribute access. Current text indexes support Map expressions and compressed postings, but tokenization must not replace exact typed key/value semantics. Verify original values and pair association. Map representation/bucket serialization and duplicate-key behavior need explicit treatment. ([OTel schema][C1], [Map][C2], [projections][C3], [text index][C4])

Require both a tuned mixed-workload CH schema **and an optimized exact-attribute projection/table/MV alternative** for the decisive arbitrary-key query, including keys not prepromoted to columns. The latter indexes scoped typed key/value pairs, not independent key/value membership that invents associations. Freeze DDL, EXPLAIN, selected marks/granules/bytes, verification semantics, backfill, storage and write/merge costs for both arms; an untuned Map-only arm cannot decide this RFC. Current projection documentation restricts lightweight updates/deletes; ReplacingMergeTree replacement occurs through merges and needs the appropriate query semantics, often `FINAL`. Async inserts with `wait_for_async_insert=1` wait for flush, but replication/durability/deduplication settings still determine the observable contract. Count their costs; do not call buffered acknowledgment equivalent to durable indexed visibility. ([Async insertion][C5], [ReplacingMergeTree][C6])

FDB plus an outboxed CH analytical replica is a legitimate decision boundary: exact fresh operational access in FDB, broad scans and longer retention in CH/object storage, with explicit replica watermarks and separately disclosed query semantics. If users mainly need minute-fresh dashboards, percentiles and large exports, CH alone can win by avoiding the FDB posting bill. If cheap historical trace search dominates, immutable object-store/Tempo-like designs merit testing. A full FDB design wins only where its **measured** correctness/latency/economics justify it; owning Record Layer lets us improve its indexes, not repeal physical costs.

| Offered ingestion | Open-loop 0/1K/10K/25K spans/s, plus 0.1 logs/span; batches at most 256 records or 50 ms. Add 2% duplicate submissions, 1% corrections and 0.1% deletes; count all extra work. Sweep until saturation rather than discard overload cells. |
| Offered queries | Independently 5/25/100 QPS: 30% trace lookup capped at 64 spans/256 KB returned metadata, 25% rare key, 10% session page, 10% same-span, 10% cross-span/log existential, 5% numeric, 5% structural, 5% wide analytics. Same-span/model queries split requested/actual-model predicates equally. |
| Healthy-load acceptance | At least 99.9% of valid offered records durably acknowledged within 5 s; unexpected query errors/timeouts at most 0.1%. Target-class budget exhaustion counts as failure and must be at most 0.1% for a claimed SLO cell. Explicit over-quota fixtures are a separate expected-rejection population. |
| Stability/latency | At least 30 measured minutes after warmup; queue growth slope in final 15 minutes at most 0.1% of offered records/queries per second, maximum queue age 1 s, drain within 10 s. Proposed p99 ingest acknowledgment <500 ms; p99 bounded trace/rare-key query <100 ms. Report all percentiles and failures, not successful-only wins. |
| Visibility | A seeded uniform 1% sample is polled independently every 10 ms after durable acknowledgment; charge this extra query load. Hold sampled revisions unchanged until observation or the 5-s deadline; churn has a separate oracle. All applicable lookup/equality/range/session paths must return that revision, using commit barriers where available. Proposed p99 <1 s, p99.9 <5 s; censored/missing observations fail. Measure receiver/collector-arrival latency separately. |

Generate fixture choices from counter-based SHA-256 with domain-separated labels and seed 283; freeze generator bytes, rather than relying on unspecified language PRNG behavior. Assign 50% of spans to 100 of 10K tenants and the rest to 9,900, using Zipf exponent 1 within each group; 100 services use exponent 1.1. Trace-size mixture by trace count is 90% discrete-uniform 2–20, 9% 21–1,000, 1% 1,001–100,000, with deterministic truncation at the corpus boundary. Independently shuffle traces into sessions of 10/1,000/10,000 traces with 90%/9%/1% weights; force cross-day membership. Record realized counts, not just intended distributions.

Use both §8 attribute populations. Across 1K custom keys/tenant, vary value cardinality 1/10/1K/near-unique independently of queried frequencies 1/10/1K/100K per million spans, reporting key-presence counts and excluding mathematically infeasible cells; high cardinality alone is not selectivity. Requested models have 10 names, actual models 20, with 20% differing aliases; provider has 5 values, operation 12. Include missing counts, event-only content, mixed SDK conventions and scope/type collisions. Arrival delay is 95% within one second, 4% within one hour, 1% within two days. Resource reuse, content sizes and over-limit attempted attributes are separate seeded sweeps; publish realized bytes and rejected populations.

**Decisive rare-key case `Qrare`:** reserve tenant `bench/rare` with exactly 1M spans in `[T-24h,T)`. Previously unpromoted string key `span.customer.incident_key_283 = "needle-283"` occurs on exactly 1,000 spans in 500 traces, two witnesses each, uniformly shuffled across time/shards. Populate 100K other distinct string values; integer/string lookalikes and other-scope occurrences are negative controls. Query newest 100 distinct trace IDs ordered by `(maximum matching anchor start_ns DESC, trace_id DESC)`, returning witness IDs; generate concrete UTC request bounds from frozen `T`. Sweep candidate frequency independently, including 1 and 100K. Oracle fixes exact identities, witnesses and tie order.

Run **both** full-candidate `EQ` scan + top-K and `TIME` frontier drivers against that oracle. Default page budget is one second, 20K examined candidates and 4 MB total scanned/fetched bytes, additionally subject to FDB hard limits. TIME can legitimately exhaust before finding 100 distinct traces; that is a measured failure, not an approximate answer or a reason to hide the arm. Record candidates/probes/bytes and `QueryBudgetExceeded` rate. A term-time accelerator is a separately costed variant with build/dual-write/storage costs, not an assumed free baseline. CH's optimized pair-indexed alternative must receive this same unseen-key workload.

Restore the same initial corpus and replay the same offered stream for each arm. Run cold/warm cells, idle and concurrent ingest, retention/build activity, skew and failure recovery. Use open-loop arrivals to avoid coordinated omission. At least three independently repeated rotated runs and initially 10K completed operations per query class/run provide preliminary tails; extend low-QPS cells beyond 30 minutes to reach that population, increase unstable tail samples, and retain confidence intervals/raw histograms. Report absolute p50/p95/p99, visibility tails, throughput, failures, CPU/memory/I/O/network, scanned/fetched bytes, replicas/logs/backups/content and temporary build/merge debt. Record actual-versus-cached correctness execution separately from warm query caches.

### 11.4 Gates and remaining decisions

**Go** from proof to serving implementation only when exactness, tenant/content isolation, lifecycle and boundedness pass. Approve trace/log adapters, admission limits, source conflict rules and pagination contracts before expanding API claims. Implement reusable validation/candidacy/scan/lifecycle changes alongside production maintenance, then add resource normalization or compressed history only when the byte/read ledger justifies them. SQL integration, durable snapshot export, arbitrary full-text/vector content and nonidempotent rollups are separately scoped phases.

**Disprove the selective-win hypothesis** if tuned CH matches or beats FDB p99 at matched sustainable offered load and budgets, or if an apparent latency advantage vanishes when replication, writes, verification, privacy and retention are included. Any silent coverage gap, false positive after verification, resurrection, unsafe custom candidacy or unbounded hot membership is a correctness no-go regardless of speed. If measured replicated bytes/span or total cost breaches the approved budget, shorten the FDB hot window, adopt normalized/immutable storage, choose the hybrid, or stop; never silently drop arbitrary attributes to manufacture a win.

Open owner decisions are actual workload/SLO/cost targets; approved content/deletion policy and replay horizon; deployed SDK/producer identity/revision guarantees; bucket/shard defaults; direct versus normalized resource index economics; and which query semantics justify a production SQL surface. These decisions do not block the small correctness proof. Receipt/opaque-data retention policy, staging/pin deadlines, executable durability settings and the numeric benchmark manifest still require owner approval and failure-oracle validation; this revision is not final design approval. They **do** block any claim that this is globally optimal, production-ready or faster than ClickHouse.

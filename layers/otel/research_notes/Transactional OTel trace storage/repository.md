# Repository feasibility: transactional OTel trace storage

## Can an external package maintain custom indexes transactionally, including online builds and deletion?

### Takeaway
Yes: the existing extension point hands an external maintainer the same writable transaction that saves/deletes records, with freedom to lay out primary and secondary index keys. This is sufficient for a small synchronous postings-index prototype without modifying production Record Layer code, but NOT a promise that arbitrary index formats get queueing, online-build correctness, deletion, validation, or SQL integration automatically.

### Cited Findings
- Research base is worktree HEAD `a7349ff657e1448a4f6937535129cfdb5afafcda` (`a7349ff65`), confirmed by `git rev-parse HEAD`; initial `git status --short` was empty. Source findings below concern these bytes. Repository rules require matching declared shared formats and distinguishing workload evidence from readiness — [CLAUDE.md](../../../../CLAUDE.md).
- `IndexMaintainerFactory` requires `IndexTypes() []string`, `NewIndexMaintainer(IndexMaintainerState) (IndexMaintainer,error)`, `ValidateIndexOptions(*Index) error`, and `ValidateChangedOptions(old,new *Index, changed map[string]bool) error`. `RegisterIndexMaintainerFactory` is process-global, intended for package `init()`, canonicalizes type names, and panics on duplicate registration. `IndexMaintainerState` exposes `Store`, `Context`, `Index`, `IndexSubspace`, **`Transaction fdb.WritableTransaction`**, and `Timer` — [registry lines 16–80](../../../../pkg/recordlayer/index_maintainer_registry.go#L16).
- `createIndexMaintainer` obtains `store.context.Transaction()`; the registered factory receives exactly that transaction/context/store. `FDBDatabase.runContexts` creates a fresh record context around each transaction attempt, and its precommit runs checks and flushes version mutations. Explicit `FDBRecordContext.Commit` owns its own corresponding lifecycle. A maintainer must not commit independently or retain transaction-local instances across retries — [store lines 1531–1539,1619–1627](../../../../pkg/recordlayer/store.go#L1531), [database lines 346–380](../../../../pkg/recordlayer/database.go#L346), [precommit lines 421–441](../../../../pkg/recordlayer/database.go#L421), [explicit commit lines 955–966](../../../../pkg/recordlayer/database.go#L955).
- The mandatory maintainer methods are `MergeIndex`, `Update(old,new)`, `UpdateWhileWriteOnly`, the three queue capability/serialization/replay methods, `Scan(TupleRange,continuation,ScanProperties) RecordCursor[*IndexEntry]`, `DeleteWhere`, and **`CanDeleteWhere`**. `old=nil` means insert, `new=nil` means delete — [interface lines 38–99](../../../../pkg/recordlayer/index_maintainer.go#L38).
- External packages can embed `NewStandardIndexMaintainer(state)` and access `Index()`, `IndexSubspace()`, `Transaction()`, `Store()`, `FilteredIndexEntries`, `NewEvaluatedIndexEntry`, `NewIndexEntry` (explicit PK), `NewErrorCursor`, `FilterCursor`, and `RemoveCommonEntries`. This is the working external vector implementation pattern — [exported helper file](../../../../pkg/recordlayer/standard_index_maintainer_api.go#L16), [filtered entries lines 535–550](../../../../pkg/recordlayer/index_maintainer.go#L535), [vector construction lines 24–32](../../../../pkg/recordlayer/vectorindex/vector_index_maintainer_factory.go#L24).
- **Normal maintenance is synchronous.** `updateOneIndex` skips disabled indexes; queued WRITE_ONLY serializes/enqueues; ordinary WRITE_ONLY calls `UpdateWhileWriteOnly`; otherwise it calls `Update` before returning. No detached worker is implicit in a readable index — [store lines 1411–1450](../../../../pkg/recordlayer/store.go#L1411).
- Queueing is explicit, stateful lifecycle support, not an automatic async readable-index path. The base standard maintainer returns false for `IsPendingWriteQueueAllowed` and errors on serialize/replay. The test-only `value_with_queue` factory overrides capability and declares idempotence; vector has production queue support. `MergeIndex` on standard/text/bitmap/atomic/HNSW is a no-op; SPFresh has separate rebalance logic. Deferred-maintenance control is transaction-local and exposes precommit registration for backends that need heartbeat protection, including child transactions — [queue defaults](../../../../pkg/recordlayer/index_maintainer_queue.go#L10), [queue example lines 14–40](../../../../pkg/recordlayer/value_index_maintainer_with_queue_test.go#L14), [deferred control lines 236–262](../../../../pkg/recordlayer/index_deferred_maintenance.go#L236).
- **Key layout freedom exists within owned index subspaces.** `Store.IndexSubspace(index)` and `IndexSecondarySubspace(index)` are exported. HNSW stores graphs under the primary and merge bookkeeping under secondary; SPFresh owns generation-prefixed primary data. TEXT uses a primary bunched token map and secondary tokenizer-version data. BITMAP_VALUE stores raw bitmap bytes with atomic BitOr/BitAnd rather than one tuple entry per record — [store API lines 31–40](../../../../pkg/recordlayer/store_api.go#L31), [vector factories lines 24–55](../../../../pkg/recordlayer/vectorindex/vector_index_maintainer_factory.go#L24), [text fields/construction lines 30–74](../../../../pkg/recordlayer/text_index_maintainer.go#L30), [bitmap layout lines 30–40](../../../../pkg/recordlayer/bitmap_value_index_maintainer.go#L30), [bitmap atomic update lines 196–233](../../../../pkg/recordlayer/bitmap_value_index_maintainer.go#L196).
- Online builds ask optional structural factory method **`IsIdempotent(*Index) bool`** (the interface type itself is private, but its method is exported and externally implementable); absent implementation defaults to false. Idempotent targets use snapshot scanning, with explicit record conflicts on relevant build paths; nonidempotent targets use serializable scans. The indexer invokes maintainer `Update(nil, record)` while backfilling, not its foreground `UpdateWhileWriteOnly` — [registry lines 34–40](../../../../pkg/recordlayer/index_maintainer_registry.go#L34), [idempotence dispatch lines 2416–2454](../../../../pkg/recordlayer/online_indexer.go#L2416), [scan isolation lines 2074–2084](../../../../pkg/recordlayer/online_indexer.go#L2074), [by-index conflicts/update lines 2368–2375](../../../../pkg/recordlayer/online_indexer.go#L2368).
- **Actual online API gap:** the reusable nonidempotent WRITE_ONLY algorithm is private `updateWhileWriteOnlyNonIdempotent`, relying on private `IndexStoreContext.isKeyInIndexBuildRange`, `writeOnlyBuildSource`, and `sourceIndexEntryKey`. An external nonidempotent aggregate cannot simply call this correct by-records/by-index coordination helper. Base `UpdateWhileWriteOnly` is only an unconditional call to the base `Update` and should not be mistaken for dynamic dispatch to an external override. An external idempotent custom maintainer should override `UpdateWhileWriteOnly` explicitly to call its OWN `Update`; nonidempotent maintainers need their own proven protocol or an API change. SPFresh does implement its own staged/generation-fenced protocol — [private context requirements lines 169–188](../../../../pkg/recordlayer/index_maintainer.go#L169), [base pass-through lines 249–254](../../../../pkg/recordlayer/index_maintainer.go#L249), [private algorithm lines 84–180](../../../../pkg/recordlayer/atomic_index_helpers.go#L84), [SPFresh WRITE_ONLY protocol lines 268–307](../../../../pkg/recordlayer/vectorindex/spfresh_index_maintainer.go#L268).
- **Deletion is not free:** `DeleteRecordsWhere` is a primary-key-prefix range-clear operation. Every active index must align with the deleted PK prefix, and the store preflights maintainer `CanDeleteWhere` before staging record clears; queue state serializes a `DELETE_WHERE` operation instead. A custom format must describe its actual prefix semantics and clear ALL its secondary structures itself. The base `DeleteWhere` clears only primary index subspace; embedded overrides must run their own stricter check because method dispatch inside the base is static — [store delete contract lines 21–35](../../../../pkg/recordlayer/store_delete_where.go#L21), [preflight lines 197–234](../../../../pkg/recordlayer/store_delete_where.go#L197), [queue/delete dispatch lines 269–300](../../../../pkg/recordlayer/store_delete_where.go#L269), [base clear lines 505–525](../../../../pkg/recordlayer/index_maintainer.go#L505).
- `DeleteAllRecords` does not call a maintainer hook; it explicitly range-clears store keyspaces including primary index (2), secondary index (3), index build/queue (9), and sliding window (10), preserving header/index-state. Put custom data under primary/secondary, not an invented store-level or external prefix that deletion/rebuild cannot know about. The narrower `DeleteIndexEntries` helper only clears primary — [delete-all lines 1175–1231](../../../../pkg/recordlayer/store.go#L1175), [primary-only helper lines 1151–1172](../../../../pkg/recordlayer/store.go#L1151).

### Inferences
- A per-span secondary posting key updated with Set/Clear and stable record PKs is a better first experiment than an atomic COUNT or shared mutable block: it can be idempotent and avoid the external nonidempotent build-helper gap. However correct online interleavings still need tests, not just a true `IsIdempotent` declaration.
- A retention-first schema needs tenant/time-bucket alignment across records and every custom index, or separate stores per retention bucket. A trace-id-first PK plus unrelated time-prefixed index cannot assume `DeleteRecordsWhere(time)` is available. Whether splitting a trace across retention stores is acceptable is an application-level decision.
- An arbitrary `fdb.WritableTransaction` technically permits writes outside an owned index prefix, but this is not lifecycle support: deletion, state transitions, former-index cleanup, and repair will not follow invented keys.

### Gaps
- No custom OTel online-build/queue/deletion regression has been run. No claim here establishes concurrency safety of a future posting/block/bitmap layout.
- Factory hooks expose no public reusable nonidempotent build coordination API; extending it would be a separate justified production change, not necessary for the suggested proof.

## What serialization, cursor, metadata, planner, and executor integration exists, and what are the actual limits?

### Takeaway
The record and cursor substrate is usable, including protobuf serialization and per-record compression. A direct typed trace-query API over a registered maintainer is achievable now; arbitrary new query semantics are not automatically understood by SQL/Cascades, and some declared extension hooks are only partially wired. We own this Record Layer: these are actionable design inputs for reusable improvements, not external blockers or reasons to distort the tracing architecture.

### Cited Findings
- `FDBRecordStore.SaveRecord` takes `proto.Message`. The store writes a record-type union field around inner protobuf bytes; it preserves prior map-wire ordering where needed and uses deterministic reflection marshal otherwise. Determinism is explicitly NOT canonical or guaranteed byte equality across languages/releases. Keep raw OTLP bytes in an envelope if exact incoming byte preservation matters — [save API lines 522 onward](../../../../pkg/recordlayer/store.go#L522), [serialization lines 2462–2553](../../../../pkg/recordlayer/store.go#L2462).
- Decode rules preserve unknown fields rather than discard them (default `proto.UnmarshalOptions`); closed enums have deliberate Java-compatible handling. Project rules require preserving field presence, open enum values, and unknown fields. This is compatible with storing a complete OTLP message, but flattening into a hand-selected schema can still discard resource/scope/schemaURL/unknown information in application code — [decode options lines 31–50,78–79](../../../../pkg/recordlayer/proto_closed_enums.go#L31), [project serialization rule](../../../../CLAUDE.md).
- Builder `SetSerializer` accepts **concrete `*TransformedRecordSerializer`**, not an arbitrary public `RecordSerializer` interface. Unset writes bare unions. Transformed serializer compresses then optionally encrypts the union, with Java-format transform prefixes/header; zlib compression is kept only if header+compressed bytes are smaller than original. This is record-level compression, not columnar/block compression or an arbitrary custom codec hook — [builder lines 1154–1162](../../../../pkg/recordlayer/store_builder.go#L1154), [transform format and object lines 27–44,114–136](../../../../pkg/recordlayer/transformed_record_serializer.go#L27), [compression lines 444–477](../../../../pkg/recordlayer/transformed_record_serializer.go#L444).
- `RecordCursor[T]` requires `OnNext(ctx)`, `Close`, `IsClosed`; each result carries a continuation and terminal reason. Reasons distinguish source exhaustion from row/byte/time/scan limits. `ExecuteProperties` exposes returned rows, scanned records/bytes, time, isolation and shared scan state; zero limits are unlimited. Internal normal KV/index cursor limit checks and Java wrapped key continuations exist, but they are not a public generic cursor constructor/limiter for arbitrary external raw layouts. An external custom cursor must implement honest accounting and continuation semantics, or delegate to the existing standard `Scan` — [cursor lines 20–65,222–236](../../../../pkg/recordlayer/cursor.go#L20), [properties lines 140–219](../../../../pkg/recordlayer/scan_properties.go#L140), [private limit helper lines 57–71](../../../../pkg/recordlayer/index_cursor_limits.go#L57), [private KV continuation wrapper lines 22–75](../../../../pkg/recordlayer/key_value_cursor.go#L22).
- `ScanIndex` checks scannable index state and delegates a tuple-range scan. `GetIndexMaintainer` is public; `IndexMaintainerAs[T]` unwraps supported decorators. A package can define a typed `TracePostingScanner` interface and obtain it with these two methods, but it must add its own state/budget checks for such a direct path. `ScanIndexByType` has a fixed switch: BY_TEXT_TOKEN and aggregate/rank use concrete built-ins, BY_DISTANCE and ordered vector streaming use public capability interfaces, and default falls back to ordinary `Scan`. There is no registry for arbitrary new typed bounds or scan kinds — [store get-maintainer lines 1142–1148](../../../../pkg/recordlayer/store.go#L1142), [scan dispatch lines 275–313,338–423](../../../../pkg/recordlayer/index_scan.go#L275), [vector interfaces lines 806–820](../../../../pkg/recordlayer/index_scan.go#L806), [generic unwrapping lines 191–202](../../../../pkg/recordlayer/sliding_window_index_maintainer.go#L191).
- **Important actual planner integration hazard (not a whitelist):** relational `metadataPlanContext.buildMatchCandidates` recognizes built-in aggregate/vector candidates, skips built-in atomic types, then falls through to a VALUE-style candidate for remaining indexes. The repository's classification test explicitly calls this fail-open and contrasts Java factory opt-in. An external exotic format is not automatically safe for SQL; keep it outside SQL or wire correct candidacy/plan/executor handling. The factory interface has no planner expansion hook — [candidate generation lines 3227–3282](../../../../pkg/relational/core/embedded/cascades_generator.go#L3227), [classification explanation lines 17–31](../../../../pkg/recordlayer/index_candidacy_classification_test.go#L17), [factory interface](../../../../pkg/recordlayer/index_maintainer_registry.go#L21).
- **Actual validation wiring gap:** although every factory must declare `ValidateIndexOptions`, metadata build currently calls it only for sliding VECTOR or plain VECTOR paths. `validateIndexType` returns nil for custom unrecognized types, without factory dispatch. Thus constructor-time custom validation is necessary today; do not claim generic build-time custom validation works. By contrast `ValidateChangedIndexOptions` DOES dispatch registered factories in its default arm, then validates remaining unhandled options — [type validator lines 109–158](../../../../pkg/recordlayer/index_validator.go#L109), [build paths lines 477–505](../../../../pkg/recordlayer/index_validator.go#L477), [evolution hook lines 833–864](../../../../pkg/recordlayer/metadata_evolution_validator.go#L833).
- Metadata has strict version, PK, record-type-key and union evolution checks; index subspace keys must be distinct and index versions cannot exceed metadata version. Custom layout/version changes should use validated options and new index/rebuild policy, not silently reinterpret existing bytes. Existing generic `ValidateIndex` assumes expected entries come from root key expression and actual entries from primary tuple keys: it is not a custom physical-format validator callback — [evolution version lines 234–245](../../../../pkg/recordlayer/metadata_evolution_validator.go#L234), [identity checks lines 342–355](../../../../pkg/recordlayer/metadata_evolution_validator.go#L342), [index versions/subspace lines 508–522](../../../../pkg/recordlayer/index_validator.go#L508), [generic physical validation lines 47–114](../../../../pkg/recordlayer/index_validation.go#L47).
- OTel SDK/exporter/OTLP protobuf modules are already pinned (`otel` SDK/exporter 1.45.0, OTLP proto 1.11.0), and OTLP is already a direct Bazel module repository. This avoids introducing another protobuf dependency merely to read trace messages — [go.mod lines 30–33](../../../../go.mod#L30), [MODULE.bazel direct repos](../../../../MODULE.bazel#L58).

### Inferences
- **(1) Existing support to reuse:** transactional factory/state delivery, primary/secondary index ownership, old/new record callbacks, metadata versioning, standard cursor abstractions, serialization/compression, index state/build machinery. Avoid rebuilding these in a tracing service.
- **(2) Small reusable upstream-in-this-repository improvements to consider in the RFC:** dispatch `ValidateIndexOptions` to every registered factory during metadata build (retain built-in structural checks and compatibility/loading behavior); make custom query candidacy explicitly opt-in rather than letting unknown physical layouts fall through to VALUE candidates; expose a validated nonidempotent WRITE_ONLY coordination helper with an explicit update callback (cover by-records AND by-index sources), and an idempotent lifecycle helper that does not rely on embedded Go method dispatch. Add focused positive/negative regression cases for each improved contract.
- **(2, continued) Clean query extension direction:** prefer a typed access-method/capability interface or registered descriptor that owns supported scan bounds, output entry contract, ordering/distinctness, cursor continuation identity, isolation and budget accounting. The central store scan path should retain state checks/instrumentation and invoke a backend capability, rather than require each tracing API to reproduce them. Export a reusable bounded raw-KV cursor/scan helper if the chosen posting layout needs it. Reuse/extend `IndexMaintainerAs` for decorator-safe capability discovery. A generic planner candidate provider/capability should explicitly declare applicable logical predicates, returned record identities/covering values, ordering/distinctness and costs; only implement SQL/Cascades integration if the RFC actually requires those queries. An opaque trace-specific scanner method alone is not a universal planner abstraction.
- **(3) Tracing-specific package:** own the lossless OTLP envelope/resource/scope representation, attribute typing/normalization, span/trace identities, time retention layout, physical postings/block/summary indexes, trace-vs-same-span predicate semantics, and query-to-access-path decisions. Keep these out of generic Record Layer APIs. Best physical architecture should drive justified reusable changes, not be restricted to today's inherited standard scan shape.
- These improvements are recommendations inferred from the concrete call-site gaps above, not already implemented APIs and not a mandate to build all of them before a bounded proof. Factory validation dispatch and fail-closed candidacy are particularly small, generally useful correctness improvements; a universal planner plugin framework is potentially larger and should be scoped to requirements.
- A typed application query engine can execute bounded index scans, intersect/union span PK postings, fetch records, and validate trace predicates without SQL planner changes. Trace-wide conjunction and same-span conjunction need different physical/query semantics; registration alone does not supply those semantics.
- Store an envelope with indexed extracted fields plus lossless serialized OTLP data for a first proof. Resource/scope deduplication, stable attribute typing, schemaURL fidelity, and exact wire-byte requirements remain explicit design choices.
- Per-record compression is an available baseline but says nothing about whether dictionary-coded blocks, roaring postings, or a columnar analytics engine will win. Additional compression/layout complexity should await evidence.

### Gaps
- No arbitrary custom scan-type registration API, public generic raw-KV cursor/limit wrapper, general serializer interface, or factory planner hook was found in the examined current interfaces. These are concrete surface limits, not claims about all Java features/parity.
- No semantic OTel query planner, TraceQL integration, or current-cut trace-workload benchmark was found in the scoped source/benchmark search. No global absence proof is claimed.

## Is a small real-FDB proof worthwhile now, and how should it be verified and measured?

### Takeaway
A bounded real-FDB custom-maintainer correctness proof can be worthwhile after the RFC fixes its semantic contract; the current recommendation is a transparent **no-benchmark-yet RFC**, not a raw-KV microbenchmark presented as end-to-end tracing evidence. The custom lifecycle/query implementation is nontrivial and no matched ClickHouse baseline is available. No benchmark, test, container startup, database write, or change to existing container state was performed for this research.

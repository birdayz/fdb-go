# OTel data semantics and real AI-agent observability workloads

## What data model must a Span-record store preserve, and what constitutes a trace relationship?

### Takeaway
A trace store must preserve typed, scoped telemetry—not a flat string tag map—and distinguish span identity, parentage, links, span events, and correlated log events. A span is the right atomic record boundary for many operational lookups, but is not a complete container for a long agent conversation or for GenAI content/evaluation events emitted on the logs signal. [OTLP trace proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/trace/v1/trace.proto); [GenAI events](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/gen-ai-events.md)

#### Identity, envelope, scope, values

- OTLP is `ResourceSpans -> ScopeSpans -> Span`. `ResourceSpans.schema_url` applies to resource attributes; `ScopeSpans.schema_url` applies to scope, spans and their events. The instrumentation scope has name, version, attributes and a dropped-attribute count. Therefore resource, scope and span attributes with identical key text are different fields; schema URLs cannot be collapsed into a single vaguely defined version. [Trace proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/trace/v1/trace.proto); [Common proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/common/v1/common.proto)
- A trace ID is **16 bytes**; a span ID is **8 bytes**, unique **within its trace**, not an independently global database key. Zero or wrong-length IDs are invalid. `parent_span_id` is empty for a root. Start/end timestamps are Unix-epoch **nanoseconds**, distinct from GenAI seconds-valued timing attributes/metrics. Span kind, status, flags/tracestate, events, links and drop counters are independent fields, not inferred from an attribute naming convention. [Trace proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/trace/v1/trace.proto)
- `AnyValue` has a protobuf `oneof`: string, bool, signed int64, double, array of `AnyValue`, key-value-list of `AnyValue`, bytes; all unset represents empty. Nested structures and heterogeneous arrays are representable. Keys in key-value lists must be unique; duplicate-key handling is described as unpredictable. `string_value_strindex`/`key_strindex` are profiling-only and should not be reinterpreted as ordinary span values. [Common proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/common/v1/common.proto)
- The **current** common specification also permits arrays/maps and deep nesting, and describes meaningful empty values, preservation of array positions/nulls, recursive length limits, and a default depth limit of 64. Do not repeat the once-common assertion that OTel can only transport scalar attributes or homogeneous primitive arrays. SDK/language support can still lag; the GenAI convention explicitly provides JSON-string fallback on spans. [Common specification](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/common/README.md); [GenAI content representation](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/gen-ai-spans.md#recording-content-on-attributes)
- Span events have their own name, timestamp and attributes. Their recorded order should be preserved, but custom event timestamps can be out of chronological order and even outside the span start/end interval. Links likewise carry their own attributes and target trace/span context. Resource/scope/span/event/link attributes must not be flattened without an explicit namespace and association rule. [Trace API: events and links](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/trace/api.md); [Trace proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/trace/v1/trace.proto)
- Logs/events can carry trace ID and span ID correlation and a structured body, independently of a Span message. Current GenAI inference detail and evaluation events refer to the logs event model. A deployment configured for `EVENT_ONLY` content capture can have a content-free Span record and content-bearing log event. [Logs data model](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/logs/data-model.md); [GenAI events](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/gen-ai-events.md); [Inference operation details event](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/client-inference.md#event-gen_aiclientinferenceoperationdetails)

#### Causality, arrival and completeness

- A span has **zero or one parent** and any number of children. A child uses the parent's trace ID. Links may refer to a span **in the same or another trace**; multiple links are not multiple parents, and shared conversation IDs do not establish parentage. Links can be added after creation, although samplers may not consider late-added links. [Trace API](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/trace/api.md)
- Ending a span does not end its children. An ended span can still be used as a parent in a context. SDK implementations should ignore later mutation calls to ended spans (with possible streaming-event implementation exceptions). Consequently, even a known root end timestamp does not prove all descendants have arrived or even ended. [Trace API: End](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/trace/api.md#end)
- OTLP explicitly acknowledges duplicate delivery after an interrupted acknowledgment and retry; its delivery guarantee is hop-by-hop, not an end-to-end exactly-once guarantee across a collection pipeline. Partial-success responses report rejected counts and must not be retried as if the whole batch failed. These are delivery semantics, not a standardized ordered revision/upsert protocol for mutable spans. [OTLP specification: reliability, partial success, duplicate data](https://github.com/open-telemetry/opentelemetry-proto/blob/main/docs/specification.md)
- OTel SDK limits and dropped-attribute/event/link counters can make absence genuinely ambiguous. A stored span may not contain a key because the application never emitted it, it was dropped/truncated, sampling excluded related spans, or collection lost data. The underlying Span includes separate dropped counters but cannot reconstruct omitted values. [Trace proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/trace/v1/trace.proto); [Common attribute limits](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/common/README.md#attribute-limits)

### Inferences

- **Design proposal:** primary record key `(tenant, trace_id, span_id)`; preserve the original typed OTLP projection plus independent resource/scope data or immutable references. Make query attribute addresses explicit: `(scope, key)`, with event/link identity and nested path where applicable. A tenant prefix must be an authenticated storage namespace, not a client-controlled OTel attribute.
- **Design proposal:** store int64 and double distinctly; do not stringify everything or route timestamps/int64 through a lossy JavaScript-number representation. Define typed comparison, coercion, NaN/infinity handling, bytes equality, missing versus empty, and JSON-string versus structured-object behavior in the query contract. Preserve raw keys including literal dots; `a.b` as a key is not automatically nested path `a -> b`.
- **Design proposal:** keep a base-span ingest transaction and the affected postings consistent, but make deduplication/conflicting retransmission policy explicit. Candidate policies include byte-identical replay no-op, producer revision where available, and quarantining incompatible same-ID values. **Do not invent a universal “latest arrival wins” rule as OTel semantics.**
- **Design proposal:** track event time, ingestion time, last mutation/version, an operational completeness/watermark state and retention separately. Trace summaries should say “observed span count/error count” unless a stronger application-specific finalization contract exists. A transactionally consistent current view is not a proof of trace completeness.
- **Design proposal:** parent adjacency and link-edge indexes are different structures. A cross-trace conversation/session membership index is a third relation. Keep incomplete/missing-parent edges valid and repairable; do not fabricate an ancestor tree by sorting timestamps.

### Gaps

- Need the RFC to choose whether it ingests correlated logs/GenAI events, or deliberately supports only Span-contained telemetry and documents that `EVENT_ONLY` content/evaluations are not searchable there.
- Need an explicit producer-conflict and correction contract. OTLP itself supplies no monotonic semantic revision for each span.
- Need compatibility testing against the SDK/language versions actually used; the current generic type spec and the GenAI structured-attribute fallback warn against assuming uniform SDK implementation.

## Which GenAI fields and real workloads exist now, and which are drafts, legacy or vendor conventions?

### Takeaway
The live GenAI conventions are **Development**, have moved repositories, and are evolving quickly; a storage design should preserve raw fields and instrumentation/schema provenance rather than hard-code one historic spelling. Conversations, model calls, tool calls, agent definitions/invocations, token usage, evaluation and human feedback are related but different entities; neither trace ID nor a synthesized random ID is a valid substitute for an absent conversation identity. [GenAI overview](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/README.md); [Inference conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/client-inference.md)

### Cited Findings

#### Real agent workloads and vendor/custom boundaries

- **Langfuse sessions** group observations and their enclosing traces by session ID and support session replay/evaluation. This documents a real many-trace interaction model, not one giant trace per lifelong user conversation. Their session-ID restriction (US-ASCII string under 200 characters) is a **Langfuse** implementation constraint, not an OTel trace-ID or conversation-ID standard. [Langfuse sessions](https://langfuse.com/docs/observability/features/sessions)
- The current **Cursor integration** documents one trace per turn, one LLM observation per assistant message, tool executions with input/output/duration/working directory, nested subagents, context compaction events, and skill tags. All turns in a conversation share a session. **Token usage/cost is reported once per turn on the last LLM observation**; naïvely interpreting all intermediate missing counts as zero or assuming every model-looking span has complete usage would misstate costs. Different CLI/cloud surfaces supply less data; the page explicitly documents missing prompt/token data in some modes. [Langfuse Cursor integration](https://langfuse.com/integrations/developer-tools/cursor)
- The same integration derives trace identity from the conversation/turn so a re-export updates the same trace, and ingestion is asynchronous. This is concrete **vendor integration** behavior motivating idempotency/update support; it is not a normative OTLP revision protocol. [Langfuse Cursor integration](https://langfuse.com/integrations/developer-tools/cursor)
- Langfuse accepts `langfuse.user.id`/`user.id`, `langfuse.session.id`/`session.id`, `langfuse.observation.usage_details` JSON, and `langfuse.observation.cost_details` JSON. Its mapping also accepts `gen_ai.usage.cost` into cost totals, but acceptance by a vendor is not standardization. It asks applications to propagate user/session/tags/metadata to **each observation** for per-observation filtering/aggregation, not only root spans. [Langfuse OTel property mapping](https://langfuse.com/docs/opentelemetry/get-started#property-mapping)
- Particularly relevant to arbitrary custom attributes: Langfuse's mapping docs say ordinary OTel span/resource attrs land under `metadata.attributes` / `metadata.resourceAttributes`; only top-level metadata keys are filterable. Emit `langfuse.observation.metadata.<key>` to make that property top-level/filterable. This is an observed product behavior that a purpose-built typed-attribute lookup could address; it does **not** establish a universal limitation of ClickHouse, OTel, or all observability platforms. [Langfuse OTel metadata filtering](https://langfuse.com/docs/opentelemetry/get-started#property-mapping)
- Langfuse tracks usage details and **USD** cost details, accepts provider/SDK values, otherwise infers from model definitions/prices; ingested values take precedence. Prices/usage types are model-specific; hidden reasoning tokens prevent accurate cost inference from visible text alone in the documented reasoning-model example. [Langfuse token/cost tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)
- **OpenInference is a separate Arize-led convention**, not interchangeable with OTel GenAI semconv. Its own specification uses `openinference.span.kind`, `session.id`, `user.id`, `llm.token_count.prompt`, `.completion`, `.total`, `llm.cost.prompt`, `.completion`, `.total` (USD), `input.value`, `output.value`, flattened indexed message paths and JSON-string metadata. Preserve these as namespaced source conventions or explicitly versioned adapters; do not silently rename them to a supposed universal stable `gen_ai.*` schema. [OpenInference semantic conventions](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md)
- Human **corrected outputs** in Langfuse are shown alongside originals with a diff and used for training/evaluation. This means “correction” may mean an annotator's desired answer, not correction of the telemetry record or retroactive model output. [Langfuse corrected outputs](https://langfuse.com/docs/observability/features/corrections)

### Inferences

- **Design proposal:** record source convention/schema/instrumentation provenance, retain raw names and types, and expose explicitly versioned normalized fields for common queries. Avoid a destructive ingestion migration that makes historical instrumentation impossible to inspect.
- **Design proposal:** exact identifiers worth purpose-built indexes include authenticated tenant/project, `gen_ai.conversation.id`, provider `gen_ai.response.id`, provider tool-call ID, general `user.id` or permitted pseudonym, agent ID/version, and **custom** `app.run.id`, repository, workflow/task, prompt version, feature/team and customer identifiers. Names beginning `app.*` here are examples for the RFC, **not standardized OTel fields**.
- **Design proposal:** correlate aliases (`gen_ai.conversation.id`, OpenInference/Langfuse `session.id`) through configurable, auditable mappings with explicit conflict rules. Conversation scope may be provider-specific; qualify by tenant/project/provider where needed. No evidence says provider response/tool/session IDs are globally unique across all tenants/providers.
- **Design proposal:** model observed usage, inferred usage, billed usage, cost and human evaluation as distinct values with provenance, currency/unit and pricing version/effective time. Do not reconstruct costs by summing every numeric attr, summing inclusive input plus cache subsets, or double-counting a parent aggregate and child call costs.
- **Design proposal:** keep long conversation membership/querying independent of span lifetime and trace parentage. Provide trace-per-turn + session-across-turns as a first-class workload, including resumed sessions and tool/subagent spans. A conversation index is useful even when instrumentation emits no cross-trace links.
- **Design proposal:** attribute lookup and its APIs must support ordinary microservice resource/span attrs as well as `gen_ai.*`; e.g. service/env/version + HTTP route/error + DB system/operation, with arbitrary customer rollout/request keys. GenAI is not a reason to make the store unusable for network/database/tool-service spans in the same request graph.

### Gaps

- No representative customer workload distribution or vendor-independent measured ingest/query scale was established in these sources. Do not claim these sources prove 100k spans/s, a latency SLO, or FoundationDB superiority over ClickHouse.
- Agent ID, response ID, session ID and user ID namespace/propagation quality must be validated per actual SDK/provider; documentation is not evidence every event carries every identifier.
- Need selected source conventions/SDK versions for an interoperability matrix. The current Development snapshot is unusually rich and must not be confused with what deployed SDKs from earlier years emit.

## Which queries deserve purpose-built transactional indexes, and how do privacy and incomplete telemetry constrain them?

### Takeaway
The strongest candidate workload is selective tenant-scoped operational retrieval—exact IDs and custom attributes, narrow ranges, trace/session reconstruction and structural filtering—combined with predictable ingest/update/delete visibility. Index design must distinguish same-span, same-event, any-span-in-trace and any-trace-in-session quantification; sensitive payload indexing must be a separate explicit opt-in, not an accidental consequence of “index all attributes.” [TraceQL scope/structure semantics](https://grafana.com/docs/tempo/latest/traceql/construct-traceql-queries/); [OTel sensitive content guidance](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/gen-ai-spans.md#capturing-instructions-inputs-and-outputs)

### Cited Findings

- TraceQL distinguishes intrinsic fields from scoped custom attrs: `span:duration`, `trace:duration`, `event:name`, `link:traceID`, instrumentation name/version versus `span.foo`, `resource.foo`, `event.foo`, `link.foo`. Its docs explicitly distinguish conditions joined on the same span, matching multiple spans in a trace, descendant/child/sibling relations and trace-level intrinsics. This is a useful primary example of a real query language exposing the distinctions our indexes must not erase. [TraceQL query construction](https://grafana.com/docs/tempo/latest/traceql/construct-traceql-queries/); [Trace structure](https://grafana.com/docs/tempo/latest/traceql/trace-structure/)
- The GenAI content section says instructions/prompts/responses are often **large and sensitive**, should **not be captured by default**, and suggests external storage with separate access controls for production. Structured content may exceed backend envelope/attribute limits and may need structure-preserving truncation. The common convention has a **TODO** for standardized external-content reference representation and a **TODO** for streaming chunks; do not invent either as settled interoperable OTel formats. [GenAI content capture/storage](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/gen-ai-spans.md#capturing-instructions-inputs-and-outputs)
- Current draft content capture configuration uses `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT` with `NO_CONTENT` default, `SPAN_ONLY`, `EVENT_ONLY`, `SPAN_AND_EVENT`; invalid values should fall back to no content. It gates instructions/messages/tool arguments/results/retrieval query/prompt variables/memory content. **Tool definition schemas are explicitly not governed by this switch**, so application privacy policy still must assess descriptions/schemas/URLs/custom attrs. [GenAI content configuration](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/gen-ai-spans.md#content-capture-configuration)
- Provider/request streaming is modeled, inference logical spans should last until the response is fully received or error/cancellation, and partial streamed output may still be recorded when content capture is enabled. `fetch_response` spans can observe queued/in-progress/completed/failed/cancelled lifecycle states, but should **not** report token usage again. This prevents a response-polling loop from inflating token totals. [Inference semantics](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/client-inference.md); [Fetch response span](https://github.com/open-telemetry/semantic-conventions-genai/blob/e19717d65f890955777b044bca2a3cd71ae8b498/docs/gen-ai/gen-ai-spans.md#fetch-response)
- OTel security guidance discusses collecting only necessary data and filtering/redacting/hashing sensitive information. Langfuse supports client-side masking of inputs/outputs/metadata before export. Its Cursor integration documents that prompts, assistant thinking, tool I/O, file edits and other context can be uploaded, demonstrating why content policy must cover more than text chat. [OTel sensitive-data handling](https://opentelemetry.io/docs/security/handling-sensitive-data/); [Langfuse masking](https://langfuse.com/docs/observability/features/masking); [Cursor data privacy](https://langfuse.com/integrations/developer-tools/cursor)
- Langfuse warns baggage is propagated across service boundaries and third-party APIs. Copying sensitive user/customer information into baggage to make all spans filterable has a cross-boundary exposure risk; propagation is not authorization. [Langfuse OTel attribute propagation](https://langfuse.com/docs/opentelemetry/get-started#property-mapping)

### Inferences

#### Representative query/workload matrix — proposed evaluation workload, not measured performance

All examples below are **design proposals**, grounded in the source workloads above. `app.*`, cost columns and normalized session fields are explicitly custom/storage projections. Each query is tenant/ACL scoped and normally bounded by an explicit time horizon.

| Query/workload | Exact semantics / example | Candidate physical support | Semantic/performance trap to test |
|---|---|---|---|
| Direct span / full trace | `(trace_id, span_id)` detail; enumerate all observed spans in a trace, including late children | Primary key `(tenant, trace_id, span_id)`; trace-membership/time ordering as required | A trace ID does not authorize access; a root's presence/end is not trace completeness. |
| High-cardinality exact custom lookup | `span.app.request_id = X`, `resource.app.repository_id = R`, provider response/tool ID exact match | Scoped typed equality postings ending in span PK; selected composite hot indexes | Do not force users to promote attrs to vendor metadata namespaces; limit fan-out and protect sensitive identifier postings. |
| Same-span conjunction | A **single span** has `gen_ai.request.model = M AND error.type = timeout AND app.feature = F` | Intersect postings **by span PK**, or composite index for a demonstrated hot combination | Intersecting only trace IDs gives false positives when different spans satisfy the clauses. |
| Trace existential across spans | Some span has model M **and some possibly different span** has failed tool `charge_card` | Project each span-level match to trace ID, intersect; retain witness span IDs | Not the same as same-span AND; explain returned witness spans and deduplicate trace IDs. |
| Same event / same link / same array object | One event has evaluation name N **and** score < V; one tool-call message has name T **and** argument field K | Postings carry event/link/array-element identity or verify candidates against source record | Flattening all event attrs or every array leaf creates cross-event/cross-element false positives. Preserve choice index, message role and nested object association. |
| Cross-trace conversation / user journey | Replay all turns for conversation C; find sessions containing expensive call **and later** denied tool action | Conversation/session-to-trace membership ordered by observed operation time; separate user-to-session map where permitted | Shared IDs are correlation, not ancestry; session may span retention windows and providers, and IDs may exist only on selected spans. |
| Structural relation | Failed `execute_tool` descendant of agent A; tool-service HTTP span child of tool wrapper; sibling parallel model calls | Parent adjacency + bounded ancestor verification; optional maintained ancestry summaries only if justified | Descendant != temporal overlap; links != parents; sampled/missing parents yield unknown paths. Transitive closure can be expensive to maintain on late parent arrival. |
| Linked async workflow | Agent turn links to queue consumer or another trace; inspect reverse incoming links | Forward/reverse link index keyed by `(tenant,target_trace_id,target_span_id)` | A link may point outside retained data; shared session ID alone does not prove a link or causal edge. |
| Time/error/duration filters | Service/env/route error spans started in [T0,T1), duration > D; slow model or tool calls | Tenant/service/time + selected duration/status range indexes; overlapping-time support if needed | Start-time window versus interval overlap differ. OTLP timestamps are ns, duration often projected ns, GenAI first-chunk attr seconds. Trace duration from observed extrema differs from root duration and sum of spans. |
| Token / cost threshold | Calls with output > N; sessions with known billed cost > C; cache-read ratio low | Typed numeric range postings for popular keys; per-trace/session aggregate records if update semantics are specified | Unknown != zero; subsets overlap; parent and child totals double-count; inferred and reported costs differ; currency/pricing version matter. |
| Real-time incident tail | New errored tool calls for feature F after ingestion cursor; read after acknowledged ingestion | Ingest-version/time index plus stable continuation; transactional postings update | Event time can precede arrival by hours; corrections/deletes change prior results; “consistent snapshot” and “live tail” need separate contracts. |
| Arbitrary attribute discovery | Which keys/types exist for this service/env/time? What values/prefixes occur for selected key? | Scoped key/type presence catalog; bounded value enumeration; count/sampling policy | Catalog leaks secrets/tenant names; global cardinality counters create write hotspots; “not indexed” != “absent”. Time-bucket expiry/redaction must maintain counts or document approximation. |
| Array membership / nested lookup | `finish_reasons` contains `length`; tool args `customer.region = EU`; document metadata match | Explicit scalar membership index or opted-in nested-path postings; element witness where conjunction matters | Whole-array equality differs from membership; mixed types/empty/null and dotted literal keys require defined semantics; giant arrays multiply mutations. |
| Substring/regex/full text | Prompt contains secret pattern; answer semantic/vector search | Separate **explicitly enabled** content/text/vector index or external engine; bounded scan fallback | Equality indexes do not implement substring or semantic retrieval. Blindly indexing prompts leaks content and explodes index fan-out. |
| Dashboard/global analytics | Hourly model spend/tokens, percentiles by service/model/release, broad multi-tenant scans | Precomputed aggregates, analytical replica/store, or separately benchmarked scan path | A transactional inverted index is not evidence of competitive large scans, approximate distincts, compression or percentile aggregation. Compare ClickHouse/Tempo/other choices fairly. |
| Redaction / subject deletion | Remove user U's prompt/tool payloads and all derived searchability; preserve permitted operational counters | Subject/content reverse references, policy-versioned postings, delete/tombstone generations, async verified cleanup for large fan-out | One record delete does not remove postings, object blobs, caches, replicas, aggregate contributions, backups or exported datasets. Multi-trace deletion can exceed one transaction. |

#### Purpose-built index contract — proposals to take into the RFC

These are desired semantic/physical capabilities, **not constraints imposed by today's Record Layer APIs**. Because this project owns the Record Layer, the RFC may propose new index-maintainer/scan/planner/transactional-summary extension points where that is the clean architecture; classify implementation gaps separately from the target design. No prototype or production changes were made in this research workstream.

1. **Typed, scoped equality as the base arbitrary-attribute capability.** A conceptual posting key is `(tenant, scope, key, value_type, canonical_value, time_bucket?, trace_id, span_id, occurrence?)`. It is conceptual, **not** a claim that one giant FDB tuple encoding is safe for every payload. Long values require size limits/digests plus collision verification or no index. A digest is not redaction or anonymization.
2. **Separate coverage from storage.** Store raw accepted attributes without promising every one is indexed. Expose which keys/types/paths are indexed, policy version, key-count/value-size/array/depth budgets, exclusions, rebuild state and fallback behavior. Otherwise “arbitrary attr query” can silently return false negatives.
3. **Same-span first, trace-set second.** Index intersection on span PK answers a conjunction; projection to trace sets answers existential trace queries. Maintain witnesses for explaining matches. A “trace contains A and B” posting schema alone cannot correctly implement same-span conjunctions.
4. **Hot composites are workload decisions.** Service/env/time, provider/model/error/time, conversation/time, and tenant custom request ID are candidates, not a request to index every permutation. General equality postings plus bounded candidate verification are a safer baseline than exponential composite coverage.
5. **Range policy is separate from equality policy.** Numeric duration/token/cost/time queries need ordered typed keys or targeted projections; stringified numerics are incorrect. Prefix/regex/full-text/nested-path semantics require explicit support, not an equality-index marketing claim.
6. **Update/delete work must retract old derived values.** Atomic per-span replacement should remove obsolete postings and summaries rather than append another count. Session/trace summaries need non-monotone correction handling, idempotent contribution identities and rebuild paths. Large fan-out maintenance may require generations/watermarks rather than pretending an entire trace/session update fits one transaction.
7. **Operational freshness is measurable.** Benchmark time from durable ingest acknowledgment to equality/range/trace/session visibility, plus correctness under concurrent updates/deletes; do not call eventual ingest “read-your-writes” without defining the acknowledgment boundary.
8. **Performance hypotheses, not findings:** selective lookup might benefit from transactionally maintained postings and span-record locality; broad scans/aggregations might favor columnar analytics. Measure ingest bytes, mutations/postings per span, write/read amplification, p50/p95/p99 tail latency, range selectivity, retention churn, ACL checks, payload-fetch cost, and rebuild/deletion duration on **the same data/query semantics** before comparing FoundationDB with ClickHouse.

#### Privacy, ACL and large-payload contract — proposals, not claims of legal compliance

- **Default metadata-only indexing.** Content capture opt-in and **content indexing opt-in are separate decisions**. Receiving `gen_ai.input.messages` does not authorize creating equality, full-text, embedding or nested-path indexes over it. Treat tool arguments/results, retrieval documents, prompt variables, instructions, shell/file content, thinking, custom attrs, names/descriptions and externally stored URLs as potential sensitive data.
- **Policy before persistence.** Apply authenticated tenant assignment, allowed-key/type checks, redaction and content routing before writing both base records and postings. An ingest pipeline that redacts only the display projection still leaks secrets through indexes. Record policy version and provenance; preserve an appropriate operational indication of omission without retaining the removed secret.
- **Separate content objects/access.** Keep compact operational span metadata and secure large payload references/objects separate where justified. Enforce different ACLs and retention for content, and authorize blob reads independently. Do not place signed bearer URLs or entire payloads into ordinary index keys. Reference formats remain an OTel TODO, so any proposed URI/digest schema must be explicitly product-defined.
- **No hidden index side channels.** Apply tenant/row/content authorization to query planning, postings, key discovery, facet counts, search suggestions, session/trace reconstruction, export and errors; a user prohibited from content should not learn it through a facet or existence oracle. Default-deny cross-tenant linked-trace traversal.
- **Deletion is a workflow.** Enumerate records, payloads, derived indexes/aggregates, evaluation/feedback links, object versions, caches and downstream analytical copies. Use deletion generations/tombstones to hide data before all physical cleanup completes, reject resurrection from replayed late telemetry where policy requires, and verify completion. Scope backup/export retention requirements separately; no source supports declaring universal GDPR compliance from transactional delete alone.
- **Sampling/retention and negative predicates.** Define “no matching tool/error/user attr” as absence among **observed authorized indexed telemetry**, not proof no such operation occurred. Distinguish unknown/missing/dropped/not-indexed/redacted; avoid negative searches that falsely imply completeness.

### Gaps

- Need actual workload traces with attribute cardinality/type distribution, array/nested depth, message sizes, duplicate/revision rates, trace/session length, late-arrival distribution, retention and ACL fan-out. Public documentation provides realistic shapes, not sizing data.
- Need product choices for index coverage budgets and “arbitrary attr” fallback (bounded scan, asynchronous index build, explicit unsupported query); silently incomplete search is unacceptable.
- Need formal query semantics for absent versus null/empty, integer versus double comparison, whole-array equality versus membership, same-element nested conjunctions, event/log correlation and time-window membership for long traces/sessions.
- Need sensitivity policy and deletion requirements from the actual deployment. Neither OTel's opt-in controls nor masking examples establish sufficient authorization, legal basis or deletion guarantees.
- Need clarify whether corrected telemetry, human corrected answers, provider cost reconciliation and late evaluation scores are separate records/revisions; treating all as “Span upsert” destroys meaning.
- Need comparative benchmarks under matched data/query/retention semantics. This research makes **no claim** that FoundationDB is faster or cheaper than ClickHouse, Tempo, OpenSearch or another tracing/analytics store.

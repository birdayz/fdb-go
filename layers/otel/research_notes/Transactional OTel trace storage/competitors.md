# Competitor storage engines and fair performance comparisons

All sources were fetched 2026-10-27. Search performed with Google HTML and Bing RSS for “clickhouse lightweight projections observability”, “tempo traceql dedicated columns”, “langfuse clickhouse tracing architecture”, and “jaeger elasticsearch storage indexes”. Google returned a JavaScript challenge rather than usable search results; Bing RSS returned results, though most Tempo/Jaeger results were irrelevant. Findings below come from directly retrieved primary documentation and source, not search snippets. No benchmark was run.

## What can a current, well-tuned ClickHouse trace backend do?

### Takeaway
ClickHouse is an indexed, compressed columnar engine with several independently tunable access paths, not simply a full table scan. Compare against a realistically configured current version, including physical design and ingest semantics, rather than an untuned default.

### Cited Findings
- GitHub's latest-release API returned ClickHouse **v26.10.2.103-stable**, published October 24, 2026; pin the exact artifact and edition for any test rather than assuming docs describe an older installation. [ClickHouse release API](https://api.github.com/repos/ClickHouse/ClickHouse/releases/latest)
- MergeTree sorting determines physical order and a sparse primary index; ClickHouse's official OTel example includes bloom skip indexes on TraceId, resource/span map keys and values, a minmax duration index, ZSTD, and time partitioning. This is already a much stronger baseline than scanning every span. Skip indexes eliminate granules, not necessarily individual rows; bloom false positives still require data verification. [OTel schema guide](https://clickhouse.com/docs/use-cases/observability/schema-design); [skip indexes](https://clickhouse.com/docs/optimize/skipping-indexes)
- Projections can store an alternative physical ordering. Since 25.5, a projection may store sorting keys plus `_part_offset` and retrieve other columns from the base part, or mix stored columns and offsets. The current guide describes multiple projections contributing to pruning; use `EXPLAIN` to establish actual selected paths. The guide says lightweight updates and deletes are unsupported on tables with projections, an important design/semantics constraint. [Projections](https://clickhouse.com/docs/data-modeling/projections)
- Current production text-index documentation recommends version >=26.2. A text index is an inverted mapping of tokens to row numbers, supports String, arrays and Map expressions, and has configurable tokenizer and compressed posting lists. Tokenized matching must not silently substitute for exact typed attribute semantics; verify original values and null/absence distinctions. [Text index](https://clickhouse.com/docs/engines/table-engines/mergetree-family/textindexes)
- `Map(K,V)` is an array of tuples and can contain duplicate keys; `m[k]` scans the map, linear in its size. The current guide also documents alternate bucket serialization; measure the chosen representation and query shape rather than assuming every map query performs equally. Promote frequent fields to typed columns or projections, while retaining arbitrary attributes and exact semantics. [Map type](https://clickhouse.com/docs/sql-reference/data-types/map)
- PREWHERE delays reading other columns until filter columns narrow surviving blocks; materialized views process inserted blocks into target tables and can preaggregate, with additional storage/write/merge cost. Projections and MVs differ in filters, joins, TTL, and chaining; include both where useful. [PREWHERE](https://clickhouse.com/docs/optimize/prewhere); [incremental materialized views](https://clickhouse.com/docs/materialized-view/incremental-materialized-view); [projections](https://clickhouse.com/docs/data-modeling/projections)
- With async inserts, `wait_for_async_insert=1` acknowledges after successful flush; `=0` acknowledges on buffering and may hide later failure. Async deduplication requires configuration; retry dedup has engine/settings/window constraints, so it is not equivalent to indefinite per-span uniqueness. ReplacingMergeTree replacement happens at background merges and is not a guarantee that duplicates are immediately absent; `FINAL` changes query work. [Async inserts](https://clickhouse.com/docs/optimize/asynchronous-inserts); [retry deduplication](https://clickhouse.com/docs/guides/developer/deduplicating-inserts-on-retries); [ReplacingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree)

### Inferences
- Use competing tuned CH variants: time/service ORDER BY plus selective TraceId and attribute skip indexes; alternative projection on tenant/trace ID or attribute/time; targeted materialized columns/MVs; text index only for eligible text predicates. Count all copies and ingestion work. Test `EXPLAIN` and actual granules, not the existence of DDL alone.
- Selective, high-cardinality arbitrary attributes distributed across time can make granule skips ineffective; projections or text postings can change that, so FDB advantage is a hypothesis dependent on query shape and index design—not a general claim.

### Gaps
- Exact replication, crash durability, read-after-write and deduplication guarantees depend on engine, quorum, asynchronous settings, topology and query routing; they must be configured and experimentally checked, not inferred from `wait_for_async_insert` alone.
- No direct speed or dollar comparison was measured. Current docs are live and can change; archive versioned docs and schemas for a future experiment.

## What do trace-native and agent-observability systems teach us?

### Takeaway
Trace queries include topology and session semantics beyond a span filter, and other systems already optimize for them. Agent applications expand the data model to multi-trace sessions, token usage, evaluations and large multimodal payloads.

### Cited Findings
- Tempo latest-release API reports **v3.1.1**, published October 21, 2026. Its vParquet5 is documented as the default from Tempo 3.1, with up to 20 dedicated string and 5 dedicated integer columns per span/resource/event scope, event-scoped columns and blob compression options for high-cardinality/long strings. Version and block format must be pinned in comparisons. [Tempo release API](https://api.github.com/repos/grafana/tempo/releases/latest); [Tempo Parquet schema](https://grafana.com/docs/tempo/latest/configuration/parquet/)
- Tempo search shards queries into jobs and uses vParquet blocks and configurable dedicated attribute columns; caches include bloom, Parquet page and footer caches. TraceQL supports scoped attributes and structural operators including descendant, child and sibling relationships. Matching these semantics is a materially harder benchmark than simply selecting spans with a SQL predicate. [Tempo backend search](https://grafana.com/docs/tempo/latest/operations/backend_search/); [TraceQL](https://grafana.com/docs/tempo/latest/traceql/construct-traceql-queries/)
- Jaeger 2.22 documents separate Elasticsearch storage configuration, Elasticsearch 7/8 compatibility, shard/replica choices, write modes, idempotency, durability-versus-searchability, and index lifecycle management; it also offers Cassandra and ClickHouse backends. Jaeger is not itself one storage/index architecture. [Jaeger Elasticsearch](https://www.jaegertracing.io/docs/latest/storage/elasticsearch/); [Jaeger storage](https://www.jaegertracing.io/docs/latest/storage/)
- Langfuse architecture separates Postgres transactional workloads, ClickHouse traces/observations/scores, Redis/Valkey queues, and S3/blob data. It describes a mostly immutable observations table avoiding read-time joins/deduplication, persisting incoming events to S3 first, and storing multimodal payloads in blob storage. This is a meaningful alternative to compare as an end-to-end pipeline, not just a DB microbenchmark. [Langfuse self-hosting](https://langfuse.com/self-hosting)
- LangSmith describes runs as units of work, traces as a single operation and threads as multi-turn sessions joining traces; a trajectory flattens session messages. These are domain requirements, not evidence of a particular internal storage engine. [LangSmith observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- Lucene 10.3's postings format uses packed integer blocks for fast decode. The transferable principle is to combine compressed, ordered posting lists for selective predicates, while retaining correct final verification and accounting for index/update cost. [Lucene postings](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/codecs/lucene103/Lucene103PostingsFormat.html); [ClickHouse text index](https://clickhouse.com/docs/engines/table-engines/mergetree-family/textindexes)

### Inferences
- Transactional index candidates: `(tenant, trace_id, time, span_id)` for reconstructing traces; `(tenant, session_id, time, trace_id)` for multi-trace sessions; `(tenant, attribute_key, type, value, time, trace_id, span_id)` for selective typed predicates; and parent/child lookup for topology. These are hypotheses, not verified existing Record Layer functionality. Avoid cross-tenant leakage, accidental same-trace versus same-span intersection, and duplicate/missing updates.
- Dense bitmap intersections favor common terms but can be large/hot for popular tenant-attribute pairs; sorted/compressed postings favor sparse terms but amplify writes, compaction and pagination. Numeric ranges need an ordered encoding or another appropriate index. Treat hybrid choices as experiments.
- Likely transactional-index candidates for a win: point trace retrieval, small selective custom-attribute sets, read-immediately-after-write correctness, incremental parent/child navigation, and idempotent modifications under bounded index fanout. Likely columnar strengths: broad time windows, large result sets, aggregation, quantiles, scans of a few compressed columns, and storage cost per span. Both remain unmeasured hypotheses.

### Gaps
- Jaeger's actual index mapping and query plans, Phoenix's production persistence architecture, and LangSmith's proprietary storage architecture were not sufficiently verified; no internal engine claim for those products should be made. TraceQL relationship semantics are not automatically equivalent to a proposed SQL implementation.

## How should a defensible comparison be run?

### Takeaway
Define equal observable semantics and report a multidimensional Pareto frontier, not one latency number. Pay for all indexes, replication, background work, freshness, retention and auxiliary systems, and verify answers before comparing speed.

### Cited Findings
- ClickHouse's documented buffering and background duplicate removal affect acknowledgement, visibility and answer correctness; Tempo's dedicated columns and cache hierarchy affect query cost. These are workload variables, not implementation details to omit. [Async insert](https://clickhouse.com/docs/optimize/asynchronous-inserts); [ReplacingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree); [Tempo search](https://grafana.com/docs/tempo/latest/operations/backend_search/)

### Inferences
- **Fixture and correctness:** deterministic seeded OTLP spans with trace/span IDs, tenant, timestamp, resources, custom typed attributes, events, links, errors, duration, model/provider, token and cost fields; realistic missing, repeated and late spans, updates/deletes/retries and duplicate IDs. Generate an independent reference oracle for exact span sets, trace sets, tree relationships, counts, order and continuation boundaries; define snapshot/cutoff semantics and make every answer match, including cross-tenant authorization and map duplicate keys.
- **Equal contract:** same data retention, coverage and payload (including object storage if used), accepted loss/failure model, replica count and failure domains, durable acknowledgement/quorum, retry/idempotence guarantees, index visibility and query freshness SLO, concurrent update semantics, exact vs approximate aggregates. If equivalent consistency cannot be configured, report it as a semantic difference and separate results, not a win. Measure ingest-to-durable-ack and ingest-to-queryable distribution, and correctness at each stage; test crash/restart and retry.
- **Tuned configurations:** disclose exact software/build, schema, partitioning, indexes/projections/MVs, table engines, cache, thread counts, shard/replication placement, batching, TTL, collector, compression and query plans. Tune CH indexes/ordering independently for each declared workload, including a single mixed-workload configuration and cost of alternative copies. Tune FDB key distributions, indexing and partitioning equally; no free asynchronous side index if freshness differs. Include Tempo separately only for workloads with equivalent supported semantics.
- **Workload grid:** trace lookup and tree reconstruction; short and very long sessions spanning many traces and partitions; span vs trace-level AND/OR and ancestor/descendant predicates; arbitrary high-cardinality keys and rare/common values, known and previously unseen fields, absence/null; ranges on time/duration/cost and exact text vs token search; top-k, group-by, quantiles, scans and large exports; tenant skew, bursty hot IDs, out-of-order spans, retries, update/delete and TTL expiry. Sweep selectivity, cardinality, field count, result size and 1h/1d/retention-wide windows.
- **Method:** run at least three independent repetitions per setting with randomized order, fixed seeds and separately disclosed warm/cold cache conditions; at least 10,000 completed operations per query class per run for preliminary p99, with confidence intervals and raw histograms. Increase sample count when tails or run-to-run variance are unstable. Use open-loop offered load plus concurrency sweeps to expose queueing; record timeouts/errors as outcomes, not discarded latencies, and avoid coordinated omission. Include idle, sustained ingest, and concurrent ingest+query at several utilization levels until saturation; hold datasets steady before each comparison.
- **Scale/cost:** start with a declared concrete population and several growth points (e.g. 10M, 100M, 1B spans where feasible), span/trace/session distributions and actual bytes, rather than only a synthetic uniform dataset. Same provisioned hardware, cores, RAM, SSD, network and placement; disclose $/hour and amortized storage costs if cloud. Measure data+index+replica+logs+blob bytes, peak/steady disk, bytes written, compaction/merge debt, CPU, I/O, network, ingest spans/s, sustainable query throughput, p50/p95/p99 and tail confidence, per-tenant fairness and recovery; include initial build/backfill and expiration costs. Compare total cluster including collectors, queues and object storage at equal availability.
- **Interpretation:** present absolute results and ratios per query class with sample count, hardware, cache and exact version; stratify by selectivity and growth. Only assert a win for measured configurations that pass equivalence and freshness checks. Include negative results and cases where CH wins.

### Inferences (concrete, falsifiable candidate experiment)
- **Fixture, proposed rather than measured:** 100M spans, 10K tenants, 30-day retention; 50% of spans in largest 1% of tenants with Zipf-distributed tenant traffic; 100 services; 10 attributes/span median and 50 at p99; 1K distinct attribute keys per tenant across the corpus. Distribute attribute values with explicitly recorded frequencies: model/provider/operation each 10–100 values; user/session 10K–1M per large tenant; `customer.request_id` or tool-call ID near unique. Include scoped GenAI attributes `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model` and `gen_ai.response.model`, verifying names and types against the exact semantic-convention version selected for the test; do not assume every SDK populates them. Generate 90% short traces (2–20 spans), 9% medium (21–1K), 1% long (1K–100K); independently generate multi-trace sessions (median 10 traces, p99 10K) with late arrivals and sessions crossing time partitions. The exact numbers are seeds to vary, not claimed real-world distributions.
- **Explicit query classes:** (1) tenant + trace ID, fetch all spans; (2) tenant + exact session ID, ordered trace summaries, paginate 100 at a time, plus full-session completion; (3) tenant + rare custom key/value + 24h time range, selectivity 1 in 1M spans, return newest 100 matching trace IDs; (4) tenant + `gen_ai.request.model` + provider + error in last hour, plus a separate `gen_ai.response.model` query; (5) rare request ID plus common operation name, with same-span semantics vs explicitly separate same-trace semantics; (6) duration/cost range + service over 1h, 1d, 30d with counts and group-by; (7) parent/descendant error relationship. Vary both cardinality and selectivity independently: high cardinality alone does not guarantee rare query results. Include absent keys and typed comparisons. All implementations must preserve same scope, sort order, result cap and tie-break, result verification, and retention window.
- **Strong ClickHouse counterfactual:** benchmark full original Map plus optimized bucket serialization where supported; compare common GenAI attributes as typed materialized columns with practical ORDER BY and alternate projection(s), sparse primary-key pruning, PREWHERE, bloom indexes for map keys/values, text indexes where appropriate, and a targeted MV or alternative physical table for rare exact key/value queries. Measure both known indexed keys and unforeseen rare keys; use key/value pair encoding or verification to prevent false associations, and exact checks after probabilistic/token indexes. Include backfill, duplicate handling and all additional copies. Make execution evidence (`EXPLAIN`, granules read, selected marks, bytes read) mandatory. A comparison that only scans an unoptimized Map is not evidence against ClickHouse.
- **Target contract, not a promise:** an experimentally testable target is tenant-scoped rare exact attribute search returning the newest 100 distinct trace IDs, and point-trace retrieval, over a 24h window, at p99 <100 ms end-to-end while 99% of successfully durably acknowledged individual spans are visible to both lookup and search within 1 second and 99.9% within 5 seconds. A query must match the exact oracle at its declared read snapshot; span+index publication should be atomic if claiming transactional freshness. Define a trace as partial unless a specific completion signal exists: this contract does not assert entire distributed traces are complete at first span ack. Measure visibility from durable ack, not from receiver buffering, and disclose client/collector clocks and timing errors. This is a proposed target only; 100 ms and 1 s are not verified capabilities or user-approved SLOs.
- **Disproof:** reject an FDB win for that workload if any backend fails the same correctness/tenant isolation/durability/freshness gates; if optimized CH has equal or lower p99 at matched sustainable offered load, hardware and replication; or if FDB p99 advantage disappears when full indexed storage, CPU and write throughput are counted at equal budget. Publish confidence intervals and complete latency/visibility distribution and repeat across warm/cold, skew, and growth points; an advantage at one point does not generalize. For an apples-to-apples stronger target, compare at both equal hardware and equal total cost. Long sessions crossing transaction/snapshot lifetimes require explicit pagination consistency and cannot silently be called one atomic snapshot.

### Gaps
- No workload distribution, fleet budget, service-level objectives, feasible sample size or competitive benchmark results were supplied. The suggested sample sizes, numerical SLO and distributions are experimental starting points, not power calculations, real-world telemetry statistics, evidence that tails are stable, or proven achievable latency.

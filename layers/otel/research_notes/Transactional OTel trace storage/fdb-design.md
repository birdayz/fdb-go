# FoundationDB transactional trace indexes

## Can FoundationDB support the latency and scale claim under its actual constraints?

### Takeaway
A credible design is possible for a **transactionally indexed, recent-data serving tier**, but FoundationDB plus Record Layer is not evidence of a best-in-class general trace analytics engine. The highest-risk choices are indexing every custom field with multiple physical orders, repeatedly modifying compressed posting chunks, and treating a continuation as a durable snapshot. Benchmark the simplest exact per-span index first; add compressed immutable history only when measurements justify its lifecycle cost.

Research access date: **2026-10-27 UTC**, from the machine clock. Primary-source pages were fetched with curl. Upstream main and online documentation are moving targets; the FDB 7.3.77 and Record Layer 4.14.2.0 source links below are version-pinned where possible. This is research and proposed design, not a claim that this repository already implements the system. A concise source manifest (version refs, captured GenAI tree/blob SHAs, original retrieval digests) and short supporting excerpts are in `fdb-design-artifacts/`; full upstream downloads and failed-response bodies were removed after research.

### Cited Findings
- The version-pinned FoundationDB 7.3.77 limitations documentation specifies **10,000,000 affected bytes per transaction**, **10,000-byte keys**, and **100,000-byte values**. Affected data includes written keys/values/ranges and read keys/ranges, but not read values; conflict-range treatment matters. It explicitly advises redesign if a transaction exceeds one megabyte. It also describes the five-second transaction limitation, including reads becoming too old and write commits failing. These are decimal byte limits, not 10 MiB/100 KiB. — [FDB 7.3.77 known limitations](https://github.com/apple/foundationdb/blob/7.3.77/documentation/sphinx/source/known-limitations.rst); [rendered current docs](https://apple.github.io/foundationdb/known-limitations.html).
- The same pinned document says large-offset key selectors are O(offset), recommends continuation from the last returned key rather than OFFSET pagination, notes no user-level access control for cluster-connected clients, and warns that read traffic to one key or a small contiguous set cannot scale without bound. Its historical tested-scale claims (500 processes/cores and 100 TB logical KV data) are **not** modern capacity guarantees or a ceiling; do not extrapolate a trace-store capacity from them. — [FDB 7.3.77 limitations](https://github.com/apple/foundationdb/blob/7.3.77/documentation/sphinx/source/known-limitations.rst).
- `commit_unknown_result` can cause a retry loop to execute a transaction twice. The developer guide recommends stable IDs generated outside retry loops and checking an existing side effect/unique marker when needed. Blind atomic counter increments are not automatically ingestion-idempotent. Snapshot reads relax conflict behavior; they do not create indefinite historical snapshots. — [FDB developer guide: transactions with unknown results, snapshot reads, long-running transactions](https://apple.github.io/foundationdb/developer-guide.html).
- Record Layer's abstract `IndexMaintainer` translates **record saves/deletes** to secondary-index updates, exposes old/new record update, scans with continuations and scan properties, `updateWhileWriteOnly`, idempotence/build checks, pending-write support, and prefix-delete capabilities. Its documentation explicitly calls out non-idempotent indexes during online construction. A custom maintainer is more than a serialization function. — [Record Layer 4.14.2.0 IndexMaintainer.java](https://github.com/FoundationDB/fdb-record-layer/blob/4.14.2.0/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/IndexMaintainer.java).
- `IndexingBase.markReadableIfBuilt()` tests the index build range set for missing ranges before marking readable; index construction is a multi-transaction stateful protocol, not a one-shot scan followed by an unchecked flag flip. — [IndexingBase.java, markReadableIfBuilt and handleStateAndDoBuildIndexAsync](https://github.com/FoundationDB/fdb-record-layer/blob/4.14.2.0/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/IndexingBase.java); [OnlineIndexer.java](https://github.com/FoundationDB/fdb-record-layer/blob/4.14.2.0/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/OnlineIndexer.java).
- Published precedents show why posting-layout claims require workload qualification. Prometheus's block format uses a deduplicated symbol table, series references, postings, and per-chunk time ranges. Lucene 10.3 encodes long postings in packed integer blocks of 128, VInt tails, and skip data, with a special singleton representation. These are **formats**, not evidence that updating a packed list transactionally on every span is cheap. — [Prometheus index format](https://github.com/prometheus/prometheus/blob/main/tsdb/docs/format/index.md); [Lucene103PostingsFormat](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/codecs/lucene103/Lucene103PostingsFormat.html).
- Quickwit separates searchable splits, split metadata with time bounds/state, searcher fanout/merge, object-store data, and janitor retention/deletion. This is a useful concrete alternative architecture, not a latency comparison: its quoted split-opening behavior must not be substituted for end-to-end query P99. — [Quickwit 0.9 architecture](https://quickwit.io/docs/overview/architecture).
- **Local code evidence**, inspected at HEAD `a7349ff657e1448a4f6937535129cfdb5afafcda`: `pkg/recordlayer/index_maintainer_registry.go` exposes `IndexMaintainerFactory`, `IndexMaintainerState` with the writable transaction and index subspace, and custom-factory registration; `pkg/recordlayer/index_maintainer.go` requires update, WRITE_ONLY update, pending-queue decisions, scan, and safe prefix deletion. This establishes an extension seam, not trace-store correctness or planner support. — [local registry](../../../../pkg/recordlayer/index_maintainer_registry.go); [local maintainer](../../../../pkg/recordlayer/index_maintainer.go). Repository research from the coordinator separately identifies planner unknown-type VALUE candidacy, incomplete generic metadata-time option validation dispatch, and unexported non-idempotent online helper as implementation gates; those claims should cite `repository.md`'s exact code evidence rather than be represented as independently verified here.

### Inferences

**Recommendation and physical alternatives (design proposals, not measurements):**

1. **A: exact hot FDB baseline — recommended first experiment.** Keep a stable primary span key `(tenant, traceShard, traceID, spanID)` with a small indexed projection and retained payload/reference. Keep bucket-first secondary indexes for easy retention-range removal. Use one KV posting per span/term, no global ID allocator and no read-modify-write posting chunks. Query traces by direct primary-key range; append one expiry key per retained span. This makes direct trace lookup independent of a time-bucket directory. Primary expiration requires a bounded per-span sweeper: do not claim that bucket-first secondary range clears also delete trace-first primaries. A generation/idempotency row should survive secondary bucket deletion until the primary is removed.
2. **B: bucket-first primary plus trace locator.** `(tenant, retentionBucket, traceShard, traceID, spanID)` enables fast bulk primary expiry but needs locator entries from traceID to buckets or probes of every retained bucket. Exact locator witnesses `(tenant, traceID, bucket, spanID)` avoid shared counters, but add O(spans) locator writes/bytes and cleanup. A compact `(traceID,bucket)` entry needs reference counting or an equivalent membership protocol when individual spans can be deleted. Avoid pretending a single monotonic min/max bucket field handles updates, expiration, gaps, or unbounded sessions. An immutable trace manifest is possible only after a defensible sealing policy, with a delta path for late data.
3. **C: FDB hot exact indexes + immutable compressed segment history.** Seal bounded immutable blocks, assign **block-local** dense doc IDs, build sorted dictionaries/postings/columnar numeric data, then atomically publish a manifest in FDB. Use term/time/tenant pruning to choose blocks. Keep late arrivals/updates/deletes as exact delta postings/tombstones; compact later. This matches the shape of published posting systems more naturally, but adds visibility, pinning, payload durability, compaction, reclamation, and query-union machinery. FDB can hold block chunks or manifests for object-store blocks; these are different cost envelopes.
4. **D: external search/columnar engine with FDB authority.** Credible if broad aggregations and arbitrary wide-time scans dominate. Ingestion then needs a durable outbox/change stream and explicit query watermark; an asynchronous secondary engine must not be advertised as transactionally current. Compare this architecture against A/C rather than assume FDB must hold the analytics hot path.

**Bounded ingestion:** Decode/validate, redact and canonicalize before the transaction; estimate affected bytes **including every index and replacement clear**, not just protobuf size. Proposed initial budget: target <500 KB affected bytes and <1 s transaction elapsed time, with smaller adaptive batches on contention; these are conservative design budgets, not FDB guaranteed safe throughput. Put deterministic span identity, indexed projection, payload visibility marker, all synchronous postings, expiry bookkeeping, and version decision in the same transaction. Read the existing span/revision with normal conflict semantics before replacing it; calculate old-versus-new posting set difference. Retry the whole bounded unit with stable IDs. A single oversized span must have a staging/reference protocol or be explicitly rejected; splitting an OTLP request is not sufficient if one span itself exceeds the budget.

**Atomic ingestion does not imply a complete distributed trace.** A trace can arrive through different collectors, in arbitrary batches, with missing spans and late updates. Return ingest/index watermarks and a clearly named quiescence/sealed hint if useful; do not claim a final end-of-trace signal absent an application protocol. Even one atomic OTLP request contains only the submitted spans.

**Ownership and reusable Record Layer improvements:** We own Record Layer; existing API/planner gaps are designable changes, not external constraints. Prefer one clean custom-index contract with explicit scan kinds/order/capabilities, metadata-time option validation, planner eligibility, exactness/coverage descriptors, versioned continuations, safe delete-prefix capability, and exported bounded online-build/idempotence hooks. Generic reusable pieces include staged immutable-block publication, build-range/epoch manifests, bounded cursors and generation pinning; trace-specific maintainers supply typed attribute term extraction, span identity, session witnesses, trace/ancestry predicates and trace-aware cost estimates. Fix generic planner classification rather than permanently hiding the trace index from SQL or bypassing Record Layer with ad hoc raw-engine code. Physical alternative D is an economics comparison, not an escape forced by current extension APIs.

**Pagination and consistency:** A last-key continuation avoids OFFSET cost but does not preserve one snapshot across minutes. Reopening a transaction at the old read version eventually encounters the same MVCC age limit; snapshot reads do not remove it. Offer one of: (a) explicit live pagination with stable tuple ordering, documented duplicate/omission behavior under concurrent mutation, and dedup at the query coordinator; (b) immutable sealed-block manifests pinned by query lease plus a frozen/referenced hot result set; (c) application-level versioned rows and a committed visibility frontier that proves all data <= frontier is present. A wall-clock cutoff alone is insufficient because late spans and backdated timestamps can appear behind it. Resuming a key range after an unseen insertion behind the last key can omit that insertion. Durable exact pagination over arbitrarily changing hot data requires extra storage/protocol, not just a cursor token.

### Gaps
- No measured spans/s, dollar/GB-month, index bytes/span, query P99, write contention, or distributed-trace workload result was found that validates **this proposed** FDB physical design. Vendor architectural descriptions and FDB's general scale cannot fill this gap.
- The custom-index SQL planner and lifecycle paths need repository-specific engineering/verification; the presence of an interface does not establish that arbitrary custom continuation/scan semantics are exposed safely through SQL.
- A Record Layer paper PDF was downloaded but not used as evidence here; its contents were not extracted. Failed 404 fetches (old layer-design/Quickwit blog paths and initial moved GenAI paths) are not cited as facts.

## How should arbitrary custom OTel and GenAI attributes be indexed exactly without a fixed allowlist?

### Takeaway
Index **every eligible scalar attribute by default**, in resource/scope/span namespaces, with complete equality and numeric-range coverage. Adaptive promotion should add faster representations, not silently decide which arbitrary fields exist to queries. Explicit privacy/size/type exclusions and coverage metadata are part of the API contract, not an implementation footnote.

### Cited Findings
- The current OTel common specification defines primitive string, boolean, IEEE754 double and signed-64-bit integer values; homogeneous primitive arrays, byte arrays, arrays of AnyValue, maps and empty values; arbitrary nested structures; case-sensitive unique map keys; and preservation of meaningful empty/zero values. It warns that string conversion loses type information and may lose numeric precision. Thus treating attributes as `map[string]string` is not full OTel semantics. — [OTel common specification, AnyValue and maps](https://opentelemetry.io/docs/specs/otel/common/).
- The OTLP trace protobuf distinguishes `ResourceSpans.resource`, `ScopeSpans.scope`, span attributes, span event attributes and link attributes, plus separate schema URLs. It gives 16-byte trace IDs, 8-byte span IDs, parent IDs and start/end timestamps. Flattening every domain into a single same-name namespace discards distinctions present in the wire model. — [opentelemetry-proto trace.proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/trace/v1/trace.proto).
- **Important currency correction:** the original official GenAI spans documentation currently says the conventions moved to `open-telemetry/semantic-conventions-genai`; the new repository says it extends core conventions and currently has a schema-URL TODO. Do not assert a frozen/stable GenAI schema from an old URL or assume a single historic semantic convention version covers all producers. — [old page source/move notice](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/gen-ai-spans.md); [current GenAI repository README](https://github.com/open-telemetry/semantic-conventions-genai).
- Current GenAI span docs include `gen_ai.conversation.id` as a development-stage string for a conversation/session/thread and say it should be populated when available, **not synthesized from a UUID, trace ID, or content hash as fallback**. Tool-call ID is supplied only if the model/provider supplied one; agent and conversation identifiers are not interchangeable with trace identity. — [GenAI spans: execute-tool attributes and notes](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md); [agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md).
- Current GenAI docs describe instructions/input/output as large and sensitive, recommend not capturing by default and enabling user opt-in, and recommend external content storage/references for production where volume/security is a concern. They allow structured representations and, in some span contexts, JSON-string representations, and mark tool call arguments/results as opt-in. A storage engine must not blindly flatten, index or expose all prompt text just because arbitrary scalar indexing is the normal policy. — [GenAI spans: full buffered content, recording content, external storage](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md).
- Record Layer TEXT records the tokenizer version per record so deletes use the same version as original insertion; updates can reindex using a newer version. It uses a bunched-map representation rather than one giant token list. This is a directly applicable precedent for versioned attribute canonicalization/deletion and compact postings, **not** proof that TEXT is appropriate for opaque arbitrary attribute equality. — [TextIndexMaintainer.java, versioning and BunchedMap](https://github.com/FoundationDB/fdb-record-layer/blob/4.14.2.0/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/indexes/TextIndexMaintainer.java).

### Inferences

**Proposed completeness policy:**
- Default complete equality for all admitted scalar keys/values in `resource`, `scope`, and `span`; complete ordered numeric range indexes for admitted integer/double scalars; existence/type postings if the query language supports them. No fixed-field allowlist is sufficient. GenAI model/provider/operation/agent/tool/conversation fields are ordinary typed custom keys with additional semantic aliases/version metadata, not a privileged route required for queryability.
- Publish quotas (attribute count, UTF-8 key bytes, scalar bytes, nesting, array fanout, per-span total index bytes). Oversized strings may still have exact whole-value equality via streaming HMAC, provided the original value is retained/retrievable for collision verification. This avoids long keys, not the I/O cost of exact verification. If size/cardinality admission fails, reject with a specific response or store with an explicit nonindexed coverage record; **never silently truncate the value and report complete exact lookup**. “All eligible” is not a loophole: eligibility must be query-visible and default scalar coverage must remain broad.
- Separate sensitive-content policy precedes indexing. Default excluded content namespaces include GenAI instructions/messages/tool arguments/results and arbitrary tenant-marked PII/secrets, regardless of whether producer encoded them as JSON strings. An administrator may opt into exact content lookup, field/path indexing or full text with explicit access controls and retention. Keep operational IDs queryable by default if tenant policy permits. A JSON-string payload is not automatically safe merely because it is a scalar.
- Index array **whole-value equality** with a deterministic typed length-prefixed canonical form; preserve element order, duplicates, nulls and type tags. Offer explicit `contains`/`any` indexes using deduplicated typed element terms, plus element count/type metadata; cap fanout and expose excluded elements. Never make `array = scalar` an undocumented alias for `contains`. Nested map/path indexing is a separate capability: full object equality can use canonical key-sorted maps and hashes, but arbitrary path predicates are not supported just by hashing the object. Expose that boundary.
- No implicit string/int/double/bool coalescing. Keep integer 64-bit precision rather than cast to float; define cross-type numeric comparisons explicitly (initially exact typed domains with safe planner union for cross-type requests). Define NaN semantics (`is_nan`, no ordinary ordered range), infinities, signed zero (numerical equality normalizes ±0, optional bitwise predicate distinct), and NaN-payload normalization. Encoding and query evaluation must agree exactly. Keep original protobuf and canonicalizer version, not only normalized values. These are proposed language rules, not claims the OTel spec prescribes SQL equality semantics.

**Proposed base posting layout and algorithms:**

`P = (tenant, indexEpoch, retentionBucket, traceShard, namespace, attrKeyToken, scalarType, valueToken, traceID, spanID)` -> minimal revision/time witness.

`R = (tenant, indexEpoch, retentionBucket, traceShard, namespace, attrKeyToken, numericType, sortableNumeric, traceID, spanID)` -> revision/time witness.

- `traceShard = hash(traceID) mod S` aligns trace membership across predicates and session discovery. Prepend shard before term to distribute hot terms; use a fixed small S initially, measured rather than reflexively 256. Encoding should use compact tenant/key IDs only when their dictionary lifecycle is demonstrably cheaper; a domain-separated hash key token avoids a dictionary round-trip but loses efficient plaintext lexical field enumeration unless maintained separately.
- `valueToken = HMAC(tenantSecret, domain || encodingVersion || namespace || key || type || canonicalValue)` (with collision-resistant length, e.g. 256 bits) avoids long keys and cross-tenant dictionary correlation. **Hash equality is candidate equality, not proof.** Verify original canonical typed key/value for every candidate or retain an encrypted canonical side record. Include key identity in verification too, because hashed key names can collide. Collision tests must deliberately use a truncated token to force collisions. Never overwrite a dictionary slot solely because its hash matches. Support HMAC key IDs and multi-version lookup during rotation/backfill; deletion uses the version recorded at ingestion.
- Ordered numeric keys must contain a true sortable numeric representation, not HMAC. Integer sign mapping and float sortable-bit transforms require thorough boundary tests; normalize according to the declared comparison semantics. Ordered values leak order and distribution, so do not advertise HMAC equality as protecting those indexes. Prefix/regex/substring requires a separate index or fallback; a hash is not a general text-search structure.
- For a conjunction of same-span attributes, enumerate the narrowest bounded term posting by `(traceID,spanID)` and do batched point probes into the other exact terms for that bucket/shard; or merge-intersect lists with identical ordering. This supports arbitrary keys without global dictionaries or bitmap IDs. Cost is O(candidate count × other predicates) probes or O(total scanned posting length), not O(results). Bound the candidate count, bytes and elapsed time; return a continuation/explicit resource limit instead of claiming every query is millisecond-scale.
- Timestamp in the **value** preserves common ID order for intersections but requires residual time filtering within a coarse bucket. Putting timestamp ahead of trace ID improves newest-first fetching and finer time bounds but destroys cheap ID-order merge intersections. Neither layout wins both. Offer an optional timestamp-ordered acceleration for common predicates or a timestamp candidate index plus exact probes; do not unconditionally double all attribute postings without measured benefit. For random trace IDs, trace order has no time pruning beyond the bucket.
- Numeric ranges fan out across type/bucket/shard, scanning ordered keys; choose a selective equality anchor instead when it wins. Duration is `end-start` with checked validity, stored as an ordered numeric scalar, not a string. **Exact recent top-K algorithm:** choose a timestamp-ordered complete driver (global time index or timestamp-ordered chosen-term accelerator), open one reverse cursor for every relevant bucket/shard/epoch, heap-merge by `(timestamp,traceID,spanID)`, exact-probe residual predicates, and emit accepted spans in that order. Once K distinct accepted rows exist, stop only when every cursor's next-unseen upper bound is <= the Kth row's total sort key; unopened event-time buckets can be skipped only when their certified timestamp maxima satisfy that bound. Late data and updates still require the declared snapshot/live semantics. If the only driver is trace-ID order, no useful timestamp frontier exists: scan all candidates in the eligible time partitions and maintain a bounded top-K heap, or choose another index. Duration-ordered top-K analogously needs complete ordered duration drivers and per-shard bounds. Arbitrary residual conjunction can reject arbitrarily many candidates even with a correct ordered driver; return budget continuation/error, not a fabricated exact K. Top-K **traces** additionally needs an explicit score (latest matching span vs trace start/end), dedup, and bounds for unseen spans that might change a trace's score. Approximate quantile/range sketches may guide plans, not establish exact answers. FDB ranked-set/rank maintenance on every arbitrary numeric attribute adds write work and should not be assumed necessary.

**Cardinality and session access:**
- High-cardinality unique values have no dictionary amortization: one value dictionary row plus refcount plus ID allocation can cost more than direct hashed posting keys. Prefer per-block dictionaries in sealed history; maybe globally intern popular **key names**, not every value. No global monotonically allocated trace/span ID or hot key allocator. If compact IDs are wanted online, allocate independent shard-local ranges and preserve collision-free `(shard,id)` identity; immutable block-local IDs are simpler.
- Efficient conversation lookup must work across many traces: reuse exact session field lookup for arbitrary names, with optional dedicated `C = (tenant, sessionKeyToken, sessionValueToken, retentionBucket, traceShard, traceID, spanID)` -> source witness/revision for no-time lookup. Range scan known session prefix discovers its existing buckets/traces; paginate/deduplicate trace IDs and exact-verify the session identifier. No mutable per-session min/max/count record. For time-bounded sessions, use bucket-first layout and probe B×S ranges, or keep a small bounded tree of immutable bucket manifests. A dedicated session-order index is justified by measured workload, not by pretending sessionID == traceID.
- A per-span session witness deliberately produces duplicates at trace level but supports exact deletion without shared membership counters. If compaction deduplicates to `(session,bucket,traceID)`, retain a reference count/witness list or a certified immutable source set. Refcounts need existing-span/revision checks to make unknown-commit retries exact; a bitmap clear or unconditional delete from one span cannot delete another span's surviving trace membership. Very hot single sessions still need shard fanout (hash by traceID; exceptionally hot traces may need span-sharded session witnesses), but no aggregate row must serialize every write.
- Attribute names are themselves high-cardinality attack surfaces. Tenant quotas on distinct keys and index-byte budgets are necessary, with query-visible coverage and admission statistics, not silent hardcoded field choices. Source resource/scope attrs may be dictionary-deduplicated in payload storage, but their span-membership postings still require explicit cost accounting; updating a shared resource object cannot quietly change already committed spans' query meaning.

**Adaptive/tiered coverage:** Keep the complete base hash/range index for eligible scalar attrs, promote to cached roaring/packed lists, dedicated time order or materialized session directory using workload statistics. Track `(tenant,indexEpoch,namespace,key,type,bucket,shard)` coverage and promotion state plus canonicalizer/HMAC version. During backfill, planner uses baseline or union of complete old representation with the new one; deduplicate by span identity/revision. Switch only when immutable covered ranges plus concurrent-write maintenance prove coverage, using an atomic manifest generation. If policy deliberately skips base indexing, exact query must scan uncovered primary ranges or return `incomplete/not-indexed` metadata/error; “index is hot now” is not historical completeness. Neither sampling nor Bloom filters can be the sole exclusion proof for data that never entered them. Demotion likewise needs a fallback before deleting the last complete representation.

### Gaps
- The current GenAI repository is evolving and its README schema-URL entry is unfinished. Pin producer schema/convention versions and retain raw keys; a reliable complete alias migration table is not established here.
- This research does not prove an ideal array/map query algebra or universal numeric coercion policy. These require an explicit contract and differential/property tests; OTel wire types alone do not define the database query language.
- HMAC protects against some plaintext correlation/dictionary leakage, not equality-frequency leakage, ordered-value leakage, access-pattern leakage, or malicious cluster access. Key management/access-control design remains necessary.

## Which exactness, amplification and benchmark gates make this a go or no-go?

### Takeaway
The project should proceed only as a benchmarked prototype with a deliberately narrow consistency contract, not an RFC that assumes packed transactional trace postings solve arbitrary OTel search. No-go conditions are silent coverage gaps, unbounded shared memberships/transactions, or failure to compete on total replicated bytes and P99 under ingest plus retention/backfill/failure load.

### Cited Findings
- Record Layer BITMAP_VALUE uses integer positions and fixed-size chunks. Java defaults to **10,000 bits per entry**, permits at most **250,000**, and uses FDB BIT_OR/BIT_AND mutations. This avoids client read-modify-write for individual bit operations but still operates on fixed chunk operands/keys. The local Go implementation similarly constructs full masks and `CompareAndClear`s all-zero entries. That does not solve trace-ID mapping or reference ownership. — [Java BitmapValueIndexMaintainer](https://github.com/FoundationDB/fdb-record-layer/blob/4.14.2.0/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/indexes/BitmapValueIndexMaintainer.java); [local Go maintainer](../../../../pkg/recordlayer/bitmap_value_index_maintainer.go).
- The maintainer contract distinguishes safe prefix deletes from arbitrary deletes and explicitly exposes WRITE_ONLY update handling; online construction must reason about already-indexed ranges for non-idempotent maintainers. A bulk record delete cannot safely range-clear an index unless its physical layout aligns with that record prefix. — [IndexMaintainer.java](https://github.com/FoundationDB/fdb-record-layer/blob/4.14.2.0/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/IndexMaintainer.java); [IndexingBase.java](https://github.com/FoundationDB/fdb-record-layer/blob/4.14.2.0/fdb-record-layer-core/src/main/java/com/apple/foundationdb/record/provider/foundationdb/IndexingBase.java).
- OTLP retries can resend telemetry; retryable transport failures differ from partial success. The protocol says clients must not retry requests with populated partial-success responses, and allows error cases where acceptance is unspecified. Therefore request arrival is not an exactly-once event boundary. — [OTLP specification: partial success, failures and retry handling](https://opentelemetry.io/docs/specs/otlp/).
- FoundationDB's transaction age/size/value limits continue to apply to compaction, online build, membership cleanup and large payloads, not just normal ingest. The documented workaround for bulk inserts includes indirection and small transactions, not waiving the limits. — [FDB 7.3.77 limitations and workarounds](https://github.com/apple/foundationdb/blob/7.3.77/documentation/sphinx/source/known-limitations.rst).

### Inferences

**Structural-query correctness:**
- Same-span `A AND B`, trace-exists-span(A) AND trace-exists-span(B), parent-child, and descendant queries are distinct. Intersecting span IDs answers the first, intersecting trace IDs produces only candidates for the others. A trace bitmap collapses away which span matched and its time/parent relationship; it cannot answer structural predicates without verification. Keep parent IDs and efficient trace fetch/child adjacency if structural queries are core.
- A trace can cross event-time and retention buckets; `exists A` in bucket X and `exists B` in bucket Y must join by traceID across all relevant buckets, not intersect only within each bucket. Explicit algorithm: for each predicate build/stream `T_i = DISTINCT UNION_{all relevant bucket,shard,layout-epoch} traceID(posting_i)`; then intersect T_i globally (or drive the smallest T_i and globally probe the other predicates through trace-local data). Never compute only `UNION_partition INTERSECT_predicate posting`, which misses cross-partition witnesses. Sharding by traceID makes a trace co-shard only within one unchanged shard scheme; span-sharded accelerators, shard-count changes and old/new index epochs require routing both layouts or globally merging. Keep bucket/shard/epoch provenance in cursors and budget the global distinct/join state or spill it. The same rule applies when joining session membership across traces and when ancestry witnesses lie in different partitions. For existential trace predicates, union A candidates across applicable buckets then semi-join against B candidates or probe the trace. A parent may be outside the user's span-time window: define whether time applies to every matching span, the anchor span, or trace overlap before choosing buckets. Links cross traces and need a separate relation if supported. Parent IDs alone do not identify the lexical descendant interval in arbitrary span-ID order.
- Keep query state outside the transaction and bound each batch (candidate IDs, fetched spans, bytes, wall time). Broad structural queries over incomplete traces may need disk spill/continuation and explicit budget failure. Do not promise all arbitrary joins in a single five-second transaction. Query verification must check visibility generation/revision and retention, especially when old/new epoch representations coexist.

**Membership, updates, retry and expiration:**
- Use span identity `(tenant,traceID,spanID)` as the dedup key. **Correction/bucket-routing protocol:** option A reads the stable identity row with ordinary conflict checking, decides accepted revision, retains its original and new bucket/index versions, clears every removed old posting/session witness/expiry key, writes new postings/witnesses/expiry generation, and replaces the identity row in one bounded transaction. Thus a changed timestamp changes index routing without creating a second logical span. Cleanup reads `(identity,expectedRevision,expectedExpiryGeneration)` and removes only if all still match; a stale expiry entry cannot delete a corrected span. Under option B, a stable identity locator `(tenant,traceID,spanID)->(bucket,revision,payloadGeneration)` is mandatory for dedup/corrections; read it, clear old routed data and publish new location atomically. Bucket-only dedup is incorrect. If replacement fanout exceeds the transaction budget, stage new immutable data, maintain version-tagged side postings, atomically switch identity/visibility generation, and make readers reject noncurrent generations until bounded GC; this is an explicit more complex protocol, not permission to partially move a span. Define conflict policy for divergent retries: immutable-first, authoritative source version, or explicit correction API; last arrival wins is a policy, not truth. Without a producer monotonic revision, timestamps are not a safe merge order. Store old canonicalization/index policy versions so update/delete clears exactly the entries originally written.
- A trace-level `(term,traceID)` row/bit shared by many spans needs membership witnesses/counting. Deleting span A must preserve the row when span B still has that term. The same applies to repeated elements, resource attr projections, session-to-trace rows and existence indexes. Unique per-span postings make ownership straightforward; optional deduplicated trace postings are a separate derived structure with exact source counts or immutable manifest coverage. Atomics can be individually idempotent yet a multi-step membership protocol still be wrong under replay.
- Do not expire dedup markers before the last retry you intend to suppress. Unlimited exporter retry horizon implies no finite dedup horizon guarantee; choose/document one and reject old ingress after cutoff, or keep identity/tombstone records longer. If events are partitioned by start time, a retry must not reappear in a newer bucket merely because ingestion time changed. Conversely, backdated new events may target an already-retired bucket: reject/quarantine by explicit policy rather than resurrect it silently. Separate ingest/event-time retention and grace windows.
- Run retention with an epoch/cutoff manifest. Readers exclude retired data immediately; physical clearing is asynchronous and idempotent. Bucket-first secondary clear-range is cheap in transaction metadata but storage reclamation is not instantaneous, and trace-first primary/session-directory cleanup still requires bounded work. With option A, expiry rows enumerate primary spans and side witnesses; small cleanup transactions verify generation, remove exact ownership and write tombstone if needed. Query must not treat already-retired primary leftovers as current. With bucket-first primary plus scattered reverse directories, retain expiry manifests to clean those scattered keys; directories do not expire magically with the primary range.

**Bitmap/chunk critique and block lifecycle:**
- Random 128-bit trace IDs do not directly make dense bitmap positions. A global compact-ID map is another persistent structure and potential allocator hotspot. Block-local IDs plus per-block trace/span dictionaries are appropriate for sealed data; different blocks require mapping/merge to recover global IDs. Hashing trace IDs into bits causes collisions and cannot be an exact membership index by itself.
- A 10,000-bit fixed bitmap operand is about 1,250 bytes before key/log overhead. For sparse or singleton custom terms, one such chunk per value can be far worse than one span posting. Popular terms target hot active chunks; atomic operations reduce conflict retries but do not remove server/log bandwidth limits. Roaring/variable compressed mutation typically requires decoding/rewriting a container with conflict checking, and variable length changes complicate atomicity. Measure hot chunks and cold sparse terms separately.
- Bunched map packing reduces repeated key overhead but adds read-modify-write conflict domains and chunk splits. Prefer append-only per-span delta keys during hot ingestion, then compact immutable sealed runs into versioned compressed blocks. Chunk bounds must leave headroom below 100,000-byte values; chunk splitting alone does not solve transaction age/size. Store encoding version, checksum, codec/dictionary IDs, key/HMAC version, min/max time/numeric bounds, term counts and stable block ID in manifests. Deletion during compaction must be version-aware; do not clear a delta range that gained new writes after the compactor's snapshot.
- Build blocks out of band in bounded chunks; verify complete durable block/checksum, then atomically publish a manifest pointer. Query union covers active delta + immutable blocks + relevant tombstones; compaction swaps manifests atomically. Pin old manifests with bounded query leases/epochs and delay GC until readers finish. On failure, orphan staged blocks are reclaimed separately. For object-store payloads, upload immutable content before publishing its FDB pointer and verify durability/version; FDB transaction atomicity cannot make an external upload atomic. Never perform external side effects inside retry loops assuming exactly once.
- New index generation: versioned subspace; WRITE_ONLY concurrent maintenance; bounded backfill with persisted covered ranges/continuations; compare expected postings; publish READABLE atomically only at complete coverage; retain old generation for active query cursors; GC later. Non-idempotent counters need the Record Layer built-range protocol, not a blanket claim of idempotence. Packed trace indexes must opt out of unsafe prefix delete and unsupported SQL scans. The repository integration caveats supplied by coordinator are explicit implementation gates, not reasons to abandon Record Layer.

**Large GenAI payloads and privacy:** Keep indexed projection small; store content separately with independent ACL/retention/encryption keys and immutable references. A <=100,000-byte chunk rule applies to FDB values; payload compression may reduce storage but must not allow decompression bombs or defeat admission estimation. An arbitrarily large payload staged over transactions is not atomically readable until its manifest is committed; retain unreferenced-upload GC. Do not pack unrelated tenants/users' prompts into inseparable encrypted blocks if selective deletion or key destruction is required. Redaction happens before equality hashes, full text, logs or diagnostic payload copies. HMAC token retention can still retain a stable identifier after payload erasure, so deletion policy must cover indexes too.

**Amplification ledger to measure (algebra, not an empirical result):**

Let N spans, A admitted distinct scalar attrs/span after resource/scope expansion, R numeric attrs, E existence/type terms, M array element terms, D dedicated accelerators/session witnesses, C payload chunks, L mean stored key+value bytes per posting, P projection/payload bytes, q equality predicates, B buckets, S shards. Baseline logical writes/span are approximately `C + A + R + E + M + D + primary metadata + expiry/dedup metadata`; updates additionally clear removed terms and replace affected chunks. Duplicate attributes across namespaces remain distinct A terms. If numeric equality reuses R instead of a parallel hash representation, reduce A accordingly only after documenting the equality query tradeoff. Sharing a resource payload does not remove per-span attr-membership writes.

- Resource/scope tradeoff: if there are A_span span scalars, A_resource resource scalars and A_scope scope scalars, direct per-span projection has `A=A_span+A_resource+A_scope` equality memberships regardless of shared payload dictionaries. For an illustrative 10 span + 25 resource + 5 scope attributes, A=40; resource/scope account for 30/40=75% of equality membership writes. Payload-interning can remove repeated resource/scope protobuf bytes, but does not remove those 30 membership writes. A normalized alternative stores resource/scope term indexes once per immutable descriptor plus `(descriptorID,spanID/time)` memberships. With reuse factor F, descriptor term cost amortizes roughly `(A_resource+A_scope)/F` per span, plus 1–2 descriptor-to-span memberships, rather than A_resource+A_scope postings. However a predicate now joins matching descriptors to spans, multi-resource trace predicates require global trace joins, numeric/top-K need time-ordered membership drivers, and a single service descriptor can have enormous fanout. Descriptor identity must include full immutable attrs/schema/scope semantics and collision verification; mutable descriptor updates must not rewrite historical span meaning. Benchmark this as a legitimate RL reusable normalized-index/covering-join improvement, not as free dedup or a reason to omit arbitrary resource fields.
- Logical bytes/span approximately `P + sum(posting key/value bytes) + dictionaries + directories + version/tombstone overhead`; replication, transaction logs, storage-engine amplification, temporary compaction copies and backups are **additional**, not already in this sum.
- Illustrative **assumption only**: A=40 and L=100 bytes implies 4,000 bytes/span of equality postings alone. At 1,000,000 spans/s that is 4 GB/s logical posting bytes and 345.6 TB/day, before primary payload, numeric/existence indexes, replication or storage overhead. This arithmetic is a warning about requirement scale, **not** a throughput estimate. Timestamp acceleration duplicating all those terms doubles that component. Every proposed “one extra index” needs this multiplication.
- Equality fanout lower bound for a bucket-first sharded representation is B×S ranges per term unless metadata prunes them. q predicates can mean q×B×S range setups, followed by posting reads or probes. Smaller buckets improve pruning/retention precision but increase seek/fanout/metadata. Larger S reduces contention concentration but raises query work and heap state. A sparse directory can prune empty buckets/shards only if maintained completely; otherwise it creates false negatives.
- Selective same-span query work: either scanned posting bytes across predicates, or narrowest candidate count n × (q−1) point probes plus n projection reads; exact hash verification adds payload/side-record fetch bytes. Broad aggregation and exact facet discovery are proportional to inspected postings/values unless separately materialized. Trace-level candidate collapsing reduces fetches but may require large dedup state. Top-K requires accounting for rejected candidates and per-shard frontier reads, not just K returned rows.
- Online index build adds a retained-data scan plus all new index bytes, concurrent maintenance, verification and temporary dual-generation storage; compaction adds reads of delta/old blocks plus writes of new blocks/tombstones. Retention adds sweep key work and background disk reclamation. Report amplification in **bytes/span, mutations/span, reads/query, CPU seconds, P50/P95/P99/P99.9**, and peak live/temporary disk, not one microbenchmark's ops/s.

**Proposed benchmark gates (requirements must set final numeric SLOs; these are experiments, not claims of achieved results):**
1. **Completeness/exactness oracle:** compare primary-scan truth with every query/index plan across arbitrary unknown scalar keys; integer boundaries beyond 2^53, ±0, NaNs/infinities; Unicode/case; arrays/nulls/duplicate elements; resource/scope/span key collisions; forced hash collisions; HMAC/canonicalizer rotation; huge values; unseen field promotion. Zero false negatives/false positives after exact verification, or explicit query incompleteness. Verify session lookup across >one trace and time bucket.
2. **Concurrency/failure oracle:** two spans share term/trace/session membership; delete/update either while another inserts; duplicate requests and unknown commits; updates racing backfill/compaction; crash before/after manifest publication; TTL boundary and post-dedup retries; schema/index-epoch changes mid-pagination. Differentially compare settled truth and declared read consistency. No silent resurrection or leaked membership.
3. **Workload matrix:** low-cardinality hot terms, 100%-unique IDs/custom keys, Zipf mixtures; resource-heavy spans; one hot session with millions of traces and one huge trace; 1/10/100+/1000 attrs, long content and missing/rootless spans. Sweep bucket width and S. Test narrow equality, multi-equality, custom numeric ranges, session first-page/deep-page, trace lookup, cross-bucket parent/descendant joins, NOT/existence and wide exact top-K. Broad NOT requires a complete universe; don't benchmark only positive equality.
4. **Competitive mixed load:** hold offered ingestion and query rate, compare A/B/C and a credible search/columnar baseline on identical hardware, durability/replication, retention, query completeness, cardinality and result freshness. Measure cold/warm caches separately and all latency percentiles. Run retention, index builds and compaction concurrently; include storage-node loss, network/retry pressure and skew. “Best-in-class” is no-go until an agreed competitive workload/SLO/cost frontier is met, not merely a successful FDB ingest benchmark.
5. **Boundedness gate:** no transaction approaches the hard limits under worst admitted spans/index fanout; no unbounded per-session/trace summary; no immutable block publication exposing missing chunks; no scan beyond time/byte/key budget without an explicit continuation/error. Prove configured quotas bound affected bytes and retain operational headroom. Check retry amplification and ingest tail latency under concurrent membership writers.
6. **Economics gate:** report replicated on-disk bytes/span and logical-to-physical write amplification after steady-state compaction; dollars per retained billion spans and per query/SLO; payload/index ratio; per-tenant attribution; build/delete/recovery temporary headroom. If broad custom indexing makes FDB prohibitively expensive, keep exact recent FDB tier and move sealed analytics history rather than weaken completeness invisibly.

**Go/no-go recommendation:** Go for A as a controlled complete-custom-attribute prototype plus direct trace/session access. Gate C on measured retention economics. Do not commit to globally dense trace bitmaps, universally duplicated time+trace posting orders, or adaptive field exclusion as the primary exact index. No-go for a product claim of globally snapshot-consistent indefinite pagination, universally atomic multi-collector trace completion, or arbitrary low-latency structural/range queries independent of selectivity. Record Layer is a useful atomic-maintenance/lifecycle substrate, not a substitute for these contracts and measurements.
